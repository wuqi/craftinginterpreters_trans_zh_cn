13 . 1超类与子类

既然这个概念叫「继承」，你大概会希望他们挑一套前后一致的比喻，管它们叫「父类」和「子类」吧，可那样 可哪有那么便宜的事。早年间，C. A. R. 霍尔造出「子类」这个词，用来指一个精修 了另一种类型的记录类型。Simula 借用了这个词，指一个从另一个类继承而来的类。我觉得直到 Smalltalk 出现，才有人把拉丁语前缀翻过来，用「超类」指这段关系的另一头。从 C++ 那边，你还会听到 「基类」和「派生类」的说法。我大体上就沿用「超类」和「子类」。

在拉丁语里，「super-」和「sub-」分别是「上」和「下」的意思。把继承树想象成一棵家谱树，根在最上面 ——在图上，子类位于超类的下方。更宽泛地说，「sub-」指的是那些精修了某个更普遍的概念、或被其包含的 东西。在动物学里，亚纲（subclass）就是对一大类生物所作的一种更细的归类。

在集合论里，一个子集被一个更大的超集包含，后者拥有子集的全部元素，可能还更多。集合论与编程语言在 类型论里相遇。在那里，你有「超类型」和「子类型」。

在静态类型的面向对象语言里，子类往往也是其超类的一个子类型。假设我们有一个 Doughnut（甜甜圈）超类和一个 BostonCream（波士顿奶油夹心甜甜圈）子类。每个 BostonCream 也是一个 Doughnut 实例，但可能存在不是 BostonCream 的甜甜圈 对象（比如 Cruller，一种扭花甜甜圈）。

把一个类型想象成该类型所有值构成的集合。所有 Doughnut 实例的集合包含了所有 BostonCream 实例的 集合，因为每个 BostonCream 也是一个 Doughnut。于是 BostonCream 是一个子类，也是一个子类型，而它 的实例是一个子集。全都对得上。

我们支持继承的第一步，是在声明类时能指定一个超类。这件事的语法花样很多。C++ 和 C# 在子类名后面放 一个 :，跟上超类名。Java 改用 extends。Python 把超类（们）放进类名后面的圆括号里。Simula 把超类 的名字放在 class 前面。

事情都到这份上了，我不太想再给词法分析器加一个新的保留字或词法单元。我们既没有 extends，连 : 也没有，所以我们跟 Ruby 学，用一个小于号（<）。

class Doughnut {
  // 甜甜圈的那些通用东西……
}

class BostonCream < Doughnut {
  // 波士顿奶油专属的东西……
}

13 . 2继承方法

从另一个类继承，意味着凡是对超类成立的东西，对子类也或多或少应该成立。 在静态类型语言里，这会带来一大堆牵涉。子类也必须是一个子类型，内存布局也受到管控，好让你 能把子类的一个实例传给一个期待超类的函数，而它仍能正确地访问那些继承来的字段。

这条含糊其辞的准则，有个更花哨的名字，叫里氏替换原则。芭芭拉·利斯科夫在面向对象编程 的形成期，在一场主题演讲里提出了它。

Lox 是动态类型语言，所以我们的要求简单得多。基本上，它意味着：如果你能在超类的一个实例上调用某个 方法，那么拿到子类的一个实例时，你也应该能调用那个方法。换句话说，方法是从超类继承来的。

这和继承的目标之一吻合——给用户一种跨类复用代码的办法。在我们的解释器里实现这点，容易得惊人。

      return methods.get(name);

13 . 3调用超类方法

在 findMethod() 里，我们在当前类上先找一个方法，之后才沿着超类链往上走。如果子类和超类里都 存在一个同名方法，子类的那个会优先，也就是覆盖超类的方法。有点像内层作用域里的变量遮蔽外层 那样。

如果子类想彻底替换超类的某个行为，那这很棒。但实践中，子类常常想精修超类的行为。它们想干 一点子类专属的活，但也想执行超类原本的行为。

然而，由于子类已经覆盖了这个方法，就没法再引用原来那个了。如果子类方法试图按名字调用它，只会递归地 撞上自己的覆盖版本。我们需要一种说法：「调用这个方法，但直接到我超类上去找，别管我的覆盖」。Java 为此用 super，我们在 Lox 里也用同样的语法。举个例：

class Doughnut {
  cook() {
    print "Fry until golden brown.";
  }
}

class BostonCream < Doughnut {
  cook() {
    super.cook();
    print "Pipe full of custard and coat with chocolate.";
  }
}

BostonCream().cook();

如果运行这段代码，它应该打印：

Fry until golden brown.
Pipe full of custard and coat with chocolate.

我们多了一种新的表达式形式。super 关键字后面跟一个点号和一个标识符，用来查找叫这个名字的方法。 和 this 上的调用不同，搜索从超类开始。

13 . 3 . 1语法

对 this 来说，这个关键字有点像个魔法变量，表达式就是那孤零零的一个词法单元。但对 super 来说， 后面的 . 和属性名是 super 表达式不可分割的部分。你不可能有一个光秃秃、孤零零的 super 词法单元。

print super; // 语法错误。

所以我们在语法里给 primary 规则加的新子句，也把属性访问一并包含进去了。

primary        → "true" | "false" | "nil" | "this"
               | NUMBER | STRING | IDENTIFIER | "(" expression ")"
               | "super" "." IDENTIFIER ;

通常，super 表达式是拿来做方法调用的，但和普通方法一样，参数列表并不是表达式的一部分。反过来， 一次 super 调用 是一次 super 访问 后面跟一个函数调用。和其他方法调用一样，你可以拿到超类 某个方法的句柄，再单独调用它。

method();

13 . 3 . 2语义

前面我说，super 表达式从「超类」开始查找方法，可是哪个超类呢？朴素的答案是 this 的超类， 也就是环绕它的那个方法被调用时所在的对象。这在很多情况下碰巧会得出正确的行为，但它其实并不对。请看：

class A {
  method() {
    print "A method";
  }
}

class B < A {
  method() {
    print "B method";
  }

  test() {
    super.method();
  }
}

class C < B {}

C().test();

把这个程序翻译成 Java、C# 或 C++，它会打印「A method」，这也是我们希望 Lox 做的。这个程序运行时， 在 test() 的方法体内，this 是一个 C 的实例。C 的超类是 B，但那不是查找应该开始的地方。如果 从那里开始，我们就会撞上 B 的 method()。

反过来，查找应该从包含这个 super 表达式的那个类的超类开始。在这个例子里，由于 test() 定义在 B 里面，它内部那个 super 表达式应该从 B 的超类——A——开始查找。

执行流程大致是这样：

  1. 我们在 C 的一个实例上调用 test()。

  2. 这会进入从 B 继承来的 test() 方法。它调用 super.method()。

  3. B 的超类是 A，于是调用链接到 A 上的 method()，程序打印「A method」。

因此，为了求值一个 super 表达式，我们需要访问环绕这次调用的那个类定义所属的超类。唉，悲哉，在 解释器里执行 super 表达式的那一点，我们手边并不容易拿到它。

我们本可以给 LoxFunction 加一个字段，存一个指向拥有该方法的 LoxClass 的引用。解释器会保留 一个指向当前正在执行的那个 LoxFunction 的引用，这样等我们撞上 super 表达式时就能回头查它。从 那里，我们能拿到方法所属的 LoxClass，再拿到它的超类。

那可是不少管道工程。在上一章里，我们需要给 this 加支持时，也遇到过类似的问题。 那次，我们用已有的环境和闭包机制，存了一个指向当前对象的引用。那我们能不能用类似的办法来存超类 ？ 嗯，如果答案是不行，我大概就不会在这儿讲这事了，所以……行。

13 . 3 . 3super 的无效用法

和之前的语言特性一样，用户写对代码时我们的实现运转正常，但我们还没把解释器做成防弹的、能扛住坏代码。 具体来说，看看这个：

class Eclair {
  cook() {
    super.cook();
    print "Pipe full of crème pâtissière.";
  }
}

这个类有一个 super 表达式，却没有超类。运行时，求值 super 表达式的代码会假设「super」被成功 解析过、能在环境里找到。这里这会失败，因为既然没有超类，就没有为超类准备的环境。JVM 会抛出一个 异常，把我们的解释器撂倒在地。

嘿，还有更简单的 super 错误用法：

super.notEvenInAClass();

我们本可以在运行时通过检查「super」的查找是否成功，来处理这类错误。但我们可以静态地——单看源码就 知道——Eclair 没有超类，因而它内部任何 super 表达式都不会起作用。同样，在第二个例子里，我们知道 那个 super 表达式根本不在方法体里面。

尽管 Lox 是动态类型的，但这不意味着我们想把所有东西都推迟到运行时。如果用户犯了错，我们想帮 他们早一点发现，而不是晚一点。所以我们在作用域解析器里静态地报这些错。

习题

  1. Lox 只支持单继承——一个类只能有一个超类，而这也是跨类复用方法的唯一途径。别的语言探索过 各种各样的办法，来更自由地跨类复用与共享能力：混入（mixin）、特质（trait）、多重继承、虚继承、扩展方法等等。

    如果你要往 Lox 里加一个这类特性，你会挑哪个，为什么？如果你觉得胆气够壮（到这个份上你应该够 了），就去把它加进来。

  2. 在 Lox 里，和大多数其他面向对象语言一样，查找一个方法时，我们从类层级的最底下开始，一路往上走 ——子类的方法优先于超类的方法。要从一个覆盖方法内部够到超类的方法，就用 super。

    语言 BETA 采取相反的路子。当你调用一个方法时，它从类层级的顶端开始，一路往 下走。超类方法胜过子类方法。要够到子类的方法，超类方法可以调用 inner，它有点像 super 的反面。它会把调用链接到层级中下一个往下的方法。

    由超类方法来掌控：子类什么时候、在哪里被允许精修自己的行为。如果超类方法根本不调用 inner， 那么子类就没办法覆盖或改动超类的行为。

    把 Lox 当前的覆盖和 super 行为拿掉，换成 BETA 的语义。简而言之：

    • 在某个类上调用方法时，优先选该类继承链上最高的那个方法。

    • 在一个方法体的内部，一次对 inner 的调用，会沿着「包含这个 inner 的类」与「this 所属 的类」之间的继承链，在最近的子类里找一个同名的方法。如果没有匹配的方法，这次 inner 调用 什么也不做。

    例如：

    class Doughnut {
  cook() {
    print "Fry until golden brown.";
    inner();
    print "Place in a nice box.";
  }
}

class BostonCream < Doughnut {
  cook() {
    print "Pipe full of custard and coat with chocolate.";
  }
}

BostonCream().cook();

    它应该打印：

    Fry until golden brown.
Pipe full of custard and coat with chocolate.
Place in a nice box.
