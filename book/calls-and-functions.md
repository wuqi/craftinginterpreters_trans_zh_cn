## 函数对象

VM 里最有趣的结构性改动围绕着栈展开。我们**已经**有一个栈用来放局部变量和临时值，所以已经

## 编译成函数对象

目前我们的编译器假定自己总是在编译到同一个代码块里。随着每个函数的代码各自住在独立的
代码块里，这事变复杂了。当编译器碰到一条函数声明时，它需要在编译函数体时把代码发射进那个
函数的代码块。在函数体的末尾，编译器需要回到它之前在用的那个代码块。

对函数体内部的代码来说这没问题，但对不在函数体里的代码呢？Lox 程序的「顶层」也是命令式
代码，我们也需要一个代码块来编译它。我们可以把那层顶层代码也放进一个自动定义的函数里，
这样就能同时简化编译器和 VM。这样编译器永远处在某个函数体内部，VM 也永远通过调用一个函数
来运行代码。就好像整个程序都被<span name="wrap">包在</span>一个隐式的 `main()` 函数里。

<aside name="wrap">

这个类比在一处语义上不成立，就是全局变量。它们有一套不同于局部变量的特殊作用域规则，
所以在这个意义上，脚本的顶层并不像函数体。

</aside>

那么在讲到用户定义的函数之前，我们先来做这个重组，以支持那个隐式的顶层函数。它从
Compiler 结构体开始。它不再直接指向一个供编译器写入的 Chunk，而是持有一个对正在构建的
函数对象的引用。

函数的函数体。编译器的大部分代码并不关心这个——所以它才是个有用的抽象——但在一两个地方
这个区别是有意义的。我们后面会碰到一处。

## 调用帧

是时候做一次大的概念跳跃了。在实现函数声明和调用之前，得先让 VM 准备好接待它们。有两个
主要问题需要考虑：

### 分配局部变量

编译器为局部变量分配栈槽位。当一个程序里的局部变量分散在多个函数中时，这件事该怎么办？

一种做法是让它们彻底分开。每个函数在 VM 栈里拥有自己专属的一组槽位，<span name="static">永远</span>归它所有，
哪怕这个函数当前没被调用。整个程序里的每个局部变量都会在 VM 里占一块只属于它自己的内存。

<aside name="static">

这基本上就是你在 C 程序里把每个局部变量都用 `static` 声明时会得到的东西。

</aside>

信不信由你，早期的编程语言实现确实是这么干的。最早的 Fortran 编译器为每个变量静态分配内存。
显而易见的问题是它效率极低。大多数函数在任何时刻都不正处于被调用的状态，所以替它们占着
用不上的内存纯属浪费。

不过更根本的问题是递归。有了递归，你可以同时「处于」对同一个函数的多次调用之中。每次调用
都需要<span name="fortran">自己</span>的内存来放局部变量。在 jlox 里，我们靠每次调用
函数或进入一个块时都动态分配一份环境内存来解决。在 clox 里，我们不想让每次函数调用都背上
这种性能开销。

<aside name="fortran">

Fortran 干脆完全禁止递归来回避这个问题。在当时，递归被视为一项进阶而深奥的特性。

</aside>

我们的做法则落在 Fortran 的静态分配与 jlox 的动态方案之间。VM 的值栈基于这样一个观察：
局部变量和临时值的行为是后进先出的。幸运的是，即使加上函数调用，这一点依然成立。举个例子：

```lox
fun first() {
  var a = 1;
  second();
  var b = 2;
}

fun second() {
  var c = 3;
  var d = 4;
}

first();
```

一步步走过这个程序，看看每个时刻内存里有哪些变量：

<img src="image/calls-and-functions/calls.png" alt="走一遍上一个程序的执行，展示每一步的变量栈。" />

执行流经这两次调用时，每个局部变量都遵守这样一条原则：后声明的变量，总是先于先声明的变量被丢弃。这一点跨越调用也成立。我们知道用完 `c` 和 `d` 会早于用完 `a`。
看来我们确实可以把局部变量分配到 VM 的值栈上。

理想情况下，我们仍然在编译期决定每个变量会放到栈上的**哪里**。这样操作变量的字节码指令
才能保持简单快速。在上面那个例子里，我们可以相当直接地<span name="imagine">想象</span>出
这种做法，但并非总是行得通。考虑：

<aside name="imagine">

我说「想象」，是因为编译器其实没法把它算出来。因为函数在 Lox 里是一等的，我们无法在编译期
确定哪个函数调用哪个函数。

</aside>

```lox
fun first() {
  var a = 1;
  second();
  var b = 2;
  second();
}

fun second() {
  var c = 3;
  var d = 4;
}

first();
```

在第一次调用 `second()` 时，`c` 和 `d` 会落进 1 号和 2 号槽位。但第二次调用时，我们需要给
`b` 腾出位置，所以 `c` 和 `d` 得待在 2 号和 3 号槽位。因此编译器无法跨函数调用为每个局部
变量钉死一个确切的槽位。但在某个函数**内部**，各局部变量的**相对**位置是固定的。
变量 `d` 永远紧跟在 `c` 后面。这就是关键所在。

函数被调用时，我们不知道栈顶会在哪里，因为它可能从不同的上下文被调用。但不管那个栈顶碰巧
在哪里，我们都清楚这个函数的所有局部变量相对于那个起点会在哪里。所以，和很多问题一样，
我们用一层间接来解决分配问题。

在每次函数调用的开头，VM 记录下该函数自己的局部变量从哪个槽位开始。那些操作局部变量的
指令，会按相对于这个位置的槽位索引来访问它们，而不是像现在这样相对于栈底。编译期我们算出
这些相对槽位；运行时我们把相对槽位加上本次函数调用的起始槽位，换算成绝对的栈索引。

这就像函数在更大的栈里获得了一个「窗口」或「帧」，可以在里面存放自己的局部变量。
**调用帧**的位置在运行时确定，但在那块区域之内、相对于它，我们知道东西在哪儿。

<img src="image/calls-and-functions/window.png" alt="second() 被调用时的两个时刻的栈，各有一个窗口悬浮其上，显示该函数使用的两个栈槽位。" />

这个记录「函数局部变量从何处开始」的位置，其历史名称叫**帧指针**，因为它指向函数调用帧的
开头。有时你也听人叫它**基址指针**，因为它指向那个「函数所有变量都叠在其上」的基准栈槽位。

这是我们需要追踪的第一份数据。每次我们调用一个函数，VM 都会确定该函数的变量从哪个栈槽位
开始。

### 返回地址

目前，VM 是靠递增 `ip` 字段在指令流中前进的。唯一有意思的行为在控制流指令附近，它们会给
`ip` 加上更大的偏移。**调用**一个函数相当直接——只要把 `ip` 设成指向那个函数代码块中的第一条
指令就行。但函数执行完之后呢？

VM 需要<span name="return">返回</span>到调用它的那个代码块，并从紧挨着调用之后的那条
指令继续执行。所以对每一次函数调用，我们都需要追踪「调用完成时该跳回哪里」。这叫**返回
地址**，因为它就是 VM 在调用结束后要回到的那条指令的地址。

同样因为递归，一个函数可能对应多个返回地址，所以这是每次**调用**的属性，而不是函数
本身的属性。

<aside name="return">

早期 Fortran 编译器的作者们实现返回地址用过一个聪明的技巧。既然他们**不**支持递归，任何一个
函数在任何时刻只需要一个返回地址。于是当一个函数在运行时被调用时，程序会**修改自己的代码**，
把函数末尾的跳转指令改成跳回它的调用者。有时候天才与疯狂之间只隔着一根头发丝。

</aside>

### 调用栈

于是，对每一次活着的函数调用——每一次尚未返回的调用——我们都需要追踪该函数的局部变量从
栈上何处开始，以及调用方该从哪里恢复。我们把这些连同别的东西一起放进一个新结构体。

^code call-frame (1 before, 2 after)

一个 CallFrame 表示一次进行中的函数调用。`slots` 字段指向 VM 值栈里这个函数可以使用的第一个
槽位。我给它起了个复数名字，因为——拜 C 那个古怪的「指针差不多就是数组」特性所赐——我们会
把它当数组用。

返回地址的实现和我上面描述的稍有不同。我们不是把返回地址存在被调用方的帧里，而是让调用方
存下自己的 `ip`。当我们从一个函数返回时，VM 会跳到调用方 CallFrame 的 `ip` 并从那里恢复。

我还把一个指向被调用函数的指针塞在了这里。我们会用它查常量，以及做另外几件事。

每次函数被调用，我们都创建这样一个结构体。我们本可以在堆上<span name="heap">动态</span>
分配它们，但那样太慢。函数调用是核心操作，所以必须尽可能快。幸运的是，我们可以做和变量
那个一样的观察：函数调用具有栈语义。如果 `first()` 调用了 `second()`，那么对 `second()` 的
调用会在 `first()` 完成之前完成。

<aside name="heap">

很多 Lisp 实现会动态分配栈帧，因为那样实现[延续][cont]更简单。如果你的语言支持延续，那么
函数调用就**不**总是具有栈语义。

[cont]: https://en.wikipedia.org/wiki/Continuation

</aside>

### 一栈编译器

有意思的部分是上面和下面那些跟编译器有关的东西。Compiler 结构体存放诸如「哪些槽位归哪些
局部变量所有」「我们当前嵌了几层块」之类的数据。这些全都是针对单个函数的。但现在前端需要
处理编译彼此<span name="nested">嵌套</span>的多个函数。

<aside name="nested">

记住编译器把顶层代码当作一个隐式函数的函数体，所以只要我们加上**任何**函数声明，我们就进入
了嵌套函数的世界。

</aside>

管理这事的诀窍是：为每个正在编译的函数创建一个独立的 Compiler。我们开始编译一条函数声明时，
就在 C 栈上创建一个新 Compiler 并初始化它。`initCompiler()` 把这个 Compiler 设为当前的那个。
然后在编译函数体时，所有会发射字节码的函数都写进新 Compiler 那个函数所拥有的代码块。

在到达函数块函数体的末尾之后，我们调用 `endCompiler()`。它交出刚编译出来的函数对象，我们
把它作为常量存进**外围**函数的常量表。可是等等，我们怎么回到外围函数去？`initCompiler()`
覆盖当前编译器指针的时候，我们把它弄丢了。

我们的办法是把这一串嵌套的 Compiler 结构体当成一个栈来对待。和 VM 里的 Value 栈、
CallFrame 栈不同，我们不用数组，而是用链表。每个 Compiler 都指回包围它的那个函数对应的
Compiler，一路指回顶层代码的根 Compiler。

^code enclosing-field (2 before, 1 after)

在 Compiler 结构体内部，我们没法引用 Compiler 的 **typedef**，因为那个声明还没结束。于是我们
给结构体本身起了个名字，用它来做这个字段的类型。C 真奇怪。

初始化新 Compiler 时，我们把那个即将不再是「当前」的 Compiler 捕获进这个指针。

^code store-enclosing (1 before, 1 after)

然后当一个 Compiler 结束时，它通过把前一个编译器恢复成新的「当前」来把自己弹出栈。

^code restore-enclosing (2 before, 1 after)

注意我们甚至都不需要<span name="compiler">动态</span>分配这些 Compiler 结构体。每个都
作为局部变量存在 C 栈上——要么在 `compile()` 里，要么在 `function()` 里。Compiler 组成的
链表就穿行在 C 栈之中。我们之所以能有任意多个，是因为我们的编译器用递归下降，所以有了嵌套
函数声明时 `function()` 最终会递归调用自己。

<aside name="compiler">

用原生栈存放 Compiler 结构体，确实意味着我们的编译器对函数声明能嵌套多深有个实际限制。
走得太远就可能撑爆 C 栈。如果我们希望编译器对病态甚至恶意代码更健壮——这对 JavaScript VM
之类的工具是个真正的关切——那么让编译器人为地限制它允许的函数嵌套层数会更好。

</aside>

### 把实参绑定到形参

在动手实现之前，我们得先想清楚调用点上栈是什么样子，以及从那里起我们该做什么。当我们执行到
调用指令时，被调用函数的表达式已经执行过了，紧跟着是它的实参。假设我们的程序是这样：

```lox

  return a + b + c;
}

```

如果我们在那次 `sum()` 调用的 `OP_CALL` 指令上把 VM 暂停，栈长这样：

<img src="image/calls-and-functions/argument-stack.png" alt="栈：4、fn sum、5、6、7。" />

站在 `sum()` 自身的角度想象一下。编译器编译 `sum()` 时自动分配了 0 号槽位，然后在它之后依次
为形参 `a`、`b`、`c` 分配了局部槽位。要完成一次对 `sum()` 的调用，我们需要一个初始化好的
CallFrame，里面放着被调用的函数和一块它可以使用的栈槽位区域。然后我们得把传给该函数的实参
收集起来，放进形参对应的那些槽位。

当 VM 开始执行 `sum()` 的函数体时，我们希望它的栈窗口长这样：

<img src="image/calls-and-functions/parameter-window.png" alt="同一个栈，sum() 函数的调用帧窗口把 fn sum、5、6、7 围在中间。" />

你注意到调用方准备好的实参槽位与被调用方需要的形参槽位，顺序完全对得上吗？多方便！
这绝非巧合。当我讲每个 CallFrame 都有自己的栈内窗口时，从没说过这些窗口必须**互不重叠**。
没有什么能阻止我们让它们像这样重叠：

<img src="image/calls-and-functions/overlapping-windows.png" alt="同一个栈，顶层调用帧覆盖整个栈，sum() 函数的调用帧窗口把 fn sum、5、6、7 围在中间。" />

调用方在那些槽位之上没有别的槽位在用，因为求值实参表达式时需要的任何临时值这时都已经被丢弃

<aside name="lua">

不同的字节码 VM 和真实的 CPU 架构有不同的**调用约定**，也就是它们各自传递实参、存放返回

</aside>

相当直白。这就是为什么我们把每个函数的元数存在它的 ObjFunction 里面。

还有另一个错误要报告，不过它跟用户的糊涂相比更关乎我们自己。由于 CallFrame 数组大小固定，
我们得确保很深的调用链不会把它撑爆。

^code check-overflow (2 before, 1 after)

实践中，如果一个程序接近了这个限制，那多半是某段失控的递归代码里有 bug。

### 打印堆栈跟踪

既然说到运行时错误，我们花点时间让它们更有用。遇到运行时错误就停下来，对于防止 VM 以某种
未定义的方式崩溃烧毁是很重要的。但仅仅中止并不能帮用户修好那些**导致**了这个错误的代码。

辅助调试运行时故障的经典工具是**堆栈跟踪**——把程序死掉时仍在执行的每个函数都打印出来，
外加它死掉那一刻执行到了哪里。现在我们有了调用栈，又顺手把每个函数的名字都存了下来，于是可以在运行时错误把用户折腾得够呛时，把整个栈显示出来。它长这样：

^code runtime-error-stack (2 before, 2 after)

<aside name="minus">

那个 `- 1` 是因为 IP 已经停在下一条待执行指令上了，而我们希望堆栈跟踪指向上一条失败的指令。

</aside>

打印完错误信息本身，我们从<span name="top">栈顶</span>（最近被调用的那个函数）走到栈底
（顶层代码）。对每一帧，我们找出该帧函数内部与当前 `ip` 对应的行号，然后把行号连同函数名
一起打印出来。

<aside name="top">

对于堆栈跟踪里各帧该按什么顺序展示，是有些分歧的。多数实现把最内层的函数放在第一行，然后
朝栈底方向排下去。Python 则按相反的顺序打印。所以从上往下读，能知道你的程序是怎么走到现在
这个位置的，而最后一行才是错误实际发生的地方。

这种风格是有道理的。它保证你总能看到最内层的函数，哪怕堆栈跟踪太长塞不进一屏。另一方面，
新闻业里的「[倒金字塔][inverted pyramid]」告诉我们，在一段文字里应该把最重要的信息放在**最前面**。在堆栈
跟踪里，那就是错误实际发生的那个函数。其他大多数语言实现都是这么做的。

[inverted pyramid]: https://en.wikipedia.org/wiki/Inverted_pyramid_(journalism)

</aside>

比如说，如果你运行这个坏掉的程序：

```lox
fun a() { b(); }
fun b() { c(); }
fun c() {
  c("too", "many");
}

a();
```

它会打印出：

```text
Expected 0 arguments but got 2.
[line 4] in c()
[line 2] in b()
[line 1] in a()
[line 7] in script
```

看起来还不赖，是吧？

### 从函数返回

我们快接近了。我们能调用函数，VM 也会执行它们。但我们还不能从它们**返回**。`OP_RETURN`
指令我们已经挂了挺久了，可它里面一直挂着某种临时代码，只为把我们从字节码循环里捞出来。
现在是给它一个正式实现的时候了。

^code interpret-return (1 before, 1 after)

当一个函数返回值时，那个值会在栈顶。我们正要丢弃被调用函数整个的栈窗口，所以先把返回值弹出
来攥在手里。然后丢弃返回中那个函数的 CallFrame。如果那已经是最后一个 CallFrame，就说明我们
执行完了顶层代码。整个程序结束了，于是我们把主脚本函数从栈上弹出，然后退出解释器。

否则，我们丢弃被调用方用来放形参和局部变量的所有槽位。这里面包括调用方当初用来传实参的
同一批槽位。现在调用已经结束，调用方不再需要它们了。这就意味着栈顶最终正好落在返回中那个
函数的栈窗口开头处。

我们把返回值压回栈上那个更低的、新的位置。然后更新 `run()` 那个缓存的当前帧指针。就像我们
开始一次调用时一样，在字节码分派循环的下一轮迭代里，VM 会从那个帧读出 `ip`，执行就跳回
调用方，正好停在你离开的地方，紧跟在 `OP_CALL` 指令之后。

<img src="image/calls-and-functions/return.png" alt="返回过程的每一步：弹出返回值、丢弃调用帧、压入返回值。" />

注意我们在这里假定函数**确实**返回了值，但一个函数也可以执行到函数体末尾而隐式返回：

```lox
fun noReturn() {
  print "Do stuff";
  // No return here.
}

print noReturn(); // ???
```

这个也得正确处理。语言规定这种情况下隐式返回 `nil`。为此我们加上这个：

^code return-nil (1 before, 2 after)

编译器调用 `emitReturn()` 在函数体末尾写出 `OP_RETURN` 指令。而在那之前，它会先发射一条把
`nil` 压栈的指令。就这样，我们有了能用的函数调用！它们甚至还能接收形参！看起来我们几乎像是
知道自己在干什么。

## Return 语句

如果你想要一个返回隐式 `nil` 以外的东西的函数，就需要一条 `return` 语句。我们来把它搞定。

^code match-return (1 before, 1 after)

当编译器看到 `return` 关键字时，它会走到这里：

^code return-statement

返回值表达式是可选的，所以解析器会去找分号词法单元来判断有没有给出值。如果没有返回值，这条语句
隐式返回 `nil`。我们通过调用 `emitReturn()` 来实现，它会发射一条 `OP_NIL` 指令。否则，我们
编译返回值表达式，并用一条 `OP_RETURN` 指令返回它。

这就是我们已经实现过的同一条 `OP_RETURN` 指令——我们不需要任何新的运行时代码。这和 jlox
差别相当大。在那里，执行一条 `return` 语句时我们不得不用异常把栈退回去。那是因为你可以从
某堆嵌套块的深处返回。既然 jlox 是递归遍历 AST 的，那就意味着一堆我们需要逃出去的 Java
方法调用。

我们的字节码编译器把这一切都抹平了。解析阶段我们做递归下降，但运行时，VM 的字节码分派循环
是完全扁平的。C 这一层根本没有任何递归。所以返回——哪怕是从某堆嵌套块内部返回——就像从函数体
末尾返回一样简单。

不过我们还没完全干完。新的 `return` 语句带来一个要操心的编译错误。返回对从函数里返回很有用，
但 Lox 程序的顶层也是命令式代码。你不该能从那里<span name="worst">返回</span>。

```lox
return "What?!";
```

<aside name="worst">

允许在顶层 `return` 也不算是世界上最糟的主意。它会给你一个自然的方式来提前终止脚本。
你甚至可能可以用返回的数字来表示进程的退出码。

</aside>

我们规定在任何函数之外出现 `return` 语句都是编译错误，实现方式如下：

^code return-from-script (1 before, 1 after)

这也是我们给编译器加上那个 FunctionType 枚举的原因之一。

## 原生函数

我们的 VM 越来越强了。有了函数、调用、形参、返回。你可以定义很多不同的函数，并以各种
有意思的方式互相调用。但归根结底，它们其实做不了**任何**事。不管一个 Lox 程序有多复杂，
用户唯一看得到的操作只有打印。要增加更多能力，我们得把它们暴露给用户。

一个编程语言实现是靠**原生函数**跟外部世界打交道的。如果你希望用户能写出检查时间、读取
用户输入或访问文件系统的程序，我们就需要加入原生函数——从 Lox 可调用、但用 C 实现的函数——
来暴露这些能力。

在语言层面，Lox 已经相当完整了——它有闭包、类、继承，还有其他一堆好玩的东西。它之所以让人
感觉像个玩具语言，很大程度上是因为它几乎没有任何原生能力。加上长长一串之后，它就能变成一门
真正的语言。

不过，啃完一大堆操作系统调用其实没什么教育意义。一旦你看懂了怎么把一段 C 代码绑定到 Lox，
道理就通了。但你确实得看**一个**，而且哪怕单个原生函数也要我们把 Lox 与 C 互操作的整套机制
搭出来。所以我们会走完这套流程，把苦活干完。然后，等做完之后，我们再加一个小原生函数，
只为证明它确实能用。

我们需要新机制，是因为从实现的角度看，原生函数和 Lox 函数不一样。它们被调用时不会压入
CallFrame，因为没有字节码代码可供那一帧指向。它们没有字节码代码块，而是以某种方式引用了
一段原生的 C 代码。

我们在 clox 里的做法，是把原生函数定义成一个完全不同的对象类型。

^code obj-native (1 before, 2 after)

它的表示比 ObjFunction 简单——只有一个 Obj 头部和一个指向实现该原生行为的 C 函数的指针。
这个原生函数接收实参个数和一个指向栈上第一个实参的指针。它通过那个指针访问实参。干完之后，
它返回结果值。

和往常一样，新对象类型总带着一套附属品。要创建一个 ObjNative，我们声明一个类似构造函数
的函数。

^code new-native-h (1 before, 1 after)

我们这样实现它：

^code new-native

这个「构造函数」接收一个要包进 ObjNative 的 C 函数指针。它搭好对象头部并存下该函数。头部
这边，我们需要一个新的对象类型。

^code obj-type-native (2 before, 2 after)

VM 还得知道怎么释放一个原生函数对象。

^code free-native (1 before, 1 after)

这里没什么内容，因为 ObjNative 不拥有任何额外的内存。所有 Lox 对象支持的另一项能力是被打印。

^code print-native (1 before, 1 after)

为了支持动态类型，我们有一个宏来判断一个值是不是原生函数。

^code is-native (1 before, 1 after)

假定这个宏返回真，这个宏就从代表原生函数的 Value 里取出 C 函数指针：

^code as-native (1 before, 1 after)

这一整套行头让 VM 能像对待任何其他对象那样对待原生函数。你可以把它们存进变量、到处传递、
给它们办生日派对等等。当然，我们真正关心的是**调用**它们——在调用表达式里把一个当作左操作数。

在 `callValue()` 那边，我们再加一个类型分支。

^code call-native (2 before, 1 after)

如果被调用的对象是个原生函数，我们就当场调用那个 C 函数。完全没必要去折腾 CallFrame 之类
的东西。我们只要把活交给 C，拿回结果，再塞回栈里。这让原生函数快到了极致。

这样一来，用户应该能调用原生函数了，可我们还没有任何原生函数可调。没有像外部函数接口
（FFI）这样的东西，用户无法定义自己的原生函数。那是我们作为 VM 实现者的活儿。我们先从
一个定义新原生函数、并暴露给 Lox 程序的辅助函数开始。

^code define-native

它接收一个 C 函数的指针，以及这个函数在 Lox 中将要使用的名字。我们把该函数包进一个
ObjNative，然后把那个对象存进一个同名的全局变量里。

你可能在想，为什么我们要把名字和函数在栈上压进去又弹出来。看起来很奇怪，对吧？这类事情
正是<span name="worry">垃圾</span>回收介入时你不得不操心的事。`copyString()` 和 `newNative()` 都会动态分配内存。
这意味着一旦我们有了 GC，它们就可能触发一次回收。如果真发生了，我们得确保回收器知道我们
还没用完那个名字和那个 ObjFunction，这样它才不会在我们脚下把它们释放掉。把它们存在值栈上
就达到了这个目的。

<aside name="worry">

如果你没跟上上面那一大段，也没关系。等我们真的[实现 GC][gc]的时候，它会好懂得多。

[gc]: garbage-collection.html

</aside>

感觉很傻，但干完上面那一大堆活之后，我们只加了一个小原生函数。

^code clock-native

它返回程序开始运行以来经过的时间，单位是秒。拿它给 Lox 程序做基准测试很方便。在 Lox 里，
我们把它命名为 `clock()`。

^code define-native-clock (1 before, 1 after)

为了用到 C 标准库里的 `clock()` 函数，「vm」模块需要加一个 include。

^code vm-include-time (1 before, 2 after)

要消化的材料可真不少，不过我们还是干完了！把这些输进去试试：

```lox
fun fib(n) {
  if (n < 2) return n;
  return fib(n - 2) + fib(n - 1);
}

var start = clock();
print fib(35);
print clock() - start;
```

我们可以写一个效率低得惊人的递归斐波那契函数。更妙的是，我们还能测量它<span name="faster">**有多**</span>低效。
这当然不是算斐波那契数最聪明的方式。但它是一个检验语言实现对函数调用支持程度的好办法。
在我的机器上，在 clox 里跑这段比在 jlox 里跑快大约五倍。这可是相当大的改进。

<aside name="faster">

它比同样一个程序用 Ruby 2.4.3p205 跑要慢一点，比用 Python 3.7.3 跑快大约 3 倍。而且我们的
VM 里还有很多简单的优化可以做。

</aside>

## 习题
1.  读写 `ip` 字段是字节码循环里最频繁的操作之一。目前我们是通过一个指向当前 CallFrame 的
    指针来访问它。这需要一层指针间接，可能会迫使 CPU 绕过缓存去访问主存。那可能是个实打实
    的性能黑洞。

    理想情况下，我们会把 `ip` 放在 CPU 的原生寄存器里。C 不让我们在不写内联汇编的前提下
    **强制**这一点，但我们可以组织代码来鼓励编译器做这个优化。如果我们把 `ip` 直接存成一个
    C 局部变量并标记为 `register`，C 编译器很有可能答应我们这个客气的请求。

    这确实意味着我们得小心，在函数调用开始和结束时把局部 `ip` 正确地写回对应的 CallFrame。
    实现这个优化。写几个基准测试，看看它对性能的影响。你觉得多出来的代码复杂度值吗？

2.  原生函数调用快，部分原因是我们没有校验这次调用传入的实参个数是否与函数期望的相同。
    我们其实真该校验，否则一次实参不足的错误原生函数调用就可能让函数去读未初始化的内存。
    加上元数检查。

3.  目前，原生函数没有办法发出运行时错误。在一个真实的实现里，这是我们必须支持的，因为
    原生函数生活在静态类型的 C 世界里，却被来自动态类型的 Lox 世界的程序调用。比如用户
    试着给 `sqrt()` 传一个字符串，那个原生函数就需要报运行时错误。

    扩展原生函数系统来支持这件事。这项能力会怎么影响原生调用的性能？

4.  再加几个你觉得有用的原生函数。用它们写些程序。你加了些什么？它们对这门语言的手感和实用性有多大影响？
