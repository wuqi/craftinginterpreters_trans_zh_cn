要让计算机执行用户源码命令它做的事，语言实现有很多办法。它可以把源码编译成机器码，
翻译成另一种高级语言，或者化简成某种字节码格式交给虚拟机运行。不过对我们这第一个

眼下，我们的语法解析器只支持表达式。所以要「执行」代码，我们就得对一个表达式求值，
产出一个值。我们能语法解析的每一种表达式语法——字面量、运算符等等——都需要一段对应的

1. 我们产出哪些种类的值？

2. 我们又怎么组织这些代码？

## 表示值

在 Lox 里，<span name="value">值</span>由字面量创造，由表达式算出，存在变量里。用户把它们
看成 Lox 对象，但它们是拿我们写解释器所用的底层语言实现的。这就意味着要给 Lox 的动态类型
和 Java 的静态类型这两片地搭桥。Lox 里的一个变量可以存任意（Lox）类型的值，甚至能在不同
时刻存不同类型的值。那我们该用 Java 的哪种类型来表示它呢？

<aside name="value">

在这里，「值」和「对象」两个词我基本是混着用的。后面写 C 解释器时，我们会把它们稍微
区分开，但那多半只是为了给实现里的两个不同角落——原地存储的数据和堆上分配的数据——各
准备一个专门的词。从用户的角度看，这两个词是一回事。

</aside>

给定一个具有该静态类型的 Java 变量，我们还必须能在运行时判断它装的是哪种值。解释器执行
`+` 运算符时，需要分清自己是在把两个数字相加，还是在把两个字符串拼接。有没有哪种 Java
类型能装数字、字符串、布尔值等等？有没有一种能告诉我们它的运行时类型是什么？有的！就是
我们的老朋友 java.lang.Object。

在解释器里需要存 Lox 值的地方，我们都可以用 Object 当类型。Java 的原始类型都有装箱版本，
且都继承自 Object，所以我们能用它们来做 Lox 的内置类型：

## 对表达式求值

接下来，对于我们能语法解析的每一种表达式，都需要一坨坨代码来实现它的求值逻辑。我们
可以把这些代码塞进语法树类里，比如写成 `interpret()` 方法。实际上就是告诉每个语法树节点：
「解释你自己」。这就是 GoF 的[解释器模式][interpreter design pattern]。这模式很精巧，但正如
我之前提到的，一旦把五花八门的逻辑都塞进树类里，它就会乱成一团。

[interpreter design pattern]: https://en.wikipedia.org/wiki/Interpreter_pattern

所以我们换个做法，复用那个好用的[访问者模式][visitor pattern]。上一章里，我们写了个
AstPrinter 类。它接收一棵语法树，递归地遍历它，拼出一个字符串最后返回。这几乎就是一个
真正的解释器干的事，只不过解释器拼的不是字符串，而是算出值。

[visitor pattern]: representing-code.html#访问者模式

我们从一个新类开始。

^code interpreter-class

这个类声明自己是个访问者。visit 方法的返回类型会是 Object，也就是我们在 Java 代码里用来
指代 Lox 值的根类。为了满足 Visitor 接口，我们需要为语法解析器产出的四个表达式树类各定义
一个 visit 方法。先从最简单的那个开始……

### 对字面量求值

表达式树的叶子——所有其他表达式都由之拼成的原子级语法片段——就是<span name="leaf">字面量</span>。
字面量几乎已经是值了，但这个区分很重要。字面量是**一段语法**，它产出一个值。字面量总是
出现在用户源码的某个地方。而很多值是由计算产生的，在代码本身里哪儿都找不到。那些不是
字面量。字面量来自语法解析器的地盘，而值是解释器的概念，属于运行时那个世界。

[vars]: statements-and-state.html

</aside>

字面量树节点转换成运行时的值。结果发现这事微不足道。

^code visit-literal

早在扫描那一步，我们就急不可耐地算出了运行时的值，塞进了词法单元里。语法解析器拿过

### 对一元表达式求值

和分组一样，一元表达式也有一个必须先求值的子表达式。区别在于，一元表达式本身在之后还要
做一点活。

^code visit-unary

首先，我们给操作数表达式求值。然后把这个结果拿去做一元运算符本身的运算。一元表达式有
两种，靠运算符词法单元的类型来区分。

这里展示的是 `-`，它对子表达式的结果取负。子表达式必须是个数字。由于我们在 Java 里无法
**静态地**知道这一点，所以在执行运算前要先对它做<span name="cast">强制转换</span>。这次类型
转换发生在运行时，就在 `-` 被求值的时候。一门语言之所以是动态类型，核心就在这里。

<aside name="cast">

你大概在想，万一强制转换失败会怎样。别担心，我们很快就会讲到。

</aside>

你开始能看出求值是如何递归地遍历这棵树的。在给操作数子表达式求值之前，我们没法给一元
运算符本身求值。这意味着我们的解释器做的是**后序遍历**——每个节点先给它的子节点求值，再干
自己的活。

### 真值与假值

好吧，也许我们不打算真的去碰那个普世难题，但至少在 Lox 这个世界里，我们得决定：当你在像
`!` 这样的逻辑运算里，或者在别的任何需要布尔值的地方，用的是 `true` 或 `false` 之外的东西时，
会发生什么。

我们**大可以**直接说这是错误，因为我们不吃隐式转换那一套，但大多数动态类型语言没那么苦行。
它们会把所有类型的值分成两个集合：一个被定义为「真」、「为真」，或者（我最喜欢
的）「真值」（truthy），其余的则是「假」或「假值」（falsy）。这种划分多少有些随意，在少数
几种语言里还会变得<span name="weird">很古怪</span>。

<aside name="weird" class="bottom">

在 JavaScript 里，字符串是真值，但空字符串不是。数组是真值，可空数组……也是真值。数字
`0` 是假值，但**字符串** `"0"` 是真值。

在 Python 里，空字符串跟 JS 里一样是假值，但其他空序列也是假值。

在 PHP 里，数字 `0` 和字符串 `"0"` 都是假值。其他大多数非空字符串则是真值。

都记住了吗？

</aside>

Lox 遵循 Ruby 那条简单的规则：`false` 和 `nil` 是假值，其余一切都是真值。我们这样实现：

接着到最后一个表达式树类：二元运算符。它们有好几个，我们从算术那几个开始。

^code visit-binary

我想你能看出这里在干什么。它跟一元取负运算符的主要区别，在于我们要给两个操作数求值。

我漏掉了一个算术运算符，因为它有点特别。

^code binary-plus (3 before, 1 after)

`+` 运算符还能用来拼接两个字符串。为了应付这个，我们不是先假定操作数是某种类型再**强制
转换**，而是动态地**检查**类型，然后选用合适的运算。这就是为什么我们的对象表示需要支持
`instanceof`。

<aside name="plus">

我们本可以专门定义一个运算符来做字符串拼接。Perl（`.`）、Lua（`..`）、Smalltalk（`,`）、
Haskell（`++`）等就是这么干的。

我觉得，跟 Java、JavaScript、Python 等用同一套语法，能让 Lox 更好上手一点。这意味着 `+`
运算符被**重载**了，既能做数字相加，又能做字符串拼接。即便在那些不用 `+` 处理字符串的
语言里，它们也常常重载它，用来同时做整数相加和浮点数相加。

</aside>

接下来是比较运算符。

^code binary-comparison (1 before, 1 after)

它们跟算术运算符基本一样。唯一的区别是：算术运算符产出的值，类型跟操作数相同（数字或
字符串），而比较运算符永远产出一个布尔值。

最后一对运算符是相等。

^code binary-equality

比较运算符要求操作数是数字，相等运算符则不然，它支持任意类型的操作数，哪怕两边类型不同。
你不能问 Lox 3 是不是**小于** `"three"`，但你可以问它是不是<span name="equal">**等于**</span>
`"three"`。

<aside name="equal">

剧透一下：不是。

</aside>

和真值判断一样，相等逻辑被单独提到一个方法里。

^code is-equal

这正是那种棘手的地方：我们如何用 Java 来表示 Lox 对象，这个细节在这里很要紧。我们需要正确实现
**Lox 的**相等概念，它可能跟 Java 的不一样。

幸好，这两者相当接近。Lox 的相等不做隐式转换，Java 也不做。我们确实得对 `nil`/`null` 特殊
处理，免得在对 `null` 调 `equals()` 时抛出 NullPointerException。除此之外就没问题了。Java 在
Boolean、Double 和 String 上的 <span name="nan">`equals()`</span> 方法，行为正合 Lox 所需。

<aside name="nan">

你猜这个会求值成什么：

```lox
(0 / 0) == (0 / 0)
```

按照规定了双精度数行为的 [IEEE 754][]，零除以零会得到一个特殊的 **NaN**（「非数」）值。说来
奇怪，NaN **不**等于它自己。

在 Java 里，原始类型 double 上的 `==` 运算符沿用了这个行为，但 Double 类上的 `equals()`
方法没有。Lox 用的是后者，所以不遵循 IEEE。这类微妙的不兼容，占据了语言实现者生活中
令人沮丧的一大部分。

[ieee 754]: https://en.wikipedia.org/wiki/IEEE_754

</aside>

就这样！正确解释一个合法 Lox 表达式所需的代码，就这么多了。可要是**非法**的表达式呢？
具体来说，当某个子表达式求值出的对象，类型跟正在执行的运算对不上时，会怎样？

## 运行时错误

之前在子表达式产出 Object、而运算符又要求它是数字或字符串时，我就随手塞了个强制转换
进去，一副满不在乎的样子。这些强制转换可能会失败。就算用户的代码是错的，只要我们想造出
一门<span name="fail">好用</span>的语言，就有责任优雅地处理这个错误。

<aside name="fail">

我们大可以干脆不检测、也不报告类型错误。C 就是这么做的：你把指针强制转换成某种类型，而
它跟指针实际指向的数据对不上，它也不管。C 通过允许这种做法换来了灵活和速度，但也出了名
地危险。一旦你错误解读了内存里的比特，一切就都说不准了。

现代语言里很少有接受这种不安全操作的。相反，大多数语言都是**内存安全**的，通过静态检查
和运行时检查相结合，确保程序永远不会错误地解读某块内存里存着的值。

</aside>

现在该聊聊**运行时错误**了。前几章我费了不少笔墨讲错误处理，但那些都是**语法**错误或
**静态**错误。它们在**任何**代码执行之前就被检测并报告出来了。运行时错误则是语言语义要求
我们在程序运行期间检测并报告的那些失败（名字就是这么来的）。

眼下，如果某个操作数对于正在执行的运算来说类型不对，Java 的强制转换就会失败，JVM 会抛出
一个 ClassCastException。这会把整个调用栈一层层解开，退出应用，还朝用户脸上吐出一堆 Java
调用栈追踪。这多半不是我们想要的。Lox 是用 Java 实现的——这个事实应该是瞒着用户的一个
细节。我们想让他们明白：出的是一个 **Lox** 运行时错误，并且给他们一条跟我们这门语言、
跟他们这个程序相关的错误信息。

不过 Java 这种做法也有一个可取之处：错误发生时，它会正确地停止执行任何代码。假设用户
输入了这么一个表达式：

```lox
2 * (3 / -"muffin")
```

你没法对一个<span name="muffin">马芬</span>取负，所以我们得在那个内层的 `-` 表达式处报一个
运行时错误。这又意味着我们没法给 `/` 表达式求值了，因为它的右操作数已经没有意义。`*` 也
一样。所以当运行时错误发生在某个表达式的深处时，我们得一路逃到最外面去。

<aside name="muffin">

我不知道啊，老兄，你**真的**能给马芬取负吗？

<img src="image/evaluating-expressions/muffin.png" alt="一个被取负的马芬。" />

</aside>

我们可以在打印一条运行时错误之后，直接中止进程、彻底退出应用。这倒是有那么点戏剧性的
派头，差不多相当于编程语言解释器界的一次摔麦。

这虽然很诱人，但我们大概还是该做点没那么灾难性的事。运行时错误需要停止对**表达式**求值，
但不该把**解释器**弄死。如果用户正在跑 REPL，某一行代码里打了个错字，他们仍然应该能把这个
会话继续下去，接着再输入更多代码。

<aside name="operand">

还有一个微妙的语义选择：我们在检查**任一**操作数的类型之前，会先给**两个**操作数都求值。

## 设计说明：静态类型与动态类型

有些语言，比如 Java，是静态类型的，这意味着类型错误会在编译期、任何代码运行之前就被检测
并报告出来。另一些语言，比如 Lox，是动态类型的，它把类型检查推迟到运行时、就在某个运算
即将执行之前才做。我们往往觉得这是个非黑即白的选择，可实际上两者之间是一个连续谱。

事实证明，就连大多数静态类型语言，也会在运行时做**一些**类型检查。类型系统把大部分类型
规则都在静态阶段检查了，但会为另一些运算在生成的代码里插入运行时检查。

举个例子，在 Java 里，**静态**类型系统假定一个强制转换表达式总会安全成功。你把某个值
强制转换之后，就可以在静态层面把它当作目标类型来对待，不会得到任何编译错误。但向下转型
显然可能失败。静态检查器之所以能假定转换总是成功、又不违反语言的健全性保证，唯一的
原因就是转换**在运行时**会被检查，失败时抛出异常。

一个更微妙的例子是 Java 和 C# 里的[协变数组][covariant arrays]。数组的静态子类型规则允许
一些并不健全的操作。看这个：

[covariant arrays]: https://en.wikipedia.org/wiki/Covariance_and_contravariance_(computer_science)#Covariant_arrays_in_Java_and_C.23

```java
Object[] stuff = new Integer[1];
stuff[0] = "not an int!";
```

这段代码编译时没有任何错误。第一行把 Integer 数组向上转型，存进一个 Object 数组类型的
变量。第二行往它的某个格子里存了一个字符串。Object 数组类型在静态层面允许这么做——字符串
**确实**是 Object——但 `stuff` 在运行时实际指向的那个 Integer 数组，里面本就不该出现字符串！
为了避免这场灾难，当你往数组里存一个值时，JVM 会做一次**运行时**检查，确认它是允许的类型。
若不是，就抛出 ArrayStoreException。

Java 本可以通过禁止第一行那个转换，来省掉运行时的这项检查。它可以让数组变成**不变的**，
这样 Integer 数组就**不是** Object 数组。这在静态层面是健全的，但它禁止了一些常见又安全
的代码模式——那些只从数组里读取的代码。只要你不往数组里**写**，协变就是安全的。在 Java 1.0
还不支持泛型的年代，这类模式对可用性尤为重要。詹姆斯·高斯林和其他 Java 设计者牺牲了一点
静态安全性和性能——那些数组存储检查是要花时间的——换来了一些灵活性。

现代静态类型语言里，几乎没有哪个不在**某个地方**做这种取舍。就连 Haskell 也允许你运行
带有非穷尽匹配的代码。如果你正打算设计一门静态类型语言，请记住：把一部分类型检查推迟到
运行时，有时候能既给用户更多灵活性，又不至于牺牲**太多**静态安全带来的好处。

另一方面，用户选择静态类型语言的一个关键原因，是这门语言给了他们信心：某些类型的错误在
程序运行时**永远**不会发生。把太多类型检查推迟到运行时，这份信心就被你侵蚀掉了。
