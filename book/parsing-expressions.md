## 歧义与语法解析游戏

上一章我说过，你可以像玩游戏一样「玩」一套上下文无关文法，从而**生成**字符串。语法解析器
玩的是同一个游戏的反向版本：给定一个字符串——一串词法单元——我们把这些词法单元映射到文法里
的终结符上，以搞清哪些规则可能生成了这个字符串。

「可能」这两个字挺有意思。完全可以造出一套**有歧义**的文法，其中不同的产生式选择会导出同一个
字符串。用文法来**生成**字符串时，这不太要紧。字符串一旦到手，谁在乎你是怎么走到它的？

语法解析时，歧义意味着语法解析器可能误解用户的代码。语法解析的过程中，我们不光在判断这个
字符串是不是合法的 Lox 代码，还在追踪哪些规则匹配它的哪些部分，好知道每个词法单元属于这门
语言的哪一部分。这是我们上一章凑出来的 Lox 表达式文法：

```ebnf
expression     → literal
               | unary
               | binary
               | grouping ;

literal        → NUMBER | STRING | "true" | "false" | "nil" ;
grouping       → "(" expression ")" ;
unary          → ( "-" | "!" ) expression ;
binary         → expression operator expression ;
operator       → "==" | "!=" | "<" | "<=" | ">" | ">="
               | "+"  | "-"  | "*" | "/" ;
```

在这套文法里，下面这个字符串是合法的：

<img src="image/parsing-expressions/tokens.png" alt="6 / 3 - 1" />

但生成它有两条路。一种走法是：

1. 从 `expression` 出发，挑 `binary`。
2. 左边那个 `expression`，挑 `NUMBER`，用 `6`。
3. 运算符挑 `"/"`。
4. 右边那个 `expression`，再挑 `binary`。
5. 在这个嵌套的 `binary` 表达式里，挑 `3 - 1`。

另一种走法是：

1. 从 `expression` 出发，挑 `binary`。
2. 左边那个 `expression`，再挑 `binary`。
3. 在这个嵌套的 `binary` 表达式里，挑 `6 / 3`。
4. 回到外层 `binary`，运算符挑 `"-"`。
5. 右边那个 `expression`，挑 `NUMBER`，用 `1`。

这两种走法产生的**字符串**相同，但**语法树**不同：

<img src="image/parsing-expressions/syntax-trees.png" alt="两棵合法的语法树：(6 / 3) - 1 和 6 / (3 - 1)" />

换句话说，文法允许把这个表达式看成 `(6 / 3) - 1`，也允许看成 `6 / (3 - 1)`。`binary` 这条
规则让操作数爱怎么嵌套就怎么嵌套。而这又会影响对语法解析出来的树求值的结果。自从有了黑板，数学家们对付这种歧义的办法就是：为优先级和结合性定下规则。

*   <span name="nonassociative">**优先级**</span>决定在一个混着不同运算符的表达式里，先算哪个
    运算符。优先级规则告诉我们，在上面那个例子里 `/` 比 `-` 先算。优先级高的运算符先于优先级低的
    运算符求值。换句话说，优先级高的运算符「结合得更紧」。

*   **结合性**决定在一串**同样的**运算符里先算哪个。当一个运算符是**左结合**时（想想
    「从左到右」），左边的运算符比右边的先算。由于 `-` 是左结合的，这个表达式：

    ```lox
    5 - 3 - 1
    ```

    等价于：

    ```lox
    (5 - 3) - 1
    ```

    赋值运算则是**右结合**。这个：

    ```lox
    a = b = c
    ```

    等价于：

    ```lox
    a = (b = c)
    ```

<aside name="nonassociative">

如今已经不常见了，但有些语言会规定：某些运算符对之间**没有**相对优先级。在表达式里混用这些运算符
而不用显式括号，就是语法错误。

同样地，有些运算符是**非结合**的，意思是在一串里用同一个运算符超过一次就算错。比如 Perl 的
范围运算符就不是结合的，所以 `a .. b` 可以，`a .. b .. c` 报错。

</aside>

没有定义良好的优先级和结合性，一个用了好几个运算符的表达式就是有歧义的——它可以被语法解析成
不同的语法树，而这些树又可能求值出不同的结果。在 Lox 里，我们打算照搬 C 的优先级规则，从低到高。

眼下，文法把所有表达式类型都塞进了单独一条 `expression` 规则。同一条规则还被当作操作数的
非终结符来用，这让文法可以接受任何一种表达式当子表达式，不管优先级规则允不允许。

我们用<span name="massage">分层</span>文法来修这个问题。为每个优先级层各定义一条规则。

```ebnf
expression     → ...
equality       → ...
comparison     → ...
term           → ...
factor         → ...
unary          → ...
primary        → ...
```

<aside name="massage">

有些语法解析器生成器不把优先级直接烘进文法规则，而是让你保留同一套「有歧义但简单」的文法，
然后在旁边补一点显式的运算符优先级元数据，用来消歧。

</aside>

这里每条规则只匹配自己这一优先级层或更高的表达式。比如 `unary` 既匹配 `!negated` 这样的一元
表达式，也匹配 `1234` 这样的基本表达式。而 `term` 既能匹配 `1 + 2`，也能匹配 `3 * 4 / 5`。最后
那条 `primary` 规则覆盖优先级最高的形式——字面量和带括号的表达式。

我们只需要把每条规则的产生式填进去。先做容易的。最上面那条 `expression` 规则匹配任何优先级层
上的任何表达式。既然 <span name="equality">`equality`</span> 的优先级最低，匹配上它，就等于
覆盖了一切。

<aside name="equality">

我们完全可以把 `expression` 消掉，在其他含表达式的规则里直接用 `equality`，不过用 `expression`
会让那些规则读起来舒服一点。

另外，后面章节我们把文法扩展到包含赋值和逻辑运算符时，只需要改 `expression` 这一条的产生式，
不用去动每一条含表达式的规则。

</aside>

```ebnf
expression     → equality
```

再看看优先级表的另一头，一条基本表达式包含全部的字面量和分组表达式。

```ebnf
primary        → NUMBER | STRING | "true" | "false" | "nil"
               | "(" expression ")" ;
```

一条一元表达式以一个一元运算符开头，后跟操作数。由于一元运算符可以嵌套——`!!true` 是个合法
但古怪的表达式——操作数本身可以是一元运算符。一条递归规则正好能把这件事办得漂漂亮亮。

```ebnf
unary          → ( "!" | "-" ) unary ;
```

但这条规则有个问题。它永远不会终止。

别忘了，每条规则都需要匹配该优先级层**或更高**的表达式，所以我们还得让它能匹配一条基本表达式。

```ebnf
unary          → ( "!" | "-" ) unary
               | primary ;
```

这样就对了。

剩下的规则全是二元运算符。我们从乘除法那条开始。先来个第一版：

```ebnf
factor         → factor ( "/" | "*" ) unary
               | unary ;
```

这条规则靠递归来匹配左操作数，于是它能匹配 `1 * 2 / 3` 这样一串乘除表达式。把递归的产生式放在
左边、把 `unary` 放在右边，这让这条规则是<span name="mult">左结合</span>的，而且没有歧义。

<aside name="mult">

原则上，你把乘法当成左结合还是右结合都无所谓——反正结果一样。可在真实世界里、在精度有限
的情况下，舍入误差和溢出会让结合性影响一串乘法的结果。想想：

```lox
print 0.1 * (0.2 * 0.3);
print (0.1 * 0.2) * 0.3;
```

在 Lox 这种用 [IEEE 754][754] 双精度浮点数的语言里，第一行算出 `0.006`，第二行得到的却是
`0.006000000000000001`。有时候这点微小的差别是要紧的。[戈尔伯格那篇浮点数经典][float]是个学习的好去处。

[754]: https://en.wikipedia.org/wiki/Double-precision_floating-point_format
[float]: https://docs.oracle.com/cd/E19957-01/806-3568/ncg_goldberg.html

</aside>

这一切都是对的，但规则体里的第一个符号跟规则的头是同一个符号，这意味着这条产生式是**左递归**的。
有些语法解析技术——包括我们即将使用的那种——对付左递归很吃力。（别处的递归倒没问题，比如
`unary` 里的，以及 `primary` 里分组那条的间接递归。）

你可以定义出很多套匹配同一门语言的文法。怎么为某门语言建模，一半是品味问题，一半是务实问题。
这条规则是正确的，但对我们打算采用的那种语法解析方式来说并不理想。我们换用另一条非左递归的规则。

```ebnf
factor         → unary ( ( "/" | "*" ) unary )* ;
```

我们把因子表达式定义成乘法和除法的扁平**序列**。这跟上一条规则匹配的语法完全一样，但更好地
映射了我们将要写的 Lox 语法解析代码。其他所有二元运算符的优先级层都用同样的结构，于是我们得到
这份完整的表达式文法：

```ebnf
expression     → equality ;
equality       → comparison ( ( "!=" | "==" ) comparison )* ;
comparison     → term ( ( ">" | ">=" | "<" | "<=" ) term )* ;
term           → factor ( ( "-" | "+" ) factor )* ;
factor         → unary ( ( "/" | "*" ) unary )* ;
unary          → ( "!" | "-" ) unary
               | primary ;
primary        → NUMBER | STRING | "true" | "false" | "nil"
               | "(" expression ")" ;
```

这份文法比我们之前那份复杂，但作为回报，我们消掉了旧文法里的歧义。做个语法解析器，需要的正好
就是它。

## 递归下降语法解析

有一整窝语法解析技术，名字大多是「L」和「R」的排列组合——[LL(k)][llk]、[LR(1)][lr]、
[LALR][lalr]——再加上一些更冷门的家伙，比如[解析器组合子][parser combinators]、
[Earley 解析器][earley parsers]、[调度场算法][yard]，还有
[记忆化解析（packrat parsing）][packrat]。对我们的第一个解释器来说，
一种技术就绰绰有余：**递归下降**。

[llk]: https://en.wikipedia.org/wiki/LL_parser
[lr]: https://en.wikipedia.org/wiki/LR_parser
[lalr]: https://en.wikipedia.org/wiki/LALR_parser
[parser combinators]: https://en.wikipedia.org/wiki/Parser_combinator
[earley parsers]: https://en.wikipedia.org/wiki/Earley_parser
[yard]: https://en.wikipedia.org/wiki/Shunting-yard_algorithm
[packrat]: https://en.wikipedia.org/wiki/Parsing_expression_grammar

递归下降是搭一个语法解析器最简单的办法，而且不需要 Yacc、Bison、ANTLR 这类复杂的语法解析器
生成器工具。你要做的只是老老实实手写代码。不过别被它的简单骗了。递归下降语法解析器快、稳，
而且能支持精巧的错误处理。事实上，GCC、V8（Chrome 里的 JavaScript 虚拟机）、Roslyn（用 C#
写的 C# 编译器）以及许多其他重量级的生产级语言实现都在用递归下降。它贼好用。

递归下降被认为是一种**自顶向下语法解析器**，因为它从文法里最外层的那条规则（这里是
`expression`）出发，一路<span name="descent">下降</span>进那些嵌套的子表达式，最后才抵达语法
树的叶子。这跟 LR 那类自底向上的语法解析器正相反，后者从基本表达式开始，把它们拼成越来越大的
语法块。

<aside name="descent">

它之所以叫「递归**下降**」，是因为它沿着文法往下**走**。绕人的是，我们谈「高」优先级和
「低」优先级时也用方向做比喻，但方向正好是反的。在一个自顶向下的语法解析器里，你最先碰到的是
优先级最低的表达式，因为它们里面可能又装着优先级更高的子表达式。

<img src="image/parsing-expressions/direction.png" alt="自顶向下的文法规则，按优先级递增排列。" />

计算机圈的人真该聚到一块儿把各自的比喻理一理。至于栈往哪个方向长、树为什么把根搁在
上头，我一开始说就没完。

</aside>

递归下降语法解析器就是文法的规则向命令式代码的一次直译。每条规则变成一个函数。规则体的内容
大致翻译成这样：

<table>
<thead>
<tr>
  <td>文法记号</td>
  <td>代码表示</td>
</tr>
</thead>
<tbody>
  <tr><td>终结符</td><td>匹配并消费一个词法单元的代码</td></tr>
  <tr><td>非终结符</td><td>调用那条规则的函数</td></tr>
  <tr><td><code>|</code></td><td><code>if</code> 或 <code>switch</code> 语句</td></tr>
  <tr><td><code>*</code> 或 <code>+</code></td><td><code>while</code> 或 <code>for</code> 循环</td></tr>
  <tr><td><code>?</code></td><td><code>if</code> 语句</td></tr>
</tbody>
</table>

之所以说是「递归」的，是因为当一条文法规则（直接或间接）指向自己时，这就翻译成了一次递归调用。

### 语法解析器类

每条文法规则都变成这个新类里的一个方法：

^code parser

跟扫描器一样，语法解析器吃进一个扁平的输入序列，只不过现在读的是词法单元而不是字符。我们把
词法单元列表存起来，用 `current` 指向下一个正在迫不及待等着被语法解析的词法单元。

现在我们直接顺着表达式文法走一遍，把每条规则翻译成 Java 代码。第一条规则 `expression` 只是
展开成 `equality`，所以很简单。

^code expression

每个用来语法解析一条文法规则的方法，都会为那条规则产出一棵语法树并返回给调用者。当规则体里
出现一个非终结符——也就是对另一条规则的引用——我们就<span name="left">调用</span>那条规则的
方法。

<aside name="left">

这就是左递归对递归下降来说麻烦的原因。一条左递归规则的函数会立刻调用自己，自己又调用自己，
如此下去，直到语法解析器撞上栈溢出死掉。

</aside>

相等那条规则稍微复杂一点。

```ebnf
equality       → comparison ( ( "!=" | "==" ) comparison )* ;
```

翻译成 Java：

^code equality

我们一步步看。规则体里的第一个 `comparison` 非终结符，翻译成方法里的第一次 `comparison()` 调用。
我们把结果存进一个局部变量。

然后，规则里的 `( ... )*` 循环对应一个 `while` 循环。我们得知道什么时候退出这个循环。从规则本身
能看出来：我们必须先找到一个 `!=` 或者 `==` 词法单元。所以，要是**没**看到这两个里的任何一个，
说明这串相等运算符已经到头了。这个检查我们用一个顺手的 `match()` 方法来表达。

^code match

它检查当前词法单元是不是给定的那几个类型之一。如果是，就消费掉这个词法单元并返回 `true`；
否则返回 `false`，当前词法单元原封不动。`match()` 方法是由两个更基础的操作定义出来的。

`check()` 方法在当前词法单元是给定类型时返回 `true`。跟 `match()` 不同，它从不消费词法单元，
只是看一眼。

^code check

`advance()` 方法消费当前词法单元并返回它，跟扫描器里那个爬字符的方法差不多。

^code advance

这些方法最终都落在最后那几个原始操作上。

^code utils

`isAtEnd()` 检查我们的词法单元是不是已经用光了。`peek()` 返回当前那个还没被消费的
词法单元，`previous()` 返回最近刚被消费掉的那个。有了后者，先用 `match()` 再去访问刚刚匹配上
的词法单元就方便多了。

我们需要的大部分语法解析基础设施到此为止。刚才说到哪儿了？对了，如果我们正待在 `equality()`
里的那个 `while` 循环中，那就说明我们找到了一个 `!=` 或 `==` 运算符，而且正在语法解析一条相等
表达式。

我们把匹配到的运算符词法单元抓过来，好知道我们遇到的是哪一种相等表达式。然后再调一次
`comparison()` 来语法解析右操作数。我们把运算符和它的两个操作数组装成一个新的 `Expr.Binary`
语法树节点，然后接着转下一圈。每一轮循环，我们把得到的表达式重新存回同一个 `expr` 局部变量。
这样一路穿过一串相等表达式，就造出了一棵左结合的二元运算符节点嵌套树。

<span name="sequence"></span>

<img src="image/parsing-expressions/sequence.png" alt="语法解析 'a == b == c == d == e' 造出的语法树" />

<aside name="sequence">

语法解析 `a == b == c == d == e`。每一轮循环，我们都以上一个表达式为左操作数，造出一个新的
二元表达式。

</aside>

一旦撞上一个不是相等运算符的词法单元，语法解析器就掉出循环。最后返回那个表达式。注意，如果
语法解析器从来没遇到相等运算符，它就压根儿不会进循环。这种情况下，`equality()` 方法实际上
是调用 `comparison()` 并把结果返回。这样一来，这个方法匹配的既是一个相等运算符，**也**是任何
优先级更高的东西。

接着看下一条规则……

```ebnf

```

匹配的运算符类型，以及我们为操作数调用的方法——现在是 `term()` 而不是 `comparison()`。剩下那两条
二元运算符规则也是同一个套路。

按优先级来，先是加法和减法：

^code factor

到这儿，所有二元运算符都语法解析完了，优先级和结合性也都正确。我们正沿着优先级这座梯子往上爬，
现在爬到了一元运算符。

```ebnf
unary          → ( "!" | "-" ) unary
               | primary ;
```

这段代码稍微有点不一样。

^code unary

我们照例看<span name="current">当前</span>词法单元来决定怎么语法解析。如果它是 `!` 或 `-`，那准是
一个一元表达式。这种情况下，我们把词法单元抓过来，然后递归再调一次 `unary()` 来语法解析
操作数。把这些包成一个一元表达式语法树，就完事了。

<aside name="current">

语法解析器会前瞻后面即将到来的词法单元来决定怎么解析——就凭这一点，递归下降被归进了
**预测性语法解析器**这一类。

</aside>

否则，我们就一定是抵达了最高优先级那一层，也就是基本表达式。

```ebnf
primary        → NUMBER | STRING | "true" | "false" | "nil"
               | "(" expression ")" ;
```

这条规则的大部分情况都是单个终结符，所以语法解析很直白。

^code primary

有意思的是处理括号的那个分支。在匹配掉一个开头的 `(` 并语法解析完里面的表达式之后，我们**必须**
找到一个 `)` 词法单元。要是找不到，那就是个错误。

## 语法错误

一个语法解析器真有两份活：

1.  给定一串合法的词法单元，造出对应的语法树。

2.  给定一串**非法**的词法单元，找出所有错误并告诉用户他错在哪儿。

别低估第二份活有多重要！在现代 IDE 和编辑器里，语法解析器一直在反复语法解析代码——往往用户
还在编辑的时候就已经在解析了——好做语法高亮、支撑自动补全之类的东西。这意味着它**时时处处**
都会碰到残缺不全、半对半错的代码。

用户自己没意识到语法错了的时候，就得靠语法解析器把他领回正道。它报告错误的方式，是一门语言
用户界面的重要组成部分。好的语法错误处理很难。按定义，此时的代码并不处于一个良定义的状态，
所以没有任何万无一失的办法能知道用户**本来想**写什么。语法解析器读不了你的<span
name="telepathy">心</span>。

<aside name="telepathy">

至少现在还不行。看看如今机器学习这个领域的发展势头，谁知道将来会怎么样呢？

</aside>

语法解析器撞上语法错误时，有几条硬性要求。一个语法解析器必须：

*   **发现并报告错误。** 要是不把错误<span name="error">发现</span>出来，把那棵畸形语法树
    递给解释器，各种恐怖都会被招来。

    <aside name="error">

    从哲学上说，如果一个错误没被发现、而解释器还把代码跑了下去，那它**算**错误吗？

    </aside>

*   **不崩溃、不挂起。** 语法错误是生活的一部分，语言工具必须能扛住。段错误或者卡在死循环里
    都不行。源码可能不是合法的**代码**，但它仍然是**语法解析器的合法输入**，因为用户要靠语法
    解析器来知道什么语法是被允许的。

想在这场语法解析游戏里坐下来，这些是入场费；但你真正想把门槛抬上去的话，还应该做到：

*   **快。** 现在的计算机比语法解析技术刚发明出来时快了成千上万倍。「优化语法解析器，好让它
    在喝完一杯咖啡的工夫里啃完整个源文件」的日子已经过去。但程序员的期待涨得一样快，甚至更快。
    他们指望编辑器每敲一个键就在几毫秒内重新语法解析一遍文件。

*   **有多少个不同的错误就报多少个。** 碰到第一个错误就放弃，实现起来很容易；但要是用户每次
    修完他以为的那个唯一错误，又冒出一个新的，那就很烦人。他们想一次全看到。

*   **把连锁错误压到最少。** 一旦发现第一个错误，语法解析器其实就不太清楚状况了。它试着让
    自己回到正轨并继续往下走，但如果搞晕了，就可能报出一大堆幻影错误，而它们并不代表代码里还有
    别的真实问题。第一个错误修好之后，那些幻影就消失了，因为它们只是语法解析器自己糊涂的产物。
    连锁错误之所以烦人，是因为它们会把用户吓得以为自己代码的状况比实际糟得多。

最后两条彼此拉扯。我们想尽可能多地报告互相独立的错误，但也不想报告那些仅仅是前面某个错误的
副作用的错误。

语法解析器响应一个错误、然后继续往下找后续错误，这套做法叫做**错误恢复**。这在上世纪六十年代
是个热门研究课题。那时候，你把一摞穿孔卡片交给秘书，第二天再回来看编译器有没有成功。以那种
慢得要命的迭代循环，你**真的**会想一次就把代码里每个错误都找出来。

如今语法解析器在你还没打完字的时候就跑完了，这事就没那么要紧了。简单、快速的错误恢复就够了。

### Panic 模式错误恢复

<aside name="panic">

你知道你想按它。

<img src="image/parsing-expressions/panic.png" alt="一个又大又亮的「PANIC」按钮。" />

</aside>

当年人们设计出来的各种恢复技术里，最经得起时间考验的那一种，名字有点吓人——<span
name="panic">**panic 模式**</span>。语法解析器一发现错误，立刻进入 panic 模式。它知道，眼下它正卡在一串文法产生式中间，而手上至少有一个词法单元在这儿
讲不通。

在它能回到语法解析之前，得先让自己的状态和即将到来的词法单元序列对齐，好让下一个词法单元确实
匹配上正在语法解析的那条规则。这个过程叫做**同步**。

要同步，我们就从文法里挑一条规则来标记同步点。语法解析器先把自己从任何嵌套的产生式里一路跳
出来，直到回到那条规则，以此来修正自己的语法解析状态。接着同步词法单元流：不断丢弃词法单元，
直到碰上一个能在规则的这个位置出现的词法单元。

那些被丢弃的词法单元里如果还藏着别的真实语法错误，就不会报告了；但反过来，这也意味着那些只是
最初那个错误的副作用的、错误得不得了的连锁错误，不会被**误**报出来。这是个相当划算的取舍。

文法里传统的同步位置是在语句之间。我们还没有语句，所以这一章实际上不会真的同步，但我们先把
这套机制搭好，留着以后用。

### 进入 panic 模式

在我们绕道错误恢复之前，我们正在写语法解析带括号表达式的代码。语法解析完表达式之后，语法解析器
通过调用 `consume()` 去找那个收尾的 `)`。现在，这个方法终于出场了：

^code consume

它跟 `match()` 类似：都要检查下一个词法单元是不是期望的类型。如果是，就消费掉，一切顺遂。要是
那儿蹲着别的词法单元，那就是出错了。我们这样报告：

^code error

首先，它这样把错误显示给用户：

^code token-error

这会在给定的词法单元处报一个错误。它显示词法单元的位置和词法单元本身。这在后面会派上大用场，
因为我们在整个解释器里到处用词法单元来追踪代码中的位置。

报告完错误，用户知道自个儿错在哪儿了，可**语法解析器**接下来做什么呢？回到 `error()`，我们
创建并返回一个 ParseError，这个新类的一个实例：

^code parse-error (1 before, 1 after)

这是个简单的哨兵类，我们用它来让语法解析器一路退出。`error()` 方法**返回**这个错误而不是
**抛出**它，是因为我们想把「要不要退出」的决定权留给语法解析器内部调用它的那个方法。有些语法
错误出现在语法解析器不太可能陷进怪状态的地方，那些地方我们不需要去<span name="production">同步</span>。
在那儿，我们只要报个错，然后继续一路开下去。

比如，Lox 限制你能传给函数的参数个数。传太多了，语法解析器需要报这个错，但它完全可以、也应该
继续语法解析剩下的参数，而不是急得跳起来进入 panic 模式。

<aside name="production">

处理常见语法错误的另一个办法是**错误产生式**。你给文法加一条规则，让它能**成功**匹配那段**错误
的**语法。语法解析器把它安安全全地语法解析掉，然后报成错误，而不是产出一棵语法树。

比如有些语言有一元 `+` 运算符，像 `+123`，但 Lox 没有。这样一来，当语法解析器在表达式开头撞上
一个 `+` 时就不会懵圈，我们可以把一元那条规则扩展一下，允许它。

```ebnf
unary → ( "!" | "-" | "+" ) unary
      | primary ;
```

这让语法解析器可以吃掉 `+`，既不用进入 panic 模式，也不会把语法解析器留在一个怪状态里。

错误产生式之所以好用，是因为你——语法解析器的作者——知道代码**是怎么**错的，也知道用户多半想
干什么。这让你能给出更有帮助的提示，把用户领回正轨，比如「不支持一元 `+` 表达式」。成熟的语法
解析器往往像长藤壶一样，不断攒起错误产生式，因为它们能帮用户修掉最常见的毛病。

</aside>

不过在我们这个例子里，这个语法错误难缠到让我们想直接 panic 并同步。丢弃词法单元还算容易，可
语法解析器自己的状态该怎么同步？

### 同步一个递归下降语法解析器

在递归下降里，语法解析器的状态——它正处在哪条规则的识别中间——并没有显式地存在字段里。相反，
我们用 Java 自己的调用栈来追踪语法解析器在干什么。每一条正在语法解析到一半的规则，都是栈上的
一个调用帧。为了重置这个状态，我们需要把这些调用帧清掉。

在 Java 里，做这件事最自然的办法就是异常。想同步的时候，我们就把那个 ParseError 对象**抛**出去。
在我们正同步过去的那条文法规则的更上层，我们接住它。因为我们是在语句边界上同步的，所以会
在那里捕获这个异常。异常一被接住，语法解析器就处在正确的状态上了。剩下的就是同步词法单元。

我们想丢弃词法单元，直到正好站在下一条语句的开头。这个边界挺好认的——这正是我们当初选它的
主要原因之一。在分号**之后**，我们<span name="semicolon">大概</span>已经结束了一条语句。
大多数语句都拿关键字开头——`for`、`if`、`return`、`var` 等等。当**下一个**词法单元是其中之一
时，我们大概正要开始一条新语句。

<aside name="semicolon">

我说「大概」，是因为我们可能碰上 `for` 循环里分隔各个子句的分号。我们的同步并不完美，但没关系。
第一个错误我们已经报得又准又细，所以后面的一切都算是「尽力而为」。

</aside>

这个方法把那套逻辑包了起来：

^code synchronize

它不断丢弃词法单元，直到自己认为找到了一个语句边界。接住 ParseError 之后，我们会调这个方法，
然后我们就算是重新同步了。它要是干得漂亮，丢掉的那些词法单元反正也多半会引起连锁错误，而现在
我们可以从下一条语句开始，把文件剩下的部分语法解析下去。

可惜我们看不到这个方法实际跑起来，因为我们还没有语句。那我们在[几章之后][statements]再说。
眼下，一旦出错，我们就 panic，一路退出到顶，停止语法解析。反正我们眼下也只能语法解析单个表达式，
这损失不算大。

[statements]: statements-and-state.html

## 把语法解析器接起来

表达式这块儿我们大体上弄完了。还有另一个地方需要加一点错误处理。语法解析器顺着每条文法规则的
语法解析方法一层层下降，最终会撞上 `primary()`。如果那里面一个分支都没匹配上，就说明我们正
蹲在一个没法开头的词法单元上。这个错误也得处理。

^code primary-error (5 before, 1 after)

这样一来，语法解析器里剩下的就只是定义一个启动它的入口方法。那个方法顺理成章地叫 `parse()`。

^code parse

等我们给语言加上语句时，会回头再看这个方法。眼下它语法解析单个表达式并返回。我们还留了一些
临时代码用来退出 panic 模式。语法错误恢复是语法解析器的活儿，我们不想让 ParseError 异常漏到
解释器的其他地方去。

一旦真的发生语法错误，这个方法返回 `null`。这没关系。语法解析器保证的是：遇到非法语法不崩溃、
不挂起；它可不保证一旦发现错误就一定返回一棵**能用的语法树**。语法解析器一报出错误，
`hadError` 就被设上了，后面的阶段全被跳过。

最后，我们可以把崭新的语法解析器接到 Lox 主类上，试试看。我们还没有解释器，所以眼下先语法解析

## 设计说明：逻辑 vs 历史

假设我们决定给 Lox 加上按位运算符 `&` 和 `|`。该把它们放在优先级体系的哪个位置？C——以及大多数
跟着 C 走的语言——把它们放在 `==` 下面。这被广泛认为是个错误，因为它意味着像测试一个标志位
这样的常见操作都得加括号。

```c
if (flags & FLAG_MASK == SOME_FLAG) { ... } // 错了。
if ((flags & FLAG_MASK) == SOME_FLAG) { ... } // 对了。
```

我们该不该为 Lox 把这事修掉，把按位运算符放在优先级表上比 C 更高的位置？有两种策略可选。

你几乎从来不会想把一个 `==` 表达式的结果拿去做按位运算符的操作数。让按位运算符结合得更紧，
用户就不必那么频繁地加括号。所以如果我们这么做，而用户又理所当然地以为这个优先级是按
「尽量少加括号」的逻辑挑的，那他们多半能推断对。

这种内部自洽会让语言更好学：边缘情况和例外更少了，用户要记住的东西、
要踩了坑才纠正得过来的东西也一并更少。这是好事，因为在用户能用上我们的语言之前，他们得先把那套语法和语义全装进脑子里。一门更简单、更合乎
理性的语言**讲得通**。

但对很多用户来说，有一条更快的捷径，能让我们语言里的那些想法进他们的脑子里——**用他们已经
懂的概念**。我们语言的新手大多是从别的某几门语言过来的。如果我们这门语言在语法或语义上跟
那些语言有重合，用户要学的东西（和要**忘掉**的东西）就少多了。

这一条对语法尤其管用。你今天可能已经记不太清了，但在很久以前你刚学会第一门编程语言的时候，
代码大概看着陌生又难以接近。你是靠苦功才学会读它、接受它的。如果我们为新语言设计一套全新
语法，就等于逼着用户把那个过程从头再来一遍。

利用用户已经掌握的东西，是让一门语言被接受的最有力的工具之一。你几乎不可能高估它的价值。
但它也给你摆出一个棘手的问题：当用户全都懂的那个东西**挺烂**的时候，怎么办？C 的按位运算符
优先级是个讲不通的错误。但它是个用户**熟悉**的错误，几百万人早就习惯了、学会了跟它一起生活。

你到底是忠于自己语言内在的逻辑、无视历史？还是从一张白纸和第一性原理开始？又或者，你把自己
的语言织进编程历史的锦绣华年，让用户从他们已经熟悉的东西起步？

这里没有完美的答案，只有取舍。你我显然都偏爱新语言，所以我们自然的倾向是烧掉历史书，另起炉灶
写自己的故事。

实践中，往往还是把用户已经懂的东西用到极致更好。要把他们拉进你的语言，需要一个大跳。能把
那道鸿沟缩小多少，就有多少人愿意跨过来。可你又不能**总是**抱着历史不放，不然你的语言就拿不出
任何新鲜而有吸引力的东西，给人们一个跳过来的**理由**。
