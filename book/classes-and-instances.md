clox 里最后一块尚未实现的地盘就是面向对象编程。<span name="oop">面向对象编程</span>是一

<aside name="oop">

## 类的实例

类在一门语言里有两个主要用途：

*   **它们是你创建新实例的方式。** 有时这需要一个 `new` 关键字，有时是对类对象的一次方法
    调用，但不管怎样你通常都要**设法**按名字提到那个类，才能拿到一个新实例。

*   **它们容纳方法。** 方法定义了这类对象的所有实例如何表现。

方法要等到下一章，所以现在我们只操心第一部分。类要能创建实例，我们首先需要实例的表示。

^code obj-instance (1 before, 2 after)

实例知道自己的类——每个实例都有一个指针，指向它所属的那个类。本章我们不太用得上它，
但加上方法之后它会变得至关重要。

对这一章来说更重要的是实例怎么存自己的状态。Lox 允许用户在运行时自由地往实例上加
字段。这意味着我们需要一种可以增长的存储机制。我们可以用动态数组，但我们还想
尽快按名字查找字段。有一种数据结构正好完美契合「快速按名字访问一组值」——而且更方便的是，
我们已经把它实现过了。每个实例用一张哈希表存自己的字段。

<aside name="fields">

能在运行时自由地给对象加字段，这是大多数动态语言与静态语言之间一个很大的实际差异。
静态类型语言通常要求字段显式声明。这样编译器确切知道每个实例有哪些字段，可以据此确定
每个实例需要多少内存，以及每个字段在这块内存中的偏移量。

在 Lox 和其他动态语言里，访问一个字段通常是一次哈希表查找。是常数时间，但开销仍然不小。在 C++ 这样的语言里，访问字段跟用一个整数常量去偏移指针一样快。

</aside>

我们只需要加一个 include，就搞定了。

^code object-include-table (1 before, 1 after)

这个新结构体要配一个新的对象类型。

^code obj-type-instance (1 before, 1 after)

这里我想放慢一点，因为 Lox 这个**语言**对「类型」的理解，和 VM 这个**实现**对「类型」的
理解，会以令人困惑的方式彼此错位。在构成 clox 的 C 代码里，有若干种不同的 Obj——ObjString、
ObjClosure 等等。每一种都有自己的内部表示和语义。

在 Lox 这个**语言**里，用户可以定义自己的类——比如 Cake 和 Pie——然后创建这些类的实例。
从用户的视角看，Cake 的实例和 Pie 的实例是不同类型的对象。但在 VM 的视角里，用户定义的
每一个类都只是另一个 ObjClass 类型的值。同样地，用户程序里的每个实例，不管它是哪个类的
实例，都是一个 ObjInstance。这一个 VM 对象类型就覆盖了所有类的实例。这两个世界之间大致

## Get 与 Set 表达式

我们针对实例的对象表示已经能存状态了，所以剩下的就是把这份功能暴露给用户。字段用 get
表达式和 set 表达式来访问和修改。Lox 也不甘落后，采用了经典的「点号」语法：

```lox
eclair.filling = "pastry creme";
print eclair.filling;
```

那个句点——献给我的英语朋友们，它叫 full stop——作用<span name="sort">有点像</span>一个中缀运算符。左边有一个
先求值、产生一个实例的表达式。之后是 `.`，再跟一个字段名。既然有一个前置操作数，我们把
它作为中缀表达式挂进解析表。

<aside name="sort">

我说「有点像」，是因为 `.` 右边不是表达式，而是一个单独的标识符，它的语义由 get 或 set
表达式本身处理。它其实更接近后缀表达式。

</aside>

^code table-dot (1 before, 1 after)

和其他语言一样，`.` 运算符绑定得很紧，优先级和函数调用里的圆括号一样高。解析器吃掉点号
词法单元之后，会分派到一个新的解析函数。

^code compile-dot

解析器预期在点号后面紧接着找到一个<span name="prop">属性</span>名。我们把那个词法单元的词素
作为字符串加载进常量表，好让名字在运行时可用。

<aside name="prop">

编译器这里用「属性」而不是「字段」，别忘了，Lox 还允许你用点号语法访问一个方法而不调用
它。「属性」是我们用来指代实例上任何可访问的具名实体的总称。字段是由实例状态支撑的那
一部分属性。

</aside>

我们有两条新的表达式形式——getter 和 setter——都由这一个函数处理。如果我们在字段名后面
看到一个等号，那必然是一条给字段赋值的 set 表达式。但我们并不**总是**允许编译字段后面
的等号。考虑：

```lox
a + b.c = 3
```

按 Lox 的文法，这在语法上是非法的，也就是说我们的 Lox 实现有责任检测并报告这个错误。
如果 `dot()` 默默地把 `= 3` 那部分也解析了，我们就会错误地把这段代码理解成用户写了：

```lox
a + (b.c = 3)
```

问题在于，set 表达式里 `=` 那侧的优先级比 `.` 那部分低得多。解析器可能在优先级太高、
不允许出现 setter 的语境里调用 `dot()`。为了避免错误地放行这种情况，我们只在
`canAssign` 为真时才解析并编译等号那部分。如果 `canAssign` 为假时出现了等号词法单元，
`dot()` 会原样留下它然后返回。那种情况下，编译器最终会退回到 `parsePrecedence()`，
它停在这个意料之外的 `=` 上（它仍是下一个词法单元）并报告错误。

如果我们在**确实**允许等号的语境里找到了一个 `=`，我们就编译它后面那个表达式。之后我们
发射一条新的 <span name="set">`OP_SET_PROPERTY`</span> 指令。它带一个操作数，表示属性名
在常量表里的索引。如果我们没有编译出 set 表达式，就假定它是 getter，发射一条
`OP_GET_PROPERTY` 指令，它同样带一个属性名的操作数。

<aside name="set">

你不能**设置**一个非字段的属性，所以我想那条指令本来也可以叫 `OP_SET_FIELD`，但我觉得
跟 get 指令保持一致看起来更顺眼。

</aside>

### 解释 getter 与 setter 表达式

滑到运行时，我们先从 get 表达式开始，因为它稍微简单一点。

^code interpret-get-property (1 before, 1 after)

当解释器执行到这条指令时，点号左边的表达式已经求过值，结果实例在栈顶。我们从常量池里
读出字段名，在实例的字段表里查它。如果哈希表里有那个名字的条目，我们把实例弹出来，
把条目的值作为结果压栈。

当然，字段可能并不存在。在 Lox 里我们把这定义为运行时错误。所以我们加一个检查，
一旦发生就中止。

^code get-undefined (3 before, 2 after)

<span name="field">还有</span>另一个你大概已经注意到的失败模式要处理。上面那段代码假定
点号左边的表达式确实求值成了 ObjInstance。但没有东西能阻止用户这样写：

```lox
var obj = "not an instance";
print obj.field;
```

用户的程序是错的，但 VM 仍然得有几分体面地处理它。现在它会把 ObjString 的那些位误当成
ObjInstance，然后——我也不知道——着火什么的，反正绝对不体面。

在 Lox 里，只有实例被允许拥有字段。你没法往字符串或数字上塞字段。所以我们在访问任何
字段之前，得先检查这个值是不是实例。

<aside name="field">

Lox **可以**支持给其他类型的值加字段。这是我们的语言，我们想怎样就怎样。但这很可能是个
坏主意。它会以损害性能的方式大大复杂化实现——比如说，字符串驻留会变得难得多。

另外，它还会引出关于值的相等性与同一性的棘手语义问题。如果我给数字 `3` 挂上一个字段，
那 `1 + 2` 的结果也有那个字段吗？如果有，实现要怎么追踪这一点？如果没有，那两个算出来的
「三」还算是相等的吗？

</aside>

^code get-not-instance (1 before, 1 after)

如果栈上的值不是实例，我们报告运行时错误并安全退出。

当然，在实例都没有任何字段的时候，get 表达式也不怎么有用。为此我们需要 setter。

^code interpret-set-property (2 before, 1 after)

这比 `OP_GET_PROPERTY` 稍微复杂一点。这条指令执行时，栈顶是那个要被设置字段的实例，
它上面是要被存进去的值。和之前一样，我们读出指令的操作数，找到字段名字符串。用它把栈顶
的值存进实例的字段表。

之后是一些<span name="stack">栈</span>上的腾挪。我们先把存好的值弹出来，再弹出实例，
最后把值压回去。换句话说，我们把栈上的**第二个**元素移除，而把栈顶留着不动。setter 本身
是一个表达式，它的结果就是被赋的值，所以我们需要把那个值留在栈上。我说的就是这个意思：


和读取字段不同，我们不用担心哈希表里没有那个字段。setter 会在需要时隐式创建字段。我们
确实要处理的是用户错误地想往一个不是实例的值上存字段。

^code set-not-instance (1 before, 1 after)

和 get 表达式完全一样，我们检查值的类型，无效就报运行时错误。至此，Lox 对面向对象编程
的支持中，有状态的那一面就到位了。试试看：

```lox

print pair.first + pair.second; // 3.
```

这其实不太让人觉得**面向对象**。它更像是 C 的一个古怪的动态类型变体，对象只是些松散的、
类似结构体的数据包。算是某种动态的过程式语言。但这在表达力上是一大步。我们的 Lox 实现
现在让用户可以自由地把数据聚合成更大的单元。下一章我们会给这些惰性团块注入生命。

## 习题
1.  访问对象上不存在的字段会立刻中止整个 VM。用户没法从这个运行时错误里恢复，也没有
    任何办法在尝试访问**之前**知道字段是否存在。用户只能自己保证只读有效字段。

    其他动态类型语言怎么处理缺失的字段？你觉得 Lox 应该怎么做？实现你的方案。

1.  字段在运行时按**字符串**名字访问。但那个名字必须始终以**标识符词法单元**的形式直接出现在
    源代码里。用户程序不能命令式地构造一个字符串值、再把它当作字段名。你觉得他们应该
    能做到吗？设计一个支持这件事的语言特性并实现它。

1.  反过来，Lox 没有任何办法从实例上**移除**字段。你可以把字段的值设成 `nil`，但哈希表里
    的条目还在那儿。其他语言怎么处理这个问题？为 Lox 选择并实现一种策略。

1.  因为字段在运行时按名字访问，操作实例状态很慢。技术上这是常数时间操作——多亏了哈希表
    ——但常数因子相当大。这是动态语言比静态类型语言慢的一个主要原因。

    动态类型语言的精巧实现是怎么应对并优化这一点的？
