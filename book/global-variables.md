[上一章][hash]是对一个宏大、深奥、基础的计算机科学数据结构的一次漫长探索。理论和概念很重，可能还聊了点大 O 记号和算法。这一章没那么多智识上的架子。没有宏大的思想要学。它只是一堆直截了当的工程活。等我们把它们做完，我们的虚拟机就能支持变量了。

其实，它只支持**全局**变量。局部变量要到[下一章][next chapter]才来。在 jlox 里，我们好歹把它们俩都塞进了一章，因为所有变量我们都用同一种实现技术。我们搭了一条环境链，每个作用域一个，一路通到顶上。那是学习如何管理状态的一种简单、干净的途径。

[next chapter]: local-variables.html

但它也**慢**。每次进入一个块或调用一个函数都分配一张新的哈希表，可不是通向快虚拟机的路。考虑到有那么多代码都跟使用变量有关，变量要是慢，一切就都慢。对 clox，我们会给<span name="different">局部</span>变量用一套高效得多的策略来改进这一点，但全局变量就没那么容易优化了。

<aside name="different">

这是精密语言实现里一种常见的元策略。同一个语言特性往往会有多种实现技术，各自为不同的使用模式调优。比如，JavaScript 虚拟机常常为那些用起来更像类实例的对象准备一种更快的表示法，以区别那些属性集合被更随意修改的对象。C 和 C++ 编译器通常有好几种编译 `switch` 语句的方式，视分支数量、以及分支值排布得多密而定。

</aside>

[hash]: hash-tables.html

快速温习一下 Lox 的语义：Lox 里的全局变量是「晚绑定」的，也就是动态解析的。这意味着你可以编译一段引用了某个全局变量的代码，而那个变量还没定义。只要这段代码不在定义发生之前**执行**，一切就没问题。实际来说，这意味着你可以在函数体里引用后面才出现的变量。

```lox
fun showVariable() {
  print global;
}

var global = "after";
showVariable();
```

这样的代码看着可能有点怪，但它方便定义相互递归的函数。它跟 REPL 配合得也更好。你可以在一行里写一个小函数，然后在下一行定义它用到的变量。

局部变量的运作方式不同。既然局部变量的声明**总是**发生在它被使用之前，虚拟机就能在编译期解析它们，哪怕是在一个简单的单遍编译器里。这会让我们能为局部变量用上更聪明的表示法。不过那是下一章的事了。眼下，我们只管全局变量。

## 语句

变量靠变量声明诞生，这也意味着，现在正是给编译器加上语句支持的时候。如果你还记得，Lox 把语句分成两类。「声明」是那些把一个新名字绑定到一个值上的语句。其他种类的语句——控制流、print 等等——就只叫「语句」。我们不允许在控制流语句里直接放声明，像这样：

```lox
if (monday) var croissant = "yes"; // 错误。
```

允许这种写法，会在变量作用域上引出令人困惑的问题。所以，跟其他语言一样，我们在语法上禁止它，为此给「控制流主体里**允许**出现的那部分语句子集」单独设一条文法规则。

```ebnf
statement      → exprStmt
               | forStmt
               | ifStmt
               | printStmt
               | returnStmt
               | whileStmt
               | block ;
```

然后，我们给脚本的顶层以及块内部另设一条规则。

```ebnf
declaration    → classDecl
               | funDecl
               | varDecl
               | statement ;
```

`declaration` 规则含有那些声明名字的语句，同时也包进了 `statement`，好让所有语句类型都被允许。由于 `block` 本身就在 `statement` 里，你可以把声明嵌套在一个块里，从而把它们放进<span name="parens">控制流构造内部</span>。

<aside name="parens">

块的作用有点像圆括号之于表达式。块让你把「较低优先级」的声明语句，放到只允许「较高优先级」的非声明语句出现的地方。

</aside>

本章里，我们只讲几种语句和一种声明。

```ebnf
statement      → exprStmt
               | printStmt ;

declaration    → varDecl
               | statement ;
```

到现在为止，我们的虚拟机把「程序」当作单个表达式，因为我们当时也只能解析和编译这么多。在一个完整的 Lox 实现里，程序是一串声明。我们现在准备好支持它了。

^code compile (1 before, 1 after)

我们不停地编译声明，直到撞上源文件末尾。我们用这个编译单个声明：

^code declaration

变量声明我们本章稍后再讲，所以眼下，我们只是转给 `statement()`。

^code statement

块可以含有声明，控制流语句可以含有别的语句。这意味着这两个函数最终会是递归的。我们不妨现在就把前置声明写出来。

^code forward-declarations (1 before, 1 after)

### print 语句

这一章有两种语句类型要支持。我们从 `print` 语句开始，它自然是以一个 `print` 词法单元开头的。我们用一个辅助函数来侦测它：

^code match

你可能在 jlox 里认得它。如果当前词法单元是给定的类型，我们就消费掉它并返回 `true`。否则，我们不动这个词法单元，返回 `false`。这个<span name="turtles">辅助</span>函数是建立在另一个辅助函数之上的：

<aside name="turtles">

一层套一层，全是辅助函数！

</aside>

^code check

如果当前词法单元是给定的类型，`check()` 函数就返回 `true`。把它包进一个函数似乎有点<span name="read">傻</span>，但我们后面会更多用到它，而且我觉得像这样以动词命名的小函数，能让解析器更好读。

<aside name="read">

这听起来微不足道，可非玩具语言的手写解析器会变得相当大。当你面对几千行代码时，一个能把两行变成一行、还让结果稍微好读一点的工具函数，很容易就对得起自己的存在。

</aside>

如果我们确实匹配到了 `print` 词法单元，就在这里编译这个语句的其余部分：

^code print-statement

一个 `print` 语句求值一个表达式并打印结果，所以我们先解析并编译那个表达式。文法期望它后面跟一个分号，于是我们消费掉它。最后，我们发射一条新指令来打印结果。

^code op-print (1 before, 1 after)

运行时，我们这样执行这条指令：

^code interpret-print (1 before, 1 after)

当解释器到达这条指令时，它已经执行完那个表达式的代码，把结果值留在了栈顶。现在我们只需弹出并打印它。

注意，之后我们不再压入任何东西。这是虚拟机里表达式与语句的一个关键区别。每条字节码指令都有一个<span name="effect">**栈效应**</span>，描述这条指令如何改变栈。比如，`OP_ADD` 弹出两个值、压入一个，让栈比之前少一个元素。

<aside name="effect">

执行一次 `OP_ADD` 之后，栈短了一个元素，所以它的效应是 -1：

<img src="image/global-variables/stack-effect.png" alt="一条 OP_ADD 指令的栈效应。" />

</aside>

你可以把一串指令的栈效应加起来，得到它们的总效应。把任何一个完整表达式编译出的那串指令的栈效应相加，总数都是 1。每个表达式都会在栈上留下一个结果值。

整个语句的字节码，总栈效应是零。既然语句不产出任何值，它最终让栈保持不变，尽管它在干活时当然会用到栈。这一点很重要，因为等我们做到控制流和循环时，一个程序可能会执行一长串语句。要是每条语句都让栈变大或变小，它迟早会溢出或下溢。

既然我们在解释器循环里，就该删掉一点代码。

^code op-return (1 before, 1 after)

当虚拟机只能编译并求值单个表达式时，我们在 `OP_RETURN` 里放了些临时代码来输出那个值。既然我们有了语句和 `print`，就不需要它了。我们离 clox 的完整实现又近了<span name="return">一步</span>。

<aside name="return">

不过，也就近了一步。等我们加上函数时，还会再回来改 `OP_RETURN`。眼下，它会退出整个解释器循环。

</aside>

照例，新指令需要在反汇编器里得到支持。

^code disassemble-print (1 before, 1 after)

这就是我们的 `print` 语句。愿意的话，试它一把：

```lox
print 1 + 2;
print 3 * 4;
```

激动人心！好吧，也许算不上惊心动魄，但我们现在能造出含有任意多条语句的脚本了，这感觉像是一种进步。

### 错误同步

趁我们在编译器里做这些前期工作，可以顺手把我们[好几章之前][errors]留下的一根线头收掉。跟 jlox 一样，clox 用 panic 模式的错误恢复，来把它报告的连锁编译错误数量降到最低。当编译器到达一个同步点时，就退出 panic 模式。对 Lox，我们选了语句边界作为那个点。既然我们有了语句，就能实现同步了。

^code call-synchronize (1 before, 1 after)

如果我们在解析前一条语句时撞上编译错误，就进入 panic 模式。一旦如此，在那条语句之后，我们开始同步。

^code synchronize

我们不加区分地跳过词法单元，直到到达某个看起来像语句边界的地方。我们通过找一个能结束语句的前一个词法单元（比如分号）来认出边界。或者，我们找一个能开启语句的后继词法单元，通常是控制流或声明的关键字之一。

## 变量声明

仅仅能 **print** 一下，可不会让你的语言在编程语言<span name="fair">展览会</span>上得奖，所以我们往前走一点，弄点更有野心的东西，把变量搞起来。我们需要支持三种操作：

<aside name="fair">

我忍不住想象一个「语言展览会」，就像乡村的 4H 展会那种。一排排铺着干草的展位里，满是些幼崽语言，对着彼此 **moo**、**baa** 地叫。

</aside>

*   用一条 `var` 语句声明一个新变量。
*   用一个标识符表达式访问变量的值。
*   用一个赋值表达式把一个新值存进一个已存在的变量。

后两种在有一些变量之前都做不了，所以我们从声明开始。

^code match-var (1 before, 2 after)

我们为「声明」那条文法规则草拟的占位解析函数，现在有了真正的产生式。如果我们匹配到一个 `var` 词法单元，就跳到这里：

^code var-declaration

关键字后面跟着变量名。那由 `parseVariable()` 编译，我们稍后会讲到它。然后我们找一个 `=`，后面跟着一个初始化表达式。如果用户没有初始化这个变量，编译器就发射一条 `OP_NIL` 指令，隐式地把它初始化为 <span name="nil">`nil`</span>。无论哪种情况，我们都期望这条语句以分号结束。

<aside name="nil" class="bottom">

本质上，编译器会把这样一个变量声明脱糖：

```lox
var a;
```

成：

```lox
var a = nil;
```

它为前者生成的代码，跟它为后者生成的完全相同。

</aside>

这里有两个处理变量和标识符的新函数。第一个是：

^code parse-variable (2 before)

它要求下一个词法单元是一个标识符，然后消费掉它并送到这里：

^code identifier-constant (2 before)

这个函数拿给定的词法单元，把它的词素作为字符串加进字节码块的常量表。然后返回那个常量在常量表里的下标。

全局变量在运行时是**按名字**查找的。这意味着虚拟机——那个字节码解释器循环——需要能拿到这个名字。整个字符串太大了，塞不进字节码流当操作数。于是我们把字符串存在常量表里，指令随后用它在表里的下标来指代这个名字。

这个函数把这个下标一路返回给 `varDeclaration()`，后者随后把它交给这里：

^code define-variable

<span name="helper">这个</span>输出定义新变量、并存储其初始值的那条字节码指令。变量名在常量表里的下标就是这条指令的操作数。跟基于栈的虚拟机里一如既往的做法一样，我们最后发射这条指令。运行时，我们先执行变量初始化器的代码。那把值留在栈上。然后这条指令取走那个值，存起来备用。

<aside name="helper">

我知道其中有些函数现在看着相当没用。可等我们加上更多处理名字的语言特性时，它们会更划算。函数声明和类声明都会声明新变量，而变量表达式和赋值表达式会访问它们。

</aside>

在运行时那边，我们从这条新指令开始：

^code define-global-op (1 before, 1 after)

多亏我们那好用的哈希表，实现不算太难。

^code interpret-define-global (1 before, 1 after)

我们从常量表里取出变量的名字。然后从栈顶<span name="pop">取走</span>那个值，以这个名字为键把它存进一张哈希表。

<aside name="pop">

注意，我们是在把这个值加进哈希表**之后**才**弹出**它的。这确保即使恰好在把它加进哈希表的中途触发了垃圾回收，虚拟机也仍然找得到这个值。这种可能性不小，因为哈希表在扩容时需要动态分配。

</aside>

这段代码不去检查这个键是否已经在表里。Lox 对全局变量相当宽松，允许你重新定义它们而不报错。这在 REPL 会话里很有用，所以虚拟机也支持它——如果这个键碰巧已经在哈希表里，就干脆覆盖它的值。

还有一个小辅助宏：

^code read-string (1 before, 1 after)

这个宏从字节码块里读出一个单字节操作数，把它当作字节码块常量表的一个下标，返回该下标处的字符串。它不检查这个值**是不是**字符串——它不做检查，直接强制转换。这是安全的，因为编译器从不会发射一条引用非字符串常量的指令。

因为我们在乎词法卫生，所以在 interpret 函数末尾也把这个宏取消定义。

^code undef-read-string (1 before, 1 after)

我一直说「那张哈希表」，可我们其实还没有。我们需要一个地方存这些全局变量。既然我们希望它们在 clox 运行期间一直存在，就把它们直接存在虚拟机里。

^code vm-globals (1 before, 1 after)

跟处理字符串表时一样，我们需要在虚拟机启动时把这张哈希表初始化到一个合法状态。

^code init-globals (1 before, 1 after)

退出时我们把它<span name="tear">拆掉</span>。

<aside name="tear">

进程退出时会把一切都释放掉，但要操作系统来收拾我们的烂摊子，感觉有失体面。

</aside>

^code free-globals (1 before, 1 after)

照例，我们也希望能反汇编这条新指令。

^code disassemble-define-global (1 before, 1 after)

这样一来，我们就能定义全局变量了。倒不是说用户能**看出**自己定义了它们，因为他们其实还**用**不了。所以我们接下来解决这个。

## 读取变量

就像古往今来每一门编程语言那样，我们用变量的名字访问它的值。我们在这里把标识符词法单元接到表达式解析器上：

^code table-identifier (1 before, 1 after)

这里会调用这个新的解析函数：

^code variable-without-assign

跟声明那边一样，有几个小小的辅助函数，现在看着没用，但后面几章会更有用。我保证。

^code read-named-variable

这个函数调用前面同一个 `identifierConstant()` 函数，拿给定的标识符词法单元，把它的词素作为字符串加进字节码块的常量表。剩下要做的，就是发射一条指令，加载那个名字对应的全局变量。这条指令是：

^code get-global-op (1 before, 1 after)

在解释器那边，实现跟 `OP_DEFINE_GLOBAL` 相仿。

^code interpret-get-global (1 before, 1 after)

我们从指令的操作数里取出常量表下标，得到变量名。然后用它当键，在全局变量哈希表里查出这个变量的值。

如果这个键不在哈希表里，就意味着那个全局变量从未被定义过。在 Lox 里这是运行时错误，所以一旦如此，我们报告它并退出解释器循环。否则，我们取出那个值，把它压入栈。

^code disassemble-get-global (1 before, 1 after)

再加一点反汇编，就完事了。我们的解释器现在能跑这样的代码：

```lox
var beverage = "cafe au lait";
var breakfast = "beignets with " + beverage;
print breakfast;
```

只剩一个操作了。

## 赋值

整本书里，我都尽量让你走在一条相当安全、轻松的路上。我不回避难的**问题**，但我尽量不让**解法**复杂到没必要的地步。唉，可我们<span name="jlox">字节码</span>编译器里的其他设计选择，让赋值实现起来很烦人。

<aside name="jlox">

如果你还记得，jlox 里赋值相当容易。

</aside>

我们的字节码虚拟机用的是单遍编译器。编译器边解析边生成字节码，没有任何中间的 AST。一认出一段语法，就为它发射代码。赋值天然不适合这套。看这个：

```lox
menu.brunch(sunday).beverage = "mimosa";
```

在这段代码里，解析器直到走到 `=` 才意识到 `menu.brunch(sunday).beverage` 是一次赋值的目标、而不是个普通表达式——而那早已是第一个 `menu` 之后的很多个词法单元了。到那时，编译器已经为整段东西发射了字节码。

不过问题没看上去那么严峻。看看解析器是怎样看待那个例子的：

<img src="image/global-variables/setter.png" alt="语句 menu.brunch(sunday).beverage = &quot;mimosa&quot;，显示 menu.brunch(sunday) 是一个表达式。" />

尽管 `.beverage` 那部分不能被编译成 get 表达式，但 `.` 左边的一切都是一个表达式，有着正常的表达式语义。`menu.brunch(sunday)` 那部分可以照常编译并执行。

对我们来说很幸运的是，赋值左侧唯一的语义差异，出现在词法单元最右端、紧挨着 `=` 的地方。尽管 setter 的接收者可能是一个任意长的表达式，但行为跟 get 表达式不同的那部分，只是紧挨在 `=` 前面的那个结尾标识符。我们不需要多少前瞻，就能看出 `beverage` 应该被编译成 set 表达式而不是 getter。

变量就更简单了，因为它们只是 `=` 前面一个光秃秃的标识符。于是思路是：在编译一个「也能用作赋值目标」的表达式**之前**，我们就去找后面有没有一个 `=` 词法单元。看到了，就把它编译成赋值或 setter，而不是变量访问或 getter。

我们还没有 setter 要操心，所以需要处理的只有变量。

^code named-variable (1 before, 1 after)

在标识符表达式的解析函数里，我们在标识符之后找一个等号。找到了，就不为变量访问发射代码，而是编译被赋的值，然后发射一条赋值指令。

这是本章我们需要加的最后一条指令。

^code set-global-op (1 before, 1 after)

如你所料，它的运行时行为跟定义一个新变量类似。

^code interpret-set-global (1 before, 1 after)

主要的区别在于这个键还不在全局变量哈希表里时会发生什么。如果这个变量还没被定义，试图给它赋值就是运行时错误。Lox[不做隐式变量声明][implicit]。

<aside name="delete">

对 `tableSet()` 的调用会把这个值存进全局变量表，哪怕这个变量之前没有定义过。这个事实在 REPL 会话里是可见的，因为即便运行时错误被报告之后，它还会继续运行。所以我们还特意把那个僵尸值从表里删掉。

</aside>

另一个区别是，给变量赋值不会把值从栈上弹出。记住，赋值是一个表达式，所以它得把那个值留在那儿，以防这次赋值嵌套在某个更大的表达式里。

[implicit]: statements-and-state.html#design-note

^code disassemble-set-global (2 before, 1 after)

那我们就完事了，对吧？呃……还没呢。我们犯了个错！瞧一眼这个：

```lox
a * b = c + d;
```

按照 Lox 的文法，`=` 的优先级最低，所以这大致该被解析成：

<img src="image/global-variables/ast-good.png" alt="预期的解析，形如 '(a * b) = (c + d)'。" />

显然，`a * b` 不是个<span name="do">合法</span>的赋值目标，所以这该是一个语法错误。可我们的解析器干的是这个：

<aside name="do">

不过，要是 `a * b` **真**是个合法的赋值目标，那岂不是狂野得很？你可以想象某种像代数一样的语言，它试图用某种合理的方式把被赋的值分割开、分给 `a` 和 `b`……那大概率是个糟糕透顶的主意。

</aside>

1.  首先，`parsePrecedence()` 用 `variable()` 这个前缀解析器解析 `a`。
2.  之后，它进入中缀解析循环。
3.  它走到 `*`，调用 `binary()`。
4.  后者递归调用 `parsePrecedence()` 去解析右操作数。
5.  那又为解析 `b` 再次调用 `variable()`。
6.  在那次对 `variable()` 的调用内部，它找一个尾随的 `=`。它看到了一个，于是把这一行的其余部分当作一次赋值解析。

换句话说，解析器把上面那段代码看成：

<img src="image/global-variables/ast-bad.png" alt="实际的解析，形如 'a * (b = c + d)'。" />

我们把优先级处理搞砸了，因为 `variable()` 没有考虑包含该变量的那个外围表达式的优先级。如果这个变量恰好是个中缀运算符的右侧、或者某个一元运算符的操作数，那么那个包含它的表达式优先级太高，不允许出现 `=`。

为修好这个，`variable()` 只应在处于一个低优先级表达式的语境里时，才去找并消费 `=`。知道当前优先级的代码，合情合理，就是 `parsePrecedence()`。`variable()` 函数不需要知道确切的层级。这个函数只关心优先级够不够低、低到允许赋值，所以我们用布尔值把这个事实传进去。

^code prefix-rule (4 before, 2 after)

由于赋值是优先级最低的表达式，我们允许赋值的情形只有一种：解析一次赋值表达式、或者像表达式语句里那样的顶层表达式时。这个标志一路传到这里的解析函数：

^code variable

再通过一个新参数把它传下去：

^code named-variable-signature (1 after)

最后在这里用到它：

^code named-variable-can-assign (2 before, 1 after)

为了把字面意义上的一个比特送到编译器里正确的位置，这铺垫可真不少，但它总算送到了。如果这个变量嵌套在某个优先级更高的表达式里，`canAssign` 就会是 `false`，那么即便那儿真有个 `=`，这里也会忽略它。然后 `namedVariable()` 返回，执行最终一路回到 `parsePrecedence()`。

然后呢？编译器拿我们之前那个坏例子怎么办？现在，`variable()` 不会消费那个 `=`，所以它就会成为当前词法单元。编译器从 `variable()` 前缀解析器返回 `parsePrecedence()`，然后试着进入中缀解析循环。没有任何解析函数跟 `=` 关联，于是它跳过那个循环。

然后 `parsePrecedence()` 悄无声息地返回调用者。那也不对。如果这个 `=` 没被当作表达式的一部分消费掉，就没有别的东西会去消费它了。这是个错误，我们该报告它。

^code invalid-assign (2 before, 1 after)

这样一来，之前那个坏程序就能正确地在编译期得到一个错误了。好，**现在**完事了吗？还没。你看，我们给其中一个解析函数传了一个参数。可那些函数存在一张函数指针表里，所以所有解析函数都得是同一个类型。尽管大多数解析函数都不支持被用作赋值目标——setter 是<span name="index">唯一</span>的另一个——我们这位友好的 C 编译器却要求它们**全都**接受这个参数。

</aside>

## 习题

1.  编译器每遇到一个标识符，就把一个全局变量的名字作为字符串加进常量表。它每次都创建一个新常量，哪怕那个变量名已经待在常量表里之前的某个槽位了。在同一个函数多次引用同一个变量的情况下，这就是浪费。这又增加了填满常量表、槽位用完的几率，因为我们一个字节码块里只允许 256 个常量。

    优化这一点。你的优化对编译期性能相比于运行期性能有何影响？这是个正确的取舍吗？

2.  每次使用全局变量都按名字在哈希表里查一遍，是相当慢的，哪怕哈希表很好。你能想出一种更高效的办法来存储和访问全局变量、又不改变语义吗？

3.  在 REPL 里运行时，用户可能会写一个引用了未知全局变量的函数，然后在下一行声明这个变量。Lox 应当从容处理这种情况：在函数首次被定义时不报告「未知变量」的编译错误。

    可当用户运行一个 Lox **脚本**时，编译器在任何代码运行之前就能拿到整个程序的完整文本。考虑这个程序：

    ```lox
    fun useVar() {
      print oops;
    }

    var ooops = "too many o's!";
    ```

    这里，我们能静态地看出 `oops` 不会被定义，因为程序里**没有**任何地方声明这个全局变量。注意 `useVar()` 也从没被调用过，所以即便这个变量没定义，也不会发生运行时错误，因为它同样从没被使用。

    我们可以把这类错误报告成编译错误，至少在从脚本运行时。你觉得我们该这么做吗？为你的回答给出理由。你了解的其他脚本语言又是怎么做的？
