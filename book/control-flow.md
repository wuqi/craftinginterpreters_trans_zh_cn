## 图灵机（简述）

上世纪早些时候，数学家们一头撞进了一连串令人困惑的<span name="paradox">悖论</span>，这些悖论让他们
开始怀疑自己立起的那座地基到底稳不稳。为了应对那场[危机][crisis]，他们退回到原点。从寥寥几条公理、
逻辑和集合论出发，他们希望在坚不可摧的地基之上重建数学。

[crisis]: https://en.wikipedia.org/wiki/Foundations_of_mathematics#Foundational_crisis

<aside name="paradox">

最著名的是[**罗素悖论**][russell]。起初，集合论允许你定义任何一种集合。只要你能用英语把它描述出来，
它就是合法的。自然而然地，鉴于数学家对自指的偏爱，集合可以包含别的集合。于是罗素这个捣蛋鬼就想出了：

**R 是所有不包含自身的集合所构成的集合。**

R 包含它自己吗？如果不包含，那么按照定义的后半句，它就应该包含。可如果它包含了，那它就不再符合那个
定义了。脑袋当场炸掉。

[russell]: https://en.wikipedia.org/wiki/Russell%27s_paradox

</aside>

他们想要严谨地回答这样一些问题：「所有为真的命题都能被证明吗？」「我们能[计算][compute]所有我们能
定义的函数吗？」乃至那个更一般的问题：「当我们声称一个函数『可计算』时，我们到底是什么意思？」

[compute]: https://en.wikipedia.org/wiki/Computable_function

他们本以为前两个问题的答案会是「是」。剩下的只是去证明它。结果发现，这两者的答案都是「否」；而且
令人惊讶的是，这两个问题深深地纠缠在一起。这是数学里一个迷人的角落，它触及关于大脑能做什么、宇宙
如何运转的根本问题。我没法在这里把它讲透。

我真正想点出的是：在证明前两个问题答案为「否」的过程中，阿兰·图灵和阿隆佐·邱奇为最后一个问题设计出
了一个精确的答案——一个关于哪些函数是<span name="uncomputable">可计算</span>的定义。他们各自精心搭建
了一个极小的系统，用最少的机械，却仍然强大到能计算（非常）庞大的一类函数中的任何一个。

<aside name="uncomputable">

他们证明第一个问题的答案是「否」，靠的是指出：那个「给定一个命题、返回其真值」的函数**不**是可计算的。

</aside>

这些如今被认为是「可计算函数」。图灵的系统叫做<span name="turing">**图灵机**</span>。邱奇的则是
**lambda 演算**。两者至今仍被广泛用作计算模型的基础；事实上，许多现代函数式编程语言的核心都用到了
lambda 演算。

<aside name="turing">

图灵管他的发明叫「a-机器」，「a」代表 automatic（自动）。他还没那么爱给自己贴金，非要冠上**自己**的
名字。后来的数学家替他这么做了。这就是既出名、又保住几分谦逊的门道。

</aside>

<img src="image/control-flow/turing-machine.png" alt="一台图灵机。" />

图灵机的名气更大——目前还没有关于阿隆佐·邱奇的好莱坞电影——但这两个形式体系在[表达能力上是等价
的][thesis]。事实上，任何一门具备最低限度表达能力的编程语言，都强大到足以计算**任何**可计算函数。

[thesis]: https://en.wikipedia.org/wiki/Church%E2%80%93Turing_thesis

你可以这样来证明：用你的语言写一个图灵机模拟器。既然图灵证明了他的机器能计算任何可计算函数，那么
推而广之，也就意味着你的语言也能。你要做的，就是把那个函数翻译成一台图灵机，然后在你的模拟器上把它
跑起来。

如果你的语言表达能力强到能做这件事，它就被认为是**图灵完备**的。图灵机其实相当简单，所以要做到这
一点并不需要多少算力。你基本上只需要算术、一点点控制流，以及分配和使用（理论上）任意大小内存的能力。
第一条我们已经有了。本章结束时，我们会拿到<span name="memory">第二条</span>。

<aside name="memory">

我们**差不多**也已经有第三条了。你可以创建并拼接任意大小的字符串，所以你能**存下**无界的内存。但
我们还没办法访问字符串的某一部分。

</aside>

## 条件执行

历史讲够了，来给我们的语言添点花样吧。控制流大致可以分成两类：

*   **条件控制流**，也叫**分支控制流**，用来**不**执行某一段代码。从命令式的角度，你可以把它想成
    向前**跳过**一段代码区域。

*   **循环控制流**会把一段代码执行不止一次。它**跳回去**，好让你再做一遍某件事。由于你通常并不想要
    **无限**循环，它一般还带有一些条件逻辑，来判断该何时停止循环。

分支更简单，所以我们从它开始。从 C 派生的语言有两个主要的条件执行特性：`if` 语句，以及那个名字起得
相当有见地的「条件」<span name="ternary">运算符</span>（`?:`）。`if` 语句让你有条件地执行语句，条件
运算符则让你有条件地执行表达式。

<aside name="ternary">

条件运算符也被叫做「三目」运算符，因为它是 C 里唯一接受三个操作数的运算符。

</aside>

为了简单起见，Lox 没有条件运算符，所以我们就直接上 `if` 语句吧。我们的语句文法多了一条产生式。

<span name="semicolon"></span>

```ebnf
statement      → exprStmt
               | ifStmt
               | printStmt
               | block ;

ifStmt         → "if" "(" expression ")" statement
               ( "else" statement )? ;
```

<aside name="semicolon">

这些规则里没加引号的分号，是文法元语法的一部分，不是 Lox 的语法。一个块末尾没有 `;`，`if` 语句也
没有，除非它的 then 或 else 语句恰好以分号结尾。

</aside>

一条 `if` 语句有一个表示条件的表达式，然后是一条在条件为真值时执行的语句。可选地，它还可以有一个
`else` 关键字，以及一条在条件为假值时执行的语句。<span name="if-ast">语法树节点</span>为这三部分各
有一个字段。

<aside name="parens">

条件外面那对圆括号只有一半有用。你需要在条件和 then 语句**之间**放某种分隔符，否则语法解析器就分不
清它何时到达了条件表达式的末尾。但 `if` 后面那个**开括号**本身并没有任何实际用处。丹尼斯·里奇把它放
在那儿，只是为了能用 `)` 当结束分隔符，而不用让括号失衡。

别的语言，比如 Lua 和某些 BASIC，用 `then` 这样的关键字当结束分隔符，条件前面什么都不放。Go 和
Swift 则要求那条语句必须是一个带花括号的块。这样一来，它们就能用语句开头的 `{` 来判断条件何时结束。

一如往常，解析代码紧贴着文法。它靠查找前面的 `else` 关键字来侦测 else 子句。如果没有，语法树里的
`elseBranch` 字段就是 `null`。

那个看似无害的可选 else，其实在我们的文法里开了一个歧义的口子。考虑：

```lox
if (first) if (second) whenTrue(); else whenFalse();
```

谜题在此：那个 else 子句属于哪一个 `if` 语句？这不只是一个关于我们如何给文法词法单元的纯理论问题。它
实际上会影响代码怎么执行：

*   如果我们把 else 挂到第一个 `if` 语句上，那么只要 `first` 为假值，就会调用 `whenFalse()`，不管
    `second` 是什么值。

*   如果我们把它挂到第二个 `if` 语句上，那么只有当 `first` 为真值且 `second` 为假值时，才会调用
    `whenFalse()`。

由于 else 子句是可选的，又没有显式的分隔符标记 `if` 语句的结尾，所以当你这样嵌套 `if` 时，文法就是
有歧义的。语法里这个经典的陷阱叫做 **[dangling else][]** 问题。

[dangling else]: https://en.wikipedia.org/wiki/Dangling_else

这里，排版凸显了 else 可以被解析成的两种方式。但要注意，由于语法解析器会忽略空白字符，这只是给人类

</aside>

确实**可以**定义一套直接避开这个歧义的上下文无关文法，但那需要把大多数语句规则劈成一对一对：一个
允许带 `else` 的 `if`，一个不允许。挺烦人的。

于是，大多数语言和解析器都用一种临时凑合的办法绕开这个问题。不管它们用什么花招脱困，选的都是同一种
解读——`else` 绑定到它前面最近的那个 `if`。

我们的语法解析器正好已经是这么做的。由于 `ifStatement()` 会在返回之前急切地查找 `else`，在一串嵌套
调用里，最内层的那次调用会在返回给外层 `if` 语句之前，抢先把这个 else 子句据为己有。

语法到手，可以解释了。

^code visit-if

解释器里的实现不过是套在同名 Java 代码外面的一层薄壳。它给条件求值。如果为真值，就执行 then 分支。
否则，如果有 else 分支，就执行那个。

把这段代码跟我们已实现的其他语法在解释器里的处理方式比一比，控制流之所以特别，就在于那条 Java 的
`if` 语句。大多数其他语法树总是会求值它们的子树。而在这里，我们可能不求值 then 或 else 语句。如果这
两者中有一个带副作用，那么「选择不求值它」这件事就会变得对用户可见。

## 逻辑运算符

既然我们没有条件运算符，你可能以为分支这块就完事了，然而并没有。就算没有三目运算符，还有另外两个
运算符在严格意义上也是控制流构件——逻辑运算符 `and` 和 `or`。

它们不像别的二元运算符，因为它们会**短路**。如果在求值完左操作数之后，我们就已经知道这个逻辑表达式的
结果必然是什么，那就不去求值右操作数。比如：

```lox
false and sideEffect();
```

要让一个 `and` 表达式求值出真值，两个操作数都必须为真值。我们刚求值完左边那个 `false` 操作数，就能
看出这不会成立，所以没必要再去求值 `sideEffect()`，它就被跳过了。

这就是当初我们没有把逻辑运算符跟其他二元运算符一起实现的原因。现在我们准备好了。这两个新运算符在优先
级表里位置很低。跟 C 里的 `||` 和 `&&` 类似，它们各有<span name="logical">自己的</span>优先级，其中
`or` 比 `and` 低。我们把它俩恰好插在 `assignment` 和 `equality` 之间。

<aside name="logical">

我一直很好奇，为什么它们不像各种比较或相等运算符那样，拥有相同的优先级。

</aside>

```ebnf
expression     → assignment ;
assignment     → IDENTIFIER "=" assignment
               | logic_or ;
logic_or       → logic_and ( "or" logic_and )* ;
logic_and      → equality ( "and" equality )* ;
```

`assignment` 现在不再兜底到 `equality`，而是往下接到 `logic_or`。两条新规则 `logic_or` 和
`logic_and`，跟<span name="same">其他二元运算符</span>类似。接着 `logic_and` 把求操作数的活儿交给
`equality`，于是我们又链回了表达式规则剩下的部分。

<aside name="same">

**语法**才不在乎它们会不会短路。那是语义上的事。

</aside>

我们本可以为这两个新表达式复用现有的 Expr.Binary 类，毕竟字段是一样的。但那样一来，`visitBinaryExpr()`
就得检查这个运算符是不是逻辑运算符之一，然后走另一条代码路径来处理短路。我觉得为这两个运算符定义

这里另一个有意思的地方，是决定该返回什么实际的值。由于 Lox 是动态类型的，我们允许任意类型的操作数，

`false`，它只保证会返回一个具有恰当真值性的值。

幸运的是，手边就有带恰当真值性的值——操作数本身求出来的结果。所以我们就用它们。比如：

```lox

print nil or "yes"; // "yes".
```

第一行里，`"hi"` 为真值，所以 `or` 短路，把它返回。第二行里，`nil` 为假值，于是求值并返回第二个
操作数 `"yes"`。

跳。** 懂了吗？你看，这就像在影射……哦，算了。

## for 循环

我们来到最后一个控制流构件——<span name="for">古早的</span> C 风格 `for` 循环。我大概不用提醒你它
长什么样，不过还是给出来：

```lox
for (var i = 0; i < 10; i = i + 1) print i;
```

用文法话来说就是：

```ebnf
statement      → exprStmt
               | forStmt
               | ifStmt
               | printStmt
               | whileStmt
               | block ;

forStmt        → "for" "(" ( varDecl | exprStmt | ";" )
                 expression? ";"
                 expression? ")" statement ;
```

<aside name="for">

大多数现代语言都有一种更高级的循环语句，用来遍历任意用户定义的序列。C# 有 `foreach`，Java 有「增强版
for」，连 C++ 现在都有了基于范围的 `for` 语句。它们比 C 的 `for` 语句语法更干净，靠的是隐式调用一个
被遍历对象所支持的迭代协议。

我很喜欢那些。但对 Lox 来说，我们受限于「一次搭一章解释器」的节奏。我们还没有对象和方法，所以没法
定义一个能让 `for` 循环使用的迭代协议。于是我们就守着老派的 C 风格 `for` 循环。把它想成「复古款」。
控制流语句里的死飞自行车。

</aside>

圆括号里面有三个子句，用分号隔开：

1.  第一个子句是**初始化器**。它只执行一次，且在任何别的东西之前。它通常是一个表达式，但为了方便，
    我们也允许变量声明。在这种情况下，这个变量的作用域延伸到 `for` 循环的其余部分——另外两个子句和
    循环体。

2.  接下来是**条件**。跟 `while` 循环一样，这个表达式控制何时退出循环。它在每一轮迭代开头求值一次，
    包括第一轮。如果结果为真值，就执行循环体。否则，就退出。

3.  最后一个子句是**增量**。它是一个任意表达式，在每一轮迭代末尾做点事。表达式的结果会被丢弃，所以
    它必须有副作用才有用。实践中，它通常是给某个变量加一。

这三个子句中的任何一个都可以省略。收尾的圆括号之后，是一条作为循环体的语句，通常是一个块。

### 脱糖

这套机制是不少，但注意，这里没有任何一件事是你用现有的语句做不到的。如果 `for` 循环不支持初始化子句，
你完全可以把初始化表达式放在 `for` 语句前面。没有增量子句的话，你自己把增量表达式放到循环体末尾就
行了。

换句话说，Lox 并**不**需要 `for` 循环，它们只是让某些常见的代码模式写起来更舒服。这类特性叫做

```lox
{

}
```

这段脚本的语义跟上一段完全一样，只是没那么养眼。像 Lox 的 `for` 循环这样的语法糖特性，会让一门语言
用起来更舒服、更高效。但是，尤其在成熟的语言实现里，每一个需要后端支持和优化的语言特性都是有代价的。

我们可以<span name="caramel">**脱糖**</span>，做到既有蛋糕、又能吃掉它。这个好玩的词描述的是这样一个
过程：前端把使用了语法糖的代码，翻译成后端已经知道怎么执行的、更原始的形式。

有意思的地方来了。脱糖就要在这里发生，所以我们会一块一块地搭起这个方法，从子句前面那个开括号开始。

紧跟其后的第一个子句是初始化器。

如果 `(` 后面的词法单元是分号，那说明初始化器被省略了。否则，我们检查有没有 `var` 关键字，看它是不是

在之前某一章里，我说过我们可以把表达式和语句的语法树拆成两个独立的类层次，因为文法里没有任何一个

^code for-body (1 before, 1 after)

我们已经把 `for` 循环的各个零件都解析完了，得到的 AST 节点正躺在一堆 Java 局部变量里。脱糖就在这里

如果从后往前做，代码会稍微简单一点，所以我们从增量子句开始。

^code for-desugar-increment (2 before, 1 after)

增量（如果有的话），会在循环每一轮迭代中、循环体之后执行。我们这样做：把循环体替换成一个小块，里面

^code for-desugar-condition (2 before, 1 after)

接下来，我们拿条件和循环体，用最原始的 `while` 循环把整个循环搭起来。如果条件被省略，我们就塞进一个
`true`，造出一个无限循环。

^code for-desugar-initializer (2 before, 1 after)

最后，如果有初始化器，它会在整个循环之前运行一次。我们这样做：再一次把整条语句替换成一个块，先运行

就这样。我们的解释器现在支持 C 风格 `for` 循环了，而且我们压根没碰 Interpreter 类。既然我们脱糖出来
的是解释器已经会访问的节点，那就没有别的活儿要干了。

终于，Lox 强大到能逗我们开心了，至少能撑几分钟。下面这个小程序打印斐波那契数列的前 21 个元素：

```lox
var a = 0;
var temp;

for (var b = 1; a < 10000; b = temp + b) {
  print a;
  temp = a;
  a = b;
}
```

<div class="design-note">

## 设计说明：一勺一勺的语法糖

当你设计自己的语言时，你要选择往文法里倒多少语法糖。你是要做成不加糖的健康食品，让每一个语义操作都
对应一个单一的语法单位，还是做成某种颓靡的甜点，让每一丁点儿行为都能用十种不同方式表达？成功的语言
分布在这条连续谱的各个点上。

在一个极端、也就是最不甜的那一端，是那些语法极度精简的语言，像 Lisp、Forth 和 Smalltalk。Lisp 派
有个有名的说法，说他们的语言「没有语法」；Smalltalk 派则得意地展示，整套文法能塞进一张索引卡。这一
族信奉的哲学是：**语言**本身不需要语法糖。它提供的那点极简的语法和语义已经足够强大，能让库代码的
表达力强得仿佛它就是语言自身的一部分。

紧挨着这些的，是 C、Lua 和 Go 之类的语言。它们追求的是简单和清晰，而非极简。有些，比如 Go，刻意
避开了语法糖，也避开了上一类那种语法的可扩展性。它们想让语法给语义让路，所以专注于把文法和库都保持
简单。代码应当首先是显而易见，其次才是漂亮。

中间某处，是 Java、C# 和 Python 之类的语言。一直往另一头走，就到了 Ruby、C++、Perl 和 D——这些语言
往自己的文法里塞进了太多语法，以至于键盘上的标点符号都快不够用了。

在某种程度上，处在这条谱上的位置与语言年龄相关。在后续版本里添加一点语法糖相对容易。新语法讨人喜欢，
而且它比胡乱改动语义更不容易破坏已有程序。一旦加上，就再也没法拿掉，所以语言往往随着时间越变越甜。
从零开始造一门新语言的主要好处之一，就是它给了你一个机会，把那些年复一年攒下的糖霜刮掉，从头再来。

在编程语言的知识精英圈里，语法糖名声不佳。那群人里对极简主义有一种真真切切的迷恋。这多少有些道理。
设计得糟糕、又没必要的语法，会增加认知负担，却没带来足以撑起这份负担的表达力。由于总有一股把新特性
硬塞进语言的压力，要想避免臃肿，就得有纪律、并且聚焦于简单。一旦加上某种语法，你就甩不掉它了，所以
精打细算才是明智的。

与此同时，大多数成功的语言确实拥有相当复杂的文法，至少在它们被广泛使用时是这样。程序员会在自己选定
的语言里投入海量时间，而这里一处、那里一处的小小便利，真的能提升他们工作的舒适度和效率。

拿捏好恰当的平衡——为你的语言选对甜度——靠的是你自己的品味。

</div>
