我们目前这个解释器，感觉不太像是在给一门真正的语言编程，倒更像是在计算器上戳按钮。在我看来，
「编程」意味着用一块块小零件搭出一个系统。眼下我们还做不到，因为我们没办法把一个名字绑定到某份
数据或某个函数上。没办法引用各个零件，就没办法组合出软件。

要支持绑定，我们的解释器就得有内部状态。当你在程序开头定义一个变量、在结尾使用它时，解释器必须
在这中间一直攥着那个变量的值。所以在这一章里，我们要给解释器装上一颗大脑，它不仅会计算，还能
**记住**。

状态和<span name="expr">语句</span>是手挽手的。按定义，语句不求值出一个值，所以它们得干点别的才有用。
那个「别的」叫做**副作用**。它可能意味着产出用户看得见的输出，或者修改解释器里某种之后能被察觉的
状态。后者让语句特别适合用来定义变量或别的具名实体。

## 语句

我们先给 Lox 的文法扩展出语句。它们跟表达式差别不大。从最简单的两种开始：

1.  **表达式语句**让你可以把一个表达式放在本该是语句的位置。它存在的意义是求值那些带副作用的
    表达式。你可能没注意到它，但你在 <span name="expr-stmt">C</span>、Java 和其他语言里一直在用它。
    只要你看到一个函数或方法调用后面跟着 `;`，那就是一条表达式语句。

    <aside name="expr-stmt">

    Pascal 是个异类。它区分**过程**（procedure）和**函数**（function）。函数返回值，过程不能。
    调用过程有专门的语句形式，而函数只能在需要表达式的地方调用。Pascal 里没有表达式语句。

    </aside>

2.  **`print` 语句**求值一个表达式，并把结果显示给用户。我承认，把打印直接焊进语言里、而不是
    做成库函数，是有点怪。这么做是让步于一个事实：我们是一章一章地搭这个解释器，想在它做完之前
    就能上手玩一玩。要是把 print 做成库函数，我们就得等到定义和调用函数的全套机械都备齐
    <span name="print">之后</span>，才能见证任何副作用。

    <aside name="print">

    我要带一点点戒备心地说一句：BASIC 和 Python 都有专门的 `print` 语句，而它们是真正的语言。
    诚然，Python 在 3.0 里把它的 `print` 语句去掉了……

    </aside>

新语法意味着新的文法规则。在这一章里，我们终于获得了语法解析整个 Lox 脚本的能力。既然 Lox 是一门
命令式、动态类型的语言，脚本的「顶层」就只是一串语句。新规则是：

```ebnf
program        → statement* EOF ;

statement      → exprStmt
               | printStmt ;

exprStmt       → expression ";" ;
printStmt      → "print" expression ";" ;
```

第一条规则现在成了 `program`，它是文法的起点，代表一个完整的 Lox 脚本或一条 REPL 输入。一个程序
就是一串语句，后面跟着那个特殊的「文件结束」词法单元。这个必须有的结束词法单元确保语法解析器会
吃光全部输入，不会悄悄放过脚本末尾遗留的、出错的词法单元。

眼下，`statement` 只为我们描述过的两种语句准备了两个分支。本章后面和接下来的几章里，我们会往里
补更多。下一步是把这个文法变成我们能存在内存里的东西——语法树。

## 全局变量

既然有了语句，我们就能开始弄状态了。在钻进词法作用域那一堆复杂东西之前，先从最简单的一种变量
开始——<span name="globals">全局变量</span>。我们需要两个新构件。

1.  一条**变量声明**语句把一个新变量带到世上。

    ```lox
    var beverage = "espresso";
    ```

    它创建一个新的绑定，把某个名字（这里是 "beverage"）跟某个值（这里是字符串 `"espresso"`）
    关联起来。

2.  这之后，一个**变量表达式**访问那个绑定。当标识符 "beverage" 被当作表达式使用时，它会查出
    绑定到那个名字上的值并返回。

    ```lox
    print beverage; // "espresso".
    ```

后面我们还会加上赋值和块作用域，但眼下这些足够开动了。

<aside name="globals">

全局状态名声不太好。的确，大量的全局状态——尤其是**可变的**状态——会让大型程序难以维护。把它用得
越少越好，这是好的软件工程。

但当你随手拼凑一门简单的编程语言时，或者更进一步，甚至只是学你的第一门语言时，全局变量那种扁平的
简单就有帮助。我的第一门语言是 BASIC，虽说我后来长大了、把它抛在了身后，但当时不必先绕明白作用域
规则就能让计算机干些好玩的事，这一点挺好的。

</aside>

### 变量的语法

跟之前一样，我们从前到后过一遍实现，从语法开始。变量声明是语句，但它们跟别的语句不一样，我们打算
把语句文法一分为二来处理它们。这是因为文法会限制某些种类的语句能出现在哪里。

控制流语句里的那些子句——想想 `if` 语句的 then 和 else 分支，或者 `while` 的循环体——每一个都是
一条单独的语句。但那条语句不允许是声明名字的那种。这样是可以的：

```lox
if (monday) print "Ugh, already?";
```

但这样不行：

```lox
if (monday) var beverage = "espresso";
```

我们**大可以**允许后一种，但它挺让人困惑。那个 `beverage` 变量的作用域是什么？它在 `if` 语句之后
还存在吗？如果存在，那在不是星期一的日子里它的值是什么？那些日子里这个变量到底存不存在？

这样的代码很怪，所以 C、Java 之流都不许这么写。就好像语句有两层<span name="brace">「优先级」</span>。
有些允许出现语句的地方——比如块内部或顶层——允许任何种类的语句，包括声明。另一些地方则只允许
「更高」优先级的语句，也就是不声明名字的那些。

<aside name="brace">

在这个类比里，块语句的作用有点像表达式里的括号。块本身处于「更高」的优先级，可以放在任何地方，
比如 `if` 语句的子句里。但它**包含**的语句可以是更低优先级的。你被允许在块内部声明变量和其他名字。
那对花括号让你能从「只允许部分语句」的地方，逃回到完整的语句文法里。

</aside>

为了容纳这个区分，我们为声明名字的那些语句再加一条规则。

```ebnf
program        → declaration* EOF ;

declaration    → varDecl
               | statement ;

statement      → exprStmt
               | printStmt ;
```

声明语句归到新的 `declaration` 规则下。眼下它只有变量，但以后还会包括函数和类。任何允许出现声明的
地方也允许非声明的语句，所以 `declaration` 规则会兜底落到 `statement`。显然，你可以在脚本顶层做
声明，所以 `program` 改接到这条新规则上。

声明变量的规则长这样：

```ebnf
varDecl        → "var" IDENTIFIER ( "=" expression )? ";" ;
```

跟大多数语句一样，它以一个领头的关键字开头。这里就是 `var`。然后是一个标识符词法单元，用来表示
正在声明的变量名，接着是一个可选的初始化器表达式。最后，我们给它扎上分号这个蝴蝶结。

要访问一个变量，我们定义一种新的基本表达式。

```ebnf
primary        → "true" | "false" | "nil"
               | NUMBER | STRING
               | "(" expression ")"
               | IDENTIFIER ;
```

那条 `IDENTIFIER` 子句匹配单个标识符词法单元，它被理解为正在被访问的变量的名字。

**字典**（dictionary，Python 和 C#）、**哈希**（hash，Ruby 和 Perl）、**表**（table，Lua），或者
**关联数组**（associative array，PHP）。早年间，它们叫**分散表**（scatter table）。

</aside>

^code environment-class

里面有一个 Java 的 Map 用来存绑定。它的键用的是裸字符串，不是词法单元。一个词法单元代表的是源文本
里某个具体位置上的一段代码；但说到查变量时，所有同名的标识符词法单元都应该指向同一个变量（暂不考虑
作用域）。用原始字符串能确保那些词法单元全都指向同一个映射键。

我们需要支持两个操作。第一，变量定义把一个新名字绑定到一个值上。

^code environment-define

算不上什么脑外科手术，但我们做了一个有意思的语义选择。往映射里加键时，我们不检查它是不是已经在了。
这意味着下面这个程序能跑：

```lox
var a = "before";
print a; // "before".
var a = "after";
print a; // "after".
```

一条变量语句不只是定义一**个新**变量，它还能用来**重新**定义一个已有变量。我们也可以
<span name="scheme">选择</span>把它变成错误。用户也许并不想重新定义一个已有变量。（要是他们真想，
多半会用赋值，而不是 `var`。）把重新定义变成错误，能帮他们揪出这个 bug。

<aside name="scheme">

我关于变量和作用域的准则就是：「拿不准的时候，就照 Scheme 的做法办。」Scheme 那群人花在琢磨变量
作用域上的时间，大概比我们这辈子都多——Scheme 的主要目标之一就是把词法作用域带给世界——所以跟着
他们的脚印走，很难走错。

Scheme 允许在顶层重新定义变量。

</aside>

所以，为了让两种模式保持一致，我们允许这么做——至少对全局变量是如此。一旦变量存在了，我们就需要
一种办法把它查出来。

^code environment-get (2 before, 1 after)

这个在语义上更有意思一点。如果找到了变量，它就简单地返回绑定到它上面的值。但要是没找到呢？又一次，
我们有几个选择：

* 把它当语法错误。

* 把它当运行时错误。

* 允许它，并返回某个默认值，比如 `nil`。

Lox 是挺随意的，但最后一个选项在我看来有点**太**宽松了。把它当语法错误——一个编译期错误——似乎是个
聪明的选择。使用未定义的变量是个 bug，错发现得越早越好。

问题在于，**使用**一个变量跟**提及**它并不是一回事。如果一块代码被裹在函数里面，你就可以提及其中
一个变量，而不必立刻对它求值。要是我们把「在变量声明之前**提到**它」变成静态错误，那定义递归函数就
难多了。

我们可以照顾到单个递归——一个调用自己的函数——办法是在查看它的函数体之前先声明它自己的名字。但这
对相互递归的过程（彼此互相调用）就没用了。看这个：

<span name="contrived"></span>

```lox
fun isOdd(n) {
  if (n == 0) return false;
  return isEven(n - 1);
}

fun isEven(n) {
  if (n == 0) return true;
  return isOdd(n - 1);
}
```

<aside name="contrived">

的确，这大概不是判断一个数是奇是偶的最高效办法（更别提你往里传个非整数或负数时会发生什么坏事了）。
忍一忍。

</aside>

我们查看 `isOdd()` 的函数体、看到它调用 `isEven()` 的那个<span name="declare">时候</span>，
`isEven()` 函数还没被定义。要是把这两个函数的顺序对调，那反过来，我们在看 `isEven()` 的函数体时，
`isOdd()` 又还没定义。

<aside name="declare">

像 Java 和 C# 这类静态类型语言，是这么解决的：规定程序的顶层不是一串命令式语句，而是一组同时诞生的
声明。实现在查看**任何**函数体之前，先声明**所有**名字。

C 和 Pascal 这类更老的语言不这么干。它们逼你加上显式的**前向声明**，在某个名字被完整定义之前先声明
它。那是对当时有限算力的让步。他们希望只把源文件从头到尾扫一遍就能编译完，所以那些编译器没法先收集
齐所有声明再去处理函数体。

</aside>

既然把它当**静态**错误会让递归声明太难办，我们就把这个错误推迟到运行时。只要你不去**求值**那个引用，
在变量定义之前提及它是没问题的。这样奇偶数的程序就能跑，但下面这段会得到一个运行时错误：

```lox
print a;
var a = "too late!";
```

跟表达式求值代码里的类型错误一样，我们通过抛异常来报告运行时错误。这个异常带着变量的词法单元，这样
我们就能告诉用户，他们的代码在哪儿出了岔子。

### 解释全局变量

Interpreter 类拿到一个 Environment 类的新实例。

^code environment-field (2 before, 1 after)

我们把它直接存成 Interpreter 里的一个字段，这样只要解释器还在跑，那些变量就一直留在内存里。

我们有两棵新语法树，所以有两个新的 visit 方法。第一个是给声明语句的。

^code visit-var

如果变量有初始化器，我们就给它求值。如果没有，我们又要做一个选择。我们本可以在语法解析器里**要求**
必须有初始化器，把它变成语法错误。但大多数语言不这么做，所以对 Lox 来说，这么做感觉有点苛刻。

我们也可以把它变成运行时错误。那样就允许你定义未初始化的变量，但要是你在给它赋值之前访问它，就会
发生运行时错误。这主意不坏，但大多数动态类型语言不这么做。那我们还是保持简单：Lox 规定，如果没被
显式初始化，变量就设为 `nil`。

```lox
var a;
print a; // "nil".
```

因此，如果没有初始化器，我们就把值设成 `null`，它是 Lox 的 `nil` 值在 Java 里的表示。然后我们让
环境把这个变量绑定到那个值上。

接下来，我们求值一个变量表达式。

^code visit-variable

它只是转发给环境，由环境做那些繁重的活，确保变量是定义过的。这下，我们有了一套初级可用的变量。
试试这个：

```lox
var a = 1;
var b = 2;
print a + b;
```

我们还不能复用**代码**，但可以开始搭出复用**数据**的程序了。

## 赋值

你完全可以造一门有变量、却不让你重新赋值——也就是**修改**——它们的语言。Haskell 就是一个例子。
SML 只支持可变的引用和数组——变量本身不能被重新赋值。Rust 用「要求加 `mut` 修饰符才能赋值」的
方式，把你从修改这件事上劝开。

修改变量是一种副作用，而这名字也暗示了，有些语言圈的人觉得副作用<span name="pure">脏</span>、不优雅。
代码应该是产出值的纯粹数学——清澈、恒定，像一场神圣的创造。而不是某个邋里邋遢的自动机，一次一下
命令式的哼哼，把一团团数据捶打成形。

<aside name="pure">

我发现一件挺好玩的事：同一群标榜自己冷静讲逻辑的人，偏偏忍不住给自己的活儿起那些情感浓烈的词：
「纯粹」、「副作用」、「惰性」、「持久」、「一等」、「高阶」。

</aside>

Lox 可没那么清高。Lox 是一门命令式语言，修改是它自带的。加几行代码支持赋值算不上什么大活。全局
变量本来就支持重新定义，所以大部分机器已经就位了。主要缺的是一个显式的赋值写法。

### 赋值语法

那个小小的 `=` 语法比它看起来要复杂。跟大多数从 C 派生的语言一样，赋值是一个<span name="assign">
表达式</span>，不是语句。也跟 C 一样，它是优先级最低的表达式形式。这意味着这条规则插在 `expression`
和 `equality`（次低优先级的表达式）之间。

<aside name="assign">

在别的语言里，比如 Pascal、Python 和 Go，赋值是一条语句。

</aside>

```ebnf
expression     → assignment ;
assignment     → IDENTIFIER "=" assignment
               | equality ;
```

这条规则说的是：一个 `assignment` 要么是一个标识符后面跟着 `=` 和一个表示值的表达式，要么是一个
`equality`（进而是任何别的）表达式。以后等我们给对象加上属性设置器，`assignment` 还会变得更复杂，
像这样：

```lox
instance.field = "value";
```

简单的那部分，是加上那个<span name="assign-ast">新语法树节点</span>。

^code assign-expr (1 before, 1 after)

<aside name="assign-ast">

新节点生成的代码在[附录二][appendix-assign]里。

[appendix-assign]: appendix-ii.html#赋值表达式

</aside>

它有一个词法单元，表示被赋值的变量；还有一个表达式，表示新值。等你跑完 AstGenerator 拿到新的
Expr.Assign 类之后，把语法解析器里现有的 `expression()` 方法体换掉，好跟更新后的规则对上。

^code expression (1 before, 1 after)

麻烦就麻烦在这儿。一个只有单 token 前瞻的递归下降语法解析器，在走完左侧、一头撞上 `=` **之前**，
是看不到足够远、判断不出自己正在解析一个赋值的。你可能会问，它为什么需要知道？毕竟，我们在解析完
左操作数之前，也不知道自己正在解析一个 `+` 表达式啊。

区别在于，赋值的左侧不是一个求值出某个值的表达式。它是一种伪表达式，求值出的是一个你可以往里赋值的
「东西」。想想这个：

```lox
var a = "before";
a = "value";
```

在第二行，我们并不**求值** `a`（那样会得到字符串 "before"）。我们搞清楚变量 `a` 指的是什么，这样
才知道该把右侧表达式的值存到哪儿。这两种<span name="l-value">构件</span>的[经典叫法][l-value]是
**左值**和**右值**。我们迄今为止见过的、产出值的表达式全是右值。左值「求值」出的是一处存储位置，
你可以往里面赋值。

[l-value]: https://en.wikipedia.org/wiki/Value_(computer_science)#lrvalue

<aside name="l-value">

其实这两个名字来自赋值表达式：**左**值出现在赋值中 `=` 的**左**边，**右**值在**右**边。

</aside>

我们希望语法树能反映出：左值不像普通表达式那样被求值。这就是为什么 Expr.Assign 节点为左侧存的
是一个 **Token**，而不是一个 Expr。问题在于，语法解析器在撞上 `=` 之前，并不知道自己正在解析一个
左值。在一个复杂的左值里，那个 `=` 可能出现在<span name="many">很多</span>个词法单元之后。

```lox
makeList().head.next = node;
```

<aside name="many">

既然属性赋值的接收者可以是任意表达式，而表达式你想让它多长就能多长，那么找到那个 `=` 可能需要
**无界**数量的前瞻词法单元。

</aside>

我们只有单 token 前瞻，那怎么办？我们用一个小花招，它长这样：

^code parse-assignment

解析一个赋值表达式的大部分代码，看着跟解析 `+` 之类的其他二元运算符差不多。我们解析左侧，它可以是
任何更高优先级的表达式。如果我们发现一个 `=`，就解析右侧，然后把这一切裹进一个赋值表达式语法树
节点里。

<aside name="no-throw">

如果左侧不是一个合法的赋值目标，我们会**报告**一个错误，但不会**抛出**它，因为语法解析器并没有
陷入那种需要进入 panic 模式再做同步的混乱状态。

</aside>

跟二元运算符有一点小小的不同：我们不会循环着去累积一串同样的运算符。因为赋值是右结合的，我们改成
递归调用 `assignment()` 来解析右侧。

花招在于：在创建赋值表达式节点之前，我们看一眼左侧那个表达式，弄清楚它是哪种赋值目标。我们把那个
右值表达式节点转换成一个左值的表示。

之所以能这么转，是因为结果证明：每一个合法的赋值目标，恰好也都是<span name="converse">合法的普通
表达式语法</span>。考虑一个
复杂的属性赋值，像这样：

<aside name="converse">

就算有些赋值目标不是合法的表达式，你也仍然能用这个花招。定义一套**覆盖文法**（cover grammar）——
一套更宽松的文法，同时接受所有合法的表达式**和**赋值目标语法。当你撞上 `=` 时，如果左侧不落在合法
赋值目标的文法里，就报错。反过来，如果你**没**撞上 `=`，而左侧又不是一个合法的**表达式**，也报错。

</aside>

```lox
newPoint(x + 2, 0).y = 3;
```

这个赋值表达式的左侧，同时也是合法的表达式。

```lox
newPoint(x + 2, 0).y;
```

第一个例子设置那个字段，第二个读取它。

这意味着我们可以把左侧**当作一个表达式**来解析，事后再产出语法树，把它变成一个赋值目标。如果左侧
表达式不是一个合法的<span name="paren">赋值目标</span>，我们就以一个语法错误失败。这就确保了我们
能对下面这种代码报错：

```lox
a + b = c;
```

<aside name="paren">

在讲语法解析那一章里，我说过我们要在语法树里表示带括号的表达式，因为以后会需要它。这就是原因。
我们需要能够区分这些情况：

```lox
a = 3;   // OK.
(a) = 3; // Error.
```

</aside>

眼下，唯一合法的赋值目标就是一个简单的变量表达式，但以后我们会加上字段。这个花招的最终产物是一个
赋值表达式语法树节点：它知道自己正在给什么赋值，并且有一个表达式子树表示被赋的那个值。所有这些，
只需要单 token 前瞻，且不回溯。

### 赋值的语义

我们有了一个新语法树节点，所以解释器也就有了一个新的 visit 方法。

^code visit-assign

出于显而易见的原因，它跟变量声明很像。它给右侧求值拿到那个值，然后把它存进那个具名变量里。它调用的
是 Environment 上这个新方法，而不是 `define()`：

^code environment-assign

赋值跟定义的关键区别在于，赋值**不**被<span name="new">允许</span>创建一个**新**变量。在我们的实现里，这就意味着：如果那个键在环境的变量映射里还不存在，这就是一个运行时错误。

<aside name="new">

跟 Python 和 Ruby 不一样，Lox 不做[隐式变量声明][]。

这个 `visit()` 方法做的最后一件事，就是返回被赋的那个值。这是因为赋值是一个表达式，可以嵌套在别的


这下我们的解释器能创建、读取、修改变量了。水平大概跟早期的 <span name="basic">BASIC</span> 差不多。
全局变量很简单，但当程序里随便两块代码都能意外踩到彼此的状态时，写一个大型程序就没啥乐趣了。我们
想要**局部**变量，也就是说，该请出**作用域**了。

## 作用域

一个**作用域**定义了一片区域，在那里一个名字映射到某个特定的实体。多个作用域让同一个名字能在不同的
上下文里指代不同的东西。在我家里，「鲍勃」通常指的是我。但也许在你那座城里，你认识另一个鲍勃。
同一个名字，说的地方不同，对应的人就不同。

<span name="lexical">**词法作用域**</span>（或者那个不那么常听到的**静态作用域**）是一种特定的作用域
风格，程序文本本身就显示了作用域从哪里开始、到哪里结束。在 Lox 里，跟大多数现代语言一样，变量是
词法作用域的。当你看到某个使用变量的表达式时，只要静态地阅读代码，就能弄清楚它指的是哪一次变量
声明。

<aside name="lexical">

「词法」（lexical）来自希腊语「lexikos」，意思是「跟词有关的」。在编程语言里用它，通常指的是那种
你无须执行任何东西、单从源代码本身就能弄明白的东西。

词法作用域随 ALGOL 登上舞台。更早的语言往往是动态作用域的。那时候的计算机科学家相信，动态作用域
执行起来更快。今天，多亏了早期 Scheme 那帮黑客，我们知道那不是真的。真要说的话，恰恰相反。

变量的动态作用域在某些角落里还活着。Emacs Lisp 的变量默认就是动态作用域。Clojure 里的
[`binding`][binding] 宏提供了它。JavaScript 里那个广遭嫌弃的 [`with` 语句][with]，会把对象上的
属性变成动态作用域的变量。

[binding]: http://clojuredocs.org/clojure.core/binding
[with]: https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/with

</aside>

举个例子：

```lox
{
  var a = "first";
  print a; // "first".
}

{
  var a = "second";
  print a; // "second".
}
```

这里有两个块，各自声明了一个变量 `a`。你我只要看一眼代码就能说出来，第一条 `print` 语句里用到的
`a` 指的是第一个 `a`，第二条指的就是第二个。

<img src="image/statements-and-state/blocks.png" alt="为每个 'a' 各自准备的一个环境。" />

这跟**动态作用域**形成对比——在动态作用域里，直到你执行代码才知道一个名字指的是什么。Lox 没有
动态作用域的**变量**，但对象上的方法和字段是动态作用域的。

```lox
class Saxophone {
  play() {
    print "Careless Whisper";
  }
}

class GolfClub {
  play() {
    print "Fore!";
  }
}

fun playIt(thing) {
  thing.play();
}
```

当 `playIt()` 调用 `thing.play()` 时，我们不知道即将听到的是「Careless Whisper」还是「Fore!」。
这取决于你传给函数的是萨克斯还是高尔夫球杆，而这件事要到运行时才知道。

作用域和环境是一对近亲。前者是理论概念，后者是实现它的机器。当我们的解释器在代码里穿行时，那些
影响作用域的语法树节点会改变环境。在 Lox 这种偏 C 的语法里，作用域是由花括号块控制的。（所以我们
管它叫**块作用域**。）

```lox
{
  var a = "in block";
}
print a; // Error! No more "a".
```

一个块的开始引入一个新的局部作用域，而当执行越过那个收尾的 `}` 时，这个作用域就结束了。块内声明的
任何变量都消失不见。

### 嵌套与遮蔽

实现块作用域的第一版草稿大概是这样的：

1.  在我们访问块内每一条语句时，记下所有被声明的变量。

2.  在最后一条语句执行完之后，告诉环境把那些变量全都删掉。

对前面那个例子来说，这能行。但记住，局部作用域的动机之一就是封装——程序某个角落里的一块代码，不该
去干扰别的某一块。看看这个：

```lox
// How loud?
var volume = 11;

// Silence.
volume = 0;

// Calculate size of 3x4x5 cuboid.
{
  var volume = 3 * 4 * 5;
  print volume;
}
```

看看那个块，我们用 `volume` 的一个局部声明来计算长方体的体积。块退出之后，解释器会把那个**全局**
`volume` 变量删掉。这可不对。退出块时，我们应该移除块内声明的任何变量，但如果块外声明了一个同名的
变量，那**是另一个变量**。它不该被碰。

当一个局部变量跟某个外围作用域里的变量同名时，它会**遮蔽**那个外层变量。块内的代码再也看不见它了
——它藏在内层变量投下的「阴影」里——但它还在那儿。

当我们进入一个新的块作用域时，需要保住那些在外层作用域里定义的变量，好让它们在退出内层块之后依然
还在。为此，我们给每个块定义一个全新的环境，里面只装着在这个作用域里定义的变量。退出块时，我们丢掉
它的环境，恢复上一个。

我们还需要处理那些**没有**被遮蔽的外围变量。

```lox
var global = "outside";
{
  var local = "inside";
  print global + local;
}
```

这里，`global` 住在外面那个全局环境里，而 `local` 定义在块自己的环境里。在那条 `print` 语句里，
这两个变量都在作用域内。为了找到它们，解释器不仅得搜当前最内层的环境，还得搜任何外围环境。

我们通过把环境<span name="cactus">串联</span>起来的办法实现这一点。每个环境都有一个指向紧邻的外围
作用域环境的引用。当我们查找一个变量时，就沿着这条链从最内层往外走，直到找到那个变量。从内层作用域
开始，正是我们让局部变量遮蔽外层变量的方式。

## 设计说明：隐式变量声明

Lox 把「声明一个新变量」和「给已有变量赋值」区分成了两套不同的语法。有些语言把这两者合并成只有赋值
一种语法。给一个不存在的变量赋值，会自动把它带到世上。这叫做**隐式变量声明**，Python、Ruby 和
CoffeeScript 等语言都有。JavaScript 有显式的语法来声明变量，但也能在赋值时创建新变量。Visual Basic
有一个[开关来启用或禁用隐式变量][vb]。

[vb]: https://msdn.microsoft.com/en-us/library/xe53dz5w(v=vs.100).aspx

当同一种语法既能赋值又能创建变量时，每种语言都必须在「用户意图不明确」的时候决定该怎么办。具体来说，
每种语言都得选定：隐式声明如何跟遮蔽互动，以及一个被隐式声明的变量落进哪个作用域。

*   在 Python 里，赋值总是在当前函数的作用域里创建一个变量，哪怕函数外面声明了一个同名的变量。

*   Ruby 靠给局部变量和全局变量定不同的命名规则，避开了一部分歧义。不过，Ruby 里的块（它更像闭包，
    而不是 C 里的「块」）有它自己的作用域，所以这个问题依然存在。Ruby 里赋值时，如果当前块外部存在
    一个同名变量，它就赋值给那个变量。否则，它就在当前块的作用域里创建一个新变量。

*   CoffeeScript 在很多方面沿袭了 Ruby，做法也类似。它明确地不允许遮蔽：规定赋值永远赋给外层作用域
    里的变量（只要存在这么一个），一路向上直到最外层的全局作用域。否则，它就在当前函数作用域里创建
    那个变量。

*   在 JavaScript 里，赋值如果能在任何外围作用域里找到已存在的变量，就修改它。如果找不到，它就隐式地
    在**全局**作用域里创建一个新变量。

隐式声明的主要好处是简单。语法更少，也没有「声明」这个概念要学。用户只管开始赋值，语言自己去弄明白。

像 C 这样更老的、静态类型的语言，则受益于显式声明，因为它给用户一处地方，去告诉编译器每个变量是什么
类型、要给它分配多少存储空间。在一门动态类型、有垃圾回收的语言里，这其实并不是必需的，所以你可以
把声明做成隐式的。这感觉更「脚本范儿」一点，更「你懂我意思」。

但这是个好主意吗？隐式声明有一些问题。

*   用户本意可能是给一个已有变量赋值，但把名字拼错了。解释器不知道这一点，于是就闷头静悄悄地创建了
    某个新变量，而用户想赋值的那个变量还是老值。在 JavaScript 里这事格外恶劣：一个拼写错误会创建
    一个**全局**变量，进而可能干扰别的代码。

*   JS、Ruby 和 CoffeeScript 靠「是否已存在一个同名变量——哪怕在外层作用域里」来判断一次赋值是创建
    新变量还是赋给已有变量。这意味着在某个外围作用域里加一个新变量，可能改变已有代码的含义。原本是
    局部变量的东西，可能无声无息地变成对外层那个新变量的赋值。

*   在 Python 里，你可能**想**给当前函数外面的某个变量赋值，而不是在当前函数里创建一个新变量，但你
    做不到。

随着时间推移，我所知道的那些有隐式变量声明的语言，最终都加上了更多特性和复杂度来处理这些问题。

*   今天，JavaScript 里全局变量的隐式声明被普遍视为一个错误。「严格模式」禁用了它，把它变成编译错误。

*   Python 加了一条 `global` 语句，让你能从函数内部显式地给全局变量赋值。后来，随着函数式编程和嵌套
    函数越来越流行，他们又加了一条类似的 `nonlocal` 语句，用来给外围函数里的变量赋值。

*   Ruby 扩展了它的块语法，允许把某些变量显式声明为块局部的，哪怕外层作用域里存在同名变量。

考虑到这些，我认为「简单」这个论据基本已经站不住脚了。有一种说法是，隐式声明是正确的**默认**，但我个人
觉得那不太有说服力。

我的看法是，隐式声明在很多年前是说得通的，那时候大多数脚本语言高度命令式、代码相当扁平。随着程序员
对深度嵌套、函数式编程和闭包越来越习惯，想要访问外层作用域变量的情况变得越来越普遍。这就让用户更容易
撞上那些棘手的情形：分不清他们到底是打算让这次赋值创建一个新变量，还是复用一个外围的变量。

所以我更偏爱显式声明变量，这也是 Lox 要求这么做的原因。
