10 . 1函数调用

C 风格的函数调用语法你肯定很熟悉，但它的文法比你可能意识到的更微妙。调用通常是指向具名 函数的，比如：

average(1, 2);

但被调用函数的名字其实并不是调用语法的一部分。被调用的那个 东西——也就是被调用者（callee）——可以是任何求值结果为函数的表达式。（好吧，它确实 得是个优先级相当高的表达式，不过用括号就能解决。）例如：

在 Pascal 里，名字就是调用语法的一部分。你只能调用具名函数，或者直接存放在变量里 的函数。

getCallback()();

这里有两个调用表达式。第一对括号的被调用者是 getCallback。但第二次调用把整个 getCallback() 表达式当成了它的被调用者。真正表示函数调用的是跟在表达式后面的那对 括号。你可以把一次调用大致看成一个以 ( 开头的后缀运算符。

这个「运算符」的优先级比任何其他运算符都高，连一元运算符都比不上。于是我们让 unary 规则向上冒泡到一个新的 call 规则，把它安放进文法里。

unary          → ( "!" | "-" ) unary | call ;
call           → primary ( "(" arguments? ")" )* ;

这条规则匹配一个基本表达式，后面跟零个或多个函数调用。如果没有括号，它解析出来的就是 一个光秃秃的基本表达式。否则，每一次调用都由一对括号识别，里面跟一个可选的实参列表。 实参列表的文法是：

这条规则用 * 来允许匹配 fn(1)(2)(3) 这样的连续调用。这样的代码在 C 系语言里不常见， 但在从 ML 派生出来的那个语言家族里很常见。在那里，定义一个接收多个实参的函数的常规 做法，是把它写成一串嵌套函数。每个函数接收一个实参，返回一个新的函数；那个新函数消费 下一个实参，再返回又一个函数，如此继续。最终，所有实参都被消费完之后，最后那个函数完成 整个操作。

这种风格叫作柯里化（currying），得名自哈斯克尔·柯里（Haskell Curry）——就是那位 名字出现在另一门著名函数式语言里的人物。这种风格被直接烙进语言语法里，所以在那里 看起来不像在这儿这么古怪。

arguments      → expression ( "," expression )* ;

这条规则要求至少有一个实参表达式，后面跟零个或多个其他表达式，每个前面都带一个逗号。 为了处理零实参的调用，call 规则本身把整个 arguments 产生式当成可选的。

我承认，对于那个常见得不能再常见的「零个或多个用逗号隔开的东西」模式，这文法看起来比 你预期的更别扭。有些更精巧的元语法能处理得更好，但在我们这套 BNF 以及我见过的许多语言 规范里，它就是这么笨重。

否则，我们解析一个表达式，然后找逗号，表明那个表达式之后还有一个实参。只要每个表达式 之后都能找到逗号，我们就一直这么做。当找不到逗号时，实参列表就一定结束了，我们吃掉那个 预期的右括号。最后，我们把被调用者和那些实参包成一个调用 AST 节点。

10 . 1 . 1最大实参数

目前我们解析实参的那个循环没有任何上界。如果你想调用一个函数并传给它一百万个实参，解析器 也不会有任何问题。我们要限制一下吗？

别的语言各有各的做法。C 标准说，一个符合规范的实现必须支持函数调用至少 127 个实参， 但没说有任何上限。Java 规范说一个方法可以接收不超过 255 个 实参。

如果方法是实例方法，上限就是 254 个实参。因为 this——方法的接收者——就像一个隐式 传给方法的实参，所以它占掉了其中一个名额。

我们的 Lox Java 解释器其实不太需要这个上限，但给实参个数设一个上限会简化第三部分的 字节码解释器。我们希望两个解释器在诸如这种古怪的边角情况下也互相兼容，所以也给 jlox 加上 同样的限制。

首先，我们对被调用者的表达式求值。通常这个表达式只是一个标识符，按名字查找那个函数， 但它也可能是别的东西。然后我们按顺序对每个实参表达式求值，把得到的值存进一个列表。

这又是那种微妙的语义选择。由于实参表达式可能有副作用，它们的求值顺序可能是用户可见的。 即便如此，Scheme 和 C 这样的语言也不规定顺序。这给了编译器为了效率而重排的自由，但也意味 着，如果实参不是按用户预期的顺序求值，用户可能会大感意外。

一旦被调用者和实参都准备好了，剩下的就只是执行这次调用。我们把被调用者转型成一个 LoxCallable，然后在它上面调用 call() 方法。任何能被像函数一样 调用的 Lox 对象，其 Java 表示都会实现这个接口。这自然包括用户定义的函数，也包括类对象， 因为类是被「调用」来构造新实例的。我们不久之后还会为另一个用途使用它。

我在名字前面加个「Lox」，是为了和 Java 标准库自己的 Callable 接口区分开。可惜，好听又 简单的名字都已经被占掉了。

10 . 1 . 4检查元数

另一个问题关系到函数的元数。元数是「一个函数或操作期望多少个实参」这件事的高级说法。 一元运算符元数为一，二元运算符为二，等等。对函数来说，元数由它声明的形参个数决定。

fun add(a, b, c) {
  print a + b + c;
}

这个函数定义了三个形参 a、b 和 c，所以它的元数是三，期望三个实参。那么如果你这样 调用它会怎样：

add(1, 2, 3, 4); // 太多了。
add(1, 2);       // 太少了。

不同语言对这个问题的做法不同。当然，大多数静态类型语言在编译期就检查，参数个数和函数 元数不匹配就拒绝编译。JavaScript 会丢弃你多传的任何实参。如果你传得不够，它就用那个 有点像 null 但又不完全是 null 的魔法值 undefined 填上缺失的形参。Python 更严格。实参 列表太短或太长，它都抛运行时错误。

我觉得后者是更好的做法。传错实参个数几乎总是个 bug，而且我自己就真犯过这个错。既然 如此，实现越早把我的注意力吸引到它越好。所以对 Lox，我们采用 Python 的做法。在调用 被调用者之前，我们检查实参列表的长度是否与被调用者的元数相符。

10 . 2原生函数

理论上我们能调用函数了，可我们还没有函数可调。在讲用户定义的函数之前，正好可以介绍语言 实现中一个至关重要、却常被忽略的方面——原生函数。 这些函数由解释器暴露给用户代码，但它们是用宿主语言（我们的情况是 Java）实现的，而不是用 被实现的语言（Lox）实现的。

有时这些函数也换个称呼：primitive、external function，或者 foreign function。 由于这些函数可以在用户程序运行期间被调用，它们构成了实现的运行时的一部分。很多编程语言 书里对此一带而过，因为这类内容在概念上没什么意思。原生函数大多是些苦力活。

有意思的是，这些函数的两个名字——「原生（native）」和「外来（foreign）」——是反义词。 也许这取决于选词的人站在什么视角。如果你把自己看成「生活」在运行时的实现（我们的情况是 Java）之内，那么用那种语言写的函数就是「原生的」。但如果你抱着自己这门语言的用户的 心态，那么运行时就是用某个别的「外来的」语言实现的。

也可能「原生」指的是底层硬件的机器码语言。在 Java 里，「native」方法指的是用 C 或 C++ 实现、并编译成原生机器码的方法。

但说到让你的语言真的擅长做有用的事，你的实现所提供的原生函数是关键。它们提供了通往那些 基础服务的通道，而所有程序都是用这些服务定义的。如果你不提供访问文件系统的原生函数， 用户要写出一个读取并显示文件的程序可有得苦了。

几乎每种语言都会提供的一个经典原生函数，是把文本打印到 stdout。在 Lox 里，我把 print 做成了内置语句，好让我们在这一章之前的章节里就能把东西显示到屏幕上。

有了函数之后，我们本可以把旧的 print 语法拆掉、换成一个原生函数，让语言更简洁一点。但 那会意味着书前面的例子在后面章节的解释器上跑不了，反之亦然。所以，对这本书，我不动它。

不过，如果你是在为你自己的语言写解释器，可能要考虑一下这件事。

很多语言还允许用户提供自己的原生函数。实现这件事的机制叫作外部函数接口（FFI）、 原生扩展、原生接口，或者诸如此类的名字。它们的好处是，让语言实现者不必为底层平台 支持的每一样能力都提供访问接口。我们不会给 jlox 定义 FFI，但会加一个原生函数，让你看看 它长什么样。

10 . 2 . 1报告时间

等我们到第三部分、开始动手做一个效率高得多的 Lox 实现时，我们会深深关心性能。性能 工作需要测量，而测量又意味着基准测试。基准测试是那些测量「跑一遍解释器的某个角落要 花多少时间」的程序。

我们可以测量「启动解释器、跑基准测试、退出」这一整段时间，但那会加进一大堆开销——JVM 启动时间、操作系统的把戏等等。当然，那些开销确实也有影响，但如果你只是想验证对解释器某个 部分的某项优化，你不会希望那些开销遮住你的结果。

一个更好的办法，是让基准测试脚本自己去测量代码里两个点之间经过的时间。要做到这一点，一个 Lox 程序得能够报时间。现在没法做到——没有对计算机底层时钟的访问，你不可能「从零开始」 实现一个有用的时钟。

所以我们要加上 clock()，一个返回「从某个固定时间点起过了多少秒」的原生函数。连续两次调用 的结果之差，就告诉你两次调用之间过了多久。这个函数定义在全局作用域里，所以我们要确保 解释器能访问它。

在 Lox 里，函数和变量占据同一个命名空间。在 Common Lisp 里，两者各活在自己的世界里。同名的 函数和变量不会打架。你调用这个名字，就查函数；你引用它，就查变量。不过，当你确实想把一个 函数当成一等值来引用时，还是得费一番周折。

理查德·加布里埃尔（Richard P. Gabriel）和肯特·皮特曼（Kent Pitman）造出了 “Lisp-1” 这个 说法，指 Scheme 那种把函数和变量放进同一个命名空间的语言；“Lisp-2” 则指 Common Lisp 那种 把二者隔离开的语言。尽管这两个名字完全不透明，此后它们还是沿用下来了。Lox 是个 Lisp-1。

如果我们想再加别的原生函数——读用户输入、处理文件等等——可以把它们各自做成一个实现 LoxCallable 的匿名类。但对这本书来说，有这一个真的就够了。

我们先别自己定义函数了，让我们的用户接手吧……

10 . 4函数对象

  @Override
  public Object call(Interpreter interpreter,
                     List<Object> arguments) {
    Environment environment = new Environment(interpreter.globals);
    for (int i = 0; i < declaration.params.size(); i++) {
      environment.define(declaration.params.get(i).lexeme,
          arguments.get(i));
    }

形参是函数的核心，尤其是函数会封装自己的形参这一点——函数之外的任何代码都看不见它们。 这意味着每个函数都有自己的环境，用来存放那些变量。

更进一步，这个环境必须是动态创建的。每次函数调用都有自己的环境。否则递归就坏了。 如果同时有多个对同一个函数的调用在进行，每一个都需要自己的环境，尽管它们全都是对同一个 函数的调用。

比如说，下面是一种拐弯抹角的数到三的办法：

  if (n > 1) count(n - 1);
  print n;
}

这就是为什么我们在每次调用时创建新环境，而不是在函数声明时。前面那个 call() 方法 就是这么做的。调用一开始，它创建一个新环境。然后它让形参列表和实参列表齐步前进。每一对上， 它创建一个以形参命名的新变量，并把它绑定到实参的值上。

要把数据传进函数，所需要的就这么多。通过在执行函数体时使用不同的环境，对同一个函数的、 代码相同的调用可以产生不同的结果。

10 . 5Return 语句

我们可以通过传形参把数据送进函数，却没办法把结果取出来。如果 Lox 是像 Ruby 或 Scheme 那样面向表达式的语言，函数体就会是一个表达式，它的值隐式地就是函数 的结果。但在 Lox 里，函数体是一列不产生值的语句，所以我们需要专门的语法来产出一个结果。 换句话说，就是 return 语句。我敢说你已经猜到文法了。

返回值是可选的，为的是支持从一个不返回有用值的函数里提前退出。在静态类型语言里， 「void」函数不返回值，非 void 的返回。由于 Lox 是动态类型的，不存在真正的 void 函数。 编译器没法阻止你从没有 return 语句的函数调用里取走返回值。

10 . 5 . 1从调用中返回

解释一条 return 语句很棘手。你可以从函数体内的任何地方返回，甚至从深深嵌在其他语句 里面的地方返回。return 执行时，解释器需要从它当前所处的任何上下文里一路跳出去，让那次 函数调用完成，像是某种被打了鸡血的控制流结构。

    print n;

10 . 6局部函数与闭包

我们的函数功能相当齐备，但还有一个洞要补。事实上这个缺口足够大，我们会把下一章的 大部分时间花在封堵它上，不过我们可以在这里先起步。

LoxFunction 的 call() 实现会创建一个新环境，用来绑定函数的形参。我给你看那段代码时， 一带而过了某个要紧的问题：这个环境的父是什么？

目前，它总是 globals，也就是最顶层的全局环境。这样，如果一个标识符没有在函数体自身 内部定义，解释器就能到函数外面的全局作用域里去找它。在斐波那契那个例子里，解释器就是这样 能在函数自己的体内查到对 fib 的递归调用的——fib 是一个全局变量。

但别忘了，在 Lox 里，函数声明允许出现在任何能绑定名字的地方。这既包括一个 Lox 脚本的顶层，也包括块内部或其他函数内部。Lox 支持局部函数，也就是定义在另一个函数里面、 或者嵌套在某个块里面的函数。

考虑这个经典例子：

fun makeCounter() {
  var i = 0;
  fun count() {
    i = i + 1;
    print i;
  }

  return count;
}

var counter = makeCounter();
counter(); // "1".
counter(); // "2".

这里，count() 用到了 i，而 i 是在包含它的那个函数 makeCounter() 里、在它自己之外 声明的。makeCounter() 返回对 count() 函数的一个引用，然后它自己的函数体就彻底执行完毕 了。

与此同时，顶层代码调用返回的那个 count() 函数。这会执行 count() 的函数体，给 i 赋值 并读取它，尽管定义 i 的那个函数早就退出了。

这种数据结构叫作闭包，因为它把函数声明处周围那些变量「闭合」 住并保留了下来。闭包从 Lisp 早期就存在了，语言黑客们也想出了各式各样的实现办法。对 jlox， 我们采用最简单可行的做法。在 LoxFunction 里，我们加一个字段来存放一个环境。

习题

  1. 我们的解释器仔细检查传给函数的实参个数是否与它所期望的形参个数相符。由于这个检查 是在运行时、每次调用时都做，它有性能代价。Smalltalk 的实现没有这个问题。为什么没有？

  2. Lox 的函数声明语法做了两件相互独立的事：它创建一个函数，还把它绑定到一个名字上。这 在你确实想给函数关联一个名字的常见情形里提升了易用性。但在函数式风格的代码里，你常常 只是想创建一个函数，立刻把它传给另一个函数，或者返回出去。那种情况下，它不需要名字。

    鼓励函数式风格的语言通常都支持匿名函数或 lambda——一种不把函数绑定到名字上 的表达式语法。给 Lox 加上匿名函数语法，让下面这段能跑起来：

    fun thrice(fn) {
  for (var i = 1; i <= 3; i = i + 1) {
    fn(i);
  }
}

thrice(fun (a) {
  print a;
});
// "1".
// "2".
// "3".
