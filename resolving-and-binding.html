哎呀，不好！我们的语言实现进水了！很久以前，我们加入变量和块的时候， 作用域还绷得又紧又严实。可后来我们加入闭包时，我们这个原本滴水不漏的 解释器上破了个洞。真实的程序大多不太可能从这个洞里漏出去，但身为语言实现者，我们 立下过神圣誓言：哪怕在语义最阴暗的角落里，也要在乎正确性。

这一整章，我们都会用来探究那个漏洞，然后小心翼翼地把它补上。在此过程中，我们会更 严谨地理解 Lox 以及承袭 C 传统的其他语言所用的词法作用域。我们还有机会认识语义 分析（semantic analysis）——一种强大的技术，能无需运行代码，就从用户的源码里提炼 出含义。

11 . 1静态作用域

快速回顾一下：Lox 和大多数现代语言一样，采用词法作用域。这意味着，光读一读程序的 文本，你就能弄清一个变量名指的是哪个声明。例如：

var a = "outer";
{
  var a = "inner";
  print a;
}

这里我们知道，被打印的 a 是上一行声明的那个变量，而不是全局那个。运行程序并不会 ——也不可能——改变这一点。作用域规则属于语言的静态语义，这也是它又叫静态 作用域的原因。

我一直没把这些作用域规则明说出来，但现在是时候讲究一下精确性了：

这比起真正的语言规范，还差得远呢。那些规范文档必须写得如此明确，以至于哪怕是个火星 人、或者一个存心使坏的程序员，只要照着规范的条文来做，也被迫实现出正确的语义。

当一门语言可能被好几家互相竞争的公司各自实现，而这些公司又想让自家产品跟别家不兼容、 好把客户锁死在自己的平台上时，这种精确性就很重要了。好在写这本书，我们可以不去理会 这类见不得光的勾当。

一个变量用法，指的是在包住该用法的那个最内层作用域里、出现于该用法之前、名字相同的 那个声明。

这句话里能拆的东西不少：

  • 我说「变量用法」而不说「变量表达式」，是为了把变量表达式和赋值都涵盖进来。后面 「该变量所用到的那个表达式」同样如此。

  • 「出现于它之前」指的是在程序文本里出现在之前。

    var a = "outer";
{
  print a;
  var a = "inner";
}

    这里，被打印的那个 a 是外层那个，因为它出现在使用它的 print 语句之前。大多数情况下，在直线型的代码里，文本上排在前面的 声明，时间上也会先于使用发生。但这并不总是成立。我们将会看到，函数可能把一整块 代码推迟执行，使得它动态的时序执行不再与静态的文本顺序相对应。

    在 JavaScript 里，用 var 声明的变量会被隐式地「提升」（hoist）到块的开头。块里对 这个名字的任何使用都会指向那个变量，哪怕那次使用出现在声明之前。当你在 JavaScript 里写下：

    {
  console.log(a);
  var a = "value";
}

    它的行为等同于：

    {
  var a; // 提升。
  console.log(a);
  a = "value";
}

    这意味着，在有些情况下，你会在一个变量的初始化器尚未运行之前就读到它——一个恼人的 bug 来源。后来语言为此加了一种声明变量的替代语法 let，来对付这个问题。

  • 「最内层」这个词儿，是为了我们的老朋友——遮蔽。包围作用域里可能不止一个变量 用了同一个名字，比如：

    var a = "outer";
{
  var a = "inner";
  print a;
}

    我们的规则靠「最内层的作用域胜出」来消解这种情况的歧义。

既然这条规则完全没提任何运行时行为，那就意味着：在程序的整个执行过程中，一个变量表达式 永远指向同一个声明。到目前为止，我们的解释器大体上正确地实现了这条规则。可当我们 加入闭包时，一个错误悄悄溜了进来。

var a = "global";
{
  fun showA() {
    print a;
  }

  showA();
  var a = "block";
  showA();
}

在你把它敲进去、运行之前，先想清楚你认为它应该打印出什么。

我知道，这是个彻头彻尾的病态、生造出来的程序。它就是怪。没有哪个正常人会写这样的 代码。唉，可要是你在编程语言这行混得够久，你生命中超出你预期的一大块时间，都会花在 对付这种畸形的代码片段上。

好……想好了吗？如果你熟悉其他语言里的闭包，你会指望它打印两遍 “global”。第一次调用 showA() 肯定应该打印 “global”，因为我们那时甚至还没走到内层 a 的声明。而且按照 我们那条「一个变量表达式永远解析到同一个变量」的规则，这就意味着第二次调用 showA() 也应该打印同样的东西。

可惜，它打印出来的是：

global
block

我要强调一下：这个程序自始至终没有重新给任何变量赋值，而且只含一条 print 语句。可 不知怎的，那条针对一个从未被赋值的变量的 print 语句，却在不同的时间点打印出了两个 不同的值。我们肯定在哪儿弄坏了什么东西。

11 . 1 . 1作用域与可变环境

在我们的解释器里，环境是静态作用域的动态化身。这两者大体上是同步的——我们进入一个新 作用域时就创建一个新环境，离开作用域时就把它丢弃。我们对环境还执行另一种操作：在某个 环境里绑定一个变量。我们的 bug 正出在这里。

我们来一步步走一遍那个有问题的例子，看看每一步的环境长什么样。首先，我们在全局作用域里 声明 a。

这样我们就得到了一个只含一个变量的环境。接着，我们进入块，执行 showA() 的声明。

我们为这个块得到了一个新环境。在它里面，我们声明了一个名字 showA，绑定到我们为表示 这个函数而创建的 LoxFunction 对象上。那个对象有一个 closure 字段，捕获了函数被声明 时所处的环境，所以它有一个指回该块环境的引用。

现在，我们调用 showA()。

解释器为 showA() 的函数体动态创建了一个新环境。这个环境是空的，因为那个函数没有声明任何 变量。该环境的父环境是这个函数的闭包——也就是外层的块环境。

在 showA() 的函数体内部，我们打印 a 的值。解释器沿着环境链一路查找这个值。它一直 走到全局环境，才在那里找到它并打印出 "global"。很好。

接下来，我们声明第二个 a，这次是在块里面。

它跟 showA() 处在同一个块——同一个作用域里——所以它进了同一个环境，而这个环境也正是 showA() 的闭包所指的那个环境。有趣的地方到了。我们再次调用 showA()。

我们又一次为 showA() 的函数体创建了一个新的空环境，把它跟那个闭包接好，然后运行函数体。 当解释器沿着环境链查找 a 时，它现在会发现块环境里那个新的 a。嘘。

当初实现环境时，我选了一种方式，本希望它能契合你对作用域的那种朴素直觉。我们倾向于 把块里的所有代码都看作处在同一个作用域里，所以我们的解释器就用单个环境来表示它。每个 环境都是一张可变的哈希表。当一个新的局部变量被声明时，它会被加进该作用域已有的那个环境里。

这种直觉，就像人生中许多直觉一样，并不十分正确。一个块并不必然处处都是同一个作用域。 想想看：

{
  var a;
  // 1.
  var b;
  // 2.
}

在标了 1 的那一行处，作用域里只有 a。到标了 2 的那一行处，a 和 b 都在了。如果你把一个 「作用域」定义为一组声明，那么这两处显然不是同一个作用域——它们所含的声明并不一样。这 就好像每条 var 语句都把块劈开成了两个独立的作用域：变量声明 之前的那个，以及之后、包含这个新变量的那个。

有些语言把这种劈开显式化了。在 Scheme 和 ML 里，当你用 let 声明一个局部变量时，你同时 也划定了新变量在作用域内的后续代码范围。那里并不存在一个隐式的「块里剩下的部分」。

可在我们的实现里，环境确实表现得像整个块就是同一个作用域，只不过是个随时间变化的作用域。 闭包不喜欢这样。当一个函数被声明时，它捕获的是对当前环境的一个引用。这个函数本应捕获 环境的一份冻结快照——函数被声明那一刻环境的样子。但事实上，在 Java 代码里，它拿到的 是对那个实际可变的环境对象的引用。当后来有一个变量被声明到该环境所对应的那个作用域里时， 闭包就看见了那个新变量，尽管那个声明并不在函数之前。

11 . 1 . 2持久化环境

有一种编程风格会用到所谓的持久化数据结构（persistent data structures）。跟你在命令式 编程里熟悉的那些软塌塌的数据结构不同，持久化数据结构永远不能被直接修改。相反，对既有结构 做的任何一次「修改」，都会产生一个崭新的对象，里面装着原来的全部 数据再加上这次修改。原对象保持不变。

这听起来好像每次操作都要复制整个结构，会白白浪费大量内存和时间。可实际上，持久化数据结构 在不同「副本」之间共享了绝大部分数据。

如果我们把这种技术用到 Environment 上，那么你每声明一个变量，都会返回一个新的环境， 里面含有此前声明的所有变量再加上这个新名字。声明一个变量就会完成那次隐式的「劈开」：变量 声明之前有一个环境，之后有一个：

闭包保留一个引用，指向函数被声明时生效的那个 Environment 实例。既然在该块里后来做的任何 声明都会产生新的 Environment 对象，那么闭包就不会看见那些新变量，我们的 bug 也就修好了。

这确实是解决这个问题的一种正当办法，也是 Scheme 解释器里实现环境的经典做法。我们也可以对 Lox 这么做，但那意味着要回头改动一大堆现有代码。

我就不拖着你走那条路了。我们保持环境的表示方式不变。与其让数据变得更静态化，我们不如把 静态的作用域解析直接烘焙进访问操作本身。

11 . 2语义分析

每次求值一个变量表达式时，我们的解释器都会解析这个变量——追查它指的是哪个声明。如果 那个变量被裹在一个运行上千次的循环里，它就会被重新解析上千次。

我们知道，静态作用域意味着一个变量用法永远解析到同一个声明，而这个声明光靠读文本就能确定。 既然如此，我们为什么每次都动态地去做呢？这么做不仅捅出了那个导致恼人 bug 的洞，还毫无必要 地拖慢了速度。

更好的做法是每个变量用法只解析一次。写一段代码，检视用户的程序，找出提到的每一个变量， 并弄清每一个指的是哪个声明。这个过程就是语义分析的一个例子。语法解析器只能告诉你一个 程序在语法上是否正确（一次语法分析），而语义分析则更进一步，开始弄清程序的各个部分究竟 是什么意思。在这个例子里，我们的分析会解析变量的绑定关系。我们不只知道某个表达式是 个变量，还知道它是哪个变量。

存储变量与其声明之间的绑定关系，有很多种办法。等我们做到 Lox 的 C 解释器时，会有一种高效 得多的局部变量存储与访问方式。但对 jlox，我想把对现有代码库造成的连带损伤降到最小。我可 不想把一大堆基本还不错的代码扔掉。

所以，我们会用一种能最大限度利用现有 Environment 类的方式来存储解析结果。回想一下那个有 问题的例子里，对 a 的访问是怎么解释的。

在第一次（正确的）求值里，我们查看了环境链里的三个环境，才找到 a 的全局声明。之后，当 内层的 a 后来在块作用域里被声明时，它遮蔽了全局那个。

下一次查找沿着环境链走，在第二个环境里找到了 a，就在那儿停下。每个环境都对应一个 声明了变量的词法作用域。如果我们能保证一次变量查找永远走过环境链里相同数量的链接， 那就能保证它每次都找到同一个作用域里的同一个变量。

要「解析」一个变量用法，我们只需算出所声明的变量在环境链里隔着多少个「跳」。有意思的问题是 什么时候来做这个计算——或者换个说法，我们要把这段计算的代码塞进解释器实现的哪里？

既然我们计算的是一个基于源码结构的静态属性，那么显而易见的答案就是放在语法解析器里。那是 它传统的归属地，也是我们后来在 clox 里会放它的地方。在这里这么做也行得通，可我想找个由头 给你展示另一种技术。我们会把作用域解析器写成一个独立的 pass。

11 . 2 . 1一趟变量作用域解析

在语法解析器产出语法树之后、解释器开始执行它之前，我们会把树遍历一趟，解析出其中所有的变量。 在语法解析和执行之间加上额外的 pass 是常见做法。如果 Lox 有静态类型，我们可以在那儿插进一个 类型检查器。优化也常常像这样用独立的 pass 来实现。基本上，任何不依赖只在运行时才有的状态的 工作，都能以这种方式来完成。

我们这趟变量作用域解析，运作起来有点像一个小小的解释器。它遍历这棵树，访问每一个节点，但 静态分析跟动态执行是不同的：

  • 没有副作用。 当静态分析访问一条 print 语句时，它并不会真的打印任何东西。对原生函数 的调用、或者其他伸向外部世界的操作，都被替换成空桩，不产生任何效果。

  • 没有控制流。 循环只会被访问一次。if 语句的两个分支都会被 访问。逻辑运算符不会被短路。

变量作用域解析把每个节点都碰且只碰一次，所以它的性能是 O(n)，其中 n 是语法树节点的 数量。更精细的分析复杂度可能更高，但大多数都被精心设计成线性的、或者离线性不远。如果你的 编译器随着用户程序变大而指数级变慢，那可是很丢人的失手。

由于作用域解析器需要访问语法树里的每一个节点，它实现了我们现有的那套访问者抽象。在解析 变量这件事上，只有少数几类节点值得关注：

  • 块语句为它所包含的语句引入一个新作用域。

  • 函数声明为它的函数体引入一个新作用域，并在这个作用域里绑定它的形参。

  • 变量声明把一个新变量加进当前作用域。

  • 变量表达式和赋值表达式需要解析它们的变量。

其余的节点不做任何特别的事，但我们仍然需要为它们实现 visit 方法，好钻进它们的子树里。尽管 一个 + 表达式本身没有任何变量需要解析，它的任一操作数却可能有。

这个字段追踪的，是当前、呃，处于作用域内的那座作用域栈。栈里的每个元素是一个 Map，代表 单独一个块作用域。键跟在 Environment 里一样，是变量名。值是布尔值，原因我很快会解释。

11 . 3 . 2解析变量声明

解析一个变量声明，就是往当前最内层作用域的 map 里加一个新条目。看着挺简单，可我们得跳一段 小小的舞步。

com\craftinginterpreters\lox\Resolver.java
加在 visitBlockStmt() 之后
  @Override
  public Void visitVarStmt(Stmt.Var stmt) {
    declare(stmt.name);
    if (stmt.initializer != null) {
      resolve(stmt.initializer);
    }
    define(stmt.name);
    return null;
  }
com\craftinginterpreters\lox\Resolver.java, 加在 visitBlockStmt() 之后

我们把绑定拆成两步——先声明、后定义——是为了处理像这样的古怪边角情况：

var a = "outer";
{
  var a = a;
}

当一个局部变量的初始化器引用了一个跟正在声明的变量同名的变量时，会发生什么？我们有几个选项：

  1. 先运行初始化器，再把新变量放进作用域。 这样一来，新的局部 a 会被初始化为 “outer”， 也就是那个全局变量的值。换句话说，上面这段声明会被脱糖成：

    var temp = a; // 运行初始化器。
var a;        // 声明这个变量。
a = temp;     // 初始化它。

  2. 先把新变量放进作用域，再运行初始化器。 这意味着你可以在一个变量被初始化之前就观察到 它，所以我们得弄清它那时会是什么值。大概是 nil。这意味着新的局部 a 会被重新初始化 成它自身的隐式初始值 nil。这时脱糖出来是这样的：

    var a; // 定义这个变量。
a = a; // 运行初始化器。

  3. 把「在初始化器里引用该变量」变成错误。 只要初始化器提到了正在初始化的那个变量， 就让解释器在编译期或运行时失败。

前两个选项里，有哪一个看起来像是用户真的想要的？遮蔽很少见，而且往往就是个错误， 所以拿被遮蔽变量的值来初始化那个遮蔽变量，不大可能是故意的。

第二个选项更没用。那个新变量永远会是 nil 值。按名字提它从来就没有任何意义。你大可以 直接写个 nil。

既然前两个选项很可能掩盖用户的错误，我们就选第三个。而且，我们要把它做成编译期错误而不是 运行时错误。这样一来，用户在任何代码跑起来之前就会收到提醒。

为了做到这一点，我们在访问表达式时，需要知道自己是不是正处在某个变量的初始化器里。我们 通过把绑定拆成两步来做到这一点。第一步是声明它。

com\craftinginterpreters\lox\Resolver.java
加在 endScope() 之后
  private void declare(Token name) {
    if (scopes.isEmpty()) return;

    Map<String, Boolean> scope = scopes.peek();
    scope.put(name.lexeme, false);
  }
com\craftinginterpreters\lox\Resolver.java, 加在 endScope() 之后

声明把变量加进最内层的作用域，好让它遮蔽任何外层同名变量，也好让我们知道这个变量存在。 我们通过把它的名字绑定到作用域 map 里的 false，来标记它「还没准备好」。作用域 map 里跟 某个键关联的值，表示我们是否已经完成了解析那个变量的初始化器。

声明完变量之后，我们在同一个作用域里解析它的初始化器表达式——此时这个新变量已经存在，但还 不可用。一旦初始化器表达式解析完毕，这个变量就准备好正式上场了。我们通过定义它来做到 这一点。

com\craftinginterpreters\lox\Resolver.java
加在 declare() 之后
  private void define(Token name) {
    if (scopes.isEmpty()) return;
    scopes.peek().put(name.lexeme, true);
  }
com\craftinginterpreters\lox\Resolver.java, 加在 declare() 之后

我们把作用域 map 里那个变量的值设成 true，标记它已完全初始化、可供使用了。它活了！

首先，我们检查这个变量是不是正在它自己的初始化器里被访问。作用域 map 里的那些值就是在这儿 派上用场的。如果这个变量存在于当前作用域、但它的值是 false，那就意味着我们已经声明了它、 却还没定义它。我们报告这个错误。

    for (int i = scopes.size() - 1; i >= 0; i--) {

这段代码看着很像 Environment 里求值变量时的那段，这是有道理的。我们从最内层作用域开始，向 外一层层找，在每个 map 里找相匹配的名字。如果找到了这个变量，我们就解析它，并传入一个数： 从当前最内层作用域到找到该变量的那个作用域之间隔了多少个作用域。所以，如果变量是在当前 作用域里找到的，我们传 0。如果它在紧挨着的外层作用域里，就传 1。道理你懂的。

如果我们走遍所有的块作用域都没找到这个变量，我们就把它搁置不解析，并假定它是全局的。稍后 我们会讲到那个 resolve() 方法的实现。眼下，我们继续把其余的语法节点啃完。

这个方法沿着父链向上走固定数量的跳，返回那里的环境。拿到它之后，getAt() 就只是返回那个 环境 map 里该变量的值。它甚至连变量在不在那儿都不必检查——我们知道它一定在，因为作用域 解析器早先已经找到过它了。

解释器假定变量就在那张 map 里，这种方式让人感觉像在盲飞。解释器的代码信任作用域解析器尽到 了职责、正确地解析了变量。这意味着这两个类之间有着紧密的耦合。在作用域解析器里，每一行触及 作用域的代码，都必须在解释器里有一行精确对应的、用于修改环境的代码。

这种耦合我是亲身领教过的，因为我在给这本书写代码时，就撞上了几个微妙的 bug——作用域 解析器和解释器的代码稍微没对上。把它们揪出来很费劲。让这件事变得更容易的一个办法，是让 解释器显式地断言——用 Java 的 assert 语句或者别的什么校验工具——它期望作用域解析器已经履行 的那份契约。

我们还可以更进一步，对那些未必错误、但大概没用的代码报告警告。比如，如果你在一条 return 语句之后有不可达的代码、或者有一个值从未被读取过的局部变量，许多 IDE 都会发出警告。 所有这些都是相当容易加到我们这趟静态访问里的，或者拆成独立的 pass。

  3. 扩展作用域解析器，让它在某个局部变量从未被使用时报告一个错误。

  4. 我们的作用域解析器算出了变量是在哪个环境里被找到的，但它在那张 map 里仍然是按名字 查找的。一种更高效的环境表示方式会把局部变量存在一个数组里，按索引来查找它们。

    扩展作用域解析器，给在一个作用域里声明的每个局部变量关联一个唯一索引。解析一次变量访问 时，既查出变量所在的作用域、又查出它的索引，并把两者都存下来。在解释器里，用这个来按 索引快速访问变量，而不是用 map。
