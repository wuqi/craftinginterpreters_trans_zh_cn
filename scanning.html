扫描

要下口就下大口。凡是值得做的事，就值得做过头。

罗伯特·A. 海因莱因，《时间足够你爱》

任何编译器或解释器的第一步都是扫描。扫描器把原始源码 当成一串字符吃进来，再把它们归组成一串我们称为词法单元的块。它们就是构成语言语法的 那些有意义的「词」和「标点」。

这些年，这活儿时而叫「扫描」，时而叫「词法分析」（lexing）。早在计算机还跟房车 一样大、内存却比你的手表还少的年代，有些人用「扫描器」专指那段从磁盘读原始源码字符、 缓冲进内存的代码，而「词法分析」则是后面的阶段——拿这些字符干正事。

如今把源文件读进内存是件小事，所以在编译器里很少单独成一个阶段。也正因为如此， 这两个词基本可以互换。

扫描对我们来说也是个好的起点，因为这代码不难——基本上就是一个自以为很了不起的 switch 语句。后面要啃更有意思的材料之前，先拿它热热身正合适。本章结束时， 我们会拥有一个功能齐全、速度飞快的扫描器：给它任意一段 Lox 源码，它能吐出词法单元， 下一章我们就把这些词法单元喂给解析器。

要是想跟你的解释器更私密地聊几句，也可以交互式地跑它。不带任何参数启动 jlox， 它会把你丢进一个提示符，你可以一行一行地输入并执行代码。

交互式提示符也叫「REPL」（读音像「rebel」，只不过多一个 p）。这名字来自 Lisp—— 在那儿实现一个 REPL，简单到只要把几个内置函数包在一个循环里：

(print (eval (read)))

从最里层的调用往外看：你读（R）一行输入，求值（E）它，打印（P）结果， 然后循环（L）回去再来一遍。

    }

4 . 1 . 1错误处理

搭框架的同时，还有一块关键的基础设施：错误处理。教科书有时会一带而过， 因为这更偏实际问题而不是正式的计算机科学问题。但如果你在意造出一门好用的语言， 那优雅地处理错误就至关重要。

我们的语言为对付错误所提供的工具，在它的用户界面里占了很大比重。用户代码正常跑着的时候， 他们根本不会想起我们的语言——脑子里全是他们自己的程序。通常只有出事的时候， 他们才会注意到我们的实现。

这时候，就得由我们来把用户需要的信息全给他，让他明白出了什么事， 再温和地把他引回他想去的地方。要做好这件事，就得在整个解释器的实现里都想着错误处理—— 从现在开始。

话虽如此，就这个解释器来说，我们要造的东西光剩个骨架。我很想聊聊交互式 调试器、静态分析器之类的好玩东西，但笔墨就那么多。

这可没什么帮助。我们至少得指出是哪一行。更好一点的做法是给出起始列和结束列，好让他们知道是 行内哪里。比那更好的是把出错那行显示给用户，比如：

Error: Unexpected "," in argument list.

    15 | function(first, second,);
                               ^-- Here.

我很想在这本书里实现个那样的东西，但老实说那是一大堆脏兮兮的字符串操作代码。 对用户很有用，但在书里读起来一点都不好玩，技术上也没什么意思。所以我们只留行号。 在你自己的解释器里，请照我说的做，别照我做的做。

我把错误报告挪到这儿来，而不是塞进扫描器以及可能出错的其他阶段，另一个原因是要提醒你： 把产生错误的代码和报告错误的代码分开，是好的工程实践。

前端会有各个阶段去发现错误，但「怎么呈现给用户」其实不是它们的活。在一个功能齐全的 语言实现里，你很可能会用多种方式来显示错误：打到 stderr、显示在 IDE 的错误窗口、 记进日志文件等等。你不想让这些代码糊得到处都是，糊满你的扫描器和解析器。

理想情况下，我们该有个真正的抽象——某种「错误报告器」接口， 传给扫描器和解析器，这样就能替换不同的报告策略。在我们这个简单的解释器里我没这么做， 但我至少把错误报告的代码挪进了另一个类。

我最初实现 jlox 的时候确实做了这么个东西。后来我把它拆了，因为对于这本书里这个 最小化的解释器来说，它显得过度设计了。

有了这点简陋的错误处理，应用外壳就绪了。等我们有了带 scanTokens() 方法的 Scanner 类，就能开始跑了。在那之前，我们先把「词法单元到底是什么」说得更精确一点。

4 . 2 . 1词法单元类型

关键字是语言语法形状的一部分，所以解析器里常有这种代码：「如果下一个词法单元是 while 就……」这意味着解析器不光要知道它拿到了某个标识符的词素，还得知道那是个 保留字，以及是哪一个关键字。

解析器当然可以直接拿原始词素比字符串来给词法单元分类，但那又慢又难看。所以我们在 认出某个词素的同时，也记下它代表的是哪一类词素。每个关键字、运算符、标点符号、 字面量类型，我们都准备一个专门的类型。

说到底，字符串比较最后还是在逐个看字符，那不正是扫描器的活吗？

4 . 2 . 2字面量值

字面量值也有词素——数字啦字符串啦这类。既然扫描器本来就得逐个走过字面量里的字符才能 正确认出它，那它也可以顺手把这个值的文本表示，转换成之后解释器要用的那个活生生的 运行时对象。

4 . 2 . 3位置信息

早先我还在大肆宣扬错误处理的时候，我们看到得告诉用户错误发生在哪里。位置追踪从 这儿开始。在这个简单的解释器里，我们只记词法单元出现在哪一行，但更精巧的实现还会 带上列号和长度。

有些词法单元的实现把位置存成两个数：一个是从源文件开头到词素开头的偏移量， 另一个是词素的长度。扫描器反正也得知道这些，所以算出来不花额外代价。

偏移量以后可以回头查源文件、数前面有几个换行符，换算成行列位置。听起来很慢， 确实很慢。但你只需要在真的要给用户显示行列的时候才做这件事。大多数词法单元一辈子 都不会出现在错误消息里。对它们来说，事先花在算位置上的时间越少越好。

我们把这些数据统统装进一个类里。

com\craftinginterpreters\lox\Token.java
新建文件
package com.craftinginterpreters.lox;

class Token {
  final TokenType type;
  final String lexeme;
  final Object literal;
  final int line; 

  Token(TokenType type, String lexeme, Object literal, int line) {
    this.type = type;
    this.lexeme = lexeme;
    this.literal = literal;
    this.line = line;
  }

  public String toString() {
    return type + " " + lexeme + " " + literal;
  }
}

现在我们有了一个结构足够完整、对解释器后续所有阶段都有用的对象。

4 . 3正则语言与正则表达式

既然已经知道要产出什么，那就……产出吧。扫描器的核心是一个循环。从源码的第一个字符开始， 扫描器弄清楚这个字符属于哪个词素，然后吃掉它，以及跟在后面、属于同一个词素的那些字符。 到这个词素末尾，它就吐出一个词法单元。

然后它回到开头再干一遍，从源码里下一个字符重新开始。它就这么一直吃下去，偶尔，呃， 拉出一些词法单元，直到读完整个输入。

词法分析鳄。

循环里那段「看一眼几个字符，判断它是哪种词素『匹配上了』」的部分，听起来可能有点熟。 如果你懂正则表达式，你可能会想：给每种词素都定义一条正则，用它们来匹配字符。比如 Lox 对标识符（变量名之类）的规则跟 C 一样。下面这条正则就能匹配一个：

[a-zA-Z_][a-zA-Z_0-9]*

你要是真想到用正则表达式去认这些词素，说明你的直觉相当敏锐。决定一门语言如何把 字符归组成词素的那套规则，叫做它的词法文法。在 Lox 里，和大多数编程语言一样， 这套文法的规则简单到足以把这门语言的词法文法归入**正则语言**。这里那个「正则」 和正则表达式里的「正则」是同一个意思。

我很难过要这么一带而过这套理论，尤其在我觉得 乔姆斯基层级 和 有限状态机 都那么有意思的时候。但老实说，别的书比我讲得好。 编译原理：原理、技术与工具（人称「龙书」）是这方面的权威参考。

你完全可以用正则精确识别出 Lox 的所有词素，这底下也堆着一大堆有意思的理论， 解释为什么行、那意味着什么。像 Lex 或 Flex 这类工具就是专门为让你干这事而设计的—— 把一把正则丢给它们，它们就把一个完整的扫描器还给你。

Lex 是迈克·莱斯克和埃里克·施密特做的。对，就是后来当上 Google 执行董事长的那个 埃里克·施密特。我不是说编程语言是通往财富和名声的必由之路，但我们中间至少能数出 一位亿万富豪。

既然我们的目标是搞懂扫描器到底怎么做到的，这活儿我们就不外包了——接下来得自己动手。

4 . 6 . 2数字字面量

4 . 7保留字与标识符

我们的扫描器快完工了。词法文法里剩下要实现的，就只有标识符和它的近亲——保留字。 你可能会想，我们可以用处理 <= 这种多字符运算符的同样办法去匹配 or 这样的关键字。

case 'o':
  if (match('r')) {
    addToken(OR);
  }
  break;

想想如果用户把一个变量命名为 orchid 会怎样。扫描器会看到头两个字母 or， 立刻吐出一个 or 关键字词法单元。这就引出了一条重要的原则，叫最长匹配。 当词法文法的两条规则都能匹配扫描器正在看的这段代码时，谁匹配的字符多谁赢。

这条规则的意思是，如果我们能把 orchid 匹配成标识符、把 or 匹配成关键字， 那前者赢。这也是为什么我们之前默认把 <= 扫成一个完整的 <= 词法单元， 而不是一个 < 后跟一个 =。

看看这段难缠的 C 代码：

---a;

它合法吗？这取决于扫描器怎么切词素。万一扫描器是这么看的：

- --a;

那就能解析了。但那会要求扫描器知道周边代码的语法结构，把事情搅得比我们想要的更乱。 所以最长匹配规则说，它总是会被扫成：

-- -a;

哪怕这么扫会导致后面在解析器里出现语法错误，它也照样这么扫。

设计说明：隐式分号

今天程序员在语言的选择上被宠坏了，对语法也变得挑剔起来。他们希望自己的语言看起来 干净、现代。几乎每门新语言都会刮掉的一层语法地衣（有些古老语言比如 BASIC 从来没有过），就是拿 ; 当显式的语句终止符。

取而代之的是，他们在说得过去的地方，就把换行当作语句终止符。「说得过去」这部分才是 难点。虽然大多数语句都单独占一行，但有时候你需要把一条语句摊到好几行上。 这些混在中间的换行就不该被当成终止符。

换行该被忽略的那些显而易见的情况，大多很好检测，但还是有几个难缠的：

  • 换行后跟着返回值：

    if (condition) return
"value"

    “value” 是被返回的值，还是说这是一条没有值的 return 语句，外加一条含字符串字面量的 表达式语句？

  • 换行后跟着一个带括号的表达式：

    func
(parenthesized)

    这是对 func(parenthesized) 的调用，还是两条表达式语句，一条是 func，另一条是 带括号的表达式？

  • 换行后跟着一个 -：

    first
-second

    这是 first - second（一个中缀减法），还是两条表达式语句，一条是 first， 另一条是对 second 取负？

在这些例子里，把换行当分隔符或不当分隔符都能产出合法代码，但可能不是用户想要的那段代码。 各个语言用来决定哪些换行算分隔符的规则，简直多得让人不安。举几个：

  • Lua 完全忽略换行，但它小心地设计语法，使得多数情况下根本不需要语句之间的分隔符。 这是完全正当的：

    a = 1 b = 2

    Lua 是靠要求 return 语句必须是块里的最后一条语句来躲开 return 问题的。如果在 return 之后、关键字 end 之前还有值，那这个值必须是给 return 的。至于另外 两种情况，它们允许显式的 ;，并期待用户真的去用。实践中这几乎从不发生，因为没人 会写一条带括号或取负的表达式语句。

  • Go 在扫描器里处理换行。如果换行出现在某几种已知可能结束语句的词法单元类型 之后，这个换行就被当成分号；否则就忽略。Go 团队提供了一个规范的代码格式化工具 gofmt，而且生态圈对它的使用相当狂热，这就保证了惯用风格的代码能很好地配合 这条简单规则。

  • Python 把所有换行都当作有意义的，除非在行尾用反斜杠显式续行。不过，只要还 处在某对括号（()、[] 或 {}）里面，任何位置的换行都会被忽略。惯用风格 强烈偏好后者。

    这条规则对 Python 之所以有效，是因为它是一门高度面向语句的语言。特别是， Python 的文法确保语句绝不会出现在表达式内部。C 也一样，但很多有「lambda」或 函数字面量语法的语言就不这样了。

    一个 JavaScript 的例子：

    console.log(function() {
  statement();
});

    这里 console.log() 这个表达式里含着一个函数字面量，函数字面量里又含有 语句 statement();。

    Python 如果想隐式接续行，就需要另一套规则了——让你在仍嵌套在括号里的情况下， 能回到那些换行该变得有意义的语句里去。

现在你知道为什么 Python 的 lambda 只允许单个表达式作为函数体了。

  • JavaScript 的「自动分号插入」规则才是真正奇怪的那个。别的语言大多假设 大多数换行都是有意义的，只有少数几个在多行语句里该被忽略；JS 假设的正好相反。 它把你的所有换行都当作无意义的空白，除非它撞上解析错误。真撞上了，它就回头 试着把上一个换行变成分号，好让结果语法合法。

    要是把「这到底怎么做到的」连同「JavaScript 这套『方案』有多少种烂法」 一起细讲，这篇设计说明就得变成一篇设计长文了。那是一团糟。JavaScript 是我唯一 知道的、很多风格指南要求每条语句后面都写显式分号的语言——哪怕这语言理论上允许 你省掉它们。

如果你在设计一门新语言，那你几乎肯定应该避开显式的语句终止符。程序员跟其他人类 一样，是追潮流的动物，而分号跟全大写关键字一样，早就过时了。只要确保你挑的那套规则 适合这门语言自己的文法和惯用法就行。还有，别学 JavaScript。
