8

语句与状态

我这一生，心里始终渴望着一件我叫不出名字的东西。 安德烈·布勒东，《疯狂的爱》

我们目前这个解释器，感觉不太像是在给一门真正的语言编程，倒更像是在计算器上戳按钮。在我看来， 「编程」意味着用一块块小零件搭出一个系统。眼下我们还做不到，因为我们没办法把一个名字绑定到某份 数据或某个函数上。没办法引用各个零件，就没办法组合出软件。

要支持绑定，我们的解释器就得有内部状态。当你在程序开头定义一个变量、在结尾使用它时，解释器必须 在这中间一直攥着那个变量的值。所以在这一章里，我们要给解释器装上一颗大脑，它不仅会计算，还能 记住。

状态和语句是手挽手的。按定义，语句不求值出一个值，所以它们得干点别的才有用。 那个「别的」叫做副作用。它可能意味着产出用户看得见的输出，或者修改解释器里某种之后能被察觉的 状态。后者让语句特别适合用来定义变量或别的具名实体。

你可以造一门语言，把变量声明当成既创建绑定、又产出值的表达式。我知道的唯一这么干的语言是 Tcl。 Scheme 看着像是个候选，但注意：一个 let 表达式求值完之后，它绑定的那个变量就被忘掉了。define 语法不是表达式。

这一章里，上面这些我们都会做。我们会定义产出输出的语句（print）和创建状态的语句（var）。我们 会加上访问变量、给变量赋值的表达式。最后，我们还会加上块和局部作用域。要往一章里塞的东西是不少， 但我们会一口一口把它啃完。

8 . 1语句

我们先给 Lox 的文法扩展出语句。它们跟表达式差别不大。从最简单的两种开始：

  1. 表达式语句让你可以把一个表达式放在本该是语句的位置。它存在的意义是求值那些带副作用的 表达式。你可能没注意到它，但你在 C、Java 和其他语言里一直在用它。 只要你看到一个函数或方法调用后面跟着 ;，那就是一条表达式语句。

    Pascal 是个异类。它区分过程（procedure）和函数（function）。函数返回值，过程不能。 调用过程有专门的语句形式，而函数只能在需要表达式的地方调用。Pascal 里没有表达式语句。

  2. print 语句求值一个表达式，并把结果显示给用户。我承认，把打印直接焊进语言里、而不是 做成库函数，是有点怪。这么做是让步于一个事实：我们是一章一章地搭这个解释器，想在它做完之前 就能上手玩一玩。要是把 print 做成库函数，我们就得等到定义和调用函数的全套机械都备齐 之后，才能见证任何副作用。

    我要带一点点戒备心地说一句：BASIC 和 Python 都有专门的 print 语句，而它们是真正的语言。 诚然，Python 在 3.0 里把它的 print 语句去掉了……

新语法意味着新的文法规则。在这一章里，我们终于获得了语法解析整个 Lox 脚本的能力。既然 Lox 是一门 命令式、动态类型的语言，脚本的「顶层」就只是一串语句。新规则是：

program        → statement* EOF ;

statement      → exprStmt
               | printStmt ;

exprStmt       → expression ";" ;
printStmt      → "print" expression ";" ;

第一条规则现在成了 program，它是文法的起点，代表一个完整的 Lox 脚本或一条 REPL 输入。一个程序 就是一串语句，后面跟着那个特殊的「文件结束」词法单元。这个必须有的结束词法单元确保语法解析器会 吃光全部输入，不会悄悄放过脚本末尾遗留的、出错的词法单元。

眼下，statement 只为我们描述过的两种语句准备了两个分支。本章后面和接下来的几章里，我们会往里 补更多。下一步是把这个文法变成我们能存在内存里的东西——语法树。

8 . 1 . 1语句的语法树

文法里没有任何地方同时允许表达式和语句。比如说，+ 的操作数永远是表达式，绝不会是语句。while 循环的循环体永远是一条语句。

8 . 2全局变量

既然有了语句，我们就能开始弄状态了。在钻进词法作用域那一堆复杂东西之前，先从最简单的一种变量 开始——全局变量。我们需要两个新构件。

  1. 一条变量声明语句把一个新变量带到世上。

    var beverage = "espresso";

    它创建一个新的绑定，把某个名字（这里是 “beverage”）跟某个值（这里是字符串 "espresso"） 关联起来。

  2. 这之后，一个变量表达式访问那个绑定。当标识符 “beverage” 被当作表达式使用时，它会查出 绑定到那个名字上的值并返回。

    print beverage; // "espresso".

后面我们还会加上赋值和块作用域，但眼下这些足够开动了。

全局状态名声不太好。的确，大量的全局状态——尤其是可变的状态——会让大型程序难以维护。把它用得 越少越好，这是好的软件工程。

但当你随手拼凑一门简单的编程语言时，或者更进一步，甚至只是学你的第一门语言时，全局变量那种扁平的 简单就有帮助。我的第一门语言是 BASIC，虽说我后来长大了、把它抛在了身后，但当时不必先绕明白作用域 规则就能让计算机干些好玩的事，这一点挺好的。

8 . 2 . 1变量的语法

跟之前一样，我们从前到后过一遍实现，从语法开始。变量声明是语句，但它们跟别的语句不一样，我们打算 把语句文法一分为二来处理它们。这是因为文法会限制某些种类的语句能出现在哪里。

控制流语句里的那些子句——想想 if 语句的 then 和 else 分支，或者 while 的循环体——每一个都是 一条单独的语句。但那条语句不允许是声明名字的那种。这样是可以的：

if (monday) print "Ugh, already?";

但这样不行：

if (monday) var beverage = "espresso";

我们大可以允许后一种，但它挺让人困惑。那个 beverage 变量的作用域是什么？它在 if 语句之后 还存在吗？如果存在，那在不是星期一的日子里它的值是什么？那些日子里这个变量到底存不存在？

这样的代码很怪，所以 C、Java 之流都不许这么写。就好像语句有两层「优先级」。 有些允许出现语句的地方——比如块内部或顶层——允许任何种类的语句，包括声明。另一些地方则只允许 「更高」优先级的语句，也就是不声明名字的那些。

在这个类比里，块语句的作用有点像表达式里的括号。块本身处于「更高」的优先级，可以放在任何地方， 比如 if 语句的子句里。但它包含的语句可以是更低优先级的。你被允许在块内部声明变量和其他名字。 那对花括号让你能从「只允许部分语句」的地方，逃回到完整的语句文法里。

为了容纳这个区分，我们为声明名字的那些语句再加一条规则。

program        → declaration* EOF ;

declaration    → varDecl
               | statement ;

statement      → exprStmt
               | printStmt ;

声明语句归到新的 declaration 规则下。眼下它只有变量，但以后还会包括函数和类。任何允许出现声明的 地方也允许非声明的语句，所以 declaration 规则会兜底落到 statement。显然，你可以在脚本顶层做 声明，所以 program 改接到这条新规则上。

声明变量的规则长这样：

varDecl        → "var" IDENTIFIER ( "=" expression )? ";" ;

跟大多数语句一样，它以一个领头的关键字开头。这里就是 var。然后是一个标识符词法单元，用来表示 正在声明的变量名，接着是一个可选的初始化器表达式。最后，我们给它扎上分号这个蝴蝶结。

要访问一个变量，我们定义一种新的基本表达式。

primary        → "true" | "false" | "nil"
               | NUMBER | STRING
               | "(" expression ")"
               | IDENTIFIER ;

那条 IDENTIFIER 子句匹配单个标识符词法单元，它被理解为正在被访问的变量的名字。

  if (n == 0) return true;

像 Java 和 C# 这类静态类型语言，是这么解决的：规定程序的顶层不是一串命令式语句，而是一组同时诞生的 声明。实现在查看任何函数体之前，先声明所有名字。

C 和 Pascal 这类更老的语言不这么干。它们逼你加上显式的前向声明，在某个名字被完整定义之前先声明 它。那是对当时有限算力的让步。他们希望只把源文件从头到尾扫一遍就能编译完，所以那些编译器没法先收集 齐所有声明再去处理函数体。

既然把它当静态错误会让递归声明太难办，我们就把这个错误推迟到运行时。只要你不去求值那个引用， 在变量定义之前提及它是没问题的。这样奇偶数的程序就能跑，但下面这段会得到一个运行时错误：

这下我们的解释器能创建、读取、修改变量了。水平大概跟早期的 BASIC 差不多。 全局变量很简单，但当程序里随便两块代码都能意外踩到彼此的状态时，写一个大型程序就没啥乐趣了。我们 想要局部变量，也就是说，该请出作用域了。

也许比那还稍微强一点。跟某些老 BASIC 不同，Lox 能处理长度超过两个字符的变量名。

8 . 5作用域

一个作用域定义了一片区域，在那里一个名字映射到某个特定的实体。多个作用域让同一个名字能在不同的 上下文里指代不同的东西。在我家里，「鲍勃」通常指的是我。但也许在你那座城里，你认识另一个鲍勃。 同一个名字，说的地方不同，对应的人就不同。

词法作用域（或者那个不那么常听到的静态作用域）是一种特定的作用域 风格，程序文本本身就显示了作用域从哪里开始、到哪里结束。在 Lox 里，跟大多数现代语言一样，变量是 词法作用域的。当你看到某个使用变量的表达式时，只要静态地阅读代码，就能弄清楚它指的是哪一次变量 声明。

「词法」（lexical）来自希腊语「lexikos」，意思是「跟词有关的」。在编程语言里用它，通常指的是那种 你无须执行任何东西、单从源代码本身就能弄明白的东西。

词法作用域随 ALGOL 登上舞台。更早的语言往往是动态作用域的。那时候的计算机科学家相信，动态作用域 执行起来更快。今天，多亏了早期 Scheme 那帮黑客，我们知道那不是真的。真要说的话，恰恰相反。

变量的动态作用域在某些角落里还活着。Emacs Lisp 的变量默认就是动态作用域。Clojure 里的 binding 宏提供了它。JavaScript 里那个广遭嫌弃的 with 语句，会把对象上的 属性变成动态作用域的变量。

举个例子：

{
  var a = "first";
  print a; // "first".
}

{
  var a = "second";
  print a; // "second".
}

这里有两个块，各自声明了一个变量 a。你我只要看一眼代码就能说出来，第一条 print 语句里用到的 a 指的是第一个 a，第二条指的就是第二个。

这跟动态作用域形成对比——在动态作用域里，直到你执行代码才知道一个名字指的是什么。Lox 没有 动态作用域的变量，但对象上的方法和字段是动态作用域的。

class Saxophone {
  play() {
    print "Careless Whisper";
  }
}

class GolfClub {
  play() {
    print "Fore!";
  }
}

fun playIt(thing) {
  thing.play();
}

当 playIt() 调用 thing.play() 时，我们不知道即将听到的是「Careless Whisper」还是「Fore!」。 这取决于你传给函数的是萨克斯还是高尔夫球杆，而这件事要到运行时才知道。

作用域和环境是一对近亲。前者是理论概念，后者是实现它的机器。当我们的解释器在代码里穿行时，那些 影响作用域的语法树节点会改变环境。在 Lox 这种偏 C 的语法里，作用域是由花括号块控制的。（所以我们 管它叫块作用域。）

{
  var a = "in block";
}
print a; // Error! No more "a".

一个块的开始引入一个新的局部作用域，而当执行越过那个收尾的 } 时，这个作用域就结束了。块内声明的 任何变量都消失不见。

8 . 5 . 1嵌套与遮蔽

实现块作用域的第一版草稿大概是这样的：

  1. 在我们访问块内每一条语句时，记下所有被声明的变量。

  2. 在最后一条语句执行完之后，告诉环境把那些变量全都删掉。

对前面那个例子来说，这能行。但记住，局部作用域的动机之一就是封装——程序某个角落里的一块代码，不该 去干扰别的某一块。看看这个：

// How loud?
var volume = 11;

// Silence.
volume = 0;

// Calculate size of 3x4x5 cuboid.
{
  var volume = 3 * 4 * 5;
  print volume;
}

看看那个块，我们用 volume 的一个局部声明来计算长方体的体积。块退出之后，解释器会把那个全局 volume 变量删掉。这可不对。退出块时，我们应该移除块内声明的任何变量，但如果块外声明了一个同名的 变量，那是另一个变量。它不该被碰。

当一个局部变量跟某个外围作用域里的变量同名时，它会遮蔽那个外层变量。块内的代码再也看不见它了 ——它藏在内层变量投下的「阴影」里——但它还在那儿。

当我们进入一个新的块作用域时，需要保住那些在外层作用域里定义的变量，好让它们在退出内层块之后依然 还在。为此，我们给每个块定义一个全新的环境，里面只装着在这个作用域里定义的变量。退出块时，我们丢掉 它的环境，恢复上一个。

我们还需要处理那些没有被遮蔽的外围变量。

var global = "outside";
{
  var local = "inside";
  print global + local;
}

这里，global 住在外面那个全局环境里，而 local 定义在块自己的环境里。在那条 print 语句里， 这两个变量都在作用域内。为了找到它们，解释器不仅得搜当前最内层的环境，还得搜任何外围环境。

我们通过把环境串联起来的办法实现这一点。每个环境都有一个指向紧邻的外围 作用域环境的引用。当我们查找一个变量时，就沿着这条链从最内层往外走，直到找到那个变量。从内层作用域 开始，正是我们让局部变量遮蔽外层变量的方式。

在解释器运行期间，这些环境构成一个线性的对象列表；但想想整个执行过程中被创建出来的那套完整环境 集合。一个外层作用域内部可能嵌套着多个块，每个都指向那个外层作用域，于是形成一棵树状结构——虽然 同一时刻，那棵树里只有一条路径存在。

设计说明：隐式变量声明

Lox 把「声明一个新变量」和「给已有变量赋值」区分成了两套不同的语法。有些语言把这两者合并成只有赋值 一种语法。给一个不存在的变量赋值，会自动把它带到世上。这叫做隐式变量声明，Python、Ruby 和 CoffeeScript 等语言都有。JavaScript 有显式的语法来声明变量，但也能在赋值时创建新变量。Visual Basic 有一个开关来启用或禁用隐式变量。

当同一种语法既能赋值又能创建变量时，每种语言都必须在「用户意图不明确」的时候决定该怎么办。具体来说， 每种语言都得选定：隐式声明如何跟遮蔽互动，以及一个被隐式声明的变量落进哪个作用域。

  • 在 Python 里，赋值总是在当前函数的作用域里创建一个变量，哪怕函数外面声明了一个同名的变量。

  • Ruby 靠给局部变量和全局变量定不同的命名规则，避开了一部分歧义。不过，Ruby 里的块（它更像闭包， 而不是 C 里的「块」）有它自己的作用域，所以这个问题依然存在。Ruby 里赋值时，如果当前块外部存在 一个同名变量，它就赋值给那个变量。否则，它就在当前块的作用域里创建一个新变量。

  • CoffeeScript 在很多方面沿袭了 Ruby，做法也类似。它明确地不允许遮蔽：规定赋值永远赋给外层作用域 里的变量（只要存在这么一个），一路向上直到最外层的全局作用域。否则，它就在当前函数作用域里创建 那个变量。

  • 在 JavaScript 里，赋值如果能在任何外围作用域里找到已存在的变量，就修改它。如果找不到，它就隐式地 在全局作用域里创建一个新变量。

隐式声明的主要好处是简单。语法更少，也没有「声明」这个概念要学。用户只管开始赋值，语言自己去弄明白。

像 C 这样更老的、静态类型的语言，则受益于显式声明，因为它给用户一处地方，去告诉编译器每个变量是什么 类型、要给它分配多少存储空间。在一门动态类型、有垃圾回收的语言里，这其实并不是必需的，所以你可以 把声明做成隐式的。这感觉更「脚本范儿」一点，更「你懂我意思」。

但这是个好主意吗？隐式声明有一些问题。

  • 用户本意可能是给一个已有变量赋值，但把名字拼错了。解释器不知道这一点，于是就闷头静悄悄地创建了 某个新变量，而用户想赋值的那个变量还是老值。在 JavaScript 里这事格外恶劣：一个拼写错误会创建 一个全局变量，进而可能干扰别的代码。

  • JS、Ruby 和 CoffeeScript 靠「是否已存在一个同名变量——哪怕在外层作用域里」来判断一次赋值是创建 新变量还是赋给已有变量。这意味着在某个外围作用域里加一个新变量，可能改变已有代码的含义。原本是 局部变量的东西，可能无声无息地变成对外层那个新变量的赋值。

  • 在 Python 里，你可能想给当前函数外面的某个变量赋值，而不是在当前函数里创建一个新变量，但你 做不到。

随着时间推移，我所知道的那些有隐式变量声明的语言，最终都加上了更多特性和复杂度来处理这些问题。

  • 今天，JavaScript 里全局变量的隐式声明被普遍视为一个错误。「严格模式」禁用了它，把它变成编译错误。

  • Python 加了一条 global 语句，让你能从函数内部显式地给全局变量赋值。后来，随着函数式编程和嵌套 函数越来越流行，他们又加了一条类似的 nonlocal 语句，用来给外围函数里的变量赋值。

  • Ruby 扩展了它的块语法，允许把某些变量显式声明为块局部的，哪怕外层作用域里存在同名变量。

考虑到这些，我认为「简单」这个论据基本已经站不住脚了。有一种说法是，隐式声明是正确的默认，但我个人 觉得那不太有说服力。

我的看法是，隐式声明在很多年前是说得通的，那时候大多数脚本语言高度命令式、代码相当扁平。随着程序员 对深度嵌套、函数式编程和闭包越来越习惯，想要访问外层作用域变量的情况变得越来越普遍。这就让用户更容易 撞上那些棘手的情形：分不清他们到底是打算让这次赋值创建一个新变量，还是复用一个外围的变量。

所以我更偏爱显式声明变量，这也是 Lox 要求这么做的原因。
