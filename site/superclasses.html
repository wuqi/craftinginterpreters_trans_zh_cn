这是我们给虚拟机添加新功能的最后一章。Lox 这门语言几乎已经整个塞进它里面了。剩下的只有 继承方法、调用超类方法。这章之后我们还有一章，但它不引入任何新行为，它 只是把已有的东西变快。读到这一章末尾，你就有了一个完整的 Lox 实现。

那个「只」字可不该让人以为让东西变快不重要！说到底，我们这整个第二台虚拟机的全部目的就是 在性能上碾压 jlox。你完全可以争辩说，过去十五章全部都是「优化」。

本章有些材料会让你想起 jlox。我们解析 super 调用的方式基本一样，只不过是通过 clox 那套更 复杂的状态存储机制来看待它。但这一回，处理继承方法调用我们用的是一套完全不同的、快得多的 办法。

29 . 1继承方法

我们先用方法继承热热身，因为它是比较简单的那一半。提醒一下自己，Lox 的继承语法长这样：

class Doughnut {
  cook() {
    print "Dunk in the fryer.";
  }
}

class Cruller < Doughnut {
  finish() {
    print "Glaze with icing.";
  }
}

这里，Cruller 类继承自 Doughnut，因此 Cruller 的实例继承了 cook() 方法。我不知道自己干吗 要把这事讲得这么啰嗦。你知道继承是怎么工作的。我们来编译这段新语法。

从栈顶往下走，先是子类，然后是超类。我们把这两个都取出来，然后干继承那点活儿。clox 就是在这里 走上了跟 jlox 不同的路。在我们的第一个解释器里，每个子类都存着一个指向它超类的引用。方法 访问时，如果我们在子类的方法表里没找到方法，就沿着继承链递归下去，逐个查看每个祖先的方法表， 直到找到为止。

要在方法调用的时候干这么多活儿，很慢。更糟的是，一个继承来的方法在祖先链上位置越高， 它就越慢。性能表现并不理想。

新办法快得多。子类声明的时候，我们把被继承那个类的所有方法全都复制进子类自己的方法表。 之后，调用方法时，任何从超类继承来的方法都会直接在子类自己的方法表里被找到。继承根本 不需要任何额外的运行时开销。到类声明完成的时候，活儿就干完了。这意味着继承来的方法调用跟 普通方法调用一样快——就一次哈希表查找。

好吧，我猜是两次哈希表查找。因为我们首先得确认实例上有没有字段遮蔽了那个方法。

我偶尔听人把这套技术叫作「复制下沉继承」。它简单又快，但和大多数优化一样，你只能在特定约束 下用它。它在 Lox 里行得通，是因为 Lox 的类是封闭的。一个类声明一旦执行完毕，这个类的方法 集合就永远不会再变。

在 Ruby、Python 和 JavaScript 这样的语言里，你可以把一个已有的类撬开， 往里头塞些新方法，甚至把方法删掉。那会毁掉我们的优化，因为如果那些修改恰好发生在子类声明 执行之后、作用在超类身上，子类就接收不到这些改动。这会破坏用户的预期——继承总是要反映 超类的当前状态。

你可以想象，在运行时用命令式的方式改变一个类所定义的方法集合，会让程序变得难以推理。 这是个非常有用的工具，但也是个危险的工具。

觉得这个工具也许有点太危险的人，给它取了个不够体面的名字，叫「猴子补丁 （monkey patching）」，或者更不体面的「鸭子重拳（duck punching）」。

对我们来说这是幸运（不过对喜欢这个特性的用户来说恐怕不是），Lox 不让你改猴子，也不让你捶鸭子， 所以我们可以放心地应用这项优化。

那方法覆盖呢？把超类的方法复制进子类的方法表，会不会跟子类自己的方法撞车？幸好不会。我们在 在创建子类的 OP_CLASS 指令之后、任何方法声明和 OP_METHOD 指令被编译之前，发射 OP_INHERIT。在我们把超类的方法复制下去的那一刻，子类的方法表是空的。子类覆盖的任何方法 都会盖掉表里那些继承来的条目。

29 . 2存放超类

你注意到了吗？加上方法继承的时候，我们其实并没有从子类往超类加任何引用。复制完继承来的方法 之后，我们就把超类彻底忘了。我们不需要握着超类的句柄，所以就不握。

但这还不够支撑 super 调用。由于子类可能覆盖了超类的方法，我们需要 能够拿到超类的方法表。在讲那套机制之前，我想先帮你回忆一下 super 调用是怎么做静态解析的。

「可能」这个词也许还不够重。那个方法多半已经被覆盖了。不然的话，你费劲用 super 而不是 直接调用它是干嘛？

在 jlox 的太平盛世里，我给你看过这个棘手的例子，用来解释 super 调用是怎么分派的：

class A {
  method() {
    print "A method";
  }
}

class B < A {
  method() {
    print "B method";
  }

  test() {
    super.method();
  }
}

class C < B {}

C().test();

在 test() 方法体内部，this 是一个 C 的实例。如果 super 调用是相对于接收者的超类来 解析的，那我们就会去查 C 的超类 B。但 super 调用是相对于调用发生处那个外层类的超类来 解析的。在这个例子里，我们身处 B 的 test() 方法，所以超类是 A，程序应该打印 “A method”。

这意味着 super 调用不是根据运行时实例动态解析的。用来查找方法的超类是一个静态的——几乎是 词法的——性质，由调用发生的位置决定。当我们给 jlox 加上继承时，我们利用了它静态的这一面：把 超类存进我们用于所有词法作用域的那个 Environment 结构体里。解释器看上面那段程序，几乎就像 这样：

class A {
  method() {
    print "A method";
  }
}

var Bs_super = A;
class B < A {
  method() {
    print "B method";
  }

  test() {
    runtimeSuperCall(Bs_super, "method");
  }
}

var Cs_super = B;
class C < B {}

C().test();

每个子类都有一个隐藏变量，存着一个指向它超类的引用。每当我们需要执行一次 super 调用，就从 那个变量里取出超类，然后告诉运行时从那儿开始找方法。

clox 我们走同样的路。区别在于，jlox 用的是堆上分配的 Environment 类，而我们用的是字节码 虚拟机的值栈加上 upvalue 系统。机制稍有不同，但整体效果一样。

新建一个词法作用域保证了：如果我们在同一个作用域里声明两个类，它们各自有一个不同的局部 槽位来存自己的超类。因为我们总是把这个变量命名为 “super”，如果不给每个子类都开一个作用域， 这些变量就会撞车。

我们把这个变量命名为 “super”，理由和我们把 this 表达式解析到的那个隐藏局部变量命名为 “this” 完全一样：“super” 是保留字，这保证了编译器的隐藏变量不会跟用户定义的变量撞车。

关键的差别在于我们传给 bindMethod() 的是哪个类。普通的属性 访问里，我们用的是那个 ObjInstance 自己的类，这给了我们想要的多态分派。而 super 调用不用 实例的类，我们用的是包含它的那个类静态解析出来的超类——编译器已经很贴心地保证它正待在栈顶 上等着我们。

我们把那个超类弹出来传给 bindMethod()，它会正确地跳过超类和实例自己的类之间任何子类里的 覆盖方法。它也正确地包含了超类从它自己的那些超类继承来的任何方法。

剩下的行为就一样了。弹出超类之后，栈顶是那个实例。bindMethod() 成功时，它弹出实例、压入 新的绑定方法。否则它报一个运行时错误并返回 false。那种情况下，我们中止解释器。

跟 OP_GET_PROPERTY 相比，另一个差别是我们不会先去查找可能遮蔽的字段。字段是不被继承的， 所以 super 表达式总是解析到方法。

如果 Lox 是一门基于原型的语言，用委托代替继承，那么就不是一个类继承另一个类， 而是实例继承（「委托给」）其他实例。那种情况下，字段是可以被继承的，我们就得在这里检查它们。

29 . 3 . 2更快的 super 调用

现在 super 类方法访问已经能用了。而既然返回的对象是一个你随后可以调用的 ObjBoundMethod， super 调用也就跟着能用了。和上一章一样，我们到达了一个语义完整正确的点。

但也和上一章一样，它相当慢。又一次，我们为每次 super 调用在堆上分配一个 ObjBoundMethod， 尽管大多数时候紧跟着的下一条指令就是一条 OP_CALL，会立刻把这个绑定方法拆开、调用它、然后 扔掉。事实上，对 super 调用来说，这比普通方法调用还更可能成立。至少在方法调用那里，还有 一种可能是用户真的在调用一个存在字段里的函数。而 super 调用，你永远是在查一个方法。唯一的 问题只是你会不会立刻调用它。

  1. 面向对象编程的一条信条是，类应该保证新对象处于一个有效状态。在 Lox 里，这意味着要定义 一个初始化器来填充实例的字段。继承让事情复杂化了，因为实例必须满足继承链上每一个类对有效状态的要求。

    容易的部分是记得在每个子类的 init() 方法里调用 super.init()。难的部分是字段。继承链上 两个类不小心占用了同一个字段名，是没有任何东西能阻止的。这种情况发生时，它们会踩到对方的 字段，还可能给你留下一个坏掉的实例。

  2. 我们的复制下沉继承优化之所以成立，只是因为 Lox 不允许你在类声明之后修改它的方法。这意味 着我们不必担心子类里那些复制来的方法跟超类后来的改动失去同步。

    其他语言，比如 Ruby，确实允许事后修改类。这类语言的实现是怎么在支持类修改的同时保持 方法查找效率的？

  3. 在jlox 讲继承那一章里，我出过一个实现 BETA 语言方法覆盖方式的题目。再做 一遍，但这次是在 clox 里。下面是上次那道题的描述：

    在 Lox 里，和大多数别的面向对象语言一样，查找方法时我们从类层级的底部开始往上走——子类的 方法优先于超类的方法。为了在一个覆盖方法内部够到超类的方法，你用 super。

    语言 BETA采取的是相反的思路。你调用一个方法时，它从类层级的顶端开始 往下走。超类的方法赢过子类的方法。为了够到子类的方法，超类方法可以调用 inner，它 有点像 super 的反面。它沿着层级链往下接到下一个方法。

    是超类方法掌控着子类何时、在何处被允许细化自己的行为。如果超类方法压根不调用 inner， 那子类就根本没有办法覆盖或修改超类的行为。

    把 Lox 现有的覆盖和 super 行为拿掉，换成 BETA 的语义。简而言之：

    • 在一个类上调用方法时，继承链上位置最高的方法优先。

    • 在方法体内部，调用 inner 会沿着 inner 所在类与 this 所在类之间的继承链，去 最近的子类里找一个同名方法。如果没有匹配的方法，这次 inner 调用什么都不做。

    举个例子：

    class Doughnut {
  cook() {
    print "Fry until golden brown.";
    inner();
    print "Place in a nice box.";
  }
}

class BostonCream < Doughnut {
  cook() {
    print "Pipe full of custard and coat with chocolate.";
  }
}

BostonCream().cook();

    它应该打印：

    Fry until golden brown.
Pipe full of custard and coat with chocolate.
Place in a nice box.
