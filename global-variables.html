全局变量

要是能有这么一项发明，能把一段记忆像香气一样封进瓶子里，那该多好。它永不消散，也永不陈腐。等到想要的时候，把瓶塞拔开，就仿佛重新活过那一刻。

达芙妮·杜穆里埃，《蝴蝶梦》

上一章是对一个宏大、深奥、基础的计算机科学数据结构的一次漫长探索。理论和概念很重，可能还聊了点大 O 记号和算法。这一章没那么多智识上的架子。没有宏大的思想要学。它只是一堆直截了当的工程活。等我们把它们做完，我们的虚拟机就能支持变量了。

其实，它只支持全局变量。局部变量要到下一章才来。在 jlox 里，我们好歹把它们俩都塞进了一章，因为所有变量我们都用同一种实现技术。我们搭了一条环境链，每个作用域一个，一路通到顶上。那是学习如何管理状态的一种简单、干净的途径。

但它也慢。每次进入一个块或调用一个函数都分配一张新的哈希表，可不是通向快虚拟机的路。考虑到有那么多代码都跟使用变量有关，变量要是慢，一切就都慢。对 clox，我们会给局部变量用一套高效得多的策略来改进这一点，但全局变量就没那么容易优化了。

这是精密语言实现里一种常见的元策略。同一个语言特性往往会有多种实现技术，各自为不同的使用模式调优。比如，JavaScript 虚拟机常常为那些用起来更像类实例的对象准备一种更快的表示法，以区别那些属性集合被更随意修改的对象。C 和 C++ 编译器通常有好几种编译 switch 语句的方式，视分支数量、以及分支值排布得多密而定。

快速温习一下 Lox 的语义：Lox 里的全局变量是「晚绑定」的，也就是动态解析的。这意味着你可以编译一段引用了某个全局变量的代码，而那个变量还没定义。只要这段代码不在定义发生之前执行，一切就没问题。实际来说，这意味着你可以在函数体里引用后面才出现的变量。

fun showVariable() {
  print global;
}

var global = "after";
showVariable();

这样的代码看着可能有点怪，但它方便定义相互递归的函数。它跟 REPL 配合得也更好。你可以在一行里写一个小函数，然后在下一行定义它用到的变量。

局部变量的运作方式不同。既然局部变量的声明总是发生在它被使用之前，虚拟机就能在编译期解析它们，哪怕是在一个简单的单遍编译器里。这会让我们能为局部变量用上更聪明的表示法。不过那是下一章的事了。眼下，我们只管全局变量。

21 . 1语句

变量靠变量声明诞生，这也意味着，现在正是给编译器加上语句支持的时候。如果你还记得，Lox 把语句分成两类。「声明」是那些把一个新名字绑定到一个值上的语句。其他种类的语句——控制流、print 等等——就只叫「语句」。我们不允许在控制流语句里直接放声明，像这样：

if (monday) var croissant = "yes"; // 错误。

允许这种写法，会在变量作用域上引出令人困惑的问题。所以，跟其他语言一样，我们在语法上禁止它，为此给「控制流主体里允许出现的那部分语句子集」单独设一条文法规则。

statement      → exprStmt
               | forStmt
               | ifStmt
               | printStmt
               | returnStmt
               | whileStmt
               | block ;

然后，我们给脚本的顶层以及块内部另设一条规则。

declaration    → classDecl
               | funDecl
               | varDecl
               | statement ;

declaration 规则含有那些声明名字的语句，同时也包进了 statement，好让所有语句类型都被允许。由于 block 本身就在 statement 里，你可以把声明嵌套在一个块里，从而把它们放进控制流构造内部。

块的作用有点像圆括号之于表达式。块让你把「较低优先级」的声明语句，放到只允许「较高优先级」的非声明语句出现的地方。

本章里，我们只讲几种语句和一种声明。

statement      → exprStmt
               | printStmt ;

declaration    → varDecl
               | statement ;

到现在为止，我们的虚拟机把「程序」当作单个表达式，因为我们当时也只能解析和编译这么多。在一个完整的 Lox 实现里，程序是一串声明。我们现在准备好支持它了。

整个语句的字节码，总栈效应是零。既然语句不产出任何值，它最终让栈保持不变，尽管它在干活时当然会用到栈。这一点很重要，因为等我们做到控制流和循环时，一个程序可能会执行一长串语句。要是每条语句都让栈变大或变小，它迟早会溢出或下溢。

21 . 1 . 3错误同步

趁我们在编译器里做这些前期工作，可以顺手把我们好几章之前留下的一根线头收掉。跟 jlox 一样，clox 用 panic 模式的错误恢复，来把它报告的连锁编译错误数量降到最低。当编译器到达一个同步点时，就退出 panic 模式。对 Lox，我们选了语句边界作为那个点。既然我们有了语句，就能实现同步了。

如果我们在解析前一条语句时撞上编译错误，就进入 panic 模式。一旦如此，在那条语句之后，我们开始同步。

compiler.c
加在 printStatement() 之后
static void synchronize() {
  parser.panicMode = false;

  while (parser.current.type != TOKEN_EOF) {
    if (parser.previous.type == TOKEN_SEMICOLON) return;
    switch (parser.current.type) {
      case TOKEN_CLASS:
      case TOKEN_FUN:
      case TOKEN_VAR:
      case TOKEN_FOR:
      case TOKEN_IF:
      case TOKEN_WHILE:
      case TOKEN_PRINT:
      case TOKEN_RETURN:
        return;

      default:
        ; // 什么都不做。
    }

    advance();
  }
}
compiler.c, 加在 printStatement() 之后

我们不加区分地跳过词法单元，直到到达某个看起来像语句边界的地方。我们通过找一个能结束语句的前一个词法单元（比如分号）来认出边界。或者，我们找一个能开启语句的后继词法单元，通常是控制流或声明的关键字之一。

21 . 2变量声明

仅仅能 print 一下，可不会让你的语言在编程语言展览会上得奖，所以我们往前走一点，弄点更有野心的东西，把变量搞起来。我们需要支持三种操作：

我忍不住想象一个「语言展览会」，就像乡村的 4H 展会那种。一排排铺着干草的展位里，满是些幼崽语言，对着彼此 moo、baa 地叫。

关键字后面跟着变量名。那由 parseVariable() 编译，我们稍后会讲到它。然后我们找一个 =，后面跟着一个初始化表达式。如果用户没有初始化这个变量，编译器就发射一条 OP_NIL 指令，隐式地把它初始化为 nil。无论哪种情况，我们都期望这条语句以分号结束。

成：

这个函数拿给定的词法单元，把它的词素作为字符串加进字节码块的常量表。然后返回那个常量在常量表里的下标。

全局变量在运行时是按名字查找的。这意味着虚拟机——那个字节码解释器循环——需要能拿到这个名字。整个字符串太大了，塞不进字节码流当操作数。于是我们把字符串存在常量表里，指令随后用它在表里的下标来指代这个名字。

这个函数把这个下标一路返回给 varDeclaration()，后者随后把它交给这里：

  emitBytes(OP_DEFINE_GLOBAL, global);
}
compiler.c, 加在 parseVariable() 之后

这个输出定义新变量、并存储其初始值的那条字节码指令。变量名在常量表里的下标就是这条指令的操作数。跟基于栈的虚拟机里一如既往的做法一样，我们最后发射这条指令。运行时，我们先执行变量初始化器的代码。那把值留在栈上。然后这条指令取走那个值，存起来备用。

21 . 4赋值

整本书里，我都尽量让你走在一条相当安全、轻松的路上。我不回避难的问题，但我尽量不让解法复杂到没必要的地步。唉，可我们字节码编译器里的其他设计选择，让赋值实现起来很烦人。

如果你还记得，jlox 里赋值相当容易。

我们的字节码虚拟机用的是单遍编译器。编译器边解析边生成字节码，没有任何中间的 AST。一认出一段语法，就为它发射代码。赋值天然不适合这套。看这个：

在这段代码里，解析器直到走到 = 才意识到 menu.brunch(sunday).beverage 是一次赋值的目标、而不是个普通表达式——而那早已是第一个 menu 之后的很多个词法单元了。到那时，编译器已经为整段东西发射了字节码。

不过问题没看上去那么严峻。看看解析器是怎样看待那个例子的：

对我们来说很幸运的是，赋值左侧唯一的语义差异，出现在词法单元最右端、紧挨着 = 的地方。尽管 setter 的接收者可能是一个任意长的表达式，但行为跟 get 表达式不同的那部分，只是紧挨在 = 前面的那个结尾标识符。我们不需要多少前瞻，就能看出 beverage 应该被编译成 set 表达式而不是 getter。

习题

  1. 编译器每遇到一个标识符，就把一个全局变量的名字作为字符串加进常量表。它每次都创建一个新常量，哪怕那个变量名已经待在常量表里之前的某个槽位了。在同一个函数多次引用同一个变量的情况下，这就是浪费。这又增加了填满常量表、槽位用完的几率，因为我们一个字节码块里只允许 256 个常量。

    优化这一点。你的优化对编译期性能相比于运行期性能有何影响？这是个正确的取舍吗？

  2. 每次使用全局变量都按名字在哈希表里查一遍，是相当慢的，哪怕哈希表很好。你能想出一种更高效的办法来存储和访问全局变量、又不改变语义吗？

  3. 在 REPL 里运行时，用户可能会写一个引用了未知全局变量的函数，然后在下一行声明这个变量。Lox 应当从容处理这种情况：在函数首次被定义时不报告「未知变量」的编译错误。
