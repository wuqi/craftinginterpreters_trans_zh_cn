Lox 是<span name="unityped">动态</span>类型的。同一个变量，在不同时间点可以装下布尔值、
数字或字符串。至少，设计上是这么打算的。此刻在 clox 里，所有值都是数字；到本章结束时，
它还会支持布尔值和 `nil`。这两样本身没什么意思，但它们逼着我们想明白一件事：值的表示得
怎么才能动态地应付不同的类型。

<aside name="unityped">

在静态类型和动态类型旁边，还站着第三类：**单一类型**（unityped）。这种范式下，所有变量
共用同一个类型，通常是机器寄存器里的一个整数。单一类型的语言今天已经不多了，但有些
Forth，还有 BCPL（启发了 C 的那门语言），走的就是这条路。

此刻，clox 就是单一类型的。

</aside>

## 带标签联合体

用 C 干活的好处是，数据结构可以从最底层的比特开始搭。坏处是，你**必须**这么干。C 在编译期
不白送你多少东西，运行时给的更少。在 C 眼里，宇宙就是一坨没有差别的字节数组。用掉其中
几个字节、它们各自代表什么，得我们说了算。

要挑一种值的表示方式，得先回答两个关键问题：

1.  **一个值的类型怎么表示？** 比如你想拿一个数字去乘 `true`，我们得在运行时察觉这个错误
    并报出来。要做到这点，就得能看出一个值是什么类型。

2.  **值本身怎么存？** 我们不光要看出三是个数字，还得看出它和四不是一回事。我知道，这看着
    很显然，对吧？但我们所在的这个层面，把这些掰开讲清楚是有必要的。

既然我们不只是在设计这门语言，还要亲手把它造出来，那回答这两个问题时，就必须同时惦记着
实现者永恒的追求：**高效**。

这些年来，语言黑客们想出了各种巧办法，把上面那点信息塞进尽可能少的比特里。眼下我们从
最简单、最经典的方案开始：**带标签联合体（tagged union）**。一个值由两部分组成：一个类型
「标签」，以及装着实际数值的载荷。要把值的类型存下来，我们就为虚拟机支持的每种值定义
一个枚举。

^code value-type (2 before, 1 after)

<aside name="user-types">

这里列的每一项，覆盖的是虚拟机**内置支持**的每一类值。等我们给语言加上类之后，用户定义
的每个类并不需要在这个枚举里占一项。在虚拟机眼里，任何类的实例都是同一种类型：「实例」。

换句话说，这是虚拟机对「类型」的定义，不是用户眼中的定义。

</aside>

眼下我们只有这么几项，但随着往 clox 里添字符串、函数和类，这个枚举还会变长。除了类型，
值的数据也得存——数字存一个 `double`，布尔值存 `true` 或 `false`。我们可以定义一个
结构体，给每种可能的类型各配一个字段。

<img src="image/types-of-values/struct.png" alt="一个结构体，两个字段在内存里并排摆放。" />

但这样浪费内存。一个值不可能同时既是数字又是布尔值，所以任一时刻只有其中一个字段用得上。
C 允许你定义一个<span name="sum">联合体（union）</span>来省掉这份浪费。联合体看起来和
结构体一模一样，区别在于它的所有字段在内存里是重叠的。

<aside name="sum">

如果你熟悉 ML 家族的语言，C 里的结构体和联合体大致对应了积类型与和类型、元组与代数
数据类型之间的那点差别。

</aside>

<img src="image/types-of-values/union.png" alt="一个联合体，两个字段在内存里彼此重叠。" />

联合体的大小等于其中最大字段的大小。因为所有字段都在复用同一批比特，用它们的时候你
必须格外小心。要是先用某个字段存了数据，再换<span name="reinterpret">另一个</span>字段去读，
你就会把底下那点比特的含义重新解释一遍。

<aside name="reinterpret">

拿联合体把一批比特当成另一种类型来解读，这正是 C 的精髓。它撬开了一堆巧妙的优化空间，
让你能把内存里每个字节随意切割重组——这些事在内存安全的语言里都是被禁止的。但它也
危险得离谱，你一个不留神，它就能心平气和地把你的手指锯下来。

</aside>

顾名思义，「带标签联合体」就是把这两样（结构体、联合体）合进同一个结构体。

布局长这样：

<aside name="as">

有位聪明的语言黑客给我出了个主意：把联合体那个字段命名成 `as`，因为把各种值取出来的时候，
它读起来很顺，几乎像在做一次类型转换。

</aside>

<img src="image/types-of-values/value.png" alt="完整的 Value 结构体，type 字段与 as 字段在内存里并排。" />

四字节的类型标签在前头，然后是联合体。多数架构希望值按自身大小对齐。既然联合体字段里装着
一个八字节的 double，编译器就会在 type 字段后面补上四字节<span name="pad">填充
（padding）</span>，好让那个 double 落在最近的八字节边界上。也就是说，我们在类型标签上
实际花掉了八字节，而类型标签只需要表示零到三之间的数。完全可以把这个枚举塞进更小的尺寸，
可那样只会让填充变多。

<aside name="pad">

我们也可以把 tag 字段挪到联合体后面，但那同样没什么用。每当我们建一个 Value 数组
（Value 的内存开销大多花在这上头），C 编译器都会在每个 Value **之间**塞进同样的一份填充，
好让那些 double 保持对齐。

</aside>

所以我们的 Value 是 16 字节，听着有点大。[以后][optimization]再改进它。在那之前，它还
小到能塞进 C 栈里、也能按值传来传去。Lox 的语义允许这么干，因为我们目前支持的类型都是
**不可变**的。假如我们把一个装着数字三的 Value 的副本传给某个函数，不必担心调用方会看到
它被改动。三是没法「修改」的，它永远是三。

[optimization]: optimization.html

## Lox 的值与 C 的值

值的表示算是定下来了，但活还没干完。此刻 clox 的其余部分都以为 Value 就是 `double` 的
别名，代码里到处是从一个直接 C 转换到另一个。现在这些代码全废了。可悲。

换上新的表示，Value 可以**装下一个** double，但它和 double 并不**等价**。从一个走到
另一个，中间必须过一道转换。我们得把代码过一遍，把这些转换插进去，才能让 clox 重新

### 一元取负与运行时错误

接下来最简单的操作是一元取负。它从栈上弹出一个值，取负，再把结果压回去。现在我们有别的
值类型了，不能再假定操作数是数字。用户完全可以写：

```lox
print -false; // 呃……
```

我们得体面地处理这种情况，也就是说，是时候上**运行时错误**了。在执行一个需要特定类型的
操作之前，先确认这个 Value **就是**那个类型。

对一元取负来说，检查长这样：

^code op-negate (1 before, 1 after)

先看栈顶那个 Value 是不是数字。不是的话，报运行时错误并<span name="halt">停掉</span>
解释器；是的话继续。只有这关验过了，我们才拆开操作数、取负、把结果裹好压回去。

<aside name="halt">

Lox 处理错误的做法相当……**简陋**。所有错误都是致命的，立刻停机。用户代码没有任何办法从
错误里恢复。如果 Lox 是门正经语言，这大概是我最先要改的事情之一。

</aside>

要取到这个 Value，我们用一个新的小函数。

^code peek

它从栈里返回一个 Value，但**不**把它<span name="peek">弹</span>出来。`distance`
参数说的是往栈顶往下数多远去找：零就是栈顶，一往下一格，以此类推。

<aside name="peek">

为什么不干脆先把操作数弹出来再检查？完全可以这么做。只是到了后面几章，把操作数留在栈上
就变得很重要了——万一操作中途触发了垃圾回收，回收器得能找到它们。我在这儿也这么干，
多半是习惯使然。

</aside>

报告运行时错误，我们用一个新的函数——接下来的书里它会一直被用到。

^code runtime-error

变参函数——接受不定数量参数的函数——你在 C 里肯定**调用**过，`printf()` 就是一个。但你
多半没**定义**过一个。这本书不是 C 语言<span name="tutorial">教程</span>，所以这里
我一带而过：`...` 和 `va_list` 那套东西，本质上是让我们能给 `runtimeError()` 传任意多个
参数。它再把这些转发给 `vfprintf()`，也就是 `printf()` 那个显式接收 `va_list` 的版本。

<aside name="tutorial">

如果你在找 C 教程，我推荐《C 程序设计语言》（The C Programming Language），通常叫
「K&R」，以纪念它的作者。它不算完全跟得上时代，但文字的质量足以弥补这一点。

[kr]: https://www.cs.princeton.edu/~bwk/cbook.html

</aside>

调用者可以给 `runtimeError()` 传一个格式串，后面跟若干个参数，就像直接调 `printf()` 那样。
`runtimeError()` 负责把这些参数格式化并打印出来。本章还用不上这个特性，但后面几章会生成
带其他数据的格式化错误消息。

在展示了那条「希望有点帮助」的错误消息之后，我们还要告诉用户，出错那一刻执行的是他代码的
哪一<span name="stack">行</span>。因为我们在编译器里留下了词法单元，可以拿它在编译进
字节码块的调试信息里查出行号。要是我们编译器干得对，这个行号就对应那段字节码所编译自的
源代码行。

查的时候用的是「当前字节码指令下标 **减一**」。因为解释器是先把指针推过一条指令、再执行
它，所以调用 `runtimeError()` 的那一刻，出事的是**上一条**指令。

<aside name="stack">

只报出错那一行，提供不了多少上下文。更好的做法是给出完整的调用栈追踪。可我们现在连函数
都还没有，也就没有调用栈可追。

</aside>

## 两种新类型

现有的 clox 代码全都能跑了。终于，可以加些新类型了。我们现在有了一台能跑的计算器，顺便
还做了一堆没必要的、疑神疑鬼式的运行时类型检查。内部已经能表示其他类型了，但用户的程序
还造不出这些类型的 Value。

至少现在还不行。我们从给三个新字面量加编译器支持开始：`true`、`false` 和 `nil`。它们
都很简单，一次性全做了。

数字字面量那边，我们得应付「数值有几十亿种可能」这件事。做法是把字面量的值存进字节码块的
常量表，再发一条字节码指令把那个常量载入。新类型其实也可以照办：比如把 `true` 存进
常量表，用 `OP_CONSTANT` 读出来。

可新类型要操心的值，说真的（嘿）就三个。为它们浪费一条两字节指令外加一个常量表条目，
既是多余的——而且<span name="small">慢</span>！

我们改为定义三条专用指令，各负责把其中一个字面量压到栈上。

<aside name="small" class="bottom">

我不是在开玩笑：为某些常量值单独设一条指令，确实更快。字节码虚拟机很大一部分执行时间都
花在读取和译码指令上。为了一段给定行为，需要的指令越少越简单，跑得就越快。为常用操作
准备短指令，是个经典优化。

比如说，Java 的字节码指令集里就有专门加载 0.0、1.0、2.0 以及 -1 到 5 这些整数的指令。
（不过如今多数成熟的 JVM 反正会先把字节码 JIT 编译成机器码再执行，所以这基本已经是个
历史遗留的优化了。）

</aside>

可我的主要目标是让你搞懂字节码编译器。我希望你开始把这么个观念吃透：**字节码指令不需要
紧贴着用户的源代码**。只要用户能看见的行为对得上，虚拟机爱用什么指令集、什么指令序列

表达式 `a != b` 和 `!(a == b)` 语义相同，所以编译器完全可以把前者当后者来编。不必搞一条
专门的 `OP_NOT_EQUAL`，输出一个 `OP_EQUAL` 再跟一个 `OP_NOT` 就行。同理，`a <= b` 和
`!(a > b)` <span name="same">一样</span>，`a >= b` 等于 `!(a < b)`。所以我们只需要三条
新指令。

<aside name="same" class="bottom">

`a <= b` **真的**总是等于 `!(a > b)` 吗？按 [IEEE 754][]，只要有一个操作数是 NaN，所有
比较运算都返回 false。也就是说 `NaN <= 1` 是 false，`NaN > 1` 也是 false。可我们的脱糖
却假定后者永远是前者的取反。

书里我们不纠结这个，但等你真去实现一门语言，这类细节就会要命。

[ieee 754]: https://en.wikipedia.org/wiki/IEEE_754

</aside>

<aside name="equal">

有些语言有「**隐式转换**」：不同类型的值，只要其中一个能转成另一个的类型，就算相等。比如
在 JavaScript 里，数字 0 等同于字符串「0」。这种松散到了一定程度就成了痛苦的来源，于是
JS 专门加了一个「严格相等」运算符 `===`。

PHP 认为字符串「1」和「01」等价，因为它们都能转成相等的数字——不过归根结底，是因为
PHP 是由一位洛夫克拉夫丁式的远古邪神设计出来，专为折磨心智而生的。

大多数把整数和浮点分开设类型的动态类型语言，只要数值相同就认为不同数值类型的值相等
（比如 1.0 等于 1）。可连这种看着人畜无害的便利，也能让大意的人栽跟头。

</aside>

每种值类型各有一个 case，负责比较值本身。各 case 这么像，你大概会想：直接 `memcmp()` 一下
两个 Value 结构体不就完了？问题在于，有了填充和大小不一的联合体字段，Value 里会含有没被
使用的比特。C 对那些比特里装着什么不作任何保证，所以两个相等的 Value 在那些用不上的
内存里完全可能不一样。
