我们说 Lox 是门「高层」语言，是因为它把程序员从那些与所解决问题无关的细节里解放出来。
用户成了一名管理者，给机器下达抽象的目标，让低贱的计算机自己去想办法怎么达成。

动态内存分配是自动化的绝佳候选。它是程序能跑起来的必要条件，手工去做既乏味又容易出错。
那些难免会犯的错误可能是灾难性的，导致崩溃、内存损坏或者安全漏洞。这正是那种机器比人
更擅长的活儿：风险与无聊并存。

这就是为什么 Lox 是一门**托管语言**——意思是语言实现替用户管理内存的分配与释放。当用户
执行一个需要动态内存的操作时，VM 自动分配。程序员从不需要操心释放任何东西。机器保证程序
用到的任何内存都会在需要的时间内一直存在。

Lox 营造出一种「计算机拥有无限内存」的幻觉。用户可以分配、分配、再分配，一次都不用想这些
字节是从哪来的。当然，计算机还没有真正**拥有**无限内存。所以托管语言维持这个幻觉的办法，
就是背着程序员把程序已经不需要的内存收回来。做这件事的组件叫**垃圾<span name="recycle">回收器</span>**。

<aside name="recycle">

「回收」其实是个更好的比喻。GC 并不把内存**扔掉**，而是把它收回来给新数据用。不过托管语言
比「地球日」还老，所以发明者选了他们熟悉的类比。

</aside>

## 可达性

这引出了一个出奇困难的问题：VM 怎么知道哪些内存是**不**需要的？只有将来还会被读取的内存才是
需要的，但除非有台时光机，实现怎么可能知道程序**将会**执行哪些代码、**将会**使用哪些数据？
剧透一下：VM 不能穿越到未来。于是语言只能做一个<span name="conservative">保守</span>的近似：如果一块内存**有可能**在将来
被读取，就认为它仍在使用中。

<aside name="conservative">

我这里说的「保守」是一般意义上的。确实存在一种叫「保守垃圾回收器」的东西，含义更具体。
所有垃圾回收器都在某种意义上是「保守」的：只要一块内存**可能**被访问，就让它活着，而不是
拥有一个能更精确预知哪些数据**将会**被访问的 Magic 8-Ball。

**保守式 GC** 是一种特殊的回收器：如果某块内存里的值看起来可能是个地址，它就把那块内存
当作指针。这与**精确式 GC** 相对——后者正是我们要实现的——它确切知道内存里哪些字是指针，
哪些存的是数字、字符串之类的其他值。

</aside>

这听起来**太**保守了。难道**任何**一块内存都有可能被读取吗？其实不然，至少在 Lox 这样的内存
安全语言里不会。举个例子：

```lox
var a = "first value";
a = "updated";
// GC here.
print a;
```

假设我们在第二行的赋值完成之后运行 GC。字符串 "first value" 仍然待在内存里，但用户的程序
已经没有任何办法够到它了。`a` 一被重新赋值，程序就失去了对那个字符串的任何引用。我们可以
安全地释放它。如果存在某种途径让用户程序引用到一个值，这个值就是**可达的**；否则，就像这里
的字符串 "first value" 那样，它是**不可达的**。

VM 可以直接访问很多值。看看这个：

```lox
var global = "string";
{
  var local = "another";
  print global + local;
}
```

在两个字符串刚拼好、`print` 语句还没执行的时候把程序暂停。VM 可以穿过全局变量表找到
`global` 对应的条目，从而到达 `"string"`。它可以遍历值栈、命中局部变量 `local` 所在的槽位，
从而找到 `"another"`。它甚至能找到拼接出来的字符串 `"stringanother"`，因为在我们暂停程序的
那一刻，这个临时值也还待在 VM 的栈上。

所有这些值都叫**根**。根是指 VM 不必经过其他对象里的引用就能直接到达的任何对象。大多数根
是全局变量或在栈上，但正如 we'll see，VM 还在另外几个地方存了它能找到的对象引用。

还有一些值要通过另一个值里的引用才能找到。类实例上的<span name="class">字段</span>是最明显
的情况，但我们还没有它们。即便没有这些，我们的 VM 仍然有间接引用。考虑：

<aside name="class">

我们[很快][classes]就会讲到！

</aside>

```lox
fun makeClosure() {
  var a = "data";

  fun f() { print a; }
  return f;
}

{
  var closure = makeClosure();
  // GC here.
  closure();
}
```

假设我们在标记行上暂停程序并运行垃圾回收器。当回收器做完、程序恢复执行时，它会调用那个
闭包，闭包进而打印 `"data"`。所以回收器需要**不**释放那个字符串。可我们暂停程序时栈的样子是：

<img src="image/garbage-collection/stack.png" alt="栈上只有脚本和闭包。" />

`"data"` 根本不在栈上。它已经被搬离栈，移进了闭包使用的那个已关闭的 upvalue 里。闭包本身
在栈上。但要够到那个字符串，我们得穿过闭包和它的 upvalue 数组。既然用户的程序**确实**可以
这么做，那么所有这些间接可达的对象也同样被认为是可达的。

<img src="image/garbage-collection/reachable.png" class="wide" alt="闭包引用的全部对象，以及从栈通向 'data' 字符串的路径。" />

这就给了我们一个关于可达性的归纳定义：

*   所有根都是可达的。

*   从一个可达对象引用到的任何对象，它自身也是可达的。

这些就是仍然「活着」、需要留在内存里的值。任何**不**满足这个定义的值，都任凭回收器收割。
这一对互相递归的规则，暗示着我们可以用一个递归算法来释放不需要的内存：

1.  从根出发，沿着对象引用遍历，找出全部可达对象的集合。

2.  释放所有**不**在这个集合里的对象。

如今有<span name="handbook">各种各样</span>的垃圾回收算法在用，但它们大致都遵循同样的结构。
有些可能会把两个步骤交错或混合，但那两个基本操作都在。它们主要区别在于**如何**执行每一步。

想探索别的 GC 算法的话，[**《垃圾回收手册》**][gc book]（Jones 等人）是权威参考。在这样一个
又深又窄的话题上，这样一本大书读起来还挺愉快。或者也许我对「乐趣」的理解有点奇怪。

## 标记-清除垃圾回收

第一款托管语言是 Lisp，它是继 Fortran 之后发明的第二门「高层」语言。约翰·麦卡锡（John
McCarthy）考虑过用手工内存管理或引用计数，但<span name="procrastination">最终</span>选择了
（并命名了）垃圾回收——程序一旦内存告急，就回头去找回那些没在用的存储空间。

<aside name="procrastination">

在约翰·麦卡锡的《Lisp 历史》里他写道：「既然我们决定了用垃圾回收，它的实际实现就可以往后
拖，因为当时做的都只是玩具例子。」我们选择把给 clox 加 GC 这件事一拖再拖，正是步巨人之后尘。

</aside>

他设计出了第一个、也是最简单的垃圾回收算法，叫做 **mark-and-sweep**，或者简称
**mark-sweep**。关于它的描述，在最初那篇 Lisp 论文里只占三个短段落。尽管它又老又简单，
同样的基本算法却支撑着许多现代内存管理器。CS 的某些角落似乎是不受时间影响的。

正如名字所暗示的，标记-清除分两个阶段：

*   **标记：** 我们从根出发，遍历或<span name="trace">**追踪**</span>这些根所引用的所有对象。
    这是一次对全部可达对象的经典图遍历。每当我们访问一个对象，就以某种方式把它**标记**起来。
    （不同实现在如何记录这个标记上各有差异。）

*   **清除：** 标记阶段一结束，堆里每个可达对象都已被标记。这意味着任何未被标记的对象都是
    不可达的，正等着被回收。我们遍历所有未标记的对象，把每一个都释放掉。

看起来大致是这样：

<img src="image/garbage-collection/mark-sweep.png" class="wide" alt="从一张对象图出发，先标记可达的那些，清除剩下的，最后只剩可达的。" />

<aside name="trace">

**追踪式垃圾回收器**指的是任何沿着对象引用图追踪的算法。这与引用计数相对，后者用的是另一套
追踪可达对象的策略。

</aside>

这就是我们要实现的东西。每当我们决定是时候回收一些字节了，我们就追踪一切、标记所有可达
对象、释放没被标记的那些，然后恢复用户的程序。

## 追踪对象引用

标记过程的下一步，是沿着对象之间的引用图追踪，找出间接可达的值。我们还没有带字段的实例，
所以含引用的对象不多，但我们确实<span name="some">有一些</span>。具体来说，ObjClosure 既
有它闭包捕获的 ObjUpvalue 列表，也有对它所包装的原始 ObjFunction 的引用。而 ObjFunction
本身又有一张常量表，里面装着函数体里创建的所有字面量的引用。对我们的回收器来说，这已经足够
织出一张相当复杂的对象之网去爬了。

<aside name="some">

我特意把这一章插在书的这个位置，正是**因为**我们现在有了闭包，能给垃圾回收器提供有意思的对象
来处理。

</aside>

现在是实现这个遍历的时候了。我们可以广度优先、深度优先，或者用别的顺序。既然我们只需要找出
全部可达对象的**集合**，访问它们的<span name="dfs">顺序</span>大多无关紧要。

<aside name="dfs">

我说「大多」，是因为有些垃圾回收器会按访问顺序搬动对象，所以遍历顺序决定了哪些对象最终在
内存里彼此相邻。这会影响性能，因为 CPU 靠局部性来决定该把哪些内存预载进缓存。

即便遍历顺序真的重要，也说不清哪种顺序**最好**。很难确定对象将来会按什么顺序被使用，所以 GC
很难知道哪种顺序对性能有帮助。

</aside>

### 三色抽象

当回收器在对象图里游走时，我们得确保它不会跟丢自己的位置，也不会绕圈子困住。这对增量式 GC
这类高级实现尤其要紧——它们会把标记与用户程序的部分执行交错起来。回收器必须能够暂停，
并在之后从停下的地方接着做。

为了帮我们这些脑子不太够用的人推理这个复杂过程，VM 黑客们想出了一个叫做 <span name="color"></span>**三色抽象** 的比喻。
每个对象都有一个概念上的「颜色」，用来跟踪对象处于什么状态、还剩什么工作要做。

<aside name="color">

高级垃圾回收算法常常会往这个抽象里再加别的颜色。我见过好几种灰，甚至在某些设计里有紫色。
可惜，我那张「淡紫-黄绿-洋红-孔雀石绿」色的回收器论文没被接收发表。

</aside>

*   **<img src="image/garbage-collection/gray.png" alt="一个灰色圆圈。"
    class="dot" /> 灰色：** 在标记过程中，我们第一次到达某个对象时，把它染成灰色。这个颜色
    表示我们知道该对象本身是可达的、不应被回收。但我们还没有**穿过**它去看它引用了**哪些**其他
    对象。用图算法的术语说，这就是**待处理列表**——我们已经知道但还没处理的那批对象。

*   **<img src="image/garbage-collection/black.png" alt="一个黑色圆圈。"
    class="dot" /> 黑色：** 当我们拿走一个灰色对象并标记了它引用的所有对象之后，就把这个灰色
    对象转成黑色。这个颜色表示标记阶段处理完了那个对象。

用这套抽象来说，标记过程现在长这样：

1.  一开始让所有对象都是白色。

2.  找出所有根，把它们标成灰色。

3.  只要还有灰色对象就重复：

    1.  挑一个灰色对象。把它提到的任何白色对象转成灰色。

    2.  把原来那个灰色对象标成黑色。

我发现这样想有助于理解。你有一张对象之间带引用的网。起初它们都是些白色小点。旁边有一些从 VM
进来的边指向那些根。那些根变成灰色。然后每个灰色对象的同胞变成灰色，而它自己变成黑色。
最终的效果是一道灰色波前扫过整张图，身后留下一片可达的黑色对象。不可达的对象波前碰都不碰，
一直是白色。

<img src="image/garbage-collection/tricolor-trace.png" class="wide" alt="一道灰色波前在节点图里推进。" />

到<span name="invariant">最后</span>，你剩下的是一片被触及的黑色对象海洋，其中散布着一座座
白色对象的小岛，可以被扫走并释放掉。一旦不可达的对象被释放，剩下的对象——全是黑色的——会
被重置为白色，进入下一个垃圾回收周期。

<aside name="invariant">

注意在这个过程的每一步，都没有任何黑节点指向白节点。这条性质叫做**三色不变式**。遍历过程
维持这条不变式，以确保可达的对象永远不会被回收。

</aside>

### 弱引用与字符串池

我们的回收工作几乎完成了。VM 里还剩一个角落对内存有着不寻常的要求。回想一下，我们给 clox
加字符串时让 VM 把它们全部驻留。这意味着 VM 有一张哈希表，里面装着指向堆里每一个字符串的
指针。VM 用它来给字符串去重。

在标记阶段，我们刻意**没有**把 VM 的字符串表当成根的来源。要是我们那么做了，就**永远**不会有任何<span name="intern">字符串</span>被回收。字符串表会一直长大，一个字节都不还给操作系统。那会很糟。

<aside name="intern">

这可能是个真问题。Java 并不驻留**所有**字符串，但它确实会驻留字符串**字面量**。它还提供了一
个 API 往字符串表里加字符串。很多年里，那张表的容量是固定的，加进去的字符串永远无法移除。
如果用户不留意自己使用 `String.intern()` 的方式，就可能耗尽内存并崩溃。

Ruby 多年来也有类似的问题：符号——被驻留的、类字符串的值——不会被垃圾回收。两者后来都让 GC
能够回收这些字符串了。

</aside>

与此同时，如果我们**确实**让 GC 释放字符串，那么 VM 的字符串表里就会留下一堆指向已释放内存的
悬垂指针。那会更糟。

字符串表很特殊，需要特殊支持。特别地，它需要一种特殊的引用。这张表应该能够引用一个字符串，
但这条链接在判定可达性时不该被当作根。这意味着被引用的对象是可以被释放的。那种情况下这个悬垂
引用也必须一并修好，有点像一个会自我清除的魔法指针。这一套语义出现得足够频繁，以至于它有了
名字：[**弱引用**][weak]。

[weak]: https://en.wikipedia.org/wiki/Weak_reference

我们已经隐式实现了字符串表那套独特行为的一半——因为我们在标记时**不**遍历它。这意味着它不会
强迫字符串保持可达。剩下的一半是清掉那些已被释放字符串的所有悬垂指针。

要移除对不可达字符串的引用，我们得知道哪些字符串**是**不可达的。而这要到标记阶段结束才知道。
但我们又不能等到清除阶段做完，因为那时对象——以及它们的标记位——都已经不存在、没法检查了。
所以正确的时机恰好是标记与清除两个阶段之间。

## 何时回收

我们现在有了一个功能完整的标记-清除垃圾回收器。压力测试标志打开时，它老是被调用，再加上
日志也打开，我们就能看着它干活，确认它确实在回收内存。但压力测试标志一关，它就完全不运行。
是时候决定在正常的程序执行中该何时调用回收器了。

就我能分辨的而言，这个问题在文献里回答得很糟。垃圾回收器刚被发明出来那会儿，计算机只有很少
一点固定内存。早期的许多 GC 论文都假设你预留几千个字的内存——换句话说就是绝大部分——然后一
用完就叫回收器。简单。

现代机器有好几 G 的物理内存，藏在操作系统更大的虚拟内存抽象背后，而这块虚拟内存要和一大堆
其他程序共享，大家都在争抢自己那份。操作系统会允许你的程序想申请多少就申请多少，然后在物理
内存满了的时候从磁盘换页进出。你永远不会真正「用完」内存，你只是变得越来越慢。

### 延迟与吞吐量

再等到「不得不」时才去跑 GC 已经没有意义了，所以我们需要一套更精细的时机策略。为了更精确地
推理这件事，是时候介绍衡量内存管理器性能时用到的两个基本数字了：**吞吐量**和**延迟**。

相比显式、由用户手写的释放，每一门托管语言都要付出性能代价。真正花在释放内存上的时间是
一样的，但 GC 还要花周期去弄清楚**哪些**内存该释放。那是**没有**花在跑用户代码、干有用工作上的
时间。在我们的实现里，那就是整个标记阶段。一个精巧的垃圾回收器的目标就是把这部分开销最小化。

有两个关键指标能帮我们更好地理解这份代价：

*   **吞吐量** 是花在跑用户代码上的时间占比，与花在垃圾回收工作上的时间之比。假设你跑一个
    clox 程序十秒，其中有一秒花在 `collectGarbage()` 里。那意味着吞吐量是 90%——90% 的时间在
    跑程序，10% 花在 GC 开销上。

    吞吐量是最基本的度量，因为它跟踪了回收开销的总成本。其他条件相同时，你想要吞吐量最大化。
    在本章之前，clox 压根没有 GC，因此吞吐量是 <span name="hundred">100%</span>。这 难超越。当然，代价是用户的程序只要跑得够久，就有可能耗尽内存而崩溃。你可以看作 GC 的目标
    就是修掉那个「小毛病」，同时尽可能少牺牲吞吐量。

    <aside name="hundred">

    嗯，不**完全**是 100%。它确实还是把分配出来的对象放进了一个链表，所以设置那些指针还是有
    一点微不足道的开销。

    </aside>

*   **延迟** 是用户程序被完全暂停、垃圾回收正在进行的**连续**时间的最长一段。它衡量的是
    回收器有多「成块」。延迟是完全不同于吞吐量的另一个指标。

    考虑同一个 clox 程序的两次运行，都花十秒。第一次运行里 GC 启动了一次，在一次大动作里
    实实在在地花了一秒在 `collectGarbage()` 上。第二次运行里 GC 被调用了五次，每次五分之一秒。
    花在回收上的**总**时间仍然是一秒，所以两种情况下吞吐量都是 90%。但第二次运行里，延迟只有
    五分之一秒，比第一次小了五倍。

    <span name="latency"></span>

    <img src="image/garbage-collection/latency-throughput.png" alt="一根代表执行时间的条，内部分成运行用户代码和运行 GC 的若干片。最大的 GC 片是延迟。所有用户代码片加起来是吞吐量。" />

    <aside name="latency">

    那根条代表一个程序的执行，被分成运行用户代码的时间和待在 GC 里的时间。最大的单片 GC 时间
    就是延迟。所有用户代码片加起来就是吞吐量。

    </aside>

    如果你喜欢类比，就想象你的程序是一家面包店，向顾客卖刚出炉的新鲜面包。吞吐量是你一天里能给
    顾客端上的温热酥脆法棍的总数。延迟是最不走运的那位顾客在轮到被服务之前要排队等多久。

    <span name="dishwasher">运行</span>垃圾回收器，就像临时关掉面包店，把所有餐具都过一遍，
    把脏的和干净的分开，然后洗掉用过的。在我们的类比里，我们没有专职洗碗工，所以这件事进行
    期间没人烘焙。面包师在洗碗。

    <aside name="dishwasher">

    如果每个人代表一个线程，那一个显而易见的优化就是让单独的线程跑垃圾回收，也就是得到一个
    **并发垃圾回收器**。换句话说就是雇几个洗碗工，别人烤面包的时候他们去清洗。这正是非常精巧的
    GC 的工作方式，因为这确实让面包师——工作线程——几乎不被打断地继续跑用户代码。

    不过这需要协调。你不希望一个洗碗工从面包师手里抢走一个碗！这种协调会增加开销和大量复杂度。
    并发回收器很快，但很难正确实现。

    <img src="image/garbage-collection/baguette.png" class="above" alt="一根法棍。" />

    </aside>

    一天少卖面包是坏事，让任何一位顾客坐着等你去洗完全部餐具也是坏事。目标是最大化吞吐量、
    最小化延迟，但即使在一家面包店里也没有免费的午餐。垃圾回收器在「牺牲多少吞吐量」和
    「容忍多少延迟」之间做出不同的取舍。

    能做这些取舍很有用，因为不同的用户程序有不同的需求。一个通宵跑的批处理作业，要从一 TB 的
    数据里生成一份报告，它只需要尽可能快地多干活。吞吐量至高无上。与此同时，一个跑在用户手机上
    的 app 需要对用户输入永远立刻响应，好让在屏幕上拖动顺滑得像<span name="butter">黄油</span>一样。这个 app 不能在
    GC 拖着那堆脏活的那几秒里冻住。

    <aside name="butter">

    显然这个面包房的类比已经钻进我脑子里了。

    </aside>

    作为垃圾回收器的作者，你可以通过选择回收算法来控制吞吐量与延迟之间的一部分取舍。但即便在
    同一个算法内部，我们对回收器运行的**频率**也有很多控制权。

    我们的回收器是一个<span name="incremental">**全停顿式 GC**</span>，意思是用户程序会被
    暂停，直到整个垃圾回收过程完成。如果我们隔很久才跑一次回收器，就会积累大量死对象。那会
    导致回收器运行时出现一段很长的暂停，从而带来高延迟。所以，显然我们希望非常频繁地跑回收器。

    <aside name="incremental">

    相对地，**增量式垃圾回收器**可以做一小会儿回收，然后跑一会儿用户代码，再回收一点，如此
    往复。

    </aside>

    但每次回收器运行时，它都要花些时间去访问活对象。那并不真的**做**任何有用的事（除了确保
    它们不会被错误地删掉）。访问活对象的时间既是不释放内存的时间，也是不跑用户代码的时间。
    如果你**非常**频繁地跑 GC，用户程序就来不及生成新垃圾给 VM 回收。VM 会把全部时间执念地、
    一遍又一遍地重访同一批活对象，吞吐量就会受损。所以，显然我们希望真正**不**频繁地跑回收器。

    事实上我们想要的是介于两者之间，而回收器运行的频率就是我们在延迟与吞吐量之间做取舍的
    主要旋钮之一。

### 自适应堆

我们希望 GC 运行得足够频繁以最小化延迟，又足够不频繁以维持不错的吞吐量。但当我们既不知道
用户程序需要多少内存、也不知道它多久分配一次时，怎么在这两者之间找到平衡？我们可以把这个问题
甩给用户，暴露 GC 调优参数逼他们自己选。很多 VM 就是这么做的。但如果我们这些 GC 作者都不
知道怎么调好，用户多半也不知道。他们应该得到一个合理的默认行为。

我跟你说实话，这不是我的专长。我跟若干职业 GC 黑客聊过——这是足以支撑起一整份职业的东西——
也读了不少文献，而我得到的全部答案都是……含糊。最后挑的策略很常见、相当简单，而且（希望！）
对大多数用途来说够用。

思路是让回收频率根据堆的存活内存量自动调整。我们跟踪 VM 已分配的托管内存总字节数。当它超过
某个阈值时，就触发一次 GC。回收之后，我们记下还剩下多少字节内存——有多少**没有**被释放。然后
把阈值调整到比那个值更大的数。

结果是：随着存活内存增加，我们降低回收频率，以免因为重访不断增长的那堆活对象而牺牲吞吐量。
随着存活内存下降，我们提高回收频率，好让等待时间不至于太久而损失太多延迟。

实现需要在 VM 里加两个新的记账字段。

^code vm-fields (1 before, 1 after)

第一个是 VM 已分配托管内存字节数的累计值。第二个是触发下一次回收的阈值。VM 启动时我们把它们
初始化好。

^code init-gc-fields (1 before, 2 after)

这里的初始阈值是<span name="lab">任意的</span>。它跟我们给各种动态数组挑的初始容量差不多。目标是既**太**快地触发
最初几次 GC，也不要等太久。如果我们有一些真实世界的 Lox 程序，就可以做性能剖析来调这个值。
但既然手上只有玩具程序，我就随便挑了个数。

<aside name="lab">

学习垃圾回收器的一个难点，是在一间孤立实验室里**非常**难发现最佳实践。除非你把回收器拿
到它真正针对的那种又大又乱的真实世界程序上跑，你根本看不出它实际表现如何。这就像调校一辆
拉力赛车——你得把它开到赛道上。

</aside>

每当我们分配或释放一些内存，就按那个差值调整计数器。

^code updated-bytes-allocated (1 before, 1 after)

当总量越过上限时，我们就跑回收器。

^code collect-on-next (2 before, 1 after)

现在，终于，我们这个垃圾回收器在用户没打开隐藏诊断标志跑程序时也会真的干点事了。清除阶段
通过调用 `reallocate()` 来释放对象，这会降低 `bytesAllocated` 的值，所以回收一结束，我们
就知道还剩多少活着的字节。我们据此调整下一次 GC 的阈值。

^code update-next-gc (1 before, 2 after)

阈值是堆大小的一个倍数。这样一来，随着程序使用的内存增长，阈值就往外挪，以限制重访更大存活
集合所花的总时间。和本章里其他数字一样，这个缩放因子基本上是任意的。

^code heap-grow-factor (1 before, 2 after)

等你的实现里有了真实程序可以拿来做基准时，你会想调调这个。现在我们至少可以把一些统计信息
记录下来。我们在回收之前捕获堆的大小。

^code log-before-size (1 before, 1 after)

然后在结束时把结果打印出来。

^code log-collected-amount (1 before, 1 after)

这样我们就能看出垃圾回收器运行时干成了多少事。

## 垃圾回收的 bug

理论上我们现在全都完成了。我们有了 GC。它周期性地启动、回收它能回收的，剩下的留下。要这是
一本典型教科书，我们就会掸掸手上的灰，沐浴在我们亲手造起的这座无瑕大理石建筑柔和的光辉里。

但我想教给你的不只是编程语言的理论，还有时而不适的真相。我要翻起一块腐烂的木头，让你看看
底下的臭虫，而垃圾回收器的 bug 确实是这世上最恶心的几种无脊椎动物之一。

回收器的职责是释放死对象、保住活对象。两个方向都很容易犯错。如果 VM 没能释放不需要的对象，
它就会慢慢泄漏内存。如果它释放了一个正在使用的对象，用户的程序就可能访问到非法内存。这些故障
往往不会立刻引发崩溃，这让我们很难倒溯时间去找到那个 bug。

更麻烦的是，我们不知道回收器什么时候会运行。任何最终会分配一些内存的调用，都是 VM 里一个
可能发生回收的地方。这就像 musical chairs。GC 随时可能停掉音乐。每一个我们想留住的、分配在堆
上的对象，都得在被清除阶段踢出局之前迅速找到一把椅子——被标记为根，或作为引用存在别的某个
对象里。

VM 后来用到某个它自己都看不见的对象，怎么可能？VM 又怎么找到它？最常见的答案是通过存在 C 栈
上某个局部变量里的指针。GC 会走 **VM 的**值栈和 CallFrame 栈，但 C 栈对它来说是<span name="c">不可见的</span>。

<aside name="c">

我们的 GC 找不到 C 栈里的地址，但很多 GC 可以。保守垃圾回收器会把整个内存都翻一遍，包括原生
栈。这一类里最有名的是 [**Boehm–Demers–Weiser 垃圾回收器**][boehm]，通常就叫「Boehm 回收器」。
（在 CS 里出名最快的路径，就是取一个字母顺序靠前的姓，这样它在排序后的名单里会排在最前面。）

[boehm]: https://en.wikipedia.org/wiki/Boehm_garbage_collector

连很多精确式 GC 也会走 C 栈。即便如此，它们也必须小心那些只存在于 **CPU 寄存器**里的、
指向活对象的指针。

</aside>

在前面的章节里，我们写过一些看似无意义的代码：把一个对象压进 VM 的值栈，做一点点工作，然后
马上又把它弹出来。大多数时候我都说这是为了 GC。现在你知道为什么了。压栈与弹栈之间的代码可能
分配内存，因而可能触发 GC。我们必须确保那个对象待在值栈上，好让回收器的标记阶段能找到它并
让它活着。

我是在把 clox 的整个实现拆成章节、写正文之前就全部写完的，所以我有充足的时间把这些边角都
找出来，并把其中大部分 bug 冲刷掉。本章开头放进去的压力测试代码加上一套相当不错的测试用例，
帮了大忙。

但我只修好了其中的**大部分**。我故意留下了一两个，因为我想让你体会一下在野外遇到这些 bug 是
什么滋味。如果你打开压力测试标志、跑几个玩具 Lox 程序，多半能碰上几个。试试看，**看看你自己
能不能修掉几个**。


### 往常量表里添加东西

你很可能会撞上第一个 bug。每个代码块所拥有的常量表是个动态数组。当编译器往当前函数的表里添加
一个新常量时，那个数组可能需要增长。而那个常量本身也可能是某个堆分配的对象，比如字符串或者
嵌套函数。

正在被加进常量表的那个新对象，会被传给 `addConstant()`。在那一刻，这个对象只能在 C 栈上
那个函数的参数里找到。那个函数把对象追加到常量表。如果表容量不够、需要增长，它会调用
`reallocate()`。这又触发一次 GC，而 GC 没能标记这个新的常量对象，于是在我们来得及把它加进
表之前就把它扫走了。崩溃。

修法跟你在别处见过的一样，是把这个常量临时压栈。

^code add-constant-push (1 before, 1 after)

一旦常量表里有了这个对象，我们再把它从栈上弹出来。

^code add-constant-pop (1 before, 1 after)

当 GC 标记根时，它会走一遍编译器链并标记其中每个编译器的函数，所以这个新常量现在是可达的了。
我们确实需要一个 include，才能从「chunk」模块调进 VM。

^code chunk-include-vm (1 before, 2 after)

### 驻留字符串

这里还有一个类似的。clox 里所有字符串都是驻留的，所以每当我们创建一个新字符串，也会把它
加进驻留表。你能猜到这要出问题。既然这个字符串是全新的，它在任何地方都不可达。而扩大字符串池
可能触发一次回收。于是我们照旧先把字符串暂存在栈上。

^code push-string (2 before, 1 after)

等它安全地落进表里之后，再把它弹出来。

^code pop-string (1 before, 2 after)

这保证了在表被扩容期间那个字符串是安全的。一旦熬过这一关，`allocateString()` 会把它返回给
某个调用者，由那个调用者负责确保在下一次堆分配发生之前这个字符串仍然可达。

### 拼接字符串

最后一个例子：在解释器那边，`OP_ADD` 指令可以用来拼接两个字符串。和处理数字一样，它把两个
操作数从栈上弹下来、算出结果、再把这个新值压回栈上。对数字来说这完全安全。

但拼接两个字符串需要在堆上分配一个新的字符数组，这又可能触发一次 GC。到那一步我们的操作数
字符串已经被弹下来了，所以它们可能被标记阶段漏掉然后扫走。我们不急着把它们弹下栈，而是 peek
它们。

^code concatenate-peek (1 before, 2 after)

这样，当我们创建结果字符串时，它们还挂在栈上。等那件事做完，我们就可以安全地把它们弹下来，
再用结果替换掉它们。

^code concatenate-pop (1 before, 1 after)

这些都相当容易，尤其是因为我**指出**了修法在哪儿。实际中，**找到**它们才是难的部分。你看到的
只是一个**本该**在那儿却不在那儿的对象。这跟别的那种「在找**导致**某个问题的代码」的 bug 不一样。
你要找的是代码的**缺失**——那段本该**防止**问题却没有的代码——这难找得多。

不过至少现在你可以放心了。据我所知，我们已经找齐了 clox 里所有的回收 bug，而现在我们有了一个
能工作、健壮、自我调谐的标记-清除垃圾回收器。

## 设计说明：分代回收器

一个回收器要是花很长时间重访那些还活着的对象，就会损失吞吐量。但如果它躲开回收、攒下一大堆
垃圾要蹚过去，又会增加延迟。要是有办法告诉我们哪些对象大概会长寿、哪些不会就好了。那样 GC
就能少去重访长寿对象、更频繁地清理短命对象。

结果还真有这么一种。很多年前，GC 研究者收集了真实世界运行程序中对象存活期的度量数据。他们
跟踪每一个对象从分配到最终不再需要的过程，然后绘制出对象通常能活多久。

他们发现了一个东西，称之为**分代假设**，或者用不那么客气的说法叫**婴儿死亡率**。他们的观察
是：大多数对象寿命很短，但一旦它们活过某个年纪，就会相当长时间地留在那里。一个对象**已经**活
得越久，它就很可能**继续**活得更久。这个观察很有力量，因为它给了他们一个抓手，把对象划分成
从频繁回收中获益的群体和不获益的群体。

他们设计出了一种叫**分代垃圾回收**的技术。它是这样工作的：每分配一个新对象，它就进入堆里
一个特殊的、相对较小的区域，叫做「苗圃」。由于对象往往英年早逝，垃圾回收器会<span name="nursery">频繁</span>地对仅仅这个区域做回收。

<aside name="nursery">

苗圃通常也是用复制式回收器来管理的，它在分配和释放对象上比标记-清除式回收器更快。

</aside>

GC 每次扫过苗圃就叫作一个「代」。任何不再需要的对象会被释放。活下来的那些现在被认为老了一代，
GC 会为每个对象跟踪这件事。如果一个对象熬过了若干代——往往只是一次回收——它就**晋升**了。
到这一步，它会被从苗圃复制到一个大得多的、给长寿对象用的堆区域里。垃圾回收器也会扫那个区域，
但频率低得多，因为那些对象很可能还活着。

分代回收器是实证数据——观察到对象寿命**并非**均匀分布——与巧妙的算法设计的一场漂亮联姻，
后者正好利用了这个事实。它们在概念上也相当简单。你可以把一个分代回收器想成两个分别调过
参数的 GC，加上一套把对象从一个搬到另一个的相当简单的策略。

</div>
