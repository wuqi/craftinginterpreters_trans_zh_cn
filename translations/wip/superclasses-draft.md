## 继承方法

我们先用方法继承热热身，因为它是比较简单的那一半。提醒一下自己，Lox 的继承语法长这样：

```lox
class Doughnut {
  cook() {
    print "Dunk in the fryer.";
  }
}

class Cruller < Doughnut {
  finish() {
    print "Glaze with icing.";
  }
}
```

这里，Cruller 类继承自 Doughnut，因此 Cruller 的实例继承了 `cook()` 方法。我不知道自己干吗
要把这事讲得这么啰嗦。你知道继承是怎么工作的。我们来编译这段新语法。

^code compile-superclass (2 before, 1 after)

编译完类名之后，如果下一个词法单元是 `<`，我们就找到了一个超类子句。我们吃掉超类的标识符
词法单元，然后调用 `variable()`。那个函数拿先前消费掉的那个词法单元，把它当成一个变量引用，
并发射代码去加载这个变量的值。换句话说，它按名字查出超类并把它压栈。

之后，我们调用 `namedVariable()` 把正在做继承的那个子类加载到栈上，紧跟着一条 `OP_INHERIT`
指令。那条指令把超类和新的子类接起来。上一章里，我们定义了 `OP_METHOD` 指令去修改一个已有的
类对象、往它的方法表里加一个方法。这条指令类似——`OP_INHERIT` 指令拿一个已有的类，把继承的
效果施加到它身上。

在上一个例子里，当编译器处理到这段语法时：

```lox

```

### 执行继承

现在来看这条新指令。

^code inherit-op (1 before, 1 after)

没有操作数需要操心。我们需要的两个值——超类和子类——都在栈上。这说明反汇编很简单。

^code disassemble-inherit (1 before, 1 after)

好戏在解释器这边。

^code interpret-inherit (1 before, 1 after)

从栈顶往下走，先是子类，然后是超类。我们把这两个都取出来，然后干继承那点活儿。clox 就是在这里
走上了跟 jlox 不同的路。在我们的第一个解释器里，每个子类都存着一个指向它超类的引用。方法
访问时，如果我们在子类的方法表里没找到方法，就沿着继承链递归下去，逐个查看每个祖先的方法表，
直到找到为止。

比如说，在一个 Cruller 实例上调用 `cook()`，会让 jlox 走上这么一段旅程：

<img src="image/superclasses/jlox-resolve.png" alt="在 Cruller 实例里解析对 cook() 的调用，意味着要走一遍超类链。" />

要在方法**调用**的时候干这么多活儿，很慢。更糟的是，一个继承来的方法在祖先链上位置越高，
它就越慢。不是个好的性能故事。

新办法快得多。子类声明的时候，我们把被继承那个类的所有方法全都复制进子类自己的方法表。
之后，**调用**方法时，任何从超类继承来的方法都会直接在子类自己的方法表里被找到。继承根本
不需要任何额外的运行时开销。到类声明完成的时候，活儿就干完了。这意味着继承来的方法调用跟
普通方法调用一样快——就<span name="two">一次</span>哈希表查找。

<img src="image/superclasses/clox-resolve.png" alt="在 Cruller 实例里解析对 cook() 的调用，这个方法就在它自己的方法表里。" />

<aside name="two">

好吧，我猜是两次哈希表查找。因为我们首先得确认实例上有没有字段遮蔽了那个方法。

</aside>

我偶尔听人把这套技术叫作「复制下沉继承」。它简单又快，但和大多数优化一样，你只能在特定约束
下用它。它在 Lox 里行得通，是因为 Lox 的类是**封闭**的。一个类声明一旦执行完毕，这个类的方法
集合就永远不会再变。

在 Ruby、Python 和 JavaScript 这样的语言里，你可以把一个已有的类<span name="monkey">撬开</span>，
往里头塞些新方法，甚至把方法删掉。那会毁掉我们的优化，因为如果那些修改恰好发生在子类声明
执行**之后**、作用在超类身上，子类就接收不到这些改动。这会破坏用户的预期——继承总是要反映
超类的当前状态。

<aside name="monkey">

你可以想象，在运行时用命令式的方式改变一个类所定义的方法集合，会让程序变得难以推理。
这是个非常有用的工具，但也是个危险的工具。

觉得这个工具也许有点**太**危险的人，给它取了个不够体面的名字，叫「猴子补丁
（monkey patching）」，或者更不体面的「鸭子重拳（duck punching）」。

<img src="image/superclasses/monkey.png" alt="一只戴着眼罩的猴子，自然了。" />

</aside>

对我们来说这是幸运（不过对喜欢这个特性的用户来说恐怕不是），Lox 不让你改猴子，也不让你捶鸭子，
所以我们可以放心地应用这项优化。

那方法覆盖呢？把超类的方法复制进子类的方法表，会不会跟子类自己的方法撞车？幸好不会。我们在
在创建子类的 `OP_CLASS` 指令之后、任何方法声明和 `OP_METHOD` 指令被编译之前，发射
`OP_INHERIT`。在我们把超类的方法复制下去的那一刻，子类的方法表是空的。子类覆盖的任何方法
都会盖掉表里那些继承来的条目。

### 无效的超类

我们的实现又简单又快，这正合我对虚拟机代码的口味。但它不健壮。没有任何东西能阻止用户从一个
根本不是类的对象继承：

```lox
var NotClass = "So not a class";
class OhNo < NotClass {}
```

显然，没有自尊的程序员才不会写这种代码，但我们得防着那些没自尊的潜在 Lox 用户。一个简单的
运行时检查就解决了。

^code inherit-non-class (1 before, 1 after)

如果从超类子句里那个标识符加载出来的值不是 ObjClass，我们就报一个运行时错误，让用户知道我们
怎么看他和他的代码。

## 存放超类

你注意到了吗？加上方法继承的时候，我们其实并没有从子类往超类加任何引用。复制完继承来的方法
之后，我们就把超类彻底忘了。我们不需要攥着超类的把手，所以就不攥。

但这还不够支撑 super 调用。由于子类<span name="may">可能</span>覆盖了超类的方法，我们需要
能够拿到超类的方法表。在讲那套机制之前，我想先帮你回忆一下 super 调用是怎么做静态解析的。

<aside name="may">

「可能」这个词也许还不够重。那个方法**多半**已经被覆盖了。不然的话，你费劲用 `super` 而不是
直接调用它是干嘛？

</aside>

在 jlox 的太平盛世里，我给你看过[这个棘手的例子][example]，用来解释 super 调用是怎么分派的：

[example]: inheritance.html#semantics

```lox
class A {
  method() {
    print "A method";
  }
}

class B < A {
  method() {
    print "B method";
  }

  test() {
    super.method();
  }
}

class C < B {}

C().test();
```

在 `test()` 方法体内部，`this` 是一个 C 的实例。如果 super 调用是相对于**接收者**的超类来
解析的，那我们就会去查 C 的超类 B。但 super 调用是相对于**调用发生处那个外层类的**超类来
解析的。在这个例子里，我们身处 B 的 `test()` 方法，所以超类是 A，程序应该打印 "A method"。

这意味着 super 调用不是根据运行时实例动态解析的。用来查找方法的超类是一个静态的——几乎是
词法的——性质，由调用发生的位置决定。当我们给 jlox 加上继承时，我们利用了它静态的这一面：把
超类存进我们用于所有词法作用域的那个 Environment 结构体里。解释器看上面那段程序，几乎就像
这样：

```lox
class A {
  method() {
    print "A method";
  }
}

var Bs_super = A;
class B < A {
  method() {
    print "B method";
  }

  test() {
    runtimeSuperCall(Bs_super, "method");
  }
}

var Cs_super = B;
class C < B {}

C().test();
```

每个子类都有一个隐藏变量，存着一个指向它超类的引用。每当我们需要执行一次 super 调用，就从
那个变量里取出超类，然后告诉运行时从那儿开始找方法。

clox 我们走同样的路。区别在于，jlox 用的是堆上分配的 Environment 类，而我们用的是字节码
虚拟机的值栈加上上值系统。机制稍有不同，但整体效果一样。

### 一个超类局部变量

我们的编译器已经发射代码把超类加载到栈上了。与其让那个槽位当临时值用，我们新建一个作用域，
把它变成一个局部变量。

^code superclass-variable (2 before, 2 after)

新建一个词法作用域保证了：如果我们在同一个作用域里声明两个类，它们各自有一个不同的局部
槽位来存自己的超类。因为我们总是把这个变量命名为 "super"，如果不给每个子类都开一个作用域，
这些变量就会撞车。

我们把这个变量命名为 "super"，理由和我们把 `this` 表达式解析到的那个隐藏局部变量命名为
"this" 完全一样："super" 是保留字，这保证了编译器的隐藏变量不会跟用户定义的变量撞车。

区别在于：编译 `this` 表达式时，我们手边正好有一个词素为 "this" 的词法单元。这里我们没这么
走运。我们改为加一个小的辅助函数，为给定的<span name="constant">常量</span>字符串造一个
合成的词法单元。

^code synthetic-token

<aside name="constant" class="bottom">

我说「常量字符串」，是因为词法单元对自己的词素不做任何内存管理。如果我们用一个堆上分配的
字符串来干这件事，就会泄漏内存，因为它永远不会被释放。但 C 字符串字面量的内存住在可执行文件的
常量数据段里，永远不需要释放，所以没问题。

</aside>

既然我们为超类变量开了一个局部作用域，就得把它关掉。

^code end-superclass-scope (1 before, 2 after)

编译完类体和它的方法之后，我们弹出这个作用域，把 "super" 变量丢弃掉。这样一来，这个变量在
子类的所有方法里都能访问到。这是个多少有点没必要的优化，不过我们只在**确实有**超类子句时
才建这个作用域。所以也只有在有超类子句时才需要关掉它。

要记住这一点，我们本可以在 `classDeclaration()` 里声明一个小的局部变量。但很快，编译器里的
其他函数也需要知道外层那个类是不是子类。所以不妨顺手给未来的自己帮个忙，现在就把这个事实
存成 ClassCompiler 里的一个字段。

^code has-superclass (2 before, 1 after)

我们第一次初始化一个 ClassCompiler 时，假定它不是子类。

^code init-has-superclass (1 before, 1 after)

然后，如果看到超类子句，我们就知道自己在编译一个子类。

^code set-has-superclass (1 before, 1 after)

这套机制给了我们一个运行时手段：可以在子类的任何一个方法内部访问外层子类的超类对象——只要
发射代码加载那个叫 "super" 的变量就行。那个变量是方法体外面的一个局部变量，但我们已有
的上值支持让虚拟机能在方法体内部、甚至在嵌套于该方法的函数里捕获这个局部变量。

## Super 调用

运行时支持到位了，我们准备实现 super 调用。和平常一样，我们从前到后，先从新语法开始。super
调用自然是以 `super` 关键字<span name="last">开始</span>的。

<aside name="last">

就到这儿了，朋友。你要往解析表里加的最后一条记录。

</aside>

^code table-super (1 before, 1 after)

表达式解析器落到一个 `super` 词法单元上时，控制权跳到一个新的解析函数，它开头是这样的：

^code super

这跟我们编译 `this` 表达式的方式相当不同。与 `this` 不同，`super` 的<span name="token">词法
单元</span>不是一个独立的表达式。相反，紧跟它后面的点号和方法名是语法不可分割的一部分。不过，
那个带括号的实参列表是分开的。和普通的方法访问一样，Lox 允许你取到超类方法的一个引用、把它
当成闭包，而不调用它：

<aside name="token">

假设性问题：如果一个光秃秃的 `super` 词法单元**真**是个表达式，它会求值成什么类型的对象？

</aside>

```lox
class A {
  method() {
    print "A";
  }
}

class B < A {
  method() {
    var closure = super.method;
    closure(); // Prints "A".
  }
}
```

换句话说，Lox 其实没有 super **调用**表达式，它有的是 super **访问**表达式，你可以选择要不要
立刻调用它。所以当编译器遇到一个 `super` 词法单元时，我们消费掉后面那个 `.` 词法单元，然后
去找方法名。方法是动态查找的，所以我们用 `identifierConstant()` 取方法名词法单元的词素，像处理
属性访问表达式那样把它存进常量表。

编译器消费掉那些词法单元之后做的事是这样的：

^code super-get (1 before, 1 after)

为了在**当前实例**上访问一个**超类方法**，运行时需要两样东西：接收者**和**外层方法所属类的
超类。第一次 `namedVariable()` 调用生成代码，去查找存在隐藏变量 "this" 里的当前接收者并压栈。
第二次 `namedVariable()` 调用发射代码，去从它的 "super" 变量里查出超类并压在接收者上面。

最后，我们发射一条新的 `OP_GET_SUPER` 指令，操作数是方法名在常量表里的索引。要在脑子里同时
装这么多东西可真够呛。来看这个例子程序，让它具体一点：

```lox
class Doughnut {
  cook() {
    print "Dunk in the fryer.";
    this.finish("sprinkles");
  }

  finish(ingredient) {
    print "Finish with " + ingredient;
  }
}

class Cruller < Doughnut {
  finish(ingredient) {
    // No sprinkles, always icing.
    super.finish("icing");
  }
}
```

为 `super.finish("icing")` 这个表达式生成的字节码，长这样、也这样工作：

<img src="image/superclasses/super-instructions.png" alt="调用 super.finish() 所生成的那串字节码指令。" />

前三条指令让运行时拿到做 super 访问所需的三份信息：

1.  第一条指令把**实例**加载到栈上。

2.  第二条指令加载**方法解析时所依据的那个超类**。

3.  然后新的 `OP_GET_SUPER` 指令把**要访问的方法名**编码成操作数。

剩下的指令就是求值一个实参列表并调用函数的常规字节码。

我们差不多准备好在解释器里实现新的 `OP_GET_SUPER` 指令了。但在那之前，编译器有些错误是它
该负责报的。

^code super-errors (1 before, 1 after)

super 调用只有在一个方法体内部（或者嵌套在方法内部的函数里）才有意义，而且只有在一个「有超类
的类」的方法内部才有意义。这两种情况我们都用 `currentClass` 的值来检测。如果它是 `NULL`，
或者指向一个没有超类的类，我们就报这些错误。

### 执行 super 访问

假设用户没有把 `super` 表达式放在不被允许的位置，他的代码就从编译器交到了运行时手里。我们有
了一条新指令。

^code get-super-op (1 before, 1 after)

我们像处理其他以常量表索引为操作数的操作码那样给它写反汇编。

^code disassemble-get-super (1 before, 1 after)

你可能以为会难一些，但解释这条新指令跟执行一次普通的属性访问差不多。

^code interpret-get-super (1 before, 1 after)

和属性一样，我们从常量表读出方法名。然后把它传给 `bindMethod()`，它在给定类的方法表里查出
这个方法，并创建一个 ObjBoundMethod，把查到的闭包和当前实例捆在一起。

关键的<span name="field">差别</span>在于我们传给 `bindMethod()` 的是**哪个**类。普通的属性
访问里，我们用的是那个 ObjInstance 自己的类，这给了我们想要的多态分派。而 super 调用不用
实例的类，我们用的是包含它的那个类静态解析出来的超类——编译器已经很贴心地保证它正待在栈顶
上等着我们。

我们把那个超类弹出来传给 `bindMethod()`，它会正确地跳过超类和实例自己的类之间任何子类里的
覆盖方法。它也正确地包含了超类从**它**自己的那些超类继承来的任何方法。

剩下的行为就一样了。弹出超类之后，栈顶是那个实例。`bindMethod()` 成功时，它弹出实例、压入
新的绑定方法。否则它报一个运行时错误并返回 `false`。那种情况下，我们中止解释器。

<aside name="field">

跟 `OP_GET_PROPERTY` 相比，另一个差别是我们不会先去查找可能遮蔽的字段。字段是不被继承的，
所以 `super` 表达式总是解析到方法。

如果 Lox 是一门基于原型的语言，用**委托**代替**继承**，那么就不是一个**类**继承另一个**类**，
而是实例继承（「委托给」）其他实例。那种情况下，字段**是**可以被继承的，我们就得在这里检查它们。

</aside>

### 更快的 super 调用

现在 super 类方法访问已经能用了。而既然返回的对象是一个你随后可以调用的 ObjBoundMethod，
super **调用**也就跟着能用了。和上一章一样，我们到达了一个语义完整正确的点。

但也和上一章一样，它相当慢。又一次，我们为每次 super 调用在堆上分配一个 ObjBoundMethod，
尽管大多数时候紧跟着的下一条指令就是一条 `OP_CALL`，会立刻把这个绑定方法拆开、调用它、然后
扔掉。事实上，对 super 调用来说，这比普通方法调用还更可能成立。至少在方法调用那里，还有
一种可能是用户真的在调用一个存在字段里的函数。而 super 调用，你**永远**是在查一个方法。唯一的
问题只是你会不会立刻调用它。

编译器如果在超类方法名后面看到一个左括号，自然就能自己回答这个问题。所以我们照做方法调用时
那一套优化。把加载超类并发射 `OP_GET_SUPER` 的那两行代码拿掉，换成这个：

^code super-invoke (1 before, 1 after)

现在，在发射任何东西之前，我们先去找一个带括号的实参列表。找到了就编译它。然后加载超类。
之后发射一条新的 `OP_SUPER_INVOKE` 指令。这条<span name="superinstruction">超级指令</span>把
`OP_GET_SUPER` 和 `OP_CALL` 的行为合在了一起，所以它带两个操作数：要查找的方法名在常量表里
的索引，以及要传给它的实参个数。

最后，流水线把我们直接倒进了解释器里。

^code interpret-super-invoke (2 before, 1 after)

就这么几行代码，基本上就是我们 `OP_INVOKE` 的实现，掺上一点 `OP_GET_SUPER`。不过栈的组织
方式还是有些差别。在未优化的 super 调用里，超类会在调用的实参求值**之前**被弹出、换成解析
出来的那个函数的 ObjBoundMethod。这保证了等到 `OP_CALL` 执行时，绑定方法位于实参列表**下面**，
正是运行时做闭包调用时期待的位置。

用上我们的优化指令，顺序就有点打乱了：

<img src="image/superclasses/super-invoke.png" class="wide" alt="用 OP_SUPER_INVOKE 调用 super.finish() 所生成的那串字节码指令。" />

现在解析超类方法成了**调用**的一部分，所以在查方法的那一刻，实参必须已经在栈上了。这意味着
超类对象位于实参之上。

除此之外，行为大致等同于一条 `OP_GET_SUPER` 后跟一条 `OP_CALL`。首先，我们取出方法名和
实参个数这两个操作数。然后把超类从栈顶弹掉，好在它的方法表里查方法。这顺便让栈的状态正好
符合一次方法调用所需。

我们把超类、方法名和实参个数传给已有的 `invokeFromClass()` 函数。那个函数在给定类上查找
给定方法，并尝试以给定的参数个数发起一次调用。如果找不到方法，它返回 `false`，我们退出
解释器。否则，`invokeFromClass()` 会在调用栈上为方法的闭包压入一个新的调用帧。这会让解释器
缓存的调用帧指针失效，所以我们刷新 `frame`。

## 习题

1.  面向对象编程的一条信条是，类应该保证新对象处于一个有效状态。在 Lox 里，这意味着要定义
    一个初始化器来填充实例的字段。继承让事情复杂化了，因为实例必须按照继承链上所有类的标准都处于有效状态。

    容易的部分是记得在每个子类的 `init()` 方法里调用 `super.init()`。难的部分是字段。继承链上
    两个类不小心占用了同一个字段名，是没有任何东西能阻止的。这种情况发生时，它们会踩到对方的
    字段，还可能给你留下一个坏掉的实例。

    如果 Lox 是你的语言，你会怎么处理这个问题——如果非处理不可的话？如果你要改这门语言，就
    实现你的改动。

2.  我们的复制下沉继承优化之所以成立，只是因为 Lox 不允许你在类声明之后修改它的方法。这意味
    着我们不必担心子类里那些复制来的方法跟超类后来的改动失去同步。

    其他语言，比如 Ruby，**确实**允许事后修改类。这类语言的实现是怎么在支持类修改的同时保持
    方法查找效率的？

3.  在[jlox 讲继承那一章][inheritance]里，我出过一个实现 BETA 语言方法覆盖方式的题目。再做
    一遍，但这次是在 clox 里。下面是上次那道题的描述：

    在 Lox 里，和大多数别的面向对象语言一样，查找方法时我们从类层级的底部开始往上走——子类的
    方法优先于超类的方法。为了在一个覆盖方法内部够到超类的方法，你用 `super`。

    语言 [BETA][beta]采取的是[相反的思路][inner]。你调用一个方法时，它从类层级的**顶端**开始
    **往下**走。超类的方法赢过子类的方法。为了够到子类的方法，超类方法可以调用 `inner`，它
    有点像 `super` 的反面。它沿着层级链往下接到下一个方法。

    是超类方法掌控着子类何时、在何处被允许细化自己的行为。如果超类方法压根不调用 `inner`，
    那子类就根本没有办法覆盖或修改超类的行为。

    把 Lox 现有的覆盖和 `super` 行为拿掉，换成 BETA 的语义。简而言之：

    *   在一个类上调用方法时，继承链上位置**最高**的方法优先。

    *   在方法体内部，调用 `inner` 会沿着 `inner` 所在类与 `this` 所在类之间的继承链，去
        最近的子类里找一个同名方法。如果没有匹配的方法，这次 `inner` 调用什么都不做。

    举个例子：

    ```lox
    class Doughnut {
      cook() {
        print "Fry until golden brown.";
        inner();
        print "Place in a nice box.";
      }
    }

    class BostonCream < Doughnut {
      cook() {
        print "Pipe full of custard and coat with chocolate.";
      }
    }

    BostonCream().cook();
    ```

    它应该打印：

    ```text
    Fry until golden brown.
    Pipe full of custard and coat with chocolate.
    Place in a nice box.
    ```

    既然 clox 讲究的不只是实现 Lox，还要实现得好、足够快，这一回请带着效率的意识去解这道题。
