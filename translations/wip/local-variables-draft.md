这里大概藏着个「立足全球，眼观局部」的冷笑话，但我怎么也想不出来。

</aside>

但还有个更重要的原因：我们处理局部变量的做法，会跟我们实现全局变量时相当不同。在 Lox 里，全局变量是晚绑定的。这里的「晚」，意思是「编译时间之后才解析」。这有利于保持编译器简单，但性能上不怎么样。局部变量是一门语言里被使用最多的<span name="params">部件</span>之一。局部变量要是慢，**一切**就都慢。所以我们要给局部变量一套尽可能高效的方案。

<aside name="params">

函数形参也是重度使用的对象。它们的作用跟局部变量一样，所以我们会对它们采用同一套实现技术。

</aside>

好在词法作用域来帮我们了。名字就像它暗示的那样：词法作用域意味着我们只要看看程序的文本，就能解析出一个局部变量——局部变量**不是**晚绑定的。我们在编译器里做的每一份处理工作，都是我们**不必**在运行时再做的工作，所以我们的局部变量实现会极大地倚重编译器。

## 表示局部变量

在如今这个时代动手改造一门编程语言，有个好处：有层出不穷的前辈语言可供借鉴。那么 C 和 Java 是怎么管理它们的局部变量的呢？当然是放在栈上！它们通常用芯片和操作系统提供的原生栈机制。这对我们来说有点太底层了，不过在 clox 这个虚拟世界里，我们有自己的栈可用。

眼下，我们只用它来保存**临时值**——计算表达式时需要记住的短命数据块。只要不妨碍那些临时值，我们也可以把自己的局部变量塞进栈里。这对性能极好。给一个新的局部变量分配空间，只需要把 `stackTop` 指针加一；释放同样是减一。从一个已知的栈槽位访问变量，就是一次带下标的数组查表。

不过我们确实得小心。虚拟机期望这个栈表现得像——嗯——一个栈。我们得接受：只能在栈顶分配新的局部变量；也只能接受在栈上它上面什么都没有时，才能丢弃一个局部变量。另外，我们得确保临时值不来捣乱。

方便的是，Lox 的设计跟这些约束**相安无事**。新的局部变量总是由声明语句创建的。而语句不会嵌套在表达式里，所以一条语句开始执行时，栈上绝不会有任何临时值。块则是严格嵌套的。一个块结束时，带走的总是最内层、最近声明的那些局部变量。既然它们也是最后才进入作用域的局部变量，那它们就该待在栈顶——正是我们需要它们在的地方。

<aside name="harmony">

这种吻合显然不是巧合。我当初把 Lox 设计成易于单遍编译成基于栈的字节码。可我并没有为了让语言符合这些限制而大幅改动它。它大部分的设计应该都会让人觉得相当自然。

这在很大程度上是因为，语言的历史跟单遍编译——以及（程度稍轻一些的）基于栈的架构——深深绑在一起。Lox 的块作用域沿着一条可以追溯到 BCPL 的传统。作为程序员，即使到今天，我们对一门语言里什么算「正常」的直觉，仍然受着当年那些硬件局限的塑造。

</aside>

一步步走过这个示例程序，看看局部变量是怎么进入和离开作用域的：

<img src="image/local-variables/scopes.png" alt="一系列局部变量以栈的方式进入和离开作用域。" />

看出它们跟栈配合得多完美了吗？看来运行时用栈来存局部变量是可行的。但我们能做得更进一步。我们不只是知道它们**会**在栈上，还能精确钉死它们在栈上的**哪个位置**。由于编译器确切知道任何时刻哪些局部变量在作用域内，它完全可以在编译过程中模拟这个栈，并记下每个变量住在栈的<span name="fn">哪里</span>。

我们会利用这一点，把这些栈偏移量当作读写局部变量的字节码指令的操作数。这让操作局部变量快得美味——像给数组下标一样简单。

<aside name="fn">

这一章里，局部变量从虚拟机栈数组的底部开始、并从那里算下标。等我们加上[函数][functions]，这套方案会稍微复杂一点。每个函数都需要在栈上有自己的一块区域，来放它的形参和局部变量。不过我们很快会看到，这带来的复杂度没有你想象的那么大。

</aside>

## 块语句

在能有任何局部变量之前，我们需要一些局部作用域。它们来自两样东西：函数体和<span name="block">块</span>。函数是一大块活儿，我们[后面某一章][functions]再去啃，所以眼下只做块。照例，我们从语法开始。我们要引入的新文法是：

```ebnf
statement      → exprStmt
               | printStmt
               | block ;

block          → "{" declaration* "}" ;
```

## 声明局部变量

通常这一节要从解析讲起，但我们的编译器已经支持解析并编译变量声明了。我们已经有了 `var` 语句、标识符表达式和赋值。只是编译器假定所有变量都是全局的。所以我们不需要新的解析支持，只需要把新的作用域语义接到现有代码上。

<img src="image/local-variables/declaration.png" alt="`varDeclaration()` 内部的代码流程。" />

变量声明的解析始于 `varDeclaration()`，并依赖另外几个函数。首先，`parseVariable()` 消费掉作为变量名的标识符词法单元，把它的词素作为字符串加进字节码块的常量表，然后返回它被加进去的那个常量表下标。接着，在 `varDeclaration()` 编译完初始化表达式之后，它调用 `defineVariable()`，发射把变量值存进全局变量哈希表的字节码。

这两个辅助函数都需要做些改动来支持局部变量。在 `parseVariable()` 里，我们加上：

^code parse-local (1 before, 1 after)

首先，我们把这个变量「声明」了。这是什么意思，我马上就说。然后，如果我们处在一个局部作用域里，就从这个函数退出。运行时，局部变量不是按名字查找的。没必要把变量的名字塞进常量表，所以如果这个声明位于一个局部作用域内，我们改为返回一个占位的表下标。

在 `defineVariable()` 那边，如果我们处在一个局部作用域里，需要发射存储局部变量的代码。长这样：

^code define-variable (1 before, 1 after)

等等，什么？没错。就是它。运行时没有任何代码用来创建局部变量。想一想虚拟机此刻处在什么状态。它已经执行完变量初始化器的代码（用户没写初始化器的话，就是那个隐式的 `nil`），那个值正待在栈顶，作为唯一剩下的临时值。我们也知道新的局部变量是在栈顶分配的……而那个值已经在那儿了。于是，什么都不用做。那个临时值就**变成**了局部变量。很难比这更高效了。

<span name="locals"></span>

<img src="image/local-variables/local-slots.png" alt="走一遍字节码执行，显示每个初始化器的结果最终落进该局部变量的槽位。" />

<aside name="locals">

左边的代码编译成右边的那串指令。

</aside>

好，那么「声明」到底声明了什么？它做的是这个：

^code declare-variable

这就是编译器记录这个变量存在的地方。我们只对局部变量这么做，所以如果我们在最外层的全局作用域里，就直接退出。因为全局变量是晚绑定的，编译器并不记录它见过它们的哪些声明。

但对局部变量来说，编译器确实需要记住这个变量存在。这正是声明它的作用——把它加进编译器「当前作用域的变量列表」。我们用另一个新函数来实现这一点。

^code add-local

它初始化编译器变量数组里下一个可用的 Local。它存下这个变量的<span name="lexeme">名字</span>，以及拥有它的那个作用域的深度。

<aside name="lexeme">

担心变量名那个字符串的生命周期？Local 直接存了标识符那个 Token 结构体的一份拷贝。词法单元存着指向其词素第一个字符的指针，以及词素的长度。那个指针指向正在编译的脚本（或 REPL 条目）的原始源代码字符串。

只要那个字符串在整个编译过程中还在（它当然得在——毕竟我们正在编译它），那么所有指向它的词法单元就都没问题。

</aside>

对一个正确的 Lox 程序，我们的实现够用了。但对错误的代码呢？我们尽量做得健壮些。要处理的第一个错误，其实不算用户的错，而更像是虚拟机的一个限制。操作局部变量的指令是按槽位下标引用它们的。那个下标存放在一个单字节操作数里，这意味着虚拟机同时只能支持最多 256 个在作用域内的局部变量。

如果我们超了这个数，不仅运行时没法引用它们，编译器自己的 locals 数组也会被覆写。我们来防住这一点。

^code too-many-locals (1 before, 1 after)

下一种情况更棘手。考虑这个：

```lox
{
  var a = "first";
  var a = "second";
}
```

在最外层，Lox 允许用跟先前声明相同的名字重新声明一个变量，因为这对 REPL 很有用。但在一个局部作用域里面，那是很<span name="rust">奇怪</span>的一件事。它很可能是个错误，而包括我们自己的 Lox 在内的许多语言，都把「这是错误」这条假定写进了成文。

有意思的是，Rust 这门语言**确实**允许这么干，而且地道的代码还依赖它。

注意，上面的程序跟这个是不同的：

```lox
{
  var a = "outer";
  {
    var a = "inner";
  }
}
```

在**不同**的作用域里有两个同名的变量是没问题的，即便这两个作用域有重叠、以至于两者同时可见。那叫遮蔽，而 Lox 确实允许。只有在**同一个**局部作用域里出现两个同名变量，才是个错误。

我们这样侦测那个错误：

^code existing-in-scope (1 before, 2 after)

先别担心那个奇怪的 `depth != -1`。我们后面会讲到它是怎么回事。

局部变量在声明时被追加到数组末尾，这意味着当前作用域永远在数组的尾部。声明一个新变量时，我们从末尾开始往前找，看看有没有一个已存在的同名变量。如果我们在当前作用域里找到了，就报告错误。否则，如果我们走到了数组开头、或者碰到一个属于别的作用域的变量，那我们就说明已经把作用域里所有已有变量都检查过了。

要看两个标识符是不是同一个，我们用这个：

^code identifiers-equal

既然我们知道两个词素的长度，就先查这个。对很多不相等的字符串，这一步会很快失败。如果<span name="hash">长度</span>相同，我们再用 `memcmp()` 检查字符。要用到 `memcmp()`，我们需要一个 include。

要是能比一比它们的哈希值，会是个挺不错的小优化。可词法单元还不是完整的 LoxString，所以我们还没算过它们的哈希。

^code compiler-include-string (1 before, 2 after)

有了这些，我们能让变量诞生了。可它们像幽灵一样，在被声明的那个作用域之外仍然赖着不走。一个块结束时，我们需要让它们安息。

^code pop-locals (1 before, 1 after)

弹出一个作用域时，我们从后往前走一遍局部数组，找出所有在我们刚离开的那个作用域深度上声明的变量。只要把数组长度减一，就把它们丢弃了。

这其中也有运行时的部分。局部变量占据栈上的槽位。当一个局部变量离开作用域，那个槽位就不再需要、应该被释放。所以对我们丢弃的每一个变量，我们还发射一条 `OP_POP` <span name="pop">指令</span>，把它从栈上弹掉。

当多个局部变量同时离开作用域时，你会得到一连串 `OP_POP` 指令，被一条条解释执行。你可以在自己的 Lox 实现里加一个简单的优化：一条专用的 `OP_POPN` 指令，它带一个操作数表示要弹掉多少个槽位，一次全弹掉。

## 使用局部变量

我们现在能编译并执行局部变量声明了。运行时，它们的值正待在栈上该待的地方。我们开始使用它们。变量访问和赋值我们一起做，因为它们碰的是编译器里同一批函数。

我们已经有了读写全局变量的代码，而且——像能干的小软件工程师那样——我们想尽可能多地复用那些现有代码。大概这样：

再往下一点，我们用这两个变量来发射正确的指令。赋值：

^code emit-set (2 before, 1 after)

访问：

^code emit-get (2 before, 1 after)

本章真正的心脏、我们解析局部变量的地方在这里：

尽管担子这么大，它很直截了当。我们走一遍当前在作用域内的局部变量列表。如果有一个跟标识符词法单元同名，那这个标识符必定指的就是那个变量。找到了！我们从后往前走数组，好找到**最后**声明的那个同名变量。这保证了内层局部变量能正确遮蔽外围作用域里的同名局部变量。

运行时，我们用栈槽位下标来加载和存储局部变量，所以编译器解析出变量之后要算的就是这个。每当一个变量被声明，我们都把它追加到 Compiler 的 locals 数组里。这意味着第一个局部变量在下标零处，下一个在下标一处，如此类推。换句话说，编译器里的 locals 数组，与运行时的虚拟机栈将有的布局**完全**相同。变量在 locals 数组里的下标，就是它的栈槽位。多方便啊！

如果走完整个数组都没找到给定名字的变量，那它一定不是局部变量。这种情况下，我们返回 `-1`，以示没找到、应当假定它是全局变量。

### 解释局部变量

我们的编译器正在发射两条新指令，我们来让它们跑起来。先是加载一个局部变量：

^code get-local-op (1 before, 1 after)

以及它的实现：

^code interpret-get-local (1 before, 1 after)

它取一个单字节操作数，表示该局部变量所在的栈槽位。它从那个下标加载出值，再把它压到栈顶，好让后面的指令能找到。

把这个局部变量的值再压一遍栈，似乎是多余的，因为它已经在栈上更靠下的某个地方了。问题在于，其他字节码指令只在栈的**顶部**找数据。这正是让我们的字节码指令集成为**基于栈**的核心特征。

[基于寄存器][reg]的字节码指令集能免去这种栈上的腾挪，代价是指令更大、操作数更多。

[reg]: a-virtual-machine.html#design-note

接下来是赋值：

^code set-local-op (1 before, 1 after)

它的实现你大概能猜到。

^code interpret-set-local (1 before, 1 after)

它从栈顶取走被赋的值，存进与该局部变量对应的栈槽位。注意，它并不把这个值从栈上弹掉。记住，赋值是一个表达式，而每个表达式都会产出一个值。赋值表达式的值就是被赋的值本身，所以虚拟机就把这个值留在栈上。

没有对这两条新指令的支持，我们的反汇编器就是不完整的。

^code disassemble-local (1 before, 1 after)

编译器把局部变量编译成对槽位的直接访问。局部变量的名字根本没有离开过编译器、进入字节码块。这对性能极好，可对内省就不那么友好了。反汇编这些指令时，我们没法像对全局变量那样显示变量名。我们只能显示槽位编号。

在编译器里抹掉局部变量名，这在我们哪天想为虚拟机实现调试器时会是个真问题。用户单步执行代码时，期望按名字看到局部变量的值。要支持这个，我们就得额外输出一些信息，记录每个栈槽位上局部变量的名字。

^code byte-instruction

### 另一个作用域边界情形

我们已经花了不少时间处理作用域周围几个古怪的边界情形。我们确保遮蔽能正确工作。我们会在同一局部作用域里两个变量同名时报错。不知为什么（我自己也没完全想明白），变量作用域似乎有不少这种皱褶。我从没见过哪门语言在这方面让人感觉完全**优雅**。

没有。连 Scheme 都不是。

本章结束前，我们还有一个边界情形要处理。还记得我们在 [jlox 的变量解析实现][shadow]里初次遇到的这只怪东西吗：

[shadow]: resolving-and-binding.html#resolving-variable-declarations

```lox
{
  var a = "outer";
  {
    var a = a;
  }
}
```

当时我们把一个变量的声明拆成两个阶段，把它斩杀了。这里我们再来一次：

<img src="image/local-variables/phases.png" alt="一个示例变量声明：变量名之前标着「已声明、未初始化」，初始化表达式之后标着「可以使用」。" />

变量声明一开始——也就是说，在它的初始化表达式之前——这个名字就在当前作用域里被声明了。这个变量存在，但处于一种特殊的「未初始化」状态。然后我们编译初始化表达式。如果在那个表达式的任何地方，我们解析出一个指回这个变量的标识符，就会看到它还没被初始化，于是报错。编译完初始化表达式之后，我们把这个变量标记为已初始化、可以使用。

要实现这一点，声明一个局部变量时，我们得想办法表示那个「未初始化」状态。我们本可以给 Local 加一个新字段，但在内存上我们还是抠一点的好。所以我们改把变量的作用域深度设成一个特殊的哨兵值：`-1`。

^code declare-undefined (1 before, 1 after)

稍后，等变量的初始化表达式编译完，我们把它标记为已初始化。

^code define-local (1 before, 2 after)

它是这样实现的：

^code mark-initialized

所以，这才是编译器里「声明」和「定义」一个变量**真正**的含义。「声明」是把变量加入作用域，「定义」是它变得可以使用。

当我们解析一个对局部变量的引用时，会检查作用域深度，看它是否已经定义完整。

^code own-initializer-error (1 before, 1 after)

如果这个变量还带着那个哨兵深度，那它必定是在引用自己初始化器里的变量，我们把这报告为一个错误。

这一章到此为止！我们加上了块、局部变量，以及货真价实的词法作用域。考虑到我们为变量引入了一套完全不同的运行时表示法，我们没写多少代码。最后的实现相当干净高效。

你会注意到，我们写的代码几乎全都在编译器里。在运行时那边，只有两条小指令。你会在 clox 里看到这是相对 jlox 一贯的**趋势**：优化器工具箱里最大的锤子之一，就是把工作前移到编译器，好让你在运行时不必再做。这一章里，这意味着精确解析出每个局部变量占据哪个栈槽位。这样一来，运行时就不需要任何查找或解析了。

你可以把静态类型看作这一趋势的一个极端例子。一门静态类型语言把全部的类型分析和类型错误处理都在编译期理清。这样运行时就不必浪费时间检查值的类型是否适合它要做的运算。事实上，在某些静态类型语言里（比如 C），你甚至在运行时**根本不知道**类型。编译器把值的一切类型表示完全抹掉，只留下光秃秃的比特。
