任何编译器或解释器的第一步都是<span name="lexing">扫描</span>。扫描器把原始源码
当成一串字符吃进来，再把它们归组成一串我们称为**词法单元**的块。它们就是构成语言语法的
那些有意义的「词」和「标点」。

<aside name="lexing">

这些年，这活儿时而叫「扫描」，时而叫「词法分析」（lexing）。早在计算机还跟 Winnebago
一样大、内存却比你的手表还少的年代，有些人用「扫描器」专指那段从磁盘读原始源码字符、
缓冲进内存的代码，而「词法分析」则是后面的阶段——拿这些字符干正事。

如今把源文件读进内存是件小事，所以在编译器里很少单独成一个阶段。也正因为如此，
这两个词基本可以互换。

</aside>

扫描对我们来说也是个好的起点，因为这代码不难——基本上就是一个自以为很了不起的
`switch` 语句。后面要啃更有意思的材料之前，先拿它热热身正合适。本章结束时，
我们会拥有一个功能齐全、速度飞快的扫描器：给它任意一段 Lox 源码，它能吐出词法单元，
下一章我们就把这些词法单元喂给解析器。

### 错误处理

搭框架的同时，还有一块关键的基础设施：**错误处理**。教科书有时会一带而过，
因为这更偏实际问题而不是正式的计算机科学问题。但如果你在意造出一门**好用**的语言，
那优雅地处理错误就至关重要。

我们的语言为对付错误所提供的工具，在它的用户界面里占了很大比重。用户代码正常跑着的时候，
他们根本不会想起我们的语言——脑子里全是**他们自己的程序**。通常只有出事的时候，
他们才会注意到我们的实现。

<span name="errors">这时候</span>，就得由我们来把用户需要的信息全给他，让他明白出了什么事，
再温和地把他引回他想去的地方。要做好这件事，就得在整个解释器的实现里都想着错误处理——
从现在开始。

<aside name="errors">

话虽如此，就**这个**解释器来说，我们要造的东西光剩个骨架。我很想聊聊交互式
调试器、静态分析器之类的好玩东西，但笔墨就那么多。

</aside>

^code lox-error

这个 `error()` 函数和它的 `report()` 帮手，会告诉用户某一行上出了个语法错误。这真的
只是「你**有**错误报告」这件事的最低门槛。想象一下，你不小心在某个函数调用里留了个
多余逗号，然后解释器打印出：

```text
Error: Unexpected "," somewhere in your code. Good luck finding it!
```

这可没什么帮助。我们至少得指出是哪一行。更好一点是给出起始列和结束列，好让他们知道是
行内**哪里**。比那更好的是把**出错那行显示给**用户，比如：

```text
Error: Unexpected "," in argument list.

    15 | function(first, second,);
                               ^-- Here.
```

我很想在这本书里实现个那样的东西，但老实说那是一大堆脏兮兮的字符串操作代码。
对用户很有用，但在书里读起来一点都不好玩，技术上也没什么意思。所以我们只留行号。
在你自己的解释器里，请照我说的做，别照我做的做。

我们把这个错误报告函数塞进主 Lox 类，首要原因就是那个 `hadError` 字段。它定义在这儿：

^code had-error (1 before)

我们用它来确保不会去执行已知有错的代码。另外，它还让我们能像个体面的命令行公民那样
用非零退出码退出。

^code exit-code (1 before, 1 after)

在交互循环里我们得重置这个标志。用户要是搞错了，不该整个会话都陪葬。

我把错误报告挪到这儿来，而不是塞进扫描器以及可能出错的其他阶段，另一个原因是要提醒你：
把**产生**错误的代码和**报告**错误的代码分开，是好的工程实践。

前端会有各个阶段去发现错误，但「怎么呈现给用户」其实不是它们的活。在一个功能齐全的
语言实现里，你很可能会用多种方式来显示错误：打到 stderr、显示在 IDE 的错误窗口、
记进日志文件等等。你不想让这些代码糊得到处都是，糊满你的扫描器和解析器。

理想情况下，我们该有个真正的抽象——某种<span name="reporter">「错误报告器」</span>接口，
传给扫描器和解析器，这样就能替换不同的报告策略。在我们这个简单的解释器里我没这么做，
但我至少把错误报告的代码挪进了另一个类。

<aside name="reporter">

我最初实现 jlox 的时候确实做了这么个东西。后来我把它拆了，因为对于这本书里这个
最小化的解释器来说，它显得过度设计了。

</aside>

## 词素与词法单元

这是一行 Lox 代码：

```lox
var language = "lox";
```

这里 `var` 是声明变量的关键字。那三个字符的序列「v-a-r」有含义。但如果从 `language`
中间抠出三个字母，比如「g-u-a」，它们单独看就没意义了。

这就是词法分析在做的事。我们的活儿是扫过那串字符，把它们归组成**还能表示点什么的**
最小序列。每个这样的字符团块叫做一个**词素**。在上面那行代码里，词素是：

<img src="image/scanning/lexemes.png" alt="'var', 'language', '=', 'lox', ';'" />

词素只是源码的原始子串。然而就在把字符序列归组成词素的过程中，我们还顺手捞到了一些
别的有用信息。把词素和那些别的数据捆在一起，产物就是一个词法单元。它包含诸如：

### 词法单元类型

关键字是语言语法形状的一部分，所以解析器里常有这种代码：「如果下一个词法单元是
`while` 就……」这意味着解析器不光要知道它拿到了某个标识符的词素，还得知道那是个
**保留**字，以及是**哪一个**关键字。

<span name="ugly">解析器</span>当然可以直接拿原始词素比字符串来给词法单元分类，但那又慢又难看。所以我们在
认出某个词素的同时，也记下它代表的是**哪一类**词素。每个关键字、运算符、标点符号、
字面量类型，我们都准备一个专门的类型。

<aside name="ugly">

说到底，字符串比较最后还是在逐个看字符，那不正是扫描器的活吗？

</aside>

^code token-type

### 字面量值

字面量值也有词素——数字啦字符串啦这类。既然扫描器本来就得逐个走过字面量里的字符才能
正确认出它，那它也可以顺手把这个值的文本表示，转换成之后解释器要用的那个活生生的
运行时对象。

### 位置信息

早先我还在大肆宣扬错误处理的时候，我们看到得告诉用户错误发生在**哪里**。位置追踪从
这儿开始。在这个简单的解释器里，我们只记词法单元出现在哪一行，但更精巧的实现还会
带上列号和长度。

<aside name="location">

有些词法单元的实现把位置存成两个数：一个是从源文件开头到词素开头的偏移量，
另一个是词素的长度。扫描器反正也得知道这些，所以算出来不花额外代价。

偏移量以后可以回头查源文件、数前面有几个换行符，换算成行列位置。听起来很慢，
确实很慢。但你只需要在**真的要给用户显示行列的时候**才做这件事。大多数词法单元一辈子
都不会出现在错误消息里。对它们来说，事先花在算位置上的时间越少越好。

</aside>

我们把这些数据统统装进一个类里。

^code token-class

现在我们有了一个结构足够完整、对解释器后续所有阶段都有用的对象。

## 正则语言与正则表达式

既然已经知道要产出什么，那就……产出吧。扫描器的核心是一个循环。从源码的第一个字符开始，
扫描器弄清楚这个字符属于哪个词素，然后吃掉它，以及跟在后面、属于同一个词素的那些字符。
到这个词素末尾，它就吐出一个词法单元。

然后它回到开头再干一遍，从源码里下一个字符重新开始。它就这么一直吃下去，偶尔，呃，
拉出一些词法单元，直到读完整个输入。

<span name="alligator"></span>

<img src="image/scanning/lexigator.png" alt="一条鳄鱼在吞字符，以及，嗯，后面那部分你就别知道了。" />

<aside name="alligator">

Lexical analygator.

</aside>

循环里那段「看一眼几个字符，判断它是哪种词素『匹配上了』」的部分，听起来可能有点熟。
如果你懂正则表达式，你可能会想：给每种词素都定义一条正则，用它们来匹配字符。比如
Lox 对标识符（变量名之类）的规则跟 C 一样。下面这条正则就能匹配一个：

```text
[a-zA-Z_][a-zA-Z_0-9]*
```

你要是真想到用正则表达式去认这些词素，说明你的直觉相当敏锐。决定一门语言如何把
字符归组成词素的那套规则，叫做它的<span name="theory">**词法文法**</span>。在 Lox 里，和大多数编程语言一样，
这套文法的规则简单到足以让这门语言被归类为一个**[正则语言][]**。这里那个「正则」
和正则表达式里的「正则」是同一个意思。

[regular language]: https://en.wikipedia.org/wiki/Regular_language

[**编译原理：原理、技术与工具**][dragon]（人称「龙书」）是这方面的权威参考。

你**完全**可以用正则精确认出 Lox 的所有词素，这底下也堆着一大堆有意思的理论，
解释为什么行、那意味着什么。像 [Lex][] 或 [Flex][] 这类工具就是专门为让你干这事而设计的——
把一把正则丢给它们，它们就把一个完整的扫描器<span name="lex">还</span>给你。

## 认出词素

循环的每一轮，我们扫描一个词法单元。这才是扫描器真正的心脏。我们从简单的开始。
想象一下要是每个词素都只有一个字符长。那你要做的就只是吃掉下一个字符，再给它挑个
词法单元类型。Lox 里确实有几个词素**就是**单字符的，那就从它们开始。

^code scan-token

<aside name="slash">

纳闷 `/` 怎么不在这儿？别急，我们待会儿就讲它。

</aside>

我们又需要几个帮手方法。

^code advance-and-add-token

`advance()` 方法吃掉源码里的下一个字符并返回它。`advance()` 管输入，
`addToken()` 管输出。它抓下当前词素的文本，给它造一个新词法单元。很快我们会用上
另一个重载版本，来处理带字面量值的词法单元。

### 词法错误

在走太远之前，先花点时间想想词法层面的错误。要是用户丢给我们一个源文件，里面有些
Lox 用不到的字符，比如 `@#^`，会怎么样？眼下这些字符会被悄悄丢掉。Lox 这门语言
不用它们，但这不代表解释器可以当它们不存在。于是我们报个错。

^code char-error (1 before, 1 after)

注意那个出错的字符仍然被前面那次 `advance()` 调用**吃掉了**。这很重要，不然我们会被
困在死循环里。

还要注意，我们<span name="shotgun">**继续扫描**</span>。程序后面可能还有别的错。尽可能一次性把那些错都发现出来，
能给用户更好的体验。否则他们就会看到一个不起眼的小错，把它修掉，然后下一个错才冒出来，
如此反复。语法错误打地鼠，一点都不好玩。

（别担心。因为 `hadError` 被设上了，我们绝不会去**执行**任何代码，哪怕扫描还会继续
把剩下的扫完。）

<aside name="shotgun">

这段代码每个非法字符都单独报一次，所以万一用户不小心粘进来一大坨怪文本，
等于一把霰弹枪把他轰个满脸。把连续的一段非法字符合并成一个错误，体验会更好。

</aside>

### 运算符

单字符词素已经能跑了，但这还没覆盖 Lox 的全部运算符。那 `!` 呢？它就一个字符，对吧？
有时候是，但要是紧接着下一个字符是等号，那我们就该造一个 `!=` 词素了。注意 `!` 和
`=` **不是**两个独立的运算符。你不能在 Lox 里写 `!   =` 然后指望它表现得像不等运算符。
这就是为什么我们得把 `!=` 当成一个词素来扫。同理，`<`、`>` 和 `=` 后面都能跟个 `=`，
组成另外那些相等和比较运算符。

这些全都需要看第二个字符。

^code two-char-tokens (1 before, 2 after)

那些情况用的是这个新方法：

^code match

它就像一个带条件的 `advance()`。只有当前字符正是我们要找的那个，我们才吃掉它。

用上 `match()`，我们分两个阶段来认词素。比如我们走到 `!`，就跳到它对应的 switch 分支。
这意味着我们知道词素**开头**是 `!`。然后再看下一个字符，判断我们面对的是 `!=` 还是
光秃秃一个 `!`。

## 更长的词素

我们还缺一个运算符：做除法的 `/`。这个字符需要一点特殊处理，因为注释也是用斜杠开头的。

^code slash (1 before, 2 after)

这跟别的双字符运算符类似，只不过当我们找到第二个 `/` 时，我们**不**就此结束这个词素。
我们继续吃字符，一直吃到行尾为止。

这就是我们处理更长词素的总策略：一旦认出开头，就转到某个词素专属的代码上去，
让它一直吃到结尾。

我们还有一个帮手：

^code peek

它有点像 `advance()`，但不吃掉字符。这叫<span name="match">**前瞻**</span>。因为它只看当前那个还没被吃掉的字符，
所以我们的前瞻量是**一个字符**。一般来说这个数越小，扫描器跑得越快。词法文法的规则
决定了我们需要多少前瞻。幸好，现实中大多数语言只往前看一两个字符。

<aside name="match">

严格说来，`match()` 也在做前瞻。`advance()` 和 `peek()` 是两个基本算子，`match()` 是
把它们组合了起来。

</aside>

注释也是词素，但它没有意义，解析器也不想跟它打交道。所以当我们走到注释末尾时，
我们**不**调 `addToken()`。等我们循环回去开始下一个词素，`start` 被重置，
这条注释的词素就一缕青烟般消失了。

既然说到这儿了，现在也正好把那些同样没意义的字符跳过去：换行和空白。

^code whitespace (1 before, 3 after)

碰到空白，我们就直接退回扫描循环的开头。这会在那个空白字符**之后**开始一个新词素。
换行也是这么处理，只不过我们还要把行号加一。（这就是为什么我们用 `peek()` 而不是
`match()` 去找注释末尾的换行——我们要的就是那个换行把我们送到这儿来，好更新 `line`。）

我们的扫描器越来越聪明了。它现在能对付相当自由的代码，比如：

```lox
// this is a comment
(( )){} // grouping stuff
!*+-/=<> <= == // operators
```

### 字符串字面量

既然长词素已经顺手了，我们就准备收拾字面量了。先做字符串，因为它们总是以某个特定字符
开头，就是 `"`。

^code string-start (1 before, 2 after)

它调用的是：

^code string

跟注释一样，我们一直吃字符，直到撞上结束字符串的那个 `"`。我们也体面地处理了
字符串还没闭合输入就完了的情况，并为此报个错。

不知为什么，Lox 支持多行字符串。这有好处也有坏处，但禁掉它比允许它稍微复杂一点，
所以我就留着了。这确实意味着我们在字符串里撞到换行时，也得更新 `line`。

最后一块有意思的地方是：造词法单元的时候，我们还顺带产出之后解释器要用的真正字符串
**值**。在这儿，这个转换只需要一个 `substring()` 把两头的引号剥掉。如果 Lox 支持
`\n` 这样的转义序列，我们就得在这儿把转义还原。

### 数字字面量

Lox 里所有数字在运行时都是浮点数，但整数和小数字面量都支持。一个数字字面量是一串
<span name="minus">数字</span>，后面可以跟一个 `.` 加一个或多个尾随数字。

<aside name="minus">

由于我们只找一个数字来开头，这就意味着 `-123` 不是一个数字**字面量**。相反，`-123`
是一个**表达式**，它把 `-` 用在数字字面量 `123` 上。实践上结果一样，不过如果我们以后
要给数字加方法调用，就会有一个有意思的边缘情况。想想：

```lox
print -123.abs();
```

它会打印 `-123`，因为取负的优先级低于方法调用。我们可以把 `-` 变成数字字面量的一部分
来修掉它。但再想想：

```lox
var n = 123;
print -n.abs();
```

这照样产出 `-123`，于是这门语言看起来就不一致了。你怎么折腾，总有个情况会变得莫名其妙。

</aside>

```lox
1234
12.34
```

我们不允许前导或尾随小数点，所以这两种都是非法的：

```lox
.1234
1234.
```

前一种要支持并不难，但我为了简单没做。后一种一旦我们想允许像 `123.sqrt()` 这样的
数字方法就会变得很怪。

要认出数字词素的开头，我们找任意一个数字就行。给十个十进制数字一个个加 case 有点
繁琐，所以我们干脆塞进 default 分支。

^code digit-start (1 before, 1 after)

这靠的是这个小工具：

^code is-digit

<aside name="is-digit">

Java 标准库提供了 [`Character.isDigit()`][is-digit]，看起来挺合适。可惜那个方法
还认天城文（Devanagari）数字、全角数字之类我们不想要的玩意儿。

[is-digit]: http://docs.oracle.com/javase/7/docs/api/java/lang/Character.html#isDigit(char)

</aside>

一旦确认我们在数字里，就分支到一个单独的方法去吃字面量的剩余部分，跟处理字符串时一样。

^code number

整数部分我们能找到多少数字就吃多少。然后我们找小数部分，也就是一个小数点（`.`）
后面跟至少一个数字。要是确实有小数部分，我们还是有多少数字吃多少。

要越过小数点去看，需要第二个字符的前瞻，因为我们不想在没确定后面还有数字**之前**就
把那个 `.` 吃掉。所以我们加上：

^code peek-next

<aside name="peek-next">

我本来可以让 `peek()` 收一个参数表示往前看几个字符，而不是定义两个函数，但那样就允许
**任意远**的前瞻了。提供这两个函数，能让读代码的人一眼看出我们的扫描器最多往前看两个
字符。

</aside>

最后，我们把词素转换成它的数值。我们的解释器用 Java 的 `Double` 类型表示数字，
所以我们产出这个类型的值。我们用 Java 自带的解析方法把这个词素转成真正的 Java double。
我们自己也能实现，但说实话，除非你是在为即将到来的编程面试临时抱佛脚，不然这不值得
你花时间。

剩下的字面量是布尔值和 `nil`，但我们把它们当关键字处理，这就引出了……

## 保留字与标识符

我们的扫描器快完工了。词法文法里剩下要实现的，就只有标识符和它的近亲——保留字。
你可能会想，我们可以用处理 `<=` 这种多字符运算符的同样办法去匹配 `or` 这样的关键字。

```java
case 'o':
  if (match('r')) {
    addToken(OR);
  }
  break;
```

想想如果用户把一个变量命名为 `orchid` 会怎样。扫描器会看到头两个字母 `or`，
立刻吐出一个 `or` 关键字词法单元。这就引出了一条重要的原则，叫<span name="maximal">**最长匹配**</span>。
当词法文法的两条规则都能匹配扫描器正在看的这段代码时，**谁匹配的字符多谁赢**。

这条规则的意思是，如果我们能把 `orchid` 匹配成标识符、把 `or` 匹配成关键字，
那前者赢。这也是为什么我们之前默认把 `<=` 扫成一个完整的 `<=` 词法单元，
而不是一个 `<` 后跟一个 `=`。

<aside name="maximal">

看看这段难缠的 C 代码：

```c
---a;
```

它合法吗？这取决于扫描器怎么切词素。万一扫描器是这么看的：

```c
- --a;
```

那就能解析了。但那会要求扫描器知道周边代码的语法结构，把事情搅得比我们想要的更乱。
所以最长匹配规则说，它**总是**会被扫成：

```c
-- -a;
```

哪怕这么扫会导致后面在解析器里出现语法错误，它也照样这么扫。

</aside>

最长匹配意味着，在走到「这可能其实是保留字」的边界之前，我们没法轻易判断出关键字。
毕竟保留字**就是**标识符，只不过被语言征用来自用了。「保留字」这个词就是这么来的。

于是我们先假设，任何以字母或下划线开头的词素都是标识符。

^code identifier-start (3 before, 3 after)

剩下的代码在这边：

^code identifier

我们用这几个帮手来定义它：

^code is-alpha

这样标识符就通了。至于关键字，我们去看这个标识符的词素是不是某个保留字。如果是，
就用那个关键字专属的词法单元类型。我们用一个 map 来定义保留字的集合。

^code keyword-map

扫完一个标识符之后，我们再检查它有没有匹配上 map 里的东西。

^code keyword-type (2 before, 1 after)

如果匹配上了，就用那个关键字的词法单元类型。否则，它就是个普普通通的用户自定义标识符。

至此，我们就有了覆盖整个 Lox 词法文法的完整扫描器。启动 REPL，敲点合法的和非法的代码进去。
它吐出的词法单元是你预期的吗？尽量想出一些有意思的边缘情况，看看它有没有照规矩处理。

## 设计说明：隐式分号

今天程序员在语言的选择上被宠坏了，对语法也变得挑剔起来。他们希望自己的语言看起来
干净、现代。几乎每门新语言都会刮掉的一层**语法地衣**（有些古老语言比如 BASIC
从来没有过），就是拿 `;` 当显式的语句终止符。

取而代之的是，他们在说得过去的地方，就把换行当作语句终止符。「说得过去」这部分才是
难点。虽然**大多数**语句都单独占一行，但有时候你需要把一条语句摊到好几行上。
这些混在中间的换行就不该被当成终止符。

换行该被忽略的那些显而易见的情况，大多很好检测，但还是有几个难缠的：

* 换行后跟着返回值：

    ```js
    if (condition) return
    "value"
    ```

    "value" 是被返回的值，还是说这是一条没有值的 `return` 语句，外加一条含字符串字面量的
    表达式语句？

* 换行后跟着一个带括号的表达式：

    ```js
    func
    (parenthesized)
    ```

    这是对 `func(parenthesized)` 的调用，还是两条表达式语句，一条是 `func`，另一条是
    带括号的表达式？

* 换行后跟着一个 `-`：

    ```js
    first
    -second
    ```

    这是 `first - second`（一个中缀减法），还是两条表达式语句，一条是 `first`，
    另一条是对 `second` 取负？

在这些例子里，把换行当分隔符或不当分隔符都能产出合法代码，但可能不是用户想要的那段代码。
各个语言用来决定哪些换行算分隔符的规则，简直多得让人不安。举几个：

*   [Lua][] 完全忽略换行，但它小心地设计语法，使得多数情况下根本不需要语句之间的分隔符。
    这是完全正当的：

    ```lua
    a = 1 b = 2
    ```

    Lua 是靠要求 `return` 语句必须是块里的最后一条语句来躲开 `return` 问题的。如果在
    `return` 之后、关键字 `end` 之前还有值，那这个值**必须**是给 `return` 的。至于另外
    两种情况，它们允许显式的 `;`，并期待用户真的去用。实践中这几乎从不发生，因为没人
    会写一条带括号或取负的表达式语句。

*   [Go][] 在扫描器里处理换行。如果换行出现在某几种已知可能结束语句的词法单元类型
    之后，这个换行就被当成分号；否则就忽略。Go 团队提供了一个规范的代码格式化工具
    [gofmt][]，而且生态圈对它的使用相当狂热，这就保证了惯用风格的代码能很好地配合
    这条简单规则。

*   [Python][] 把所有换行都当作有意义的，除非在行尾用反斜杠显式续行。不过，只要还
    处在某对括号（`()`、`[]` 或 `{}`）**里面**，任何位置的换行都会被忽略。惯用风格
    强烈偏好后者。

    这条规则对 Python 之所以有效，是因为它是一门高度面向语句的语言。特别是，
    Python 的文法确保语句绝不会出现在表达式内部。C 也一样，但很多有「lambda」或
    函数字面量语法的语言就不这样了。

    一个 JavaScript 的例子：

    ```js
    console.log(function() {
      statement();
    });
    ```

    这里 `console.log()` 这个**表达式**里含着一个函数字面量，函数字面量里又含有
    **语句** `statement();`。

    Python 如果想隐式接续行，就需要另一套规则了——让你在仍嵌套在括号里的情况下，
    能**回到**那些换行该变得有意义的<span name="lambda">语句</span>里去。

<aside name="lambda">

现在你知道为什么 Python 的 `lambda` 只允许单个表达式作为函数体了。

</aside>

*   JavaScript 的「[自动分号插入][asi]」规则才是真正奇怪的那个。别的语言大多假设
    **大多数**换行都是有意义的，只有少数几个在多行语句里该被忽略；JS 假设的正好相反。
    它把你的所有换行都当作无意义的空白，**除非**它撞上解析错误。真撞上了，它就回头
    试着把上一个换行变成分号，好让结果语法合法。

    要是把「这到底**怎么做到的**」连同「JavaScript 这套『方案』有多少种烂法」
    一起细讲，这篇设计说明就得变成一篇设计长文了。那是一团糟。JavaScript 是我唯一
    知道的、很多风格指南要求每条语句后面都写显式分号的语言——哪怕这语言理论上允许
    你省掉它们。

如果你在设计一门新语言，那你几乎肯定**应该**避开显式的语句终止符。程序员跟其他人类
一样，是追潮流的动物，而分号跟全大写关键字一样，早就过时了。只要确保你挑的那套规则
适合这门语言自己的文法和惯用法就行。还有，别学 JavaScript。

</div>
