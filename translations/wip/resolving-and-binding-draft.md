## 静态作用域

快速回顾一下：Lox 和大多数现代语言一样，采用**词法**作用域。这意味着，你不用做别的，
光读一读程序的文本，就能弄清一个变量名指的是哪个声明。例如：

```lox
var a = "outer";
{
  var a = "inner";
  print a;
}
```

这里我们知道，被打印的 `a` 是上一行声明的那个变量，而不是全局那个。运行程序并不会
——**也不可能**——改变这一点。作用域规则属于语言的**静态**语义，这也是它又叫**静态
作用域**的原因。

我一直没把这些作用域规则明说出来，但现在是时候讲究一下<span name="precise">精确性</span>了：

<aside name="precise">

这比起真正的语言规范，还差得远呢。那些规范文档必须写得如此明确，以至于哪怕是个火星
人、或者一个存心使坏的程序员，只要照着规范的条文来做，也**被迫**实现出正确的语义。

当一门语言可能被好几家互相竞争的公司各自实现，而这些公司又想让自家产品跟别家不兼容、
好把客户锁死在自己的平台上时，这种精确性就很重要了。好在写这本书，我们可以不去理会
这类见不得光的勾当。

</aside>

**一个变量用法，指的是在包住该用法的那个最内层作用域里、出现于它之前、名字相同的那个
声明。**

这句话里能拆的东西不少：

*   我说「变量用法」而不说「变量表达式」，是为了把变量表达式和赋值都涵盖进来。后面
    「该变量所用到的那个表达式」同样如此。

*   「出现于它之前」指的是**在程序文本里**出现在之前。

    ```lox
    var a = "outer";
    {
      print a;
      var a = "inner";
    }
    ```

    这里，被打印的那个 `a` 是外层那个，因为它出现在使用它的 `print` 语句<span
    name="hoisting">之前</span>。大多数情况下，在直线型的代码里，**文本上**排在前面的
    声明，**时间上**也会先于使用发生。但这并不总是成立。我们将会看到，函数可能把一整块
    代码推迟执行，使得它**动态的时序**执行不再与**静态的文本**顺序相对应。

    <aside name="hoisting">

    在 JavaScript 里，用 `var` 声明的变量会被隐式地「提升」（hoist）到块的开头。块里对
    这个名字的任何使用都会指向那个变量，哪怕那次使用出现在声明之前。当你在 JavaScript
    里写下：

    ```js
    {
      console.log(a);
      var a = "value";
    }
    ```

    它的行为等同于：

    ```js
    {
      var a; // 提升。
      console.log(a);
      a = "value";
    }
    ```

    这意味着，在有些情况下，你会在一个变量的初始化器尚未运行之前就读到它——一个恼人的
    bug 来源。后来语言为此加了一种声明变量的替代语法 `let`，来对付这个问题。

    </aside>

*   「最内层」这个词儿，是为了我们的老朋友——**遮蔽**。包围作用域里可能不止一个好变量
    用了同一个名字，比如：

    ```lox
    var a = "outer";
    {
      var a = "inner";
      print a;
    }
    ```

    我们的规则靠「最内层的作用域胜出」来消解这种情况的歧义。

既然这条规则完全没提任何运行时行为，那就意味着：在程序的整个执行过程中，一个变量表达式
永远指向同一个声明。到目前为止，我们的解释器**大体上**正确地实现了这条规则。可当我们
加入闭包时，一个错误悄悄溜了进来。

```lox
var a = "global";
{
  fun showA() {
    print a;
  }

  showA();
  var a = "block";
  showA();
}
```

<span name="tricky">在你把它敲进去、运行之前</span>，先想清楚你认为它**应该**打印出什么。

<aside name="tricky">

我知道，这是个彻头彻尾的病态、生造出来的程序。它就是**怪**。没有哪个正常人会写这样的
代码。唉，可要是你在编程语言这行混得够久，你生命中超出你预期的一大块时间，都会花在
对付这种畸形的代码片段上。

</aside>

好……想好了吗？如果你熟悉其他语言里的闭包，你会指望它打印两遍 "global"。第一次调用
`showA()` 肯定应该打印 "global"，因为我们那时甚至还没走到内层 `a` 的声明。而且按照
我们那条「一个变量表达式永远解析到同一个变量」的规则，这就意味着第二次调用 `showA()`
也应该打印同样的东西。

可惜，它打印出来的是：

```text
global
block
```

我要强调一下：这个程序自始至终没有重新给任何变量赋值，而且只含一条 `print` 语句。可
不知怎的，那条针对一个从未被赋值的变量的 `print` 语句，却在不同的时间点打印出了两个
不同的值。我们肯定在哪儿弄坏了什么东西。

### 作用域与可变环境

在我们的解释器里，环境是静态作用域的动态化身。这两者大体上是同步的——我们进入一个新
作用域时就创建一个新环境，离开作用域时就把它丢弃。我们对环境还执行另一种操作：在某个
环境里绑定一个变量。我们的 bug 正出在这里。

我们来一步步走一遍那个有问题的例子，看看每一步的环境长什么样。首先，我们在全局作用域里
声明 `a`。

<img src="image/resolving-and-binding/environment-1.png" alt="全局环境，其中定义着 'a'。" />

这样我们就得到了一个只含一个变量的环境。接着，我们进入块，执行 `showA()` 的声明。

<img src="image/resolving-and-binding/environment-2.png" alt="一个块环境，链接到全局环境。" />

我们为这个块得到了一个新环境。在它里面，我们声明了一个名字 `showA`，绑定到我们为表示
这个函数而创建的 LoxFunction 对象上。那个对象有一个 `closure` 字段，捕获了函数被声明
时所处的环境，所以它有一个指回该块环境的引用。

现在，我们调用 `showA()`。

<img src="image/resolving-and-binding/environment-3.png" alt="showA() 函数体的空环境，链接到前两个环境。'a' 在全局环境中被解析。" />

解释器为 `showA()` 的函数体动态创建了一个新环境。它是空的，因为那个函数没有声明任何
变量。该环境的父环境是这个函数的闭包——也就是外层的块环境。

在 `showA()` 的函数体内部，我们打印 `a` 的值。解释器沿着环境链一路查找这个值。它一直
走到全局环境，才在那里找到它并打印出 `"global"`。很好。

接下来，我们声明第二个 `a`，这次是在块里面。

<img src="image/resolving-and-binding/environment-4.png" alt="此刻块环境里同时有 'a' 和 'showA' 了。" />

它跟 `showA()` 处在同一个块——同一个作用域里——所以它进了同一个环境，而这个环境也正是
`showA()` 的闭包所指的那个环境。有趣的地方到了。我们再次调用 `showA()`。

<img src="image/resolving-and-binding/environment-5.png" alt="showA() 函数体的空环境，链接到前两个环境。'a' 在块环境中被解析。" />

我们又一次为 `showA()` 的函数体创建了一个新的空环境，把它跟那个闭包接好，然后运行函数体。
当解释器沿着环境链查找 `a` 时，它现在发现了块环境里那个**新的** `a`。嘘。

当初实现环境时，我选了一种方式，本希望它能契合你对作用域的那种不正式的直觉。我们倾向于
把块里的所有代码都看作处在同一个作用域里，所以我们的解释器就用单个环境来表示它。每个
环境都是一张可变的哈希表。当一个新的局部变量被声明时，它会被加进该作用域已有的那个环境里。

这种直觉，就像人生中许多直觉一样，并不十分正确。一个块并不必然处处都是同一个作用域。
想想看：

```lox
{
  var a;
  // 1.
  var b;
  // 2.
}
```

在我标的第一行处，在作用域里的只有 `a`。到第二行处，`a` 和 `b` 都在了。如果你把一个
「作用域」定义为一组声明，那么这两处显然不是同一个作用域——它们所含的声明并不一样。这
就好像每条 `var` 语句都把块<span name="split">劈开</span>成了两个独立的作用域：变量声明
之前的那个，以及之后、包含这个新变量的那个。

<aside name="split">

有些语言把这种劈开显式化了。在 Scheme 和 ML 里，当你用 `let` 声明一个局部变量时，你同时
也划定了新变量在作用域内的后续代码范围。那里并不存在一个隐式的「块里剩下的部分」。

</aside>

可在我们的实现里，环境确实表现得像整个块就是同一个作用域，只不过是个随时间变化的作用域。
闭包不喜欢这样。当一个函数被声明时，它捕获的是对当前环境的一个引用。这个函数**本应**捕获
环境的一份冻结快照——**函数被声明那一刻**环境的样子。但事实上，在 Java 代码里，它拿到的
是对那个实际可变的环境对象的引用。当后来有一个变量被声明到该环境所对应的那个作用域里时，
闭包就看见了那个新变量，尽管那个声明并**不**在函数之前。

### 持久化环境

有一种编程风格会用到所谓的**持久化数据结构**（persistent data structures）。跟你在命令式
编程里熟悉的那些软塌塌的数据结构不同，持久化数据结构永远不能被直接修改。相反，对既有结构
做的任何一次「修改」，都会产生一个<span name="copy">崭新</span>的对象，里面装着原来的全部
数据再加上这次修改。原对象保持不变。

<aside name="copy">

这听起来好像每次操作都要复制整个结构，会白白浪费大量内存和时间。可实际上，持久化数据结构
在不同「副本」之间共享了绝大部分数据。

</aside>

如果我们把这种技术用到 Environment 上，那么你每声明一个变量，它都会返回一个**新的**环境，
里面含有此前声明的所有变量再加上这个新名字。声明一个变量就会完成那次隐式的「劈开」：变量
声明之前有一个环境，之后有一个：

<img src="image/resolving-and-binding/split.png" alt="变量声明前后各自独立的环境。" />

闭包保留一个引用，指向函数被声明时生效的那个 Environment 实例。既然在该块里后来做的任何
声明都会产生新的 Environment 对象，那么闭包就不会看见那些新变量，我们的 bug 也就修好了。

这确实是解决这个问题的一种正当办法，也是 Scheme 解释器里实现环境的经典做法。我们也可以对
Lox 这么做，但那意味着要回头改动一大堆现有代码。

我就不拖着你走那条路了。我们保持环境的表示方式不变。与其让数据变得更静态化，我们不如把
静态的作用域解析直接**烘焙**进访问**操作**本身。

## 语义分析

每次求值一个变量表达式时，我们的解释器都会**解析**这个变量——追查它指的是哪个声明。如果
那个变量被裹在一个运行上千次的循环里，它就会被重新解析上千次。

我们知道，静态作用域意味着一个变量用法永远解析到同一个声明，而这个声明光靠读文本就能确定。
既然如此，我们为什么每次都动态地去做呢？这么做不仅捅出了那个导致恼人 bug 的洞，还毫无必要
地拖慢了速度。

更好的做法是每个变量用法只解析**一次**。写一段代码，检视用户的程序，找出提到的每一个变量，
并弄清每一个指的是哪个声明。这个过程就是**语义分析**（semantic analysis）的一个例子。语法
解析器只能告诉你一个程序在语法上是否正确（一次**语法**分析），而语义分析则更进一步，开始
弄清程序的各个部分究竟是什么意思。在这个例子里，我们的分析会解析变量的绑定关系。我们不知
道某个表达式**是**个变量，还知道它是**哪个**变量。

存储变量与其声明之间的绑定关系，有很多种办法。等我们做到 Lox 的 C 解释器时，会有一种**高效
得多**的局部变量存储与访问方式。但对 jlox，我想把对现有代码库造成的连带损伤降到最小。我可
不想把一大堆基本还不错的代码扔掉。

所以，我们会用一种能最大限度利用现有 Environment 类的方式来存储解析结果。回想一下那个有
问题的例子里，对 `a` 的访问是怎么解释的。

<img src="image/resolving-and-binding/environment-3.png" alt="showA() 函数体的空环境，链接到前两个环境。'a' 在全局环境中被解析。" />

在第一次（正确的）求值里，我们查看了环境链里的三个环境，才找到 `a` 的全局声明。之后，当
内层的 `a` 后来在块作用域里被声明时，它遮蔽了全局那个。

<img src="image/resolving-and-binding/environment-5.png" alt="showA() 函数体的空环境，链接到前两个环境。'a' 在块环境中被解析。" />

下一次查找沿着环境链走，在**第二个**环境里找到了 `a`，就在那儿停下。每个环境都对应一个
声明了变量的词法作用域。如果我们能保证一次变量查找永远走过环境链里**相同数量**的链接，
那就能保证它每次都找到同一个作用域里的同一个变量。

要「解析」一个变量用法，我们只需算出所声明的变量在环境链里隔着多少个「跳」。有意思的问题是
**什么时候**来做这个计算——或者换个说法，我们要把这段计算的代码塞进解释器实现的哪里？

既然我们计算的是一个基于源码结构的静态属性，那么显而易见的答案就是放在语法解析器里。那是
它传统的归属地，也是我们后来在 clox 里会放它的地方。在这里这么做也行得通，可我想找个由头
给你展示另一种技术。我们会把作用域解析器写成一个独立的 pass。

### 一趟变量作用域解析

在语法解析器产出语法树之后、解释器开始执行它之前，我们会把树遍历一趟，解析出其中所有的变量。
在语法解析和执行之间加上额外的 pass 是常见做法。如果 Lox 有静态类型，我们可以在那儿插进一个
类型检查器。优化也常常像这样用独立的 pass 来实现。基本上，任何不依赖只在运行时才有的状态的
工作，都能以这种方式来完成。

我们这趟变量作用域解析，运作起来有点像一个小小的解释器。它遍历这棵树，访问每一个节点，但
静态分析跟动态执行是不同的：

*   **没有副作用。** 当静态分析访问一条 print 语句时，它并不会真的打印任何东西。对原生函数
    的调用、或者其他伸向外部世界的操作，都被架空成空桩，不产生任何效果。

*   **没有控制流。** 循环只会被访问<span name="fix">一次</span>。`if` 语句的两个分支都会被
    访问。逻辑运算符不会被短路。

<aside name="fix">

变量作用域解析把每个节点都碰且只碰一次，所以它的性能是 **O(n)**，其中 **n** 是语法树节点的
数量。更精细的分析复杂度可能更高，但大多数都被精心设计成线性的、或者离线性不远。如果你的
编译器随着用户程序变大而指数级变慢，那可是很丢人的失手。

</aside>

## 作用域解析器类

就像 Java 里的一切那样，我们的这趟变量作用域解析也化身在一个类里。

^code resolver

由于作用域解析器需要访问语法树里的每一个节点，它实现了我们现有的那套访问者抽象。在解析
变量这件事上，只有少数几类节点值得关注：

*   块语句为它所包含的语句引入一个新作用域。

*   函数声明为它的函数体引入一个新作用域，并在这个作用域里绑定它的形参。

*   变量声明把一个新变量加进当前作用域。

*   变量表达式和赋值表达式需要解析它们的变量。

其余的节点不做任何特别的事，但我们仍然需要为它们实现 visit 方法，好深入它们的子树。尽管
一个 `+` 表达式**本身**没有任何变量需要解析，它的任一操作数却可能有。

### 解析块

我们从块开始，因为正是块创建了那些让一切魔法得以发生的局部作用域。

^code visit-block-stmt

它会开启一个新作用域，深入到块里面的那些语句，然后丢弃这个作用域。好玩的东西都在那几个
辅助方法里。我们从最简单的那个开始。

^code resolve-statements

它会遍历一个语句列表，逐一解析每个语句。它又转而调用：

^code resolve-stmt

既然来了，我们再加一个重载，之后解析表达式时会用得上。

^code resolve-expr

这些方法跟 Interpreter 里的 `evaluate()` 和 `execute()` 很像——它们都转过身来，对给定的
语法树节点套用访问者模式。

真正有意思的行为都围绕着作用域。一个新的块作用域是这样创建的：

^code begin-scope

在解释器和作用域解析器里，词法作用域都是嵌套的。它们表现得像一座栈。解释器用一条链表
——Environment 对象链——来实现那座栈。而在作用域解析器里，我们用的是一个货真价实的 Java
Stack。

^code scopes-field (1 before, 2 after)

这个字段追踪的，是当前、呃，处于作用域内的那座作用域栈。栈里的每个元素是一个 Map，代表
单独一个块作用域。键跟在 Environment 里一样，是变量名。值是布尔值，原因我很快会解释。

这座作用域栈只用于局部的块作用域。在顶层、也就是全局作用域里声明的变量，不被作用域解析器
追踪，因为它们在 Lox 里更加动态。解析一个变量时，如果我们在局部作用域栈里找不到它，就假定
它必定是全局的。

既然作用域存在一座显式的栈里，退出一个作用域就很直接。

^code end-scope

现在我们能压入、弹出由空作用域组成的栈了。往里面放点东西吧。

### 解析变量声明

解析一个变量声明，就是往当前最内层作用域的 map 里加一个新条目。看着挺简单，可我们得跳一段
小小的舞步。

^code visit-var-stmt

我们把绑定拆成两步——先声明、后定义——是为了处理像这样的古怪边角情况：

```lox
var a = "outer";
{
  var a = a;
}
```

当一个局部变量的初始化器引用了一个跟正在声明的变量同名的变量时，会发生什么？我们有几个选项：

1.  **先运行初始化器，再把新变量放进作用域。** 这样一来，新的局部 `a` 会被初始化为 "outer"，
    也就是那个**全局**变量的值。换句话说，上面这段声明会被脱糖成：

    ```lox
    var temp = a; // 运行初始化器。
    var a;        // 声明这个变量。
    a = temp;     // 初始化它。
    ```

2.  **先把新变量放进作用域，再运行初始化器。** 这意味着你可以在一个变量被初始化之前就观察到
    它，所以我们得弄清它那时会是什么值。大概是 `nil`。这意味着新的局部 `a` 会被重新初始化
    成它自己那个隐式初始化的值，`nil`。这时脱糖出来是这样的：

    ```lox
    var a; // 定义这个变量。
    a = a; // 运行初始化器。
    ```

3.  **把「在初始化器里引用该变量」变成错误。** 只要初始化器提到了正在初始化的那个变量，
    就让解释器在编译期或运行时失败。

前两个选项里，有哪一个看起来像是用户真的**想要**的？遮蔽很少见，而且往往就是个错误，
所以拿被遮蔽变量的值来初始化那个遮蔽变量，不大可能是故意的。

第二个选项更没用。那个新变量**永远**会是 `nil` 值。按名字提它从来就没有任何意义。你大可以
直接写个 `nil`。

既然前两个选项很可能掩盖用户的错误，我们就选第三个。而且，我们要把它做成编译期错误而不是
运行时错误。这样一来，用户在任何代码跑起来之前就会收到提醒。

为了做到这一点，我们在访问表达式时，需要知道自己是不是正处在某个变量的初始化器里。我们
通过把绑定拆成两步来做到这一点。第一步是**声明**它。

^code declare

声明把变量加进最内层的作用域，好让它遮蔽任何外层同名变量，也好让我们知道这个变量存在。
我们通过把它的名字绑定到作用域 map 里的 `false`，来标记它「还没准备好」。作用域 map 里跟
某个键关联的值，表示我们是否已经完成了解析那个变量的初始化器。

声明完变量之后，我们在同一个作用域里解析它的初始化器表达式——此时这个新变量已经存在，但还
不可用。一旦初始化器表达式解析完毕，这个变量就准备好正式上场了。我们通过**定义**它来做到
这一点。

^code define

我们把作用域 map 里那个变量的值设成 `true`，标记它已完全初始化、可供使用了。它活了！

### 解析变量表达式

变量声明——以及我们稍后会讲到的函数声明——会写入作用域 map。当我们解析变量表达式时，读的
就是这些 map。

^code visit-variable-expr

首先，我们检查这个变量是不是正在它自己的初始化器里被访问。作用域 map 里的那些值就是在这儿
派上用场的。如果这个变量存在于当前作用域、但它的值是 `false`，那就意味着我们已经声明了它、
却还没定义它。我们报告这个错误。

检查之后，我们用下面这个辅助方法真正解析这个变量本身：

^code resolve-local

这段代码看着很像 Environment 里求值变量时的那段，这是有道理的。我们从最内层作用域开始，向
外一层层找，在每个 map 里找相匹配的名字。如果找到了这个变量，我们就解析它，并传入一个数：
从当前最内层作用域到找到该变量的那个作用域之间隔了多少个作用域。所以，如果变量是在当前
作用域里找到的，我们传 0。如果它在紧挨着的外层作用域里，就传 1。道理你懂的。

如果我们走遍所有的块作用域都没找到这个变量，我们就把它搁置不解析，并假定它是全局的。稍后
我们会讲到那个 `resolve()` 方法的实现。眼下，我们继续把其余的语法节点啃完。

### 解析赋值表达式

另一种引用变量的表达式是赋值。解析一个赋值表达式长这样：

^code visit-assign-expr

首先，我们解析被赋的那个值的表达式，以防它里面也引用了别的变量。然后我们用现成的
`resolveLocal()` 方法来解析被赋值的那个变量。

### 解析函数声明

最后是函数。函数既绑定名字，又引入作用域。函数自身的名字，绑定在函数被声明处的那个外围
作用域里。当我们踏入函数体时，我们又把它的形参绑定进那个内层的函数作用域。

^code visit-function-stmt

跟 `visitVariableStmt()` 类似，我们在当前作用域里声明并定义函数的名字。不过跟变量不同的
是，我们是**急切地**定义这个名字的——在解析函数体之前就定义。这让一个函数能在自己的函数体
内部递归地引用自己。

接着我们用下面这个来解析函数的函数体：

^code resolve-function

它之所以是一个单独的方法，是因为等我们之后加入类的时候，也会用它来解析 Lox 的方法。它为
函数体创建一个新作用域，然后为函数的每一个形参绑定变量。

这个作用域一准备好，它就在那个作用域里解析函数体。这跟解释器处理函数声明的方式不一样。
在**运行时**，声明一个函数并不会对函数的函数体做任何事。函数体要等到之后函数被调用时才会
被碰。而在一次**静态**分析里，我们当场就立刻深入函数体。

### 解析其余的语法树节点

文法中那些有意思的角角落落就都覆盖到了。我们处理了变量被声明、被读取、被写入的每一个地方，
也处理了作用域被创建、被销毁的每一个地方。尽管其余的语法树节点不受变量作用域解析的影响，
我们仍然需要为它们全都实现 visit 方法，好递归进入它们的子树。<span name="boring">抱歉</span>，
这一段有点枯燥，但请忍耐一下。我们会大致「自上而下」地走，先从语句开始。

我确实说过，这本书会给出这些解释器的每一行代码。可我没说它们每一行都精彩。

</aside>

一条表达式语句含有一个需要遍历的表达式。

^code visit-expression-stmt

一条 if 语句有一个表示条件的表达式，以及一个或两个表示分支的语句。

^code visit-if-stmt

在这里，我们看到作用域解析跟解释有何不同。当我们解析一条 `if` 语句时，没有控制流。我们会
解析条件以及**两个**分支。动态执行只会踏进那个**确实**被运行的分支，而静态分析是保守的——
它会分析任何**可能**被运行的分支。既然两个分支中任何一个都可能在运行时被抵达，我们就两个
都解析。

跟表达式语句一样，一条 `print` 语句含有一个子表达式。

^code visit-return-stmt

所有的语句就都覆盖完了。接下来是表达式……

^code visit-grouping-expr

^code visit-literal-expr

既然静态分析不做控制流、也不做短路，那么逻辑表达式就跟其他二元运算符完全一样。

^code visit-logical-expr

## 解释已解析的变量

来看看我们这作用域解析器有啥用。每当它访问一个变量，它都会告诉解释器：当前作用域和定义该
变量的那个作用域之间隔了多少个作用域。在运行时，这恰好对应着当前环境与那个能让解释器找到
变量值的外围环境之间隔了多少个**环境**。作用域解析器通过调用下面这个，把这个数交给解释器：

^code resolve

我们想把这些解析信息存到某处，好在之后那个变量或赋值表达式被执行时用得上，可存哪儿呢？
一个显而易见的地方就是语法树节点本身。那是个不错的做法，许多编译器就把这类分析的结果存在
那里。

我们可以那么干，但那需要去折腾我们的语法树生成器。所以我们改用另一种常见的做法，把它存到
<span name="side">一旁</span>的一张 map 里，让每个语法树节点跟它的解析数据关联起来。

<aside name="side">

我**好像**听说过这张 map 被叫做「侧表」（side table），因为它是一张表格式的数据结构，把
数据跟它相关联的那些对象分开存放。可每次我拿这个词去谷歌，搜出来的都是家具。

</aside>

像 IDE 这样的交互式工具，常常会增量地重新语法解析、重新解析用户程序的一部分。当那些需要
重算的状态藏在语法树的枝枝叶叶里时，想把它们全都找出来可能很难。把这份数据存在节点之外的
一个好处是，这让**丢弃**它变得很容易——清空那张 map 就行了。

^code locals-field (1 before, 2 after)

你也许会以为，当有多个表达式引用同一个变量时，我们需要某种嵌套的树结构来避免混淆，但每个
表达式节点都是它自己的 Java 对象，各有各的独立身份。一张单一的、铁板一块的 map 毫无困难
就能把它们区分开。

一如既往，使用一个集合需要我们 import 几个名字。

^code import-hash-map (1 before, 1 after)

还有：

^code import-map (1 before, 2 after)

### 访问已解析的变量

我们的解释器现在能拿到每个变量解析出来的位置了。终于，我们能用上它了。我们把变量表达式的
visit 方法换成这个：

^code call-look-up-variable (1 before, 1 after)

它委托给：

^code look-up-variable

这里有几件事在进行。首先，我们在 map 里查找解析出来的距离。记住，我们只解析了**局部**变量。
全局变量受到特殊对待，最终不进这张 map（`locals` 这个名字就是这么来的）。所以，如果我们在
map 里找不到距离，那它就必定是全局的。这种情况下，我们直接到全局环境里动态地查找它。如果
该变量没有定义，那就会抛出一个运行时错误。

如果**确实**拿到了一个距离，那就说明我们面对的是一个局部变量，于是我们就可以享用静态分析
的成果了。我们不调用 `get()`，而是调用 Environment 上这个新方法：

^code get-at

旧的 `get()` 方法会动态地沿着一串外围环境往下走，挨个翻找，看变量是不是藏在某处。但现在
我们确切地知道链里哪一个环境会有这个变量。我们用下面这个辅助方法抵达它：

^code ancestor

它会沿着父链向上走固定数量的跳，返回那里的环境。拿到它之后，`getAt()` 就只是返回那个环境
map 里该变量的值。它甚至都不必检查变量在不在那儿——我们知道它一定在，因为作用域解析器早先
已经找到过它了。

<aside name="coupled">

解释器假定变量就在那张 map 里，这种方式让人感觉像在盲飞。解释器的代码信任作用域解析器尽到
了职责、正确地解析了变量。这意味着这两个类之间有着紧密的耦合。在作用域解析器里，每一行触及
作用域的代码，都必须在解释器里有一行精确对应的、用于修改环境的代码。

这种耦合我是**亲身**领教过的，因为我在给这本书写代码时，就撞上了几个微妙的 bug——作用域
解析器和解释器的代码稍微没对上。把它们揪出来很费劲。让这件事变得更容易的一个办法，是让
解释器显式地断言——用 Java 的 assert 语句或者别的什么校验工具——它期望作用域解析器已经履行
的那份契约。

</aside>

### 给已解析的变量赋值

我们也能通过给变量赋值来使用它。访问赋值表达式那一处的改动与之类似。

^code resolved-assign (2 before, 1 after)

我们又一次查找该变量的作用域距离。如果找不到，就假定它是全局的，并像之前那样处理。否则，
我们调用这个新方法：

^code assign-at

`assignAt()` 之于 `assign()`，正如 `getAt()` 之于 `get()`。它走过固定数量的环境，然后把
新值塞进那张 map 里。

这就是对 Interpreter 的全部改动。正因如此，我才为我们的解析数据选了一种侵入性最小的表示
方式。其余的节点全都照旧工作。连修改环境的代码都没有变。

### 运行作用域解析器

不过，我们确实需要真正**运行**作用域解析器。我们在语法解析器施展完魔法之后插入这个新 pass。

^code create-resolver (3 before, 1 after)

只要有任何语法解析错误，我们就不运行作用域解析器。如果代码有语法错误，它根本不会运行，所以
解析它没什么价值。如果语法没问题，我们就让作用域解析器去干它的事。作用域解析器持有对解释器
的一个引用，并在遍历变量时把解析数据直接戳进解释器里。等解释器下一次运行时，它该有的东西就
都有了。

至少，在作用域解析器**成功**的前提下是这样。可要是解析过程中出错呢？

## 作用域解析错误

既然我们在做一趟语义分析，就有机会让 Lox 的语义更精确，并帮用户在他们代码跑起来之前尽早
抓到 bug。瞧瞧这个坏家伙：

```lox
fun bad() {
  var a = "first";
  var a = "second";
}
```

在**全局**作用域里，我们确实允许声明多个同名的变量，但在局部作用域里这么做，多半是个错误。
要是他们知道这个变量已经存在，就会去给它赋值、而不是用 `var` 再声明一遍。而要是他们**不**
知道它已存在，那他们大概也没打算覆盖前一个。

我们可以在解析时静态地检测出这个错误。

^code duplicate-variable (1 before, 1 after)

当我们在一个局部作用域里声明一个变量时，我们已经知道同一个作用域里此前声明过的每一个变量的
名字。如果我们看到一次撞名，就报告一个错误。

### 非法的 return 错误

下面是另一个讨厌的小脚本：

```lox
return "at top level";
```

它执行的是一条 `return` 语句，可它压根就不在任何函数里面。它是顶层代码。我不知道用户**以为**
会发生什么，但我觉得我们不会想让 Lox 允许这种事。

我们可以扩展作用域解析器，来静态地检测出它。就像我们遍历树时追踪作用域那样，我们也可以追踪
我们当前正在访问的代码是不是在一个函数声明里面。

^code function-type-field (1 before, 2 after)

我们不使用光秃秃的布尔值，而是用这个滑稽的枚举：

^code function-type

它现在看起来有点蠢，但之后我们会给它加上几个更多的情形，那时它就会更有道理了。当我们解析
一个函数声明时，我们把这个传进去。

^code pass-function-type (2 before, 1 after)

在 `resolveFunction()` 里，我们接收那个参数，并在解析函数体之前把它存进字段。

^code set-current-function (1 after)

我们先把该字段之前的值存进一个局部变量里。记住，Lox 有局部函数，所以你可以把函数声明嵌套到
任意深度。我们需要追踪的不只是「我们在某个函数里」，而是「我们在**多少层**函数里」。

为此我们可以用一座显式的、装着 FunctionType 值的栈，但我们要顺搭 JVM 的便车。我们把这个
之前的值存进 Java 栈上的一个局部变量里。等我们解析完函数体后，再把字段恢复成那个值。

^code restore-current-function (1 before, 1 after)

既然我们现在总能说出自己是不是在一个函数声明里面，那我们在解析一条 `return` 语句时就检查这
一点。

^code return-from-top (1 before, 1 after)

不错吧？

还有最后一块。回到那个把一切缝合起来的 Lox 主类里，我们小心地做到了：只要遇到任何语法解析
错误，就不运行解释器。那次检查在作用域解析器**之前**运行，好让我们不去尝试解析语法上非法的
代码。

但如果存在作用域解析错误，我们也需要跳过解释器，所以我们加上**另一个**检查。

^code resolution-error (1 before, 2 after)

你可以设想在这里做许多别的分析。比如，如果我们给 Lox 加上 `break` 语句，我们多半会想确保
它们只在循环内部使用。

我们还可以更进一步，对那些未必**错误**、但大概没用的代码报告警告。比如，如果你在一条
`return` 语句之后有不可达的代码、或者有一个值从未被读取过的局部变量，许多 IDE 都会发出警告。
所有这些都是相当容易加到我们这趟静态访问里的，或者拆成<span name="separate">独立的</span> pass。

<aside name="separate">

把多少种不同的分析塞进单独一个 pass，这个抉择很难。许多各自独立、职责单一的小 pass，实现和
维护起来更简单。然而，遍历语法树本身是有实实在在的运行时开销的，所以把多种分析捆进一个 pass
通常更快。

</aside>

不过眼下，我们就用这么多分析，不再多了。要紧的是，我们修好了那个古怪又恼人的边角情况 bug
——尽管为它花了这么大功夫，也许会让你惊讶。
