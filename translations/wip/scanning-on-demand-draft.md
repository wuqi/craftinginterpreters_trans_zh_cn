我们的第二个解释器 clox 分三个阶段——扫描器、编译器和虚拟机。每两个阶段之间用一个数据结构相接。词法单元从扫描器流向编译器，字节码块从编译器流向虚拟机。我们是从这套实现接近末尾的地方起步的——先是[字节码块][chunks]，然后是[虚拟机][vm]。现在，我们要跳回开头，搭一个能产出词法单元的扫描器。到了[下一章][next chapter]，我们会用字节码编译器把这两头接上。

## 一次一个词法单元

在 jlox 里，发令枪一响，扫描器就冲上前去，急不可耐地把整个程序扫完，返回一个词法单元列表。这么干在 clox 里会是个麻烦。我们需要某种可增长的数组或列表来存这些词法单元，还要管理词法单元本身以及那个集合的分配与释放。代码量大，内存也翻腾得厉害。

在任何时刻，编译器都只需要一两个词法单元——还记得吗，我们的文法只需要一个词法单元的前瞻——所以我们不必让**所有**词法单元同时待着。最简单的做法是：编译器需要一个词法单元时才去扫描它。扫描器提供一个词法单元时，按值把它返回。它无需动态分配任何东西——直接让词法单元在 C 的栈上传来传去就行。

可惜我们还没有一个能向扫描器要词法单元的编译器，所以扫描器只好干坐在那儿。为了让它动起来，我们写点临时代码来驱动它。

^code dump-tokens (1 before, 1 after)

<aside name="format">

格式字符串里那个 `%.*s` 是个巧妙的功能。通常，你在格式字符串里放一个数字来设定输出精度——也就是要显示的字符数。改用 `*` 的话，就能把精度当作参数传进去。所以那句 `printf()` 调用打印的是 `token.start` 处字符串的前 `token.length` 个字符。我们之所以要这样限制长度，是因为词素指向的是原始源代码字符串，末尾并没有终止符。

</aside>

这段代码会无限循环。每转一圈，它就扫描并打印一个词法单元。当它遇到一个特殊的「文件结束」词法单元或者一个错误时，就停下来。比如，我们用解释器跑这个程序：

```lox
print 1 + 2;
```

它会打印：

```text
   1 31 'print'
   | 21 '1'
   |  7 '+'
   | 21 '2'
   |  8 ';'
   2 39 ''
```

第一列是行号，第二列是词法单元<span name="token">类型</span>的数值，最后是词素。第 2 行那个空词素就是 EOF 词法单元。

<aside name="token">

没错，词法单元类型的原始下标算不上给人看的，可 C 能给的就这么点。

</aside>

本章剩下的目标，就是通过实现下面这个关键函数，让那坨代码真正跑起来：

^code scan-token-h (1 before, 2 after)

每次调用都扫描并返回源代码里的下一个词法单元。一个词法单元长这样：

^code token-struct (1 before, 2 after)

它跟 jlox 的 Token 类很像。我们用一个枚举标出它是哪种词法单元——数字、标识符、`+` 运算符等等。这个枚举跟 jlox 里的那个几乎一模一样，那我们干脆一次把它敲完。

^code token-type (2 before, 2 after)

除了给所有名字都加上 `TOKEN_` 前缀（因为 C 会把枚举名丢进顶层命名空间）之外，唯一的差别就是多了个 `TOKEN_ERROR` 类型。那是干嘛的？

扫描期间能检测到的错误只有那么几种：未终止的字符串和无法识别的字符。在 jlox 里，扫描器自己报告这些错误。在 clox 里，扫描器为这类错误造出一个合成「错误」词法单元，交给编译器。这样一来，编译器就知道出了错，可以在报告之前先启动错误恢复。

clox 的 Token 类型新颖之处，在于它怎么表示词素。在 jlox 里，每个 Token 都把词素存成自己单独的一个小 Java 字符串。要是 clox 也这么干，我们就得琢磨怎么管理这些字符串的内存。这尤其棘手，因为我们是按值传递词法单元的——多个词法单元可能指向同一个词素字符串。所有权会变得很怪。

于是，我们把原始源代码字符串当作字符仓库。一个词素，用一个指向它第一个字符的指针，加上它包含的字符数来表示。这样我们完全不必操心词素的内存管理，还能随意复制词法单元。只要主源代码字符串<span name="outlive">比</span>所有词法单元都活得久，一切就都正常。

<aside name="outlive">

我不是想显得轻佻。我们真的需要思考并确保那个源代码字符串——它是在很远之外的「main」模块里创建的——有足够长的生命周期。这就是为什么 `runFile()` 要等到 `interpret()` 执行完代码并返回，才释放这个字符串。

</aside>

### 扫描词法单元

我们准备好扫描词法单元了。我们从下面这段开始，一步步走向完整实现：

^code scan-token

由于每次调用这个函数都会扫完一个完整的词法单元，我们一进函数就知道自己正处在一个新词法单元的开头。于是我们把 `scanner.start` 设成指向当前字符，好记住我们即将扫描的词素从哪里开始。

接着，我们检查是否到了源代码末尾。到了就返回一个 EOF 词法单元，停下。这是个哨兵值，向编译器发出信号：别再要更多词法单元了。

如果没到末尾，我们就做点……事情……来扫描下一个词法单元。不过那段代码我们还没写，很快会写到。如果那段代码没能成功扫描并返回一个词法单元，我们就会走到函数末尾。那一定意味着我们碰上了一个扫描器认不出的字符，于是就为它返回一个错误词法单元。

## Lox 的词法文法

最简单的词法单元只有一个字符。我们这样识别它们：

^code scan-char (1 before, 2 after)

我们从源代码里读出下一个字符，然后做一个直白的 switch，看它是否匹配 Lox 任何一个单字符词素。要读取下一个字符，我们用一个新辅助函数，它消费掉当前字符并把它返回。

^code advance

接下来是像 `!=` 和 `>=` 这样的双字符标点词法单元。它们各自都有一个对应的单字符词法单元。这意味着，当我们看到一个像 `!` 这样的字符时，除非再看一眼下一个字符，否则不知道自己是处在 `!` 词法单元里还是 `!=` 里。我们这样处理它们：

^code two-char (1 before, 1 after)

消费掉第一个字符后，我们去找一个 `=`。找到了就消费它，并返回对应的双字符词法单元。否则，我们不去动当前字符（好让它成为**下一个**词法单元的一部分），返回相应的单字符词法单元。

有条件地消费第二个字符的那套逻辑在这里：

^code match

如果当前字符正是想要的那个，我们就前进并返回 `true`。否则返回 `false`，表示没匹配上。

现在扫描器已经支持所有类标点的词法单元了。在转向更长的那些之前，我们先绕个小弯，处理一下根本不属于任何词法单元的字符。

### 空白

扫描器需要处理空格、制表符和换行，但这些字符不会成为任何词法单元词素的一部分。我们本可以在 `scanToken()` 的主字符 switch 里去检查它们，但那样一来，要确保函数在你调用它时还能正确地找到空白**之后**的下一个词法单元，就有点麻烦了。我们得把整个函数体包进一个循环之类的东西里。

于是，在开始扫描词法单元之前，我们先岔到一个单独的函数里。

^code call-skip-whitespace (1 before, 1 after)

它让扫描器越过所有前导空白。这个调用返回之后，我们就知道紧接着的那个字符是有意义的（或者已经到了源代码末尾）。

^code skip-whitespace

它算是一个独立的小型扫描器。它循环，消费遇到的每一个空白字符。我们得小心，**别**让它消费任何非空白字符。为此，我们用这个：

^code peek

它仅仅返回当前字符，但不消费它。前面的代码处理了除换行之外的所有空白字符。

^code newline (1 before, 2 after)

当我们消费其中一个时，也把当前行号加一。

### 注释

你若想在术语上较真，注释严格来说并不算「空白」，但对 Lox 来说，它们跟空白也没两样，所以我们也跳过它们。

^code comment (1 before, 2 after)

在 Lox 里注释以 `//` 开头，所以跟 `!=` 之流一样，我们需要第二个字符的前瞻。不过，遇上 `!=` 时，即使没找到 `=`，我们仍然想消费那个 `!`。注释就不一样了。要是找不到第二个 `/`，那 `skipWhitespace()` 就不能连**第一个**斜杠也消费掉。

为了处理这一点，我们加上：

^code peek-next

它跟 `peek()` 类似，只不过是看当前字符再往后一个的字符。如果当前字符和下一个字符都是 `/`，我们就把它们消费掉，然后继续消费其他字符，直到下一个换行或源代码末尾。

我们用 `peek()` 来检查换行，但不消费它。这样一来，下一轮 `skipWhitespace()` 的外层循环里，换行就会成为当前字符，我们就能认出它并把 `scanner.line` 加一。

### 字面量词法单元

数字和字符串词法单元比较特殊，因为它们带有一个与之关联的运行时值。我们从字符串开始，因为它容易识别——它们总是以双引号开头。

^code scan-string (1 before, 1 after)

它会调用一个新函数。

^code string

跟 jlox 类似，我们不断消费字符，直到到达收尾的引号。我们还会跟踪字符串字面量里的换行。（Lox 支持多行字符串。）而且一如既往，在找到收尾引号之前就耗尽源代码时，我们会从容应对。

clox 在这里的主要变化，是某个**不存在**的东西。还是跟内存管理有关。在 jlox 里，Token 类有一个 Object 类型的字段，用来存放从字面量词法单元的词素转换出来的运行时值。

在 C 里实现那个要费不少功夫。我们需要某种联合体和类型标签，来判断词法单元里装的是字符串还是 double 值。如果是个字符串，还得想办法管理那个字符串字符数组的内存。

与其把那份复杂性加进扫描器，我们不如把字面量词素<span name="convert">转换</span>成运行时值这件事推迟到后面。在 clox 里，词法单元只存词素——也就是与用户源代码里一模一样的那串字符。到了后面编译器里，我们会在准备把它存进字节码块的常量表时，才把那个词素转换成运行时值。

<aside name="convert">

在编译器里做「词素到值」的转换确实引入了一些冗余。扫描一个数字字面量的工作，跟把一串数字字符转换成数值的工作，极其相似。但冗余也没**那么**多，又不在任何性能关键的路径上，而且能让扫描器保持简单。

</aside>

接下来是数字。与其为可能开头的十个数字各加一个 switch 分支，我们在这里处理它们：

^code scan-number (1 before, 2 after)

这用到了下面这个显而易见的工具函数：

^code is-digit

我们用它把数字扫完：

^code number

它跟 jlox 的版本几乎一模一样，只是——还是那句话——我们暂时还不把词素转换成 double。

## 标识符与关键字

最后一批词法单元是标识符，既有用户自定义的，也有保留的。这一节应该会好玩——我们在 clox 里识别关键字的方式，跟 jlox 里大不相同，还会牵涉到一些重要的数据结构。

不过首先，我们得把词素扫出来。名字以字母或下划线开头。

^code scan-identifier (1 before, 1 after)

我们用这个来识别它们：

^code is-alpha

找到一个标识符之后，我们在这里扫描它的剩余部分：

^code identifier

第一个字母之后，我们也允许数字，于是不断消费字母数字，直到用完。然后我们产出一个类型正确的词法单元。判断那个「正确」的类型，正是本章独到之处。

^code identifier-type

好吧，我猜这还没什么好激动的。这就是一个保留字都没有时的样子。那我们该怎么识别关键字呢？在 jlox 里，我们把它们一股脑塞进一个 Java Map，按名字查。clox 里我们还没有任何哈希表之类的结构，至少现在还没有。

反正哈希表也是大材小用。要在哈希<span name="hash">表</span>里查一个字符串，我们得遍历这个字符串算出它的哈希码，找到哈希表里对应的桶，然后对它碰巧找到的字符串做逐字符的相等比较。

<aside name="hash">

要是你对这个不熟，别担心。等我们[从零开始搭自己的哈希表][hash]时，会把这一切讲得纤毫毕现。

[hash]: hash-tables.html

</aside>

假设我们扫到了一个标识符 "gorgonzola"。判断它是不是保留字，**该**花多少功夫？嗯，没有任何 Lox 关键字以 "g" 开头，所以看一眼第一个字符就足以断定：不是。这比查一次哈希表简单多了。

那 "cardigan" 呢？Lox 里确实有个以 "c" 开头的关键字："class"。但 "cardigan" 的第二个字符 "a" 就把它排除了。"forest" 又怎么样？既然 "for" 是个关键字，我们就得在字符串里再往里走一段，才能确定这不是保留字。不过在大多数情况下，一两个字符就足以看出手头是个用户自定义的名字。我们应当能认出这点并快速失败。

下面这张图直观呈现了那套分支式逐字符检查逻辑：

沿着每条节点链往下读，你就会看出 Lox 的关键字浮现出来。

我们从根节点开始。如果存在一个子节点，它的字母匹配词素里的第一个字符，我们就移到那个节点。然后对词素里的下一个字母重复这一过程，依此类推。如果在任一时刻，词素里的下一个字母不匹配任何子节点，那这个标识符必定不是关键字，我们就停下。如果我们走到一个双线框，而且正处在词素的最后一个字符上，那我们就找到了一个关键字。

### 字典树与状态机

这张树状图就是一个叫做<span name="trie">[**字典树（trie）**][trie]</span>的东西的例子。字典树存储一组字符串。其他大多数存储字符串的数据结构，都是先把原始字符数组装进去，再把它们包进某个更大的、有助于更快搜索的结构里。字典树不一样。在字典树里，你哪儿都找不到一个完整的字符串。

[trie]: https://en.wikipedia.org/wiki/Trie

<aside name="trie">

"Trie" 是计算机科学里最容易叫人犯迷糊的名字之一。爱德华·弗雷德金从 "retrieval" 这个词的中间把它揪了出来，照理说它该读成 "tree"。可是，呃，早就有一个相当重要的数据结构读作 "tree"——而字典树正是它的一个特例——所以除非你从来不会把这些东西念出声，否则谁也分不清你讲的是哪一个。于是，如今大家往往把它念成 "try"，省得头疼。

</aside>

相反，字典树「包含」的每个字符串，都是顺着字符节点树的一条**路径**来表示的，就像我们上面那次遍历那样。匹配某个字符串最后一个字符的节点，带有一个特殊标记——也就是插图里的双线框。这样一来，如果你的字典树包含，比如说，"banquet" 和 "ban"，你就能判断出它**不**包含 "banque"——"e" 节点不会有那个标记，而 "n" 和 "t" 节点会有。

字典树是一个更基本的数据结构的特例：[**确定性有限自动机**][dfa]（**DFA**）。你可能还听过它的别的名字：**有限状态机**，或者干脆叫**状态机**。状态机**酷毙了**。从[游戏编程][state]到实现网络协议，它到处都能派上用场。

[dfa]: https://en.wikipedia.org/wiki/Deterministic_finite_automaton
[state]: http://gameprogrammingpatterns.com/state.html

在一个 DFA 里，你有一组**状态**，状态之间有**转移**，构成一张图。在任何时刻，这台机器都恰好「处于」一个状态。它沿着转移到达其他状态。当你用 DFA 做词法分析时，每一次转移就是字符串里被匹配到的一个字符。每个状态代表一组允许的字符。

我们那棵关键字树，正是一个识别 Lox 关键字的 DFA。但 DFA 比简单的树更强大，因为它们可以是任意的**图**。转移能在状态之间形成环。这让你能识别任意长的字符串。比如，下面这个 DFA 识别数字字面量：

<span name="railroad"></span>

<img src="image/scanning-on-demand/numbers.png" alt="一张识别整数和浮点数字面量的语法图。" />

<aside name="railroad">

这种样式的图，叫做[**语法图**][syntax diagram]，或者有个更讨人喜欢的名字——**铁路图**。后一个名字的由来是，它看上去有点像火车的调车场。

在 Backus-Naur 形式（BNF）出现之前，这是记录一门语言文法的主要方式之一。如今，我们大多用文字，可是一份**文本语言**的官方规范竟然要靠一张**图片**，这里头有种说不出的妙处。

[syntax diagram]: https://en.wikipedia.org/wiki/Syntax_diagram

</aside>

为了让图更好读，我把十个数字的节点合并成了一个，但基本流程是一样的——你沿着路径走，每当消费掉词素里一个对应的字符，就进入一个节点。要是我们乐意，完全可以构造一个庞大的 DFA，把 Lox 的**全部**词法分析都包揽下来——一台单一的状态机，识别并吐出我们需要的所有词法单元。

不过，<span name="regex">手工</span>打造那个巨型 DFA 会很棘手。这正是 [Lex][] 被创造出来的原因。你给它一份词法文法的简单文字描述——一堆正则表达式——它就会自动为你生成一个 DFA，并产出一大堆实现它的 C 代码。

[lex]: https://en.wikipedia.org/wiki/Lex_(software)

<aside name="regex">

编程语言和文本编辑器里的大多数正则表达式引擎，底层也是这么干的。它们把你的正则字符串转换成 DFA，再用它来匹配字符串。

如果你想学把正则表达式转成 DFA 的算法，[龙书][dragon]都为你准备好了。

[dragon]: https://en.wikipedia.org/wiki/Compilers:_Principles,_Techniques,_and_Tools

</aside>

我们不走那条路。我们已经有了一个完全堪用的手写扫描器。我们只需要一棵小小的字典树来识别关键字。那该怎么把它对应到代码上呢？

最最简单的<span name="v8">方案</span>，是为每个节点用一个 switch 语句，每个分支一个 case。我们从根节点开始，处理那些简单的关键字。

<aside name="v8">

简单不等于愚蠢。这套做法[差不多就是 V8 干的事][v8]，而 V8 是当今世界上最精密、最快的语言实现之一。

[v8]: https://github.com/v8/v8/blob/e77eebfe3b747fb315bd3baad09bec0953e53e68/src/parsing/scanner.cc#L1643

</aside>

^code keywords (1 before, 1 after)

这些是各自只对应一个关键字的首字母。如果我们看到一个 "s"，这个标识符唯一可能对应的关键字就是 `super`。不过也不一定，所以我们还得检查剩下的字母。在树状图里，这基本上就是从 "s" 上垂下来的那条直路。

我们不会为每个这样的节点都写一个 switch。取而代之，我们有一个工具函数，用来检验一个潜在关键字词素的剩余部分。

^code check-keyword

树里所有不分支的路径都用它。一旦找到一个只可能通向某一个保留字的前缀，我们就得核实两件事。词素必须跟关键字一样长。如果首字母是 "s"，词素仍可能是 "sup" 或 "superb"。而剩下的字符必须精确匹配——"supar" 可不行。

如果字符数正确，而且正是我们想要的那些字符，那它就是个关键字，我们返回与之关联的词法单元类型。否则，它就必定是一个普通标识符。

有几个关键字，树在首字母之后又分了叉。如果词素以 "f" 开头，那它可能是 `false`、`for` 或 `fun`。所以我们为从 "f" 节点分出的分支再加一个 switch。

^code keyword-f (1 before, 1 after)

在 switch 之前，我们得先确认**确实**有第二个字母。毕竟 "f" 本身也是个合法的标识符。另一个会分叉的字母是 "t"。

^code keyword-t (1 before, 1 after)

就这些。几个嵌套的 `switch` 语句。这段代码不仅<span name="short">短</span>，而且非常非常快。它只做检测关键字所需的最小工作，一旦看出标识符不会是保留字就立刻退出。

就这样，我们的扫描器完成了。

<aside name="short">

我们有时会掉进一个陷阱，以为性能来自复杂的数据结构、层层缓存，以及其他花哨的优化。但很多时候，所需要的只是少做点工作，而我常常发现，写出我能写的最简单的代码，就足以做到这一点。

</aside>

## 习题

1.  许多较新的语言支持[**字符串插值**][interp]。在字符串字面量里，你有某种特殊的分隔符——最常见的是开头一个 `${`、结尾一个 `}`。在这些分隔符之间，可以出现任何表达式。当字符串字面量被执行时，内部表达式会被求值、转换成字符串，然后与周围的字符串字面量合并。

    例如，如果 Lox 支持字符串插值，那么这段……

    ```lox
    var drink = "Tea";
    var steep = 4;
    var cool = 2;
    print "${drink} will be ready in ${steep + cool} minutes.";
    ```

    ……会打印：

    ```text
    Tea will be ready in 6 minutes.
    ```

    为实现字符串插值的扫描器，你会定义哪些词法单元类型？对上面那个字符串字面量，你会发出怎样的一串词法单元？

    下面这个你会发出哪些词法单元：

    ```text
    "Nested ${"interpolation?! Are you ${"mad?!"}"}"
    ```

    不妨去看看其他支持插值的语言实现，看它们是怎么处理的。

2.  有好几种语言用尖括号表示泛型，同时又有 `>>` 右移运算符。这在早期的 C++ 里引出了一个经典问题：

    ```c++
    vector<vector<string>> nestedVectors;
    ```

    它会产生一个编译错误，因为 `>>` 被词法分析成了一个单独的右移词法单元，而不是两个 `>` 词法单元。用户被迫在闭合尖括号之间加一个空格来绕开它。

    较新版本的 C++ 更聪明了，能处理上面的代码。Java 和 C# 从来没有这个问题。那些语言是如何规定并实现这一点的？

3.  许多语言，尤其是在它们演化的后期，会定义「上下文关键字」。这类标识符在某些上下文里表现得像保留字，但在另一些上下文里又可以是普通的用户自定义标识符。

    比如，在 C# 里，`await` 在 `async` 方法内部是个关键字，但在其他方法里，你可以把 `await` 当作自己的标识符来用。

    从别的语言里举出几个上下文关键字，以及它们有意义的那些上下文。拥有上下文关键字有哪些利弊？如果需要，你会怎样在你自己语言的前端里实现它们？

[interp]: https://en.wikipedia.org/wiki/String_interpolation
