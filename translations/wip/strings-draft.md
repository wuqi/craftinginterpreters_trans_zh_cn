> 「啊？对琐碎的活儿有点抵触？」大夫挑了挑眉毛。「可以理解，但大可不必。人应该珍惜那些单调乏味的活计——它们占住了身体，却让脑子和心思无拘无束。」
>
> <cite>泰德·威廉姆斯，《龙骨椅》</cite>

我们的小虚拟机现在能表示三种值：数字、布尔值和 `nil`。这几种类型有两个重要的共同点：它们不可变，而且很小。数字是最大的，也仍然塞得进两个 64 位字。这个代价小到我们为所有值都付得起，哪怕是不需要那么大空间的布尔值和 nil。

可惜，字符串就没这么娇小了。字符串根本没有最大长度。哪怕我们人为地设一个像 <span name="pascal">255</span> 个字符这样硬凑出来的上限，那要摊在每一个值上的内存也还是太多。

<aside name="pascal">

UCSD Pascal 是最早的 Pascal 实现之一，它用的正是这个上限。Pascal 字符串不像 C 那样用结尾的空字节来标记字符串的结束，而是在开头放一个长度值。由于 UCSD 只用单个字节来存长度，字符串就不能超过 255 个字符。

<img src="image/strings/pstring.png" alt="Pascal 字符串 'hello'，前面有一个值为 5 的长度字节。" />

</aside>

我们需要一种办法来支持大小会变化、有时变化很大的值。堆上的动态分配正是为此设计的。我们想分配多少字节就分配多少字节，拿回来一个指针，用它在这个值流经虚拟机时一路跟踪它。

## 值与对象

较大的、大小可变的值用堆，较小的、原子的值用栈，这就带来一种两级表示法。你能存进变量、或从表达式返回的每一个 Lox 值，都是一个 Value。对于数字这类小的、固定大小的类型，载荷就直接存进 Value 结构体内部。

如果对象更大，它的数据就住在堆上。此时 Value 的载荷是一个指向那块内存的**指针**。clox 里最终会有好几种堆分配的类型：字符串、实例、函数，你懂的。每种类型都有自己独有的数据，但也都有一些共享的状态，[我们日后的垃圾回收器][gc]会用它来管理这些对象的内存。

<img src="image/strings/value.png" class="wide" alt="数字值和对象值的字段布局。" />

</aside>

## 结构体继承

每一个堆分配的值都是个 Obj，但 <span name="objs">Obj</span> 并不都一样。对字符串，我们需要那串字符。等做到实例时，它们需要自己的数据字段。一个函数对象需要它的字节码块。面对不同的载荷和大小，我们怎么办？我们没法像 Value 那样再用一个联合体，因为大小参差不齐。

<aside name="objs">

不，我也不知道「objs」该怎么念。总觉得中间该有个元音才对。

</aside>

我们改用另一种技术。它已经存在很久了，久到 C 规范都专门为它留出了支持，但我不知道它有没有一个正式名字。它是[**类型双关**][pun]的一个例子，可那个词太宽泛了。既然想不出更好的名字，我就叫它**结构体继承**吧，因为它靠的是结构体，而且大致跟面向对象语言里状态的单继承方式相仿。

[pun]: https://en.wikipedia.org/wiki/Type_punning

跟带标签联合体一样，每个 Obj 都以一个标签字段开头，标明它是哪种对象——字符串、实例等等。标签之后是载荷字段。我们不用一个带各种类型分支的联合体，而是让每种类型各自成为一个独立的结构体。棘手的地方在于，既然 C 没有继承或多态的概念，我们要怎么一视同仁地对待这些结构体。这个我很快会解释，不过先把预备的东西清掉。

「Obj」这个名字本身就指代一个结构体，装着所有对象类型共享的状态。它有点像对象的「基类」。由于值和对象之间存在一些循环依赖，我们在「value」模块里对它做前置声明。

^code forward-declare-obj (2 before, 1 after)

而真正的定义在一个新模块里。

^code object-h

眼下它只装着类型标签。过不多久，我们会为内存管理再加一些记账信息。类型枚举是这样的：

^code obj-type (1 before, 2 after)

显然，等后面几章加上更多堆分配的类型后，它会更有用。由于我们会频繁访问这些标签类型，值得做一个小宏，从给定的 Value 里取出对象类型标签。

这就是我们的地基。

现在，我们在它之上搭出字符串。字符串的载荷定义在一个单独的结构体里。同样，我们需要对它做前置声明。

^code forward-declare-obj-string (1 before, 2 after)

定义就挨着 Obj 放。

^code obj-string (1 before, 2 after)

一个字符串对象含有一串字符。这些字符存在一个单独的、堆分配的数组里，好让每个字符串只占用所需的那么多空间。我们还存了数组里的字节数。这并非严格必需，但能让我们不必遍历字符数组去找空终止符，就知道为这个字符串分配了多少内存。

由于 ObjString 是个 Obj，它也需要所有 Obj 共享的那份状态。它做到这一点的方式，是让自己的第一个字段就是一个 Obj。C 规定结构体的字段按声明的顺序在内存里排列。而且，当你嵌套结构体时，内层结构体的字段会就地展开。所以 Obj 和 ObjString 在内存里长这样：

<img src="image/strings/obj.png" alt="Obj 和 ObjString 各字段的内存布局。" />

注意 ObjString 的头几个字节如何跟 Obj 精确对齐。这不是巧合——C <span name="spec">强制规定</span>了这一点。这样设计是为了支持一个巧妙的套路：你可以拿一个指向结构体的指针，安全地把它转成指向其第一个字段的指针，再转回来。

<aside name="spec">

规范的关键一段是：

> &sect; 6.7.2.1 13
>
> 在结构体对象内部，非位域成员，以及位域所在的单元，其地址按声明的顺序递增。一个指向结构体对象的指针，经适当转换后，指向它的初始成员（若该成员是位域，则指向它所在的单元），反之亦然。结构体对象内部可以有无名的填充，但不会出现在开头。

</aside>

给定一个 `ObjString*`，你可以安全地把它转成 `Obj*`，再从它那儿访问 `type` 字段。每个 ObjString 在「是」这个字的面向对象意义上，都「是」一个 Obj。等我们后面加入其他对象类型时，每个结构体都会把 Obj 作为它的第一个字段。任何想处理所有对象的代码，都可以把它们当成基类的 `Obj*`，忽略后面碰巧跟着的其他字段。

也可以反过来。给定一个 `Obj*`，你可以把它「向下转型」成一个 `ObjString*`。当然，你得确保手上这个 `Obj*` 指针确实指向某个真正的 ObjString 的 `obj` 字段。否则，你就是在不安全地重新解读内存里随机的比特。为了判断这样的转型是否安全，我们再加一个宏。

^code is-string (1 before, 2 after)

它接收的是一个 Value，而不是裸的 `Obj*`，因为虚拟机里大多数代码都是跟 Value 打交道。它依赖这个内联函数：

^code is-obj-type (2 before, 2 after)

随堂小测：为什么不干脆把这个函数体直接放进宏里？这一个跟其他几个有什么不同？对了，因为这个函数体用到了 `value` 两次。宏展开的方式，是把参数**表达式**插进函数体里参数名出现的每一处。如果一个宏用某个参数不止一次，那个表达式就会被求值多次。

如果这个表达式有副作用，那就糟了。要是我们把 `isObjType()` 的函数体塞进宏定义，然后你写了比如

```c

```

它就会从栈上弹出两个值！改用函数就没有这个问题。

只要我们确保在创建某种类型的 Obj 时正确设好类型标签，这个宏就能告诉我们，什么时候把一个值转成特定对象类型是安全的。我们可以用下面这些来做到：

这两个宏接收一个 Value，预期它里面装着指向堆上一个有效 ObjString 的指针。前者返回 `ObjString*` 指针，后者再往里走一步，返回字符数组本身，因为那往往是我们最终需要的东西。

### 拼接

成熟的语言为处理字符串提供了大量操作——访问单个字符、字符串长度、大小写转换、拆分、连接、查找等等。你在实现自己的语言时，多半会想要这些全套。但在这本书里，我们把东西保持得**极其**精简。

## 释放对象

瞧瞧这个看似人畜无害的表达式：

```lox
"st" + "ri" + "ng"
```

编译器把它啃过去的时候，会为那三个字符串字面量各分配一个 ObjString，存进字节码块的常量表，并生成这样的<span name="stack">字节码</span>：

<aside name="stack">

每条指令执行后栈的样子如下：

<img src="image/strings/stack.png" alt="每条指令执行时栈的状态。" />

</aside>

```text
0000    OP_CONSTANT         0 "st"
0002    OP_CONSTANT         1 "ri"
0004    OP_ADD
0005    OP_CONSTANT         2 "ng"
0007    OP_ADD
0008    OP_RETURN
```

头两条指令把 `"st"` 和 `"ri"` 压入栈。然后 `OP_ADD` 把它们弹出并拼接。这会在堆上动态分配一个新字符串 `"stri"`。虚拟机把它压入，接着压入常量 `"ng"`。最后那条 `OP_ADD` 弹出 `"stri"` 和 `"ng"`，把它们拼接起来，再压入结果：`"string"`。很好，正是我们要的。

可是等等。那个 `"stri"` 字符串怎么了？我们动态分配了它，然后虚拟机在把它和 `"ng"` 拼接之后就把它丢了。我们把它从栈上弹出，不再有任何引用，却从没释放它的内存。我们给自己搞出了一个经典的内存泄漏。

当然，**Lox 程序**完全可以把中间字符串忘掉、不必操心释放它们。Lox 会替用户自动管理内存。管理内存的责任并没有**消失**，它落到了我们这些虚拟机实现者的肩上。

完整的<span name="borrowed">解法</span>是一个[垃圾回收器][gc]，在程序运行期间回收不再使用的内存。在准备好着手那个项目之前，我们还有些别的东西要就位。在那之前，我们是活在借来的时间里。加回收器这件事拖得越久，就越难办。

<aside name="borrowed">

我见过不少人，在动手搞 GC 之前就先实现好了自己语言的一大片。就语言开发过程中通常跑的那类玩具程序而言，你其实在程序结束前根本不会把内存用光，所以这套做法能让你走得意外地远。

但这低估了事后再加垃圾回收器有多**难**。回收器**必须**确保它找得到每一处仍在被使用的内存，这样才不会回收掉活数据。一个语言实现能把某个对象的引用藏在上百个地方。只要有一处没找到，你就会碰上噩梦般的 bug。

我见过有语言实现因为事后想加 GC 太难，就这么死掉了。如果你的语言需要 GC，那就尽早把它弄好。它是一个触及整个代码库的横切关注点。

</aside>

## 习题

1.  每个字符串需要两次独立的动态分配——一次给 ObjString，一次给字符数组。要访问一个值里的字符，需要两次指针解引用，这对性能可能不利。更高效的解法依赖一种叫作**[柔性数组成员][flexible array members]**的技术。用它把 ObjString 和它的字符数组存进一块连续的内存分配里。

2.  我们为每个字符串字面量创建 ObjString 时，把字符复制到了堆上。这样，等这个字符串日后被释放时，我们就知道连字符一起释放也是安全的。

    这种做法更简单，但浪费一些内存，在资源极度受限的设备上可能是个问题。替代方案是，我们可以跟踪哪些 ObjString 拥有自己的字符数组，哪些是「常量字符串」，只是指回原始的源代码字符串或某个别的不可释放的位置。给它加上这个支持。

3.  假如 Lox 是你的语言，当一个用户拿 `+` 去操作一个字符串操作数和另一个别的类型的操作数时，你会让它怎么做？为你的选择给出理由。别的语言又是怎么做的？

## 设计说明：字符串编码

在这本书里，我尽量不回避你在真正的语言实现里会撞上的那些棘手问题。我们未必总用最**高精尖**的解法——毕竟这是一本入门书——但我觉得假装问题根本不存在并不诚实。不过，有一个特别难缠的谜题，我确实绕着走了：怎么表示字符串。

字符串编码有两个侧面：

*   **字符串里的一个「字符」到底是什么？** 总共有多少种不同的值，它们又代表什么？对此，第一个被广泛采纳的标准答案是 [ASCII][]。它给你 127 个不同的字符值，并规定了每个值是什么。它很棒……只要你只关心英语。它虽然有一些古怪的、大多被遗忘的字符，比如「记录分隔符」和「同步空转」，却连一个元音变音符、尖音符、抑音符都没有。它表示不了「jalapeño」「naïve」<span name="gruyere">「Gruyère」</span>，或者「Mötley Crüe」。

    <aside name="gruyere">

    不用说，一门不让人谈论 Gruyère 或 Mötley Crüe 的语言，就是一门不值得用的语言。

    </aside>

    接着登场的是 [Unicode][]。它最初支持 16,384 个不同的字符（**码点**），刚好舒舒服服地装进 16 位，还余下几个比特。后来它不断长大，如今已经有远超 100,000 个不同的码点，其中就包括像 💩 这样至关重要的人类交流工具（Unicode 字符「PILE OF POO」，`U+1F4A9`）。

    可即便那么长的一串码点，也不足以表示一门语言可能支持的每一个可见字形。为处理这一点，Unicode 还有**组合字符**，用来修饰前一个码点。例如，「a」后面跟一个组合字符「¨」，就得到「ä」。（更让人犯晕的是，Unicode **还**有一个单独的码点，长得也像「ä」。）

    如果一个用户访问「naïve」里的第四个「字符」，他期望拿回的是「v」，还是 &ldquo;¨&rdquo;？前者意味着他把每个码点连同它的组合字符看成一个整体——也就是 Unicode 所说的**扩展字形簇**；后者意味着他以单个码点为单位来思考。你的用户期望哪一种？

*   **一个单元在内存里怎么表示？** 大多数使用 ASCII 的系统给每个字符一个字节，把高位空着不用。Unicode 有好几种常见的编码。UTF-16 把大多数码点塞进 16 位。当每个码点都塞得进这个大小时，那很好。等到溢出时，他们又加上了**代理对**，用多个 16 位代码单元来表示一个码点。UTF-32 是 UTF-16 的下一步演进——它给每一个码点都足足 32 位。

    UTF-8 比前面两者都更复杂。它用数量可变的字节来编码一个码点。值较小的码点占用的字节更少。由于每个字符可能占用不同的字节数，你没法直接按索引访问字符串、定位到某个特定的码点。比如说，你想要第 10 个码点，不把前面那些逐个走过去、解码一遍，你就不知道它在字符串里的第几个字节处。

[ascii]: https://en.wikipedia.org/wiki/ASCII
[unicode]: https://en.wikipedia.org/wiki/Unicode

选择一种字符表示和编码，牵涉到根本性的权衡。跟工程里的许多事情一样，没有<span name="python">完美</span>的解法：

<aside name="python">

这个问题有多难，Python 就是个例子。从 Python 2 到 3 那段漫长到令人牙酸的过渡之所以痛苦，多半就是因为它在字符串编码上的改动。

</aside>

*   ASCII 省内存又快，但它把非拉丁语言一脚踢到边上。

*   UTF-32 快，且支持整个 Unicode 范围，但很浪费内存——毕竟大多数码点往往落在值域较低的一段，根本用不上整整 32 位。

*   UTF-8 省内存，也支持整个 Unicode 范围，但它的变长编码让随机访问码点变得很慢。

*   UTF-16 比它们全都糟——它是 Unicode 长大后溢出早先 16 位范围的丑陋后果。它比 UTF-8 更费内存，却又因为代理对而成了一种变长编码。能避开就避开。唉，可如果你的语言需要跑在浏览器、JVM 或 CLR 上，或者跟它们互操作，你可能就甩不掉它了，因为它们的字符串都用 UTF-16，而你总不想每次把字符串传给底层系统时都转换一遍。

一种选择是走最大化路线，做「最正确」的事。支持所有 Unicode 码点。在内部，根据每个字符串的内容为它选择一种编码——如果每个码点都塞得进一个字节就用 ASCII，如果没有代理对就用 UTF-16，等等。提供 API，让用户既能遍历码点、也能遍历扩展字形簇。

这能面面俱到，但真的复杂。实现、调试、优化的工作量都很大。在序列化字符串或跟其他系统互操作时，你得应对所有编码。用户需要理解两套索引 API，还得知道何时用哪一套。较新的大型语言往往走这条路——比如 Raku 和 Swift。

更简单的折中方案是始终用 UTF-8 编码，只暴露一套以码点为准的 API。想要处理字形簇的用户，让他们自己用第三方库。这不像 ASCII 那样以拉丁语为中心，却也没复杂多少。你会失去按码点快速直接索引的能力，但通常没有它也能活，或者负担得起把它做成 **O(n)** 而不是 **O(1)**。

如果我要为编写大型应用的人设计一门能扛大梁的语言，我多半会走最大化路线。而为我那门小小的嵌入式脚本语言 [Wren][]，我选了 UTF-8 加码点。
