## 函数调用

C 风格的函数调用语法你肯定很熟悉，但它的文法比你可能意识到的更微妙。调用通常是指向具名
函数的，比如：

```lox
average(1, 2);
```

但被调用函数的<span name="pascal">名字</span>其实并不是调用语法的一部分。被调用的那个
东西——也就是**被调用者（callee）**——可以是任何求值结果为函数的表达式。（好吧，它确实
得是个**优先级**相当高的表达式，不过用括号就能解决。）例如：

<aside name="pascal">

在 Pascal 里，名字**就是**调用语法的一部分。你只能调用具名函数，或者直接存放在变量里
的函数。

</aside>

```lox
getCallback()();
```

这里有两个调用表达式。第一对括号的被调用者是 `getCallback`。但第二次调用把整个
`getCallback()` 表达式当成了它的被调用者。真正表示函数调用的是跟在表达式后面的那对
括号。你可以把一次调用大致看成一个以 `(` 开头的后缀运算符。

这个「运算符」的优先级比任何其他运算符都高，连一元运算符都比不上。于是我们让 `unary`
规则向上冒泡到一个新的 `call` 规则，把它安放进文法里。

<span name="curry"></span>

```ebnf
unary          → ( "!" | "-" ) unary | call ;
call           → primary ( "(" arguments? ")" )* ;
```

这条规则匹配一个基本表达式，后面跟零个或多个函数调用。如果没有括号，它解析出来的就是
一个光秃秃的基本表达式。否则，每一次调用都由一对括号识别，里面跟一个可选的实参列表。
实参列表的文法是：

<aside name="curry">

这条规则用 `*` 来允许匹配 `fn(1)(2)(3)` 这样的连续调用。这样的代码在 C 系语言里不常见，
但在从 ML 派生出来的那个语言家族里很常见。在那里，定义一个接收多个实参的函数的常规
做法，是把它写成一串嵌套函数。每个函数接收一个实参，返回一个新的函数；那个新函数消费
下一个实参，再返回又一个函数，如此继续。最终，所有实参都被消费完之后，最后那个函数完成
整个操作。

看起来不像在这儿这么古怪。

</aside>

### 检查元数

另一个问题关系到函数的**元数**。元数是「一个函数或操作期望多少个实参」这件事的高级说法。
一元运算符元数为一，二元运算符为二，等等。对函数来说，元数由它声明的形参个数决定。

```lox
fun add(a, b, c) {
  print a + b + c;
}
```

这个函数定义了三个形参 `a`、`b` 和 `c`，所以它的元数是三，期望三个实参。那么如果你这样
调用它会怎样：

```lox
add(1, 2, 3, 4); // 太多了。
add(1, 2);       // 太少了。
```

不同语言对这个问题的做法不同。当然，大多数静态类型语言在编译期就检查，参数个数和函数
元数不匹配就拒绝编译。JavaScript 会丢弃你多传的任何实参。如果你传得不够，它就用那个
有点像 null 但又不完全是 null 的魔法值 `undefined` 填上缺失的形参。Python 更严格。实参
列表太短或太长，它都抛运行时错误。

我觉得后者是更好的做法。传错实参个数几乎总是个 bug，而且我在实践中真犯过这种错。既然
如此，实现越早把我的注意力吸引到它越好。所以对 Lox，我们采用 Python 的做法。在调用
被调用者之前，我们检查实参列表的长度是否与被调用者的元数相符。

这需要在 LoxCallable 接口上加一个新方法，让它报出自己的元数。

## 原生函数

理论上我们能调用函数了，可我们还没有函数可调。在讲到用户定义的函数之前，现在正是引入语言
实现中一个至关重要、却常被忽略的方面的好时机——<span name="native">**原生函数**</span>。
这些函数由解释器暴露给用户代码，但它们是用宿主语言（我们的情况是 Java）实现的，而不是用
被实现的语言（Lox）实现的。

有时这些函数也换个称呼：**primitive**、**external function**，或者 **foreign function**。
由于这些函数可以在用户程序运行期间被调用，它们构成了实现的运行时的一部分。很多编程语言
书对此一带而过，因为它们在概念上不有趣。它们大多是些苦力活。

<aside name="native">

有意思的是，这些函数的两个名字——「原生（native）」和「外来（foreign）」——是反义词。
也许这取决于选词的人站在什么视角。如果你把自己看成「生活」在运行时的实现（我们的情况是
Java）之内，那么用那种语言写的函数就是「原生的」。但如果你抱着自己这门语言的**用户**的
心态，那么运行时就是用某个别的「外来的」语言实现的。

也可能「原生」指的是底层硬件的机器码语言。在 Java 里，「native」方法指的是用 C 或 C++
实现、并编译成原生机器码的方法。

<img src="image/functions/foreign.png" class="above" alt="一切只看你站在哪一边。" />

</aside>

但说到让你的语言真的擅长做有用的事，你的实现所提供的原生函数是关键。它们提供了通往那些
基础服务的通道，而所有程序都是用这些服务定义的。如果你不提供访问文件系统的原生函数，
用户要写出一个读取并<span name="print">显示</span>文件的程序可有得苦了。

<aside name="print">

几乎每种语言都会提供的一个经典原生函数，是把文本打印到 stdout。在 Lox 里，我把 `print`
做成了内置语句，好让我们在这一章之前的章节里就能把东西显示到屏幕上。

有了函数之后，我们本可以把旧的 print 语法拆掉、换成一个原生函数，让语言更简洁一点。但
那会意味着书前面的例子在后面章节的解释器上跑不了，反之亦然。所以，对这本书，我不动它。

不过，如果你是在为你**自己**的语言写解释器，可能要考虑一下这件事。

</aside>

很多语言还允许用户提供自己的原生函数。实现这件事的机制叫作**外部函数接口**（**FFI**）、
**原生扩展**、**原生接口**，或者诸如此类的名字。它们的好处是，让语言实现者不必为底层平台
支持的每一样能力都提供访问接口。我们不会给 jlox 定义 FFI，但会加一个原生函数，让你看看
它长什么样。

### 报告时间

等我们到[第三部分][]、开始动手做一个效率高得多的 Lox 实现时，我们会深深关心性能。性能
工作需要测量，而测量又意味着**基准测试**。基准测试是那些测量「跑一遍解释器的某个角落要
花多少时间」的程序。

我们可以测量「启动解释器、跑基准测试、退出」这一整段时间，但那会加进一大堆开销——JVM
启动时间、操作系统的把戏等等。当然，那些开销确实也有影响，但如果你只是想验证对解释器某个
部分的某项优化，你不会希望那些开销遮住你的结果。

一个更好的办法，是让基准测试脚本自己去测量代码里两个点之间经过的时间。要做到这一点，一个
Lox 程序得能够报时间。现在没法做到——没有对计算机底层时钟的访问，你不可能「从零开始」
实现一个有用的时钟。

## 函数声明

我们终于可以在当初引入变量的那个 `declaration` 规则里加一条新的产生式了。函数声明和变量
一样，会绑定一个新的<span name="name">名字</span>。这意味着它只能出现在允许声明的地方。

<aside name="name">

一条具名的函数声明其实并不是一个单一的原子操作。它是两个不同步骤的语法糖：(1) 创建一个
新的函数对象；(2) 把一个新变量绑定到它。如果 Lox 有匿名函数的语法，我们就不需要函数声明
语句了。你可以直接这么写：

```lox
var add = fun (a, b) {
  print a + b;
};
```

不过，既然具名函数是常见情形，我索性给 Lox 配上了好看的语法。

</aside>

```ebnf
declaration    → funDecl
               | varDecl
               | statement ;
```

更新后的 `declaration` 规则引用了这条新规则：

```ebnf
funDecl        → "fun" function ;
function       → IDENTIFIER "(" parameters? ")" block ;
```

主规则 `funDecl` 用到了一条独立的辅助规则 `function`。一条函数**声明语句**就是 `fun` 关键字

形参是函数的核心，尤其是函数会**封装**自己的形参这一点——函数之外的任何代码都看不见它们。
这意味着每个函数都有自己的环境，用来存放那些变量。

更进一步，这个环境必须是动态创建的。每次函数**调用**都有自己的环境。否则递归就坏了。
如果同时有多个对同一个函数的调用在进行，每一个都需要**自己**的环境，尽管它们全都是对同一个
函数的调用。

比如说，下面是一种拐弯抹角的数到三的办法：

```lox
fun count(n) {
  if (n > 1) count(n - 1);
  print n;
}

count(3);
```

想象我们在最内层那次嵌套调用正要打印 1 的那个点上把解释器暂停。外层那些要打印 2 和 3 的
调用还没打印它们的值，所以内存里的某个地方一定还存着一些环境，记录着「`n` 在一个上下文
里绑定到 3、在另一个上下文里绑定到 2、在最内层绑定到 1」这件事，像这样：

<img src="image/functions/recursion.png" alt="每次递归调用各有各的环境。" />

这就是为什么我们在每次**调用**时创建新环境，而不是在函数**声明**时。前面那个 `call()` 方法
就是这么做的。调用一开始，它创建一个新环境。然后它让形参列表和实参列表齐步前进。每一对上，
它创建一个以形参命名的新变量，并把它绑定到实参的值上。

所以，对于这样一个程序：

```lox
fun add(a, b, c) {
  print a + b + c;
}

add(1, 2, 3);
```

在调用 `add()` 的那个位置上，解释器创建了这样一个东西：

<img src="image/functions/binding.png" alt="把实参绑定到形参。" />

然后 `call()` 让解释器在这个新的函数局部环境里执行函数体。到此为止，当前环境一直是函数
被调用的那个环境。现在，我们从那里瞬移进为这个函数新建的形参空间里。

要把数据传进函数，所需要的就这么多。通过在执行函数体时使用不同的环境，对同一个函数的、
代码相同的调用可以产生不同的结果。

一旦函数体执行完毕，`executeBlock()` 丢弃那个函数局部环境，并恢复回调用点处之前生效的那个
环境。最后，`call()` 返回 `null`，于是给调用方返回了 `nil`。（我们稍后会加上返回值。）

机械地看，代码相当简单。走几个列表。绑定几个新变量。调一个方法。但正是在这里，函数声明
那结晶般的**代码**，变成了一个活生生的**调用**。这是我整本书里最喜欢的片段之一。如果你
有兴致，尽管花点时间对着它冥想一下。

完事？好。注意我们绑定形参时，假定形参列表和实参列表长度相同。这是安全的，因为
`visitCallExpr()` 在调用 `call()` 之前检查了元数。它靠的就是函数报出自己的元数。

## Return 语句

我们可以通过传形参把数据送进函数，却没办法把结果取<span name="hotel">**出**</span>来。如果
Lox 是像 Ruby 或 Scheme 那样面向表达式的语言，函数体就会是一个表达式，它的值隐式地就是函数
的结果。但在 Lox 里，函数体是一列不产生值的语句，所以我们需要专门的语法来产出一个结果。
换句话说，就是 `return` 语句。我敢说你已经猜到文法了。

<aside name="hotel">

数据的加州旅馆。

</aside>

```ebnf
statement      → exprStmt
               | forStmt
               | ifStmt
               | printStmt
               | returnStmt
               | whileStmt
               | block ;

returnStmt     → "return" expression? ";" ;
```

我们又多了——事实上是最后一条——挂在那个德高望重的 `statement` 规则下的产生式。一条
`return` 语句就是 `return` 关键字，后面跟一个可选的表达式，以分号收尾。

返回值是可选的，为的是支持从一个不返回有用值的函数里提前退出。在静态类型语言里，
「void」函数不返回值，非 void 的返回。由于 Lox 是动态类型的，不存在真正的 void 函数。
编译器没法阻止你从一个不含 `return` 语句的函数调用结果里取走结果值。

```lox
fun procedure() {
  print "don't return anything";
}

var result = procedure();
print result; // ?
```

这意味着每个 Lox 函数都必须返回**某样东西**，哪怕它一条 `return` 语句都没有。为此我们用
`nil`，这也是 LoxFunction 的 `call()` 实现最后返回 `null` 的原因。同样地，如果你在 `return`
语句里省略了值，我们干脆把它当作等价于：

```lox
return nil;
```

### 从调用中返回

解释一条 `return` 语句很棘手。你可以从函数体内的任何地方返回，甚至从深深嵌在其他语句
里面的地方返回。`return` 执行时，解释器需要从它当前所处的任何上下文里一路跳出去，让那次
函数调用完成，像是某种被打了鸡血的控制流结构。

比如说，假设我们正在运行这个程序，正要执行那条 `return` 语句：

```lox
fun count(n) {
  while (n < 100) {
    if (n == 3) return n; // <--
    print n;
    n = n + 1;
  }
}

count(1);
```

Java 调用栈目前大致长这样：

```text
Interpreter.visitReturnStmt()
Interpreter.visitIfStmt()
Interpreter.executeBlock()
Interpreter.visitBlockStmt()
Interpreter.visitWhileStmt()
Interpreter.executeBlock()
LoxFunction.call()
Interpreter.visitCallExpr()
```

我们需要从栈顶一路回到 `call()`。我不知道你怎么想，但对我来说这听起来就是异常。执行一条
`return` 语句时，我们用一个异常让解释器穿过所有外层语句的 visit 方法一路退回到开始执行
函数体的那段代码。

我们这个新 AST 节点的 visit 方法长这样：

^code visit-return

如果有返回值，我们对它求值；否则我们就用 `nil`。然后我们把这个值包进一个自定义异常类里
抛出去。

^code return-exception

这个类把返回值和 Java 要求一个运行时异常类所必须的全套装饰包在一起。那个带着 `null` 和
`false` 参数的奇怪 super 构造调用，关掉了我们不需要的某些 JVM 机制。既然我们把这个异常类
用于<span name="exception">控制流</span>而不是真正的错误处理，就不需要堆栈跟踪这类开销。

<aside name="exception">

说在前头，我一般来说并不喜欢拿异常当控制流。但在一个深度递归的树遍历解释器里面，这是可行
的办法。既然我们自己的语法树求值和 Java 调用栈绑得如此紧密，我们就偶尔不得不做一些重量级
的调用栈操作，而异常是个顺手的工具。

</aside>

我们希望它一路退回到函数调用开始的地方，也就是 LoxFunction 里的 `call()` 方法。

^code catch-return (3 before, 1 after)

我们把对 `executeBlock()` 的调用包在一个 try-catch 块里。当它捕获到一个 return 异常时，就把
里面的值取出来，让它成为 `call()` 的返回值。如果它从未捕获到这类异常，就意味着函数执行到
函数体末尾而没有碰到 `return` 语句。那种情况下，它隐式地返回 `nil`。

来试试吧。我们终于有足够的本事来支持这个经典例子了——一个计算斐波那契数的递归函数：

<span name="slow"></span>

```lox

  if (n <= 1) return n;
  return fib(n - 2) + fib(n - 1);
}

for (var i = 0; i < 20; i = i + 1) {
  print fib(i);
}
```

这个小程序几乎用到了我们过去几章实现的每一项语言特性——表达式、算术、分支、循环、变量、
函数、函数调用、形参绑定和返回。

<aside name="slow">

你可能注意到它相当慢。显然，递归不是计算斐波那契数最高效的办法，但作为微基准测试，它很好地
检验了我们解释器实现函数调用的速度。

你看，答案是「不太快」。这没关系。我们的 C 解释器会更快。

</aside>

## 局部函数与闭包

我们的函数功能相当齐备，但还有一个洞要补。事实上这个缺口足够大，我们会把[下一章][]的
大部分时间花在封堵它上，不过我们可以在这里先起步。

LoxFunction 的 `call()` 实现会创建一个新环境，用来绑定函数的形参。我给你看那段代码时，
一带而过了某个要紧的问题：这个环境的**父**是什么？

目前，它总是 `globals`，也就是最顶层的全局环境。这样，如果一个标识符没有在函数体自身
内部定义，解释器就能到函数外面的全局作用域里去找它。在斐波那契那个例子里，解释器就是这样
能在函数自己的体内查到对 `fib` 的递归调用的——`fib` 是一个全局变量。

但别忘了，在 Lox 里，函数声明允许出现在任何名字可以被绑定的**任何地方**。这既包括一个 Lox
脚本的顶层，也包括块内部或其他函数内部。Lox 支持**局部函数**，也就是定义在另一个函数里面、
或者嵌套在某个块里面的函数。

考虑这个经典例子：

```lox
fun makeCounter() {
  var i = 0;
  fun count() {
    i = i + 1;
    print i;
  }

  return count;
}

var counter = makeCounter();
counter(); // "1".
counter(); // "2".
```

这里，`count()` 用到了 `i`，而 `i` 是在包含它的那个函数 `makeCounter()` 里、在它自己之外
声明的。`makeCounter()` 返回对 `count()` 函数的一个引用，然后它自己的函数体就彻底执行完毕
了。

与此同时，顶层代码调用返回的那个 `count()` 函数。这会执行 `count()` 的函数体，给 `i` 赋值
并读取它，尽管定义 `i` 的那个函数早就退出了。

如果你以前从没见过带嵌套函数的语言，这可能看起来很疯狂，但用户确实期待它能工作。可惜，你
现在去跑它，会在 `counter()` 那次调用里得到一个未定义变量错误，因为 `count()` 的函数体试图
去查 `i`。那是当时实际的环境链长这样：

<img src="image/functions/global.png" alt="从 count() 的函数体到全局作用域的环境链。" />

当我们调用 `count()` 时（通过存在 `counter` 里、对它的引用），我们为函数体创建一个新的空
环境。那个环境的父是全局环境。我们丢掉了 `makeCounter()` 那个绑定着 `i` 的环境。

我们把时间往回拨一点。这是我们刚在 `makeCounter()` 体内声明 `count()` 时，环境链的样子：

<img src="image/functions/body.png" alt="makeCounter() 函数体内部的环境链。" />

所以在函数声明的那个位置上，我们能看见 `i`。但当我们从 `makeCounter()` 返回、退出它的函数体
时，解释器丢弃了那个环境。既然解释器不把 `count()` 周围的环境保留下来，那就得靠函数对象
自己把它抓在手里。

这种数据结构叫作<span name="closure">**闭包**</span>，因为它把函数声明处周围那些变量「闭合」
住并保留了下来。闭包从 Lisp 早期就存在了，语言黑客们也想出了各式各样的实现办法。对 jlox，
我们采用最简单可行的做法。在 LoxFunction 里，我们加一个字段来存放一个环境。

## 挑战

1.  我们的解释器仔细检查传给函数的实参个数是否与它所期望的形参个数相符。由于这个检查
    是在运行时、每次调用时都做，它有性能代价。Smalltalk 的实现没有这个问题。为什么没有？

1.  Lox 的函数声明语法做了两件相互独立的事：它创建一个函数，还把它绑定到一个名字上。这
    在你确实想给函数关联一个名字的常见情形里提升了易用性。但在函数式风格的代码里，你常常
    只是想创建一个函数，立刻把它传给另一个函数，或者返回出去。那种情况下，它不需要名字。

    鼓励函数式风格的语言通常都支持**匿名函数**或 **lambda**——一种不把函数绑定到名字上
    的表达式语法。给 Lox 加上匿名函数语法，让下面这段能跑起来：

    ```lox
    fun thrice(fn) {
      for (var i = 1; i <= 3; i = i + 1) {
        fn(i);
      }
    }

    thrice(fun (a) {
      print a;
    });
    // "1".
    // "2".
    // "3".
    ```

    你怎么处理这种棘手的情形：匿名函数表达式出现在一个表达式语句里：

    ```lox
    fun () {};
    ```

1.  这个程序有效吗？

    ```lox
    fun scope(a) {
      var a = "local";
    ```
