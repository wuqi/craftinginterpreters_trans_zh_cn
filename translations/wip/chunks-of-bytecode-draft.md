用 jlox 我们已经做出了一套完整可用的 Lox 实现，那这本书为什么还没完？一部分原因是，jlox 靠着 <span name="metal">JVM</span> 替我们做了很多事。如果我们想弄懂解释器一路深入到最底层是怎么工作的，就得自己把这些零碎部件搭出来。

<aside name="metal">

当然，我们的第二台解释器在内存分配这类基础事情上，靠的是 C 标准库；C 编译器又替我们挡掉了底层机器码的一大堆细节。见鬼，那些机器码说不定还是用芯片上的微码实现的呢。而 C 运行时又依赖操作系统来分配内存页。可这书要想塞进你书架，我们总得在**某个地方**打住。

</aside>

jlox 不够用，还有一个更根本的原因：它太他妈慢了。树遍历解释器对某些高级的、声明式的语言来说还行。但对一门通用的命令式语言——哪怕像 Lox 这样的「脚本」语言——它就根本跑不动了。看看这个小脚本：

```lox
fun fib(n) {
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2); // [fib]
}

var before = clock();
print fib(40);
var after = clock();
print after - before;
```

<aside name="fib">

真要用它来算斐波那契数，效率低得可笑。我们的目标是看**解释器**跑得多快，不是看我们能写出多快的程序。一个干了很多活、慢吞吞的程序——有用没用都无所谓——正好拿来当测试用例。

</aside>

在我的笔记本上，jlox 执行它大约要 72 秒。等价的 C 程序半秒就跑完了。我们这门动态类型的脚本语言，永远不可能快过手动管理内存的静态类型语言，但也不必忍受慢上**两个数量级**还多。

我们可以把 jlox 丢进性能分析器里跑，开始调优、微调那些热点，但这顶多管用到一定程度。执行模型本身——遍历 AST——从根上就是个错的设计。无论怎么微优化，都到不了我们想要的性能，就像你没法把一辆 AMC Gremlin 打磨成 SR-71「黑鸟」。

我们得重新想一套核心模型。这一章就介绍这个模型——字节码——并开始打造我们的新解释器 clox。

## 字节码？

工程里，很少有什么选择是没有取舍的。要真正理解我们为什么选字节码，先把它跟另外两个方案摆在一起比比。

### 为什么不遍历 AST？

我们现有的解释器有几样好处：

*   嗯，首先，我们已经把它写出来了。它完工了。而它能这么快完工，主要是因为这种解释器**实现起来真的很简单**。代码的运行时表示直接对应语法。从语法解析器走到运行时所需的数据结构，几乎不费吹灰之力。

*   它**可移植**。我们现在的解释器用 Java 写，能跑在任何 Java 支持的平台上。用同样的路子，我们可以用 C 写一份新实现，把我们的语言编译、运行在几乎世上所有平台上。

这些都是实打实的好处。但另一方面，它**不省内存**。每一处语法都会变成一个 AST 节点。一个像 `1 + 2` 这样小小的 Lox 表达式，会变成一大串对象，对象之间还牵着好多指针，大概像这样：

<span name="header"></span>

<aside name="header">

那些「(header)」部分，是 Java 虚拟机用来支持内存管理、存放对象类型而附加的簿记信息。它们也占地方！

</aside>

<img src="image/chunks-of-bytecode/ast.png" alt="为表示“1 + 2”而创建的一棵 Java 对象树。" />

每一个这样的指针，都给对象添上 32 位或 64 位的额外开销。更糟的是，把数据以一个松散连接的网状对象撒在堆上，对<span name="locality">**空间局部性**</span>很不利。

<aside name="locality">

想深入了解的话，我在我的第一本书《游戏编程模式》（Game Programming Patterns）里，用[整整一章][gpp locality]讲了这同一个问题。

[gpp locality]: http://gameprogrammingpatterns.com/data-locality.html

</aside>

现代 CPU 处理数据的速度，远快于它从内存里取数据的速度。为了弥补这个落差，芯片设了多层缓存。如果它需要的一块内存已经在缓存里，载入就能快得多。我们说的是快上 100 **倍**还多。

数据是怎么进缓存的？机器会替你投机地往里塞。它的启发式规则相当简单：只要 CPU 从内存读一小块数据，就会顺手把相邻的整整一小捆字节一起拉进来，塞进缓存。

要是程序紧接着请求的某块数据，近得正好落在那个缓存行里，我们的 CPU 就跑得像工厂里一条上足了油的传送带。我们**真的**想把这好处吃干榨净。要有效利用缓存，代码在内存里的表示就该紧凑，并按照被读取的顺序排列。

现在再回头看看上面那棵树。那些子对象可能散落在<span name="anywhere">**任何地方**</span>。树遍历器每顺着一个引用走到一个子节点，都可能一脚踩到缓存的边界之外，逼得 CPU 停下来干等，直到能再从内存里吸溜进来一坨新数据。光是那些树节点带着的指针字段和对象头带来的**开销**，就往往把对象彼此推得越来越远，挤出缓存。

<aside name="anywhere">

就算这些对象在语法解析器刚生成时，碰巧被分配在连续的内存上，可经过几轮垃圾回收——回收会把对象在内存里搬来搬去——它们的下落就说不准了。

</aside>

我们的 AST 遍历器还有别的开销，比如接口分派和访问者模式相关的部分，但光是局部性这一个问题，就足以说明该换一种更好的代码表示。

### 为什么不直接编译成原生代码？

要**真的**快，你就得把这些层的间接统统拿开。一路到底层。机器码。光**念出来**就快。**机器码。**

运行最快的那些语言，都是直接编译到芯片支持的原生指令集。早在工程师们真的用<span name="hand">手写</span>机器码来写程序的年代，以原生代码为目标就已经是效率最高的做法了。

<aside name="hand">

是的，他们真的用手写机器码。写在打孔卡上。而那些孔，据推测，是他们**用拳头**打出来的。

</aside>

要是你从没写过机器码，或者它稍微像人话一点的近亲——汇编代码，那我就给你来一段最温柔的入门。原生代码是一连串密集的运算，直接用二进制编码。每条指令一到几个字节长，低层到近乎让人脑子发木。「把这个地址上的值移进这个寄存器。」「把这两个寄存器里的整数加起来。」诸如此类。

CPU 一条条地啃过去，按顺序解码并执行每一条。它没有像我们 AST 那样的树结构，控制流靠的是从代码里一个点直接跳到另一个点。没有间接，没有开销，没有多余的东跳西跳、追着指针跑。

快如闪电，但这份性能是有代价的。首先，编译成原生代码并不容易。今天广泛使用的芯片，大多有着庞杂的拜占庭式架构，指令堆积如山，是几十年一层层攒起来的。它们需要复杂的寄存器分配、流水线和指令调度。

而且，你当然也把<span name="back">可移植性</span>扔掉了。花几年时间精通某种架构，到头来也只够你登上市面上几种流行指令集里的**一种**。想让你的语言跑遍所有指令集，你得把它们全学会，再为每一种各写一个后端。

<aside name="back">

情况还没到那么不堪。一个架构良好的编译器，能让你把前端以及中间层大部分的优化遍，在你支持的各种架构之间共享。每次需要重写的，主要是代码生成，以及指令选择周边的一些细节。

[LLVM][] 项目能让你白捡到其中一部分。只要你的编译器输出 LLVM 自己那套特殊的中间语言，LLVM 就能反过来把它编译成原生代码，覆盖一大堆架构。

[llvm]: https://llvm.org/

</aside>

### 什么是字节码？

把这两点记牢。一端是树遍历解释器：简单、可移植，但慢。另一端是原生代码：复杂、平台相关，但快。字节码夹在中间。它保住了树遍历器的可移植性——这本书里我们不用脏手去碰汇编代码。它牺牲**一部分**简单性，换来性能提升，不过没到完全原生的那种快。

结构上，字节码类似机器码。它是一串密集、线性的二进制指令，这让开销保持很低，也和缓存相处融洽。不过，它比现实中的任何芯片都简单得多、高级得多。（在很多字节码格式里，每条指令只有一个字节长，「字节码」这名字就是这么来的。）

想象你正在为某门源语言写一个原生编译器，可以完全自由地定义一套最容易作为目标的架构。字节码大概就是这么个东西。它是一套理想化的幻想指令集，让你当编译器作者的日子好过些。

幻想架构的问题当然是它并不存在。我们的解决办法是写一个**模拟器**——用软件模拟出来的一块芯片，一次一条指令地解释字节码。你也可以叫它**虚拟机（VM）**。

这层模拟会带来<span name="p-code">开销</span>，这也是字节码慢于原生代码的一个关键原因。但作为回报，它给了我们可移植性。只要用 C 这类早就被我们关心的一切机器支持的语言来写虚拟机，我们就能在任意硬件上运行自己的模拟器。

<aside name="p-code">

最早的字节码格式之一 [p-code][]，是为尼克劳斯·维尔特的 Pascal 语言开发的。你也许会觉得，一台主频 15MHz 的 PDP-11 根本负担不起模拟一台虚拟机的开销。可那时候，计算机正处在自己的寒武纪大爆发，新架构天天冒出来。跟上最新芯片的脚步，比从每一块芯片里榨出极限性能更值。所以 p-code 里的「p」不是「Pascal」，而是「portable」（可移植）。

[p-code]: https://en.wikipedia.org/wiki/P-code_machine

</aside>

这就是我们给新解释器 clox 选的路。我们会踏着 Python、Ruby、Lua、OCaml、Erlang 等语言主流实现的脚印走。很多方面，我们虚拟机的设计会跟前一版解释器的结构平行对应：

<img src="image/chunks-of-bytecode/phases.png" alt="两套实现的各个阶段。jlox 是语法解析器→语法树→解释器。clox 是编译器→字节码→虚拟机。" />

当然，我们不会严格按顺序实现这些阶段。跟前一版解释器一样，我们会来回横跳，一个语言特性一个语言特性地把实现攒起来。这一章里，我们把程序的骨架搭好，并创建出存储、表示一个字节码块所需要的数据结构。

<aside name="amortized">

要理解这是怎么回事，我们需要[**摊还分析**](https://en.wikipedia.org/wiki/Amortized_analysis)。它告诉我们：只要按当前大小的某个倍数来扩容，那么把一**连串**追加的总成本摊开平均之后，每次追加就是 **O(1)**。

</aside>

^code memory-c

当 `newSize` 为零时，我们调用 `free()`，自己处理释放这一种情况。否则，我们依赖 C 标准库的 `realloc()` 函数。这个函数很省事，我们这套策略里另外三种情况它都能应付。当 `oldSize` 为零时，`realloc()` 等价于调用 `malloc()`。

有意思的是 `oldSize` 和 `newSize` 都非零的那些情况。它们让 `realloc()` 去改变先前分配那块内存的大小。如果新尺寸小于已有内存块，它只是<span name="shrink">更新</span>内存块的大小，并返回你给它的同一个指针。如果新尺寸更大，它就尝试扩展已有的内存块。

前提是紧挨着这块内存之后的地方没被占用。要是没地方扩展，`realloc()` 就会改为分配一块所需大小的**新**内存，把旧字节复制过去，释放旧块，然后返回指向新块的指针。记住，这正是我们动态数组想要的行为。

计算机终究是一团有限的物质，不是什么计算机科学理论想让我们相信的那种完美的数学抽象。所以内存不够时，分配会失败，`realloc()` 会返回 `NULL`。我们得处理这种情况。

为了解决这个，我们要造一个**反汇编器**。**汇编器**是一种老派程序，它拿到的文件里写着 CPU 指令的人类可读助记名，比如「ADD」「MULT」，然后把它们翻译成等价的二进制机器码。**反**汇编器则朝相反方向走——给一坨机器码，它吐出一份指令的文本清单。

## 常量

既然基础的块结构能跑了，我们开始让它更有用些。我们能在块里存**代码**，那**数据**呢？解释器处理的很多值，都是运行时由运算结果生成的。

```lox
1 + 2;
```

这里的代码里，3 这个值哪儿都没出现。但字面量 `1` 和 `2` 出现了。要把这条语句编译成字节码，我们需要某种含义为「产出一个常量」的指令，而那些字面量值也得存在块里的某处。在 jlox 里，Expr.Literal 这个 AST 节点持有该值。现在没有了语法树，我们得换一种解法。

### 表示值

这一章我们不会**运行**任何代码，但常量一只脚踩在解释器的静态世界里，一只脚踩在动态世界里，逼得我们多少得开始想想：虚拟机该怎么表示值。

眼下，我们从最简处起步——只支持双精度浮点数。这显然会随时间扩充，所以我们建一个新模块，给自己留出成长空间。

^code value-h

回到常量存在块里哪个位置的问题。对于整数这类小的定长值，很多指令集把值直接存在代码流里、紧跟在操作码后面。这些叫**立即指令**（immediate instruction），因为值的那些比特就紧贴在操作码后面。

对字符串这类大的、大小可变的常量，这招行不通。在编译到机器码的原生编译器里，那些更大的常量会存到可执行文件里一块单独的「常量数据」区。然后，加载常量的指令带有一个地址或偏移，指向值存在该区里的位置。

大多数虚拟机也做类似的事。例如，Java 虚拟机[给每个编译后的类关联一个**常量池**][jvm const]。这做法对 clox 来说够用了。每个块都会随身带一份列表，装着程序里作为字面量出现的值。为了<span name="immediate">更简单些</span>，我们**所有**常量都往里放，连简单的整数也不例外。

[jvm const]: https://docs.oracle.com/javase/specs/jvms/se7/html/jvms-4.html#jvms-4.4

## 行号信息

块几乎包含了运行时需要从用户源代码里拿到的一切信息。想想看，我们在 jlox 里创建的所有那些各不相同的 AST 类，居然能被压缩成一个字节数组加一个常量数组，有点疯狂。还差一样数据。我们需要它，尽管用户巴不得永远别见到它。

发生运行时错误时，我们会把出错的源代码行号显示给用户。在 jlox 里，这些行号存在词法单元里，而词法单元又存在 AST 节点里。既然我们抛弃语法树、改用字节码，就得给 clox 换一种解法。给定任意一条字节码指令，我们得能确定它是从用户源程序的哪一行编译来的。

我们可以用很多巧妙的方式来编码这个信息。我采用了能想出来的绝对<span name="side">最简单</span>的办法，尽管它在内存上低效得令人难堪。在块里，我们存一个与字节码平行的独立整数数组。数组里每个数字，就是字节码里对应字节的行号。发生运行时错误时，我们按当前指令在代码数组里的偏移，去同一个下标处查行号。

<aside name="side">

这个蠢笨的编码至少做对了一件事：它把行号信息放在一个**单独**的数组里，而不是把它交织进字节码本身。既然行号信息只在发生运行时错误时才用，我们就不希望它夹在指令之间，占着 CPU 缓存里宝贵的空间，害得解释器掠过它去够自己关心的操作码和操作数时多出几次缓存未命中。

</aside>

字节码指令往往相当细粒度。一行源代码常常会编译成一整串指令。为了让这一点在视觉上更清楚，凡是从与上一条相同源代码行来的指令，我们都显示一个 `|`。我们手写的那个块，输出就成了这样：

```text
== test chunk ==
0000  123 OP_CONSTANT         0 '1.2'
0002    | OP_RETURN
```

我们有了一个三字节的块。前两个字节是一条常量指令，从块的常量池里加载 1.2。第一个字节是 `OP_CONSTANT` 操作码，第二个是常量池里的索引。第三个字节（偏移 2 处）是一条单字节的返回指令。

在接下来的章节里，我们会用多得多的指令种类把它填满。但基本结构已经在这儿了，我们现在已经完全可以在虚拟机里，于运行时表示一段可执行的代码。还记得我们在 jlox 里定义的那一大家子 AST 类吗？在 clox 里，我们把它压缩成了三个数组：代码字节、常量值，以及用于调试的行号信息。

这种压缩，是我们的新解释器会比 jlox 快的一个关键原因。你可以把字节码看成对 AST 的一种紧凑序列化，它针对解释器执行时按所需顺序反序列化它的方式做了高度优化。在[下一章][vm]里，我们会看到虚拟机正是这么做的。

## 习题

1.  我们对行号信息的编码，在内存上浪费得可笑。考虑到一连串指令常常对应同一个源代码行，一个自然的解法就是对行号做某种类似[游程编码][rle]的处理。

    设计一种编码，把同一行上的一串指令的行号信息压缩起来。改写 `writeChunk()` 让它写出这种压缩形式，并实现一个 `getLine()` 函数：给定一条指令的索引，确定该指令所在的行。

    **提示：`getLine()` 不必特别高效。它只在发生运行时错误时才被调用，离那个讲究性能的关键路径远着呢。**

2.  由于 `OP_CONSTANT` 的操作数只用一个字节，一个块最多只能容纳 256 个不同的常量。这数目小得让写真实代码的人会撞上这个上限。我们可以用两三个字节来存操作数，但那会让**每一条**常量指令都占更多空间。大多数块并不需要那么多不同的常量，所以为了照顾罕见情况而浪费空间、牺牲一部分局部性，不划算。

    为了平衡这两个相互竞争的目标，很多指令集都提供多条指令，执行相同的操作，但操作数大小不同。把我们现有的一字节 `OP_CONSTANT` 指令原样留着，再定义第二条 `OP_CONSTANT_LONG` 指令。它把操作数存成 24 位数，应该绰绰有余。

    实现这个函数：

    ```c
    void writeConstant(Chunk* chunk, Value value, int line) {
      // 在这里实现……
    }
    ```

    它把 `value` 加进 `chunk` 的常量数组，然后写出一条合适的指令来加载该常量。还要给反汇编器加上对 `OP_CONSTANT_LONG` 指令的支持。

    定义两条指令似乎两边的好处都占全了。那它又逼我们付出了什么代价（如果有的话）？

3.  我们的 `reallocate()` 函数，把动态内存的分配和释放都托付给了 C 标准库。`malloc()` 和 `free()` 又不是魔法。找出它们几个开源实现，讲讲它们是怎么工作的。它们怎么追踪哪些字节已分配、哪些空闲？分配一块内存需要做什么？释放呢？它们如何做到高效？面对碎片，它们又怎么办？

    **硬核模式：** 不调用 `realloc()`、`malloc()` 或 `free()`，实现 `reallocate()`。你被允许在解释器执行开始时调用**一次** `malloc()`，分配一整块内存，让你的 `reallocate()` 函数能访问它。它就从那一整块区域——你自己私人的堆——里切出一坨坨内存。它具体怎么切，由你来定义。

</div>

## 设计说明：测试你的语言

这本书快走到一半了，有一件事我们还没聊过：**测试**你的语言实现。这不是因为测试不重要。语言有一整套好的、全面的测试套件有多关键，我怎么强调都不为过。

在动笔写这本书的第一个字之前，我就写了一套 [Lox 的测试套件][tests]（欢迎你在自己的 Lox 实现上使用）。那些测试在我的实现里找出了数不清的 bug。

[tests]: https://github.com/munificent/craftinginterpreters/tree/master/test

测试在所有软件里都重要，但对一门编程语言来说更是如此，至少有几个原因：

*   **用户指望他们的编程语言坚如磐石。** 我们对成熟稳定的编译器和解释器太习以为常了，以至于「是你代码的问题，不是编译器的问题」已经[深深嵌进了软件文化][fault]。要是你的语言实现有 bug，用户得走完悲痛的整整五个阶段，才能搞明白出了什么事，而你并不想让他们遭这份罪。

*   **语言实现是一块深度互连的软件。** 有些代码库又宽又浅。要是你的文本编辑器里加载文件的代码坏了，它——但愿如此！——不会导致屏幕上文字渲染出问题。语言实现则更窄更深，尤其是处理语言实际语义的那部分解释器核心。这让各种系统部件之间古怪的相互作用很容易悄悄引入细微的 bug。要把它们揪出来，就得靠好的测试。

*   **语言实现的输入，天生就是组合爆炸式的。** 用户可能写出的程序有无穷多种，而你的实现得把它们全都正确地跑起来。你显然没法穷尽测试，但你得下功夫，尽可能覆盖更多的输入空间。

*   **语言实现往往复杂、不断变动，还塞满了优化。** 这就带来棘手难缠的代码，到处是能让 bug 藏身的阴暗角落。

[fault]: https://blog.codinghorror.com/the-first-rule-of-programming-its-always-your-fault/

所有这一切都意味着，你会想要大量的测试。可是要**什么**测试呢？我见过的项目大多把重点放在端到端的「语言测试」上。每个测试都是用该语言写的一个程序，加上它预期产出的输出或错误。然后你有一个测试运行器，把测试程序推过你的语言实现，验证它的行为是否如预期。用语言本身来写测试，有几个不错的好处：

*   测试不跟实现的任何特定 API 或内部架构决策绑定。这让你可以自由地重组或重写解释器、编译器的部分内容，而不必更新一大堆测试。

*   同一套测试可以用于这门语言的多种实现。

*   测试常常可以写得简短，又容易读、容易维护，因为它们不过是用你的语言写的脚本。

不过也不全是美好：

*   端到端测试能帮你确定**有没有** bug，但不能确定 bug **在哪儿**。要找出实现里出错的那段代码可能更难，因为测试只告诉你正确的输出没出现。

*   要编出一个能触到实现某个晦涩角落的有效程序，可能是件苦差事。对高度优化的编译器尤其如此，你可能得写出绕来绕去的代码，才能确保自己恰好走上那条可能藏着 bug 的优化路径。

*   启动解释器、语法解析、编译并运行每个测试脚本，开销可能很高。面对一大套测试——记着，你**确实**想要一大套——那可能意味着大把时间都耗在等测试跑完上。

我还能继续讲下去，但我不想让这段变成一场说教。而且，关于**怎么**测试语言，我并不装作自己是专家。我只想让你把一件事内化进心里：**去**测试你的语言，有多么重要。说真的。测试你的语言。你会感谢我的。

</div>
