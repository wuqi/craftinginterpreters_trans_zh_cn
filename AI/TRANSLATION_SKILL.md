# 翻译 Skill — Crafting Interpreters 中译

> 译任何一章之前，先读这个文件。译完，用第 9 节的自检清单过一遍再交付。
> 术语一律以本文件第 4 节和 `book-zh/translations/glossary.zh.json` 为准，不得临时决定。

## 1. 适用范围与红线

译的是 Bob Nystrom 的 **Crafting Interpreters**，一本**口语化的第一人称技术书**，
不是学术论文。语气规则与学术翻译**相反**：学术翻译要求删「我们」、用书面语；
本书的「我们」是作者亲和力的来源，必须保留。

### 绝对不能改（动了就坏）

| 内容 | 格式 | 原因 |
|---|---|---|
| 代码片段标记 | `^code 标签 (2 before, 1 after)` | 改了就提取不到代码，且不报错 |
| 旁注锚链 | `<aside name="x">` / `<span name="x">` 的 `name` 值 | 改名就断链 |
| 章节文件名 | `book/*.md` 的英文文件名 | 文件名由 `book.dart` 从标题推导 |
| 源码工具标记 | `//>` `//<` `// [tag]` | 会变成旁注锚点，转成 span |
| 链接引用 | `[optimization]: optimization.html` | URL 与锚点不可译 |
| 结构标签 | `##` `###` `<div class="challenges">` | 数量必须与原文一致 |

### 工具链的三个坑（实测踩过的）

**① 中文链接文本不能用空引用 `[]`**

工具的 markdown 解析器在「中文 + 空引用」组合下会静默失效，链接原样输出成
`[Chomsky 层级][]`，不报错。

```
[Chomsky 层级][]          ✗ 失效
[Chomsky 层级][chomsky hierarchy]   ✓ 正常
[编译原理][dragon]       ✓ 正常（具名引用不受影响）
```

**规则：凡是链接文本含中文，一律写成具名引用 `[文本][key]`。**

**② 侧栏（`<aside>`）里的链接定义必须跟着侧栏一起留**

链接定义 `[key]: url` 要和引用它的文字在同一个 `<aside>` 块内，不能挪到正文。
挪了会丢。

**③ `<span name="...">` 锚点逐个比对，不能只数总数**

第 18 章我曾「span 数 15 = 15」判定通过，实际丢了 3 个锚点。
必须做 `name` 值的集合比对：`Compare-Object`。

### 判断规则

> **机器执行的（代码、工具标记、文件名、URL）→ 原样保留。给人读的（正文、旁注、
> 图注 alt、界面文案）→ 翻译。**
> 证据/数据类内容不译（程序输出、报错信息），叙述类内容要译。

代码注释**要译**（`c/`、`java/` 源码里的，以及 md 内手写块里的），但**程序输出不译**：

```
print !true; // "false"
                 ^^^^^^^ 这是输出，不是注释，保留
print -false; // 呃……
                 ^^^^^^ 这是注释，翻译
```

## 2. 机器校验（翻译前先跑基线）

改动前确认基线，改动后必须一致：

```powershell
cd G:\Develope\Translate\book-zh
dart tool/bin/build.dart
```

| 指标 | 必须 |
|---|---|
| `lines of code` | **恒为 5336**（原版基准） |
| `No snippet for $tag` | **0 条**，有输出说明 `^code` 断了 |
| aside / span / 代码块 / 图 | 与原文一一对应，逐章比对 |

结构比对（把译文和原文的结构标记数出来对照）：

```powershell
$f = "book\types-of-values.md"
$o = "G:\Develope\Translate\craftinginterpreters\book\types-of-values.md"
foreach ($pat in '<aside name=','<span name=','^##','^###','<img ') {
  $a = (Select-String -Path $o -Pattern $pat).Count
  $b = (Select-String -Path $f -Pattern $pat).Count
  "{0,-14} 原版 {1,3}  译文 {2,3}  {3}" -f $pat, $a, $b, $(if($a -eq $b){"OK"}else{"✗ 不一致"})
}
```

**锚点要逐个比对 name 值，不能只数总数**（总数相同也可能丢人）：

```powershell
function Names($p){ $t=[IO.File]::ReadAllText($p); [regex]::Matches($t,'name="([a-z\-]+)"') | ForEach-Object { $_.Groups[1].Value } }
$cmp = Compare-Object (Names $o) (Names $f)
if ($cmp) { $cmp | ForEach-Object { "$($_.SideIndicator) $($_.InputObject)" } } else { "name 值完全一致" }
```

**必须校验渲染后的 HTML 链接**——md 里看着对，渲染出来可能失效：

```powershell
cd G:\Develope\Translate\book-zh
dart tool/bin/build.dart | Out-Null
$h = Get-Content site\<chapter>.html -Raw
# 原版 HTML 里有的 href，译文必须有
foreach ($k in 'Chomsky_hierarchy','Finite-state_machine') {
  "{0,-22} {1}" -f $k, $(if ([regex]::Matches($h,$k).Count -gt 0) {"OK"} else {"✗ 链接丢失"})
}
# 残留未解析的引用语法（md 链接失效时方括号会原样出现）
[regex]::Matches($h,'<p>[^<]*\[[^\]]+\]\[\][^<]*') | ForEach-Object { $_.Value }
```

## 3. 译前分析（动手之前，别跳）

直接上手翻是本项目最容易翻车的地方。`unityped` 就是没预判到会卡住的地方——
译到才现编词，译完才发现读者看不懂、或者梗没了。

**每章开译前，先把原文通读一遍，只出分析、不动译文。** 产出四块：

### 3.1 内容与作者

- 这一章讲什么、核心论点是什么
- 作者在这个位置想干什么（为什么现在讲这个）
- 有没有承接上一章、埋下下一章的钩子（这些在译文里要看得见）

### 3.2 术语预判

- 通读一遍，把出现的技术术语、专有名词、缩写**先列出来**
- 逐个对照 `glossary.zh.json`，有冲突的**现在就定**，当场写进术语表
- 术语表里没有的，在这里定标准译法

### 3.3 语域判断

- 这一章偏叙述还是偏动手？Bob 是在讲故事还是在逐步指导？
- 幽默/比喻/自嘲集中在哪几段（标出行号，后面第 9 节重点查）

### 3.4 翻译难点清单（最重要）

通读时标记三类会卡住的地方，逐条写清处理方式：

| 类别 | 什么算 | 处理方式 |
|---|---|---|
| **Comprehension gaps**<br>理解落差 | 中文读者可能不懂的术语、指代、技术前提 | 加一句解释，或依赖 4.4 的受众定位决定不注 |
| **Figurative language**<br>比喻习语 | 画个括号就翻不了的东西 | 三选一：**interpret** 意译 / **substitute** 替换成中文读者熟悉的说法 / **retain** 保留原文并标注 |
| **Structural challenges**<br>结构难点 | 长难句、文字游戏、双关、需要重新编排才通顺的段落 | 标出来，写下打算怎么处理 |

**清单要落到文件**，例如 `book-zh/translations/analysis/types-of-values.md`，
否则重开会话就丢了。

> 判据：这份清单列出的条目，如果在译文里一个都没体现出「这里我做了取舍」，
> 说明译前没认真分析。

## 4. 术语表

### 4.1 规则

- **首次出现**：`中文（English）`，之后只用中文
- 术语表里没有的常见术语，首次出现同样标英文
- 缩略语首现：`中文（Full Name, ABBR）`，之后用缩写
- 全书统一，不许同义词替换
- 类名、C 类型名（`Value`、`Obj`、`double`、`uint16_t`）**不用**代码字体，
  保持正常字体（Bob 的 style guide 明确要求）

### 4.1.1 人名一律音译

**读者能查到的人名，一律音译。** 照搬英文是最刺眼的偷懒——中文学术界从维基百科到
教科书都音译，没有「Chomsky 层级」这种写法。

| 英文 | 正确 | 错误 |
|---|---|---|
| Chomsky hierarchy | **乔姆斯基层级** | ✗ Chomsky 层级 |
| Eric Schmidt | **埃里克·施密特** | ✗ Eric Schmidt |
| Mike Lesk | **迈克·莱斯克** | ✗ Mike Lesk |

译前判断三问：**读者会不会去查这个人？** 会查就音译。

例外（保留英文）：
- 代码/项目/语言本身的专名：`Lex`、`Flex`、`Lox`、`clox`
- 私人称呼：作者的家人朋友（`Megan`、`Ginny`、`Kari Somerton`）
- GitHub 用户名、代码标识符

### 4.2 高危冲突项（必须照表）

`parse` 与 `resolve` 都可译「解析」，必须拆开：

| 英文 | 中文 | 说明 |
|---|---|---|
| scanning | 扫描 | |
| parsing / parse | **语法解析** / 语法解析器 | 带「语法」二字以示区别 |
| resolving / resolver | **作用域解析** / 作用域解析器 | ch11 |
| binding | 绑定 | |

其他高频：

| 英文 | 中文 | 备注 |
|---|---|---|
| tagged union | 带标签联合体(tagged union) | |
| struct | 结构体 | |
| union | 联合体 | |
| padding | 填充 | |
| lexeme | 词素 | |
| operand | 操作数 | |
| falsey / falsiness | 假值 | |
| upvalue | 上值 | ch25 核心 |
| chunk | 字节码块 | |
| tree-walk | 树遍历 | 不用「树行走」 |
| runtime error | 运行时错误 | |
| disassembler | 反汇编器 | |
| unityped | 单一类型 | 已定 |

新增术语写进 `book-zh/translations/glossary.zh.json`。

### 4.3 治术语漂移：全书上下文

逐章翻译必然漂移——第 5 章定的译法，到第 25 章就忘了。靠记性不行。

吴恩达的做法是 `<TRANSLATE_THIS>`：**把整篇原文都给出，但只翻译标签内的部分，
其余作上下文**。翻译到本项目的对应做法：

译第 N 章时，工作上下文必须包含三样：

1. **术语表**（`glossary.zh.json`）—— 权威译法
2. **已译章节的术语用法** —— 尤其高频词（chunk、closure、upvalue、stack frame）
   在前几章实际是怎么译的。以实际用法为准，不是以术语表为准；
   若发现二者冲突，以先例为准并回头修正术语表
3. **本章原文**，且只译本章

新术语一旦确定，立即写进术语表，**当场写，不要等译完**。

### 4.4 语域定位

吴恩达的设计里有 `country` 参数，用来说明目标语言是哪个地区的口语。
本项目的固定答案是：**简体中文 + 口语化的技术书 + 第一人称**。

不是学术论文，不是大陆官方的技术文档腔。

## 5. 人称：英文最大的翻译难点

Bob 的 style guide 规定：

1. **假想执行代码的过程** → 用 `we`
2. **描述代码必须怎么改、读者必须机械做什么** → 用 `we`，**不用 `you`**
3. **描述代码一般怎么工作，或读起来更顺** → 用 `it`

> 英文靠 `we` / `it` 这组对立，区分「人做的事」和「代码做的事」。
> **中文没有这组对立。** 中文里「它」指代代码极不自然。
> 这是本书翻译最容易翻车的地方，必须按下表固定映射：

| 原文 | 中文 | 例 |
|---|---|---|
| `we` + 人做的动作 | **省略主语**，动宾开头；需要强调时用「我们」 | `We'll define a parser function.` → 「我们来实现一个解析函数。」/「来实现一个解析函数。」 |
| `we` + 读者要动手 | **「你」或无主语** + 祈使/陈述 | `Replace this line.` → 「把这一行换掉。」 |
| `it` = 代码 | **无主语**，或以代码/模块名作主语 | `The VM pops two values.` → 「虚拟机弹出两个值。」/「它弹出两个值。」**不用「它」** |
| `you`（仅第2类） | 「你」 | `you'll see` → 「你会看到」 |

**硬规则**：中文里不得出现以「它」开头指代代码的句子。代码是施动者时，
把代码名提到主语位置，或直接省略主语。

## 6. 文风

### 6.1 单一判据

> **这句读起来，像不像本来就是中文写的？**

这一条比任何清单都本质。下面的条目都服务于它。

### 6.2 CJK 专项检查项（逐项过）

英语和中文的语序、惯用法不同，这些地方最容易露出「翻译腔」：

- **多余连接词** —— 「因此」「然而」「此外」「从而」，上下文不需要就删
- **被动滥用** —— 英文爱被动，中文滥用「被／由／受到」很别扭
- **名词堆砌** —— 「虚拟机指令执行过程的中间结果表示形式」，中文要拆成短句
- **过度名词化** —— `the implementation of X` 这种英文名词化，中文用动词：「X 是怎么实现的」
- **长定语** —— 英文能套三层从句，中文要拆开或后置
- **仿译** —— 把英文词序和搭配直接搬过来，中文没人这么说
- **情感内涵被抹平** —— 原文的调侃、夸张、自嘲，被译成了中性陈述

### 6.3 本书的硬要求

- **口语化，第一人称，句式短。** 这是技术书不是论文
- 保留原文的**调侃、夸张、自嘲**。第18章的「心平气和地把你的手指锯下来」、
  「往弹射座椅的拉杆上拉一把」这类，删掉就毁了
- 保留**比喻**（chunk 是「块」、heaven/human 的升天降地意象）
- **原文什么风格就什么风格，不要把口语改成书面。**「用 C 干活」就该保留「干活」，
  改成「用 C 写代码」是错的
- `So sad.` → 「可悲。」——短促的吐槽要短促
- 段落保持口语节奏，不要合并成书面长句
- 破折号 `——` 表停顿/转折，中文全角；原文的 ` -- ` 译为 `——`
- 省略号用 `……`（六个点），不用 `...`
- 书名用《》，不用斜体（用户已定：中文不用斜体）

## 7. 强调标记

原文 `*em*` 和 `**strong**` **一律译作 `**粗体**`**，全书不得出现斜体。

原因：中文字体没有真斜体，浏览器会合成伪斜体，汉字笔画粘连糊成一片。
`shared.scss` 已加 `font-synthesis: none` 兜底，但语义上仍应统一。

- 原文 `*spare*` → `**简陋**`。粗体必须覆盖**完整**成分
- **反例**：`*spare*` → `**简**`（漏字，一个英文形容词不能只译一个字）
- 中文里 `**不**`、`**就是**`、`**别**` 是正常的强调，不必改写
- 术语首次定义 → 加粗（Bob 的 style guide 要求，且不用加引号）

## 8. 标点与代码排版

Bob 的 style guide 有明确规则，照做：

### 代码片段前的句子结尾

| 场景 | 用 `：` 还是 `。` |
|---|---|
| Java / C 代码片段前 | 末句不是完整句子、或直接指代后续代码 → `：`；独立成句也通顺 → `。` |
| 插图、Lox 示例、语法片段前 | 即使句子完整，若指向后续内容也可用 `：` |

原文是 `:` 就 `：`，是 `.` 就 `。`，**不要一律改成 `：`**（Bob 特意说明不是为了
「到处用冒号」而这么定）。

### 代码字体

- 布尔值：`true` / `false` 用代码字体；泛指真假用正常文本
- opcode：`OP_RETURN` 用代码字体
- `nil` / `null` / `NULL` 用代码字体
- 指向语句：`if` 语句、`return` 语句；指向概念：then 分支、else 分支
- 文件名加引号：`Expr.java`；C 模块名加引号：「debug」模块

### 数字

原文散文里的数字**拼成词**（one、eleven），中文沿用（一个、十一）；
指二进制位时永远是 0 或 1。

## 9. 交付流程（reflection workflow）

**核心：反思与修改必须分离。**

自己边看边改会漏——改了一处就想一处，注意力被带走，剩下的段落就走马观花。
必须先**只出建议清单**，确认无遗漏，再**统一改**。
（真实教训：`*spare*` → `**简**` 这个漏字，就是边看边改时漏掉的。）

### 中间产物：一律落文件，不要直接改 md

每一步的产物存到 `book-zh/translations/wip/`，下一步读上一步的文件往下走：

| 文件 | 内容 |
|---|---|
| `analysis/{chapter}.md` | 第 3 节的译前分析 |
| `{chapter}-draft.md` | 初译 |
| `{chapter}-critique.md` | 反思建议清单（只诊断） |
| `{chapter}-revision.md` | 按建议改完的版本 |
| `book/{chapter}.md` | 终稿（才写进正式位置） |

理由：改错了能回退到上一个阶段；用户能逐步过目，不用一次看最终结果；
跨章复查时有据可依。**跳过中间产物直接改 md，改坏了就只能靠 git 恢复。**

### 第一步：结构校验（机器，见第 2 节）

结构错了先修结构，人工看不出来。

### 第二步：反思（只出建议，禁止动手）

逐段读译文，**只写建议，一个字都不许改**。四个维度：

**(i) 准确性** —— 增译、误译、**漏字或漏成分**、该译未译

> 漏字是本项目最高频的错误。英文的形容词、副词、否定词、量词，中文必须有对应成分。
> 反例：`*spare*` → `**简**`（一个完整形容词被压成一个字，且「相当……简」根本不通顺）

同时查：数字、专有名词、代词有无丢失。

**(ii) 流畅度** —— 中文语法、标点、无冗余重复、**无机翻痕迹**

拿不准的地方念一遍。中文没人这么说的，字面对也要改。

**(iii) 风格** —— 还是不是**口语化的第一人称技术书**

- 原文的调侃、比喻、夸张、自嘲有没有被稀释
  （「心平气和地把你的手指锯下来」「往弹射座椅拉杆上拉一把」「可悲。」）
- 有没有被写成学术书面语（这是最容易犯的走偏）

**(iv) 术语** —— 与术语表是否一致；本书的结构约束有没有被破坏

- 同一个词在不同段落用了不同译法
- 首次出现有没有标英文

### 第三步：修改

按建议清单逐条改。改完**回到第一步重新校验**，再跑一次第二步，直到建议清单为空。

### 第四步：人称专项复查

单独再扫一遍第 5 节的规则。人称错误用四维度是查不出来的：

- 有没有以「它」指代代码的句子
- 读者要动手的地方，有没有写成「它」而不是省略主语或用「你」

### 第五步：通读润色（Polish）

改完建议清单**不等于完**。最后把整章当**独立成篇**从头读一遍，只做两件事：

1. **顺接缝** —— 段落之间、句子之间读着卡的地方，不是译错，是没顺过来。
   逐句对照原文改会毁掉行文节奏，通读才看得出来
2. **验第 6.1 节判据** —— 「这句像不像本来就是中文写的？」

结构此时不动、术语此时不改（那些是前四步的事），**只顺文气**。

### 第六步：更新 `PROGRESS.md`（强制，不可跳）

**每完成一章（或任一交付物），当场更新 `PROGRESS.md`，再回报。** 不更新等于没交付。

- 「已译章节」表加一行：章节名、文件名、校验结果（结构数字、name 是否一致、构建行数）
- 从「未完成」里删掉本章
- 更新「下一步」为下一章
- 术语/人名/双关若新增，`glossary.zh.json` 与 PROGRESS 的「已定决策」一并同步

### 硬规则

发现问题**改完再报**。不要把明显错误留在交付物里等用户挑。

## 10. 引用与双关

### 引用（引文、名言、书籍）

**先查现成译本，再自己译。** 依次查：官方中译本 → 权威出版物的电子版 →
读者社群流传的片段。

查到就用，并照原样给出出处。若确认没有公认译本：
在对话里说明「查过了，没有」，然后给一个平实准确的直译，不要硬造。

### 双关

比喻习语的处理方式只有三种，译前分析（第 3.4 节）就要为每个想清楚属于哪一种：

| 方式 | 含义 | 何时用 |
|---|---|---|
| **interpret** | 意译，按意图而非字面 | 读者要的是意思，效果是次要的 |
| **substitute** | 替换成中文读者熟悉的说法/已有的中文说法 | 中文本来就有对应玩法（type punning → 类型双关） |
| **retain** | 保留英文原文并标注 | 该梗无法本土化，且理解它对读懂内容有帮助 |

另加一条：**保留不成文字效果的梗，允许造词**，但造完自己念一遍，
不通顺就退回 interpret 或 substitute。

优先级：

1. **有现成中文玩法的，直接 substitute**（如 type punning → 类型双关）
2. **中文能自然造词的，造**（念一遍，不通顺就退回 3）
3. **造不出就 interpret**，接受损失
4. **只有在读者会因此误解含义时才出译注**；不要为「没译出味道」而出注

反例（我犯过的错）：引文里 Think/Thing/Thingish 三词同源，中文硬凑成
「思**想**某些**事**…显得很「**事**」的东西」——不通顺，且丢了意思。
正确做法是查现成译本（结果是没有），改用 substitute：
「像回事 / 不是那么回事」，靠「回事」这个词在中文里自然重复形成呼应。

**梗清单**存 `glossary.zh.json` 的 `_puns` 字段，随译随记。现有条目：
`unityped`、type punning、garbage collector bug、shadow realm、
yank the ejection seat lever、saw your fingers off、spare。

## 11. 全书完成后的审核

单章的 reflection 流程会漏——刚写完的句子自己看着顺。

| 轮次 | 方法 | 能抓到什么 |
|---|---|---|
| 盲读 | **只给中文译文，不给英文源文**，专门找「读起来别扭/像机翻」的地方 | 自检时的盲区 |
| 对照审 | 给英文源文，逐句查 | 漏字、误译、人称错 |
| 一致性审 | 跨章横向比 | 术语漂移、同一个梗前后不一致 |

其中**盲读**是第 9 节四维度查不到的部分：四维度都要对照原文，
而「这句中文像不像人话」不看原文也能判断——而这恰恰是用户最早两次拒绝我的理由。

**校准方式**：先只在**第 18 章**（已人工校对）上跑，看能召回多少已知问题、误报多少。
召回够高、误报可控，再铺开到全书。

盲读与四维度的分工：
- 四维度（对照源文）查**漏**——漏字、误译、术语漂移
- 盲读（只看中文）查**腔**——机翻味、不通顺、风格走偏

两者不可互相替代。

5. 译 → 初稿存 `translations/wip/{chapter}-draft.md`
6. 跑第 9 节流程：结构校验 → 反思（只出建议）→ 修改 → 人称复查 → 通读润色

8. 新术语、新梗**当场**写回 `glossary.zh.json`
