# 技术书翻译与审校

## 这个 skill 解决什么

技术书翻译的失败通常不是“英文看不懂”，而是：

- 漏掉形容词、副词、否定词、限定词；
- 逻辑方向反了（before/after、above/below、主宾）；
- 术语前后不一致；
- 强调标记被多加、少加或落错位置；
- 代码、标题、列表、链接等结构被改坏；
- 中文读起来像英文句法的搬运；
- 审校时边看边改，注意力被刚改的句子带走，后面全漏。

这个 skill 用一条可重复的流水线把这些风险逐层挡住。核心不是“翻得漂亮”，而是**先不失真，再像中文**。

## 适用场景

- 整本书、整章、教程、技术长文的翻译。
- 已有译稿的审校、润色、术语统一、漏译排查。
- 翻译项目的质量流程设计。
- 技术文档、教材、课程讲义的本地化。

纯文学、营销文案可以借用审校方法，但“术语先行”和“结构校验”权重应降低。

## 两种模式

### 完整模式

用于整章、整书、长篇技术文档。走完下面的 0–9 步，中间产物落文件。

### 轻量模式

适用于同时满足以下全部条件的文本：单段或单节、无多章交叉引用、无构建/渲染工具链、无需术语表长期维护。任一条件不满足，走完整模式。

轻量模式可以省略中间产物和机器校验，但**不能跳过交付前五项自检**（漏字、方向、强调、结构、术语）。流程：

1. 快速扫一遍术语和难点；
2. 翻译；
3. 做交付前五项自检；
4. 交付。

## 核心原则

1. **翻译单位是信息块，不是单词。** 英文一个形容词，中文可能要用一个短语；英文一个从句，中文可能要拆成两句。逐词对齐会同时损失准确和通顺。
2. **准确 > 通顺 > 风格。** 漏译、反向、错位没解决之前，润色没有意义。
3. **读者只读译文。** 每句都用“这像不像本来就是中文写的”来验，而不是“这像不像英文原文”。
4. **格式即语义。** 标题层级、列表、空行、锚点、链接、代码字体都在传递信息；改坏格式和译错一样严重。
5. **术语先行。** 译到才现编词，必然漂移。先定表，再动笔；新术语当场写回。
6. **诊断与修改分离。** 边看边改会漏。先只列问题清单，确认无遗漏，再统一修改。
7. **人做的事和代码做的事，中文要分开表达。** 英文靠 we/it 分工，中文不能直译成“它”。

## 不能改的红线（动了就坏）

下面这些是**机器读的、工具依赖的**内容，翻译时必须原样保留。翻译时最容易犯的错不是译错，而是动了这些标记：

| 内容 | 为什么不能动 |
|---|---|
| 代码片段标记（如 `^code 标签 (2 before, 1 after)`） | 改了就提取不到代码，且不报错 |
| 锚点 `name` 值（如 `<aside name="x">`、`<span name="x">`） | 改名就断链 |
| 章节/文件的英文名 | 可能由工具从标题推导，改名会断 |
| 源码工具标记（如 `//>` `//<` `// [tag]`） | 会变成旁注锚点或 span，改了就错位 |
| 链接引用定义 `[key]: url` | URL 与锚点不可译，改了链接失效 |
| 结构标签数量（`##` `###` `<div class="...">` 等） | 数量必须与原文一致 |

**判据**：机器执行的（代码、工具标记、文件名、URL、锚点）→ 原样保留；给人读的（正文、旁注、图注 alt、界面文案）→ 翻译。

## 完整流水线

### 0. 开工准备

- 读原文、作者风格指南、项目术语表、人名表、双关/习语表。
- 确认构建或渲染方式，跑一次基线，记录必须保持不变的数字（代码行数、章节数、锚点数等）。
- 确认哪些内容不能译：代码、标识符、URL、文件名、程序输出、工具标记（见上节红线表）。
- **区分代码注释和程序输出**：引号内、`//` 后的自然语言是注释 → 译；程序运行产生的字符串、报错、输出 → 不译。拿不准时看上下文：这段文字是写给读者看的，还是程序运行时打印的。
- **通读原文，做第 1 步的译前分析，再动笔。** 直接上手翻是本类项目最常见的翻车点。

**产出**：基线记录（可写入项目进度文件）。

### 1. 译前分析（只分析，不动译文）

先通读原文，只出分析。至少写清四块：

- **内容与作者意图**：这章讲什么、承接什么、埋什么钩子。
- **术语预判**：列出术语、专名、缩写，与既有术语表冲突的当场定。
- **语域判断**：叙述还是指导？幽默、比喻、自嘲集中在哪些段（标位置，后面重点查）。
- **难点清单**：理解落差、比喻习语、长难句、双关、文化专名，逐条写处理方式。

难点清单建议分三类，每类写清策略：

| 类别 | 什么算 | 处理方式 |
|---|---|---|
| 理解落差 | 目标读者可能不懂的术语、指代、技术前提 | 加一句解释，或按受众定位决定不注 |
| 比喻习语 | 直译就丢效果的说法 | interpret / substitute / retain 三选一（见第 7 节） |
| 结构难点 | 长难句、文字游戏、双关、需重排才通顺的段落 | 标出来，写下打算怎么处理 |

**产出**：`analysis/{chapter}.md`。

**通过标准**：术语表里没有的词已经定译；每个难点都有处理策略，而不是“到时候再看”。**判据：这份清单若在译文里一条取舍都体现不出来，说明译前没认真分析。**

### 2. 初译

- 按信息块译，不逐词硬贴。
- 保留全部结构标记和引用（见「不能改的红线」）。
- 拿不准的地方先译出意思，用批注标出，不要空着。
- 代码不译；代码注释要译；程序输出不译。

**产出**：`{chapter}-draft.md`。

### 3. 结构校验（先机器，后人眼）

结构错误人眼很难发现，先用机器对数：

- 标题层级与数量；
- 列表数量、编号、嵌套；
- 图片、表格、代码块；
- 锚点 `name` 值做**集合比对**，不能只数总数（总数相同也可能丢人、换人）；
- 链接定义与引用，**并校验渲染后的 HTML 链接**（md 里看着对，渲染出来可能失效）；
- **侧栏/aside 内的链接定义必须跟着侧栏走**：`[key]: url` 要和引用它的文字在同一个 `<aside>` 块内，不能挪到正文，挪了会丢；
- 空行与分段。标题和列表之间、aside/div 边界处最容易丢空行。

机器校验的通用做法（平台无关）：

```
1. 统计原文与译文的：标题数、列表项数、代码块数、图片数、aside/span 数
2. 提取所有 name="..." 的取值，做集合差集，必须为空
3. 检查 aside 块内的链接定义是否仍在同一块内
4. 构建/渲染后，在输出 HTML 里检索原文出现的关键 href/anchor，缺失即报错
5. 检索渲染结果里残留的未解析引用语法（如方括号原样出现）
```

**通过标准**：所有结构标记与原文一一对应；name 值集合完全一致；渲染后链接无丢失。

### 4. Critique（只诊断，一个字都不改）

逐段读译文，只写建议。四个维度：

- **准确性**：增译、误译、漏字或漏成分、该译未译、数字/专名/代词丢失。
- **流畅度**：中文语法、标点、冗余、机翻痕迹。
- **风格**：还是不是原文的口语/正式程度？调侃、比喻、夸张有没有被稀释？
- **术语**：与术语表是否一致；首次出现有没有标英文；有没有同词异译。

每条建议写清：位置、原文、译文、问题、建议改法、原因。用严重度分级：

- **A**：改变意思、漏关键信息、逻辑反向。
- **B**：术语不一致、格式损坏、明显翻译腔。
- **C**：可改可不改的润色。

**产出**：`{chapter}-critique.md`。

**通过标准**：A、B 类问题全部列出；没有“这里感觉怪”这种无法执行的建议。

**理由**：自己边看边改会漏——改了一处就想一处，注意力被带走，剩下的段落走马观花。所以必须只出清单，确认无遗漏，再统一改。

### 5. 修订

- 按清单逐条改，不顺手扩展范围。
- 改完回到第 3 步重验结构。
- 再跑一次 critique，直到 A、B 类清单为空。

**产出**：`{chapter}-revision.md`。

### 6. 人称专项复查

四维检查抓不到人称问题，必须单列一遍。英文用 we / you / it 区分“人做的事”和“代码做的事”，**中文没有这组对立**，直译“它”极不自然。固定映射：

| 原文 | 中文 | 例 |
|---|---|---|
| we + 人做的动作 | 省略主语，动宾开头；需要强调时用“我们” | `We'll define a parser.` → 「来实现一个解析器。」 |
| we + 读者要动手 | “你”或无主语 + 祈使/陈述 | `Replace this line.` → 「把这一行换掉。」 |
| it = 代码/模块 | 无主语，或以代码/模块名作主语；**不用“它”** | `The VM pops two values.` → 「虚拟机弹出两个值。」 |
| you（指读者） | “你” | `you'll see` → 「你会看到」 |

**注意：不要因为“技术书要正式”就删掉“我们”。** 学术翻译习惯删第一人称、用书面语，但口语化技术书的第一人称正是作者亲和力的来源。原文用 `we` 且译文用「我们」读着自然，就保留；只有译文明显啰嗦时才省略主语。判断标准是原文语域，不是“技术书应该正式”的先验印象。

> 若项目作者风格指南对人称有额外细分，以项目指南为准；上表是默认映射。

复查项：

- 有没有用“它”指代代码、模块、抽象概念？
- 读者要动手的地方，是不是误写成了“它”而不是省略主语或用“你”？
- 原文的 we / you / it 分工有没有被抹平？
- 有没有把原文的「我们」无故删成书面语？

### 7. Polish 通读

把整章当一篇独立中文文章，从头读到尾，只做两件事：

1. **顺接缝**：段落之间、句子之间读着卡的地方。逐句对照原文改会毁掉行文节奏，通读才看得出来。
2. **验判据**：这句像不像本来就是中文写的？

此时不改结构、不改术语，只顺文气。改完建议清单不等于完——最后一遍通读是独立的。

### 8. 终验与交付

- 复跑构建/渲染，确认基线数字不变。
- 复验结构、name 集合、aside 内链接定义、渲染后的链接。
- 终稿写入正式位置。
- 新术语、人名、双关写回术语表。
- **有进度文件就必须更新，不更新视为未交付。** 每完成一章当场更新再回报：章节名、文件名、校验结果（结构数字、name 是否一致、构建行数）、新定的术语/人名/双关。
- 做交付前五项自检。
- **发现问题改完再报。** 交付物里不允许留有已知的 A、B 类问题等用户挑。

### 9. 全书完成后的审核（多章项目）

单章的 reflection 流程会漏——刚写完的句子自己看着顺。全书完成后补三轮：

| 轮次 | 方法 | 能抓到什么 |
|---|---|---|
| 盲读 | **只给中文译文，不给英文源文**，专找“读起来别扭/像机翻”的地方 | 自检时的盲区 |
| 对照审 | 给英文源文，逐句查 | 漏字、误译、人称错 |
| 一致性审 | 跨章横向比 | 术语漂移、同一个梗前后不一致 |

**盲读与四维度的分工**：四维度（对照源文）查**漏**——漏字、误译、术语漂移；盲读（只看中文）查**腔**——机翻味、不通顺、风格走偏。两者不可互相替代。

**校准方式**：先在已人工校对的一章上跑，看能召回多少已知问题、误报多少；召回够高、误报可控，再铺开。

## 中间产物

完整模式建议保留：

| 文件 | 内容 |
|---|---|
| `analysis/{chapter}.md` | 译前分析 |
| `{chapter}-draft.md` | 初译 |
| `{chapter}-critique.md` | 只诊断的建议清单 |
| `{chapter}-revision.md` | 按清单改完的版本 |
| 正式位置 | 终稿 |

好处是改错能回退、用户能逐步过目、跨章复查有据可依。如果项目没有这个约定，至少把 critique 清单留在对话或一个临时文件里。**跳过中间产物直接改正式文件，改坏了只能靠版本控制恢复。**

## 技巧库

### 1. 忠实：防漏、防反、防增

**逐项清点成分**：形容词、副词、否定词、量词、代词、数字、专名、逻辑连接词，一个都不能少。

高频漏译：

- `physically`、`actually`、`even`、`just`、`only`、`mostly`、`roughly`
- `on the other hand`、`in turn`、`at the same time`
- `if there ever was one`、`as far as I can tell`
- 修饰名词的第二个形容词、插入语里的限定

**漏字是最高频错误。** 英文的形容词、副词、否定词、量词，中文必须有对应成分。反例：`*spare*` 译成「**简**」——一个完整形容词被压成一个字，且「相当……简」根本不通顺。

**检查方向与逻辑**：谁对谁、先与后、上与下、主动与被动。

反例：`cannot call a function above the code that defines it` 译成“不能调用在它上方定义的函数”，方向正好相反。正确意思是“不能在函数定义之前调用它”。

**不要升级或降级语气**：`mostly`、`a little`、`if there ever was one` 都有程度，不能译成“完全”“绝对”“第一个”。

**不要补出原文没有的因果、转折、强调。** 通顺不能靠加戏。

**警惕双重否定、否定转移、比较结构。** 先在心里画逻辑箭头，再落笔。

**注释与输出要分开**：代码注释要译，程序输出不译。判据见第 0 步。

### 2. 术语与人名

- **一书一表，先定后译。** 同词同译，异词异译。
- **术语一旦定下，全库检索回改。** 不能这一章一个译法，下一章另一个。
- **人名：读者会去查的人，一律音译并统一。** 判断三问：读者会不会去查这个人？会查就音译；先查权威译名。昵称、代码标识符、私人称呼可保留原文。
- **头衔、军衔、机构名查实际含义**，不能字面直译。`Rear Admiral` 是海军少将，不是中将。
- **首次出现标英文，格式统一**：
  - 普通术语：`中文（English）`，之后只用中文。
  - 缩略语首现：`中文（Full Name, ABBR）`，之后用缩写。
- **校验用值集合比对，不用总数。** 总数相同也可能丢人、换人。
- **新术语当场写回。** 不要等整章译完再补，那时已经漂了。
- **以先例为准**：若术语表与已译章节的实际用法冲突，以先例为准，并回头修正术语表。

**高危冲突项：两个英文词可能译成同一个中文词时，必须拆开定译。** 这类冲突不是「这个词怎么译」的问题，而是「两个词不能译成同一个词」的问题。经验上，这是错译和术语漂移最主要的来源之一：译者分别看两个词时都译得对，放在一起读才发现撞了，此时已经改不动了。发现一个就当场定一个，写进术语表，并在全库检索确认没有混用。

判据：如果两个英文词在原文里承担不同角色，译文却可能撞成同一个中文词，就必须拆开定译，不能靠上下文临时区分。拆开的方式不限于加限定词，也可以是换词根、保留英文、或按角色重命名；关键是**两个词在全书范围内永远不共用一个中文词**。

常见冲突类型（跨领域示意，按项目领域替换）：

| 冲突类型 | 示意 | 拆法 |
|---|---|---|
| 同义近义词撞车 | `method` / `approach` 都可能译「方法」 | 一个用「方法」，一个用「途径」或保留一个英文 |
| 上下位词撞车 | `error` / `exception` 都可能译「错误」 | 「错误」/「异常」固定分工 |
| 动作与结果撞车 | `compile` / `compilation` 都可能译「编译」 | 动词「编译」、名词「编译过程」或「编译产物」 |
| 通用词与专名撞车 | `model` 既指通用「模型」又指某个专有 `Model` | 通用词「模型」，专名保留 `Model` 或音译 |
| 一词多义分角色 | `state` 既指「状态」又指「声明」 | 按角色分别定译，全书不混 |

判据补充：**同一英文词在不同章节承担不同角色时，也要按角色拆开定译**，不能一个词译到底。这类冲突比「两个词撞一个中文词」更隐蔽，靠单章校对发现不了，必须跨章横向比（见第 9 步一致性审）。

### 3. 强调与格式

- 原文 `*em*` 和 `**strong**` 统一译成中文 `**粗体**`，中文不用斜体（中文字体无真斜体，浏览器合成伪斜体会糊）。
- **粗体覆盖完整语义单位**：`*spare*` → **简陋**，不能压成 **简**。
- **不要额外加粗。** 原文没有强调的地方，不能为了“醒目”加粗。
- **区分列表符号和斜体标记**：行首 `* ` 是列表，不是强调。
- **嵌套强调**：外层已是粗体时，内层不再硬加粗，但语气要保留（用“就是、正是、确实”）。
- **书名、期刊名用《》**；外文词可保留原文；是否转粗体按项目约定。
- **结构必须一一对应**：空行、标题层级、列表编号、aside/span、图片、链接。
- **中文链接文本不要用空引用 `[]`**，要写具名引用（如 `[中文文本][key]`）。
- **代码字体只给代码**：标识符、关键字、字面量、opcode 用代码字体；普通词组（`instance of`）不用。类名、类型名的字体边界见技巧库 6。

### 4. 中文表达：去翻译腔

- **人称按“谁做事”分开译**，见第 6 步映射表。代码是施动者时，把代码名提到主语位置，或直接省略主语；中文里“它”指代代码极不自然。
- **不要因为“要正式”就删「我们」或改成书面语。** 口语化技术书的第一人称是作者风格的一部分；改不改看原文语域，不看“技术书应该正式”的先验印象。
- **拆长定语。** 英文能套三层从句，中文要拆成短句或后置解释。
- **去名词化。** `the implementation of X` → “X 是怎么实现的”。
- **删多余连接词。** “因此、然而、此外、从而”，逻辑已经清楚就删。
- **慎用被动。** “被、由、受到”能换成主动就换。
- **动宾搭配要落地。**
  - “立个简写” → “约定一个简写”
  - “产出输出代码” → “生成输出代码”
  - “用比如 C 实现” → “用 C 之类的语言实现”
  - “一副文法” → “一部文法”
- **保留口语节奏和情绪。** 短句、破折号、省略号；调侃、自嘲、夸张不要洗成中性陈述。原文什么风格就什么风格，不要把口语改成书面语。
- **比喻和双关的处理见第 7 节。**
- **不要为呼应原文词头硬造中文。** 字面对但中文没人这么说，就是错。

### 5. 审校方法

- **对照审（有原文）**：查漏译、误译、反向、术语漂移、格式缺失。
- **盲读（只看译文）**：查翻译腔、卡顿、节奏、指代不清。
- 两者不能互相替代：对照审查“漏”，盲读查“腔”。
- **逐段对齐，不要只比总数。** 按空行分段，用标题、代码标记、图片等锚点对齐段落，再逐段比较强调和成分。
- **机器能查的不要靠人眼**：结构计数、name 值集合、aside 内链接定义、渲染后链接、基线数字。
- **先诊断后修改。** 不要边读边改。

### 6. 标点、数字与代码字体

- **破折号用中文全角 `——`**，不用 `--` 或单个 `-`；原文的 ` -- ` 转为 `——`。
- **省略号用 `……`**（六个点），不用 `...`。
- **代码块前的句末标点**：原文是冒号就冒号，是句号就句号，**不要一律改成冒号**。如果句子直接指向后续代码，中文用冒号更自然；如果句子本身已经独立成句，保留句号。
- **代码字体只给真正的代码成分**：标识符、关键字、字面量、opcode。
  - `true` / `false` / `nil` / `null` / `NULL` 用代码字体；泛指真假时用普通文本。
  - 类名、类型名（如 `User`、`Config`、`int`、`size_t`）默认用普通字体，按项目约定可调整。
  - 指向语句写 `if` 语句、`return` 语句；指向概念写 then 分支、else 分支，不加代码格式。
  - 文件名加引号：`Expr.java`；模块名加引号：“debug”模块。
- **散文里的数字拼成词**：原文 one、eleven 写成“一个”“十一”，不要写成 1、11；指二进制位时才是 0 或 1。**代码、表格、数据、命令行参数里的数字不拼词**，按原样保留。

### 7. 引文与双关

**引文、名言、书名、论文标题**

- 先查现成中译本：官方译本 → 权威出版物 → 读者社群流传的片段。
- 查到就用，并照原样给出出处；不要改写引文来配合自己的行文。
- 确认没有公认译本时，给平实准确的直译，并说明“查过，没有”；不要硬造一个“像名言”的句子。
- 书名、期刊名用《》；论文标题无中译时可保留原文并加中文说明。

**双关与习语**

按三种策略选，不要临时凭感觉：

| 策略 | 做法 | 何时用 |
|---|---|---|
| interpret | 意译，按意图而非字面 | 读者要的是意思，文字效果次要 |
| substitute | 替换成中文读者熟悉的说法 | 中文本来就有对应玩法 |
| retain | 保留原文并标注 | 梗无法本土化，且理解它对内容有帮助 |

优先级：

1. 有现成中文玩法的，直接 substitute（如 type punning → 类型双关）。
2. 中文能自然造词的，造；造完念一遍，不通顺就退回 3。
3. 造不出就 interpret，接受损失。
4. 只有读者会因此误解含义时才出译注；不要为“没译出味道”出注。

- 双关、习语、书名的决定写回术语表/双关表，避免跨章不一致。
- 反例：为凑原文词头硬造中文，结果不通顺且丢意思——退回 substitute。

## 高风险句型清单

- 比较级、最高级、否定转移
- `before / after / above / below` 的时间与空间方向
- 多层定语从句、插入语、破折号
- `it / this / that` 的指代
- 省略与替代：`do so`、`one`、`that of`
- 习语、双关、文化专名、书名与引用
- 数字、单位、排名、头衔、军衔
- “A 的 B 的 C”式名词堆砌

## 交付前五项自检

1. **漏字/缺成分**：形、副、否、量、代、名、数，逐个核对。
2. **通顺**：当母语读一遍，中文没人这么说就改。
3. **强调**：数量与落点对得上，粗体覆盖完整成分，无多余、无遗漏、无斜体。
4. **结构**：标题、列表、aside/span、图片、链接、分段，数量与原文一致；name 集合一致；aside 内链接定义未挪位；渲染后链接无丢失。
5. **术语**：同词同译，首现标英（格式统一），全书统一；高危冲突项已拆开，没有共用一个中文词。

## 反模式

- 边审边改，改到后面忘了前面。
- 逐词翻译，然后靠“润色”救。
- 为了让中文通顺，补出原文没有的逻辑。
- 原文没强调的地方加粗；原文强调的地方漏掉。
- 同一术语在不同章节用不同译法。
- 两个英文词撞成同一个中文词，靠上下文临时区分。
- 翻译代码、URL、文件名、程序输出。
- 中文链接文本用空引用 `[]`。
- 把 aside 内的链接定义挪到正文。
- 用“它”指代代码。
- 因为“技术书要正式”就删「我们」、改成书面语。
- 把调侃、自嘲、夸张洗成中性陈述。
- 只数结构标记总数，不比对 name 值。
- 只看 Markdown 源文件，不检查渲染后的链接。
- 改完不重跑基线，结构坏了不知道。
- 跳过中间产物直接改正式文件。
- 有进度文件却不更新。
- 把已知的 A、B 类问题留在交付物里等用户挑。

## 项目适配

如果项目已有规范，优先读项目文件：

- 作者风格指南（优先级高于本 skill 的通用建议）；
- 术语表、人名表、双关表；
- 构建/渲染工具和基线数字；
- 目录约定与中间产物位置。

如果项目没有术语表，先建一个最小表：术语、定译、首次出现位置、备注。译完一章就补一次，不要攒。

如果文本带标记语言（Markdown、HTML、reST、LaTeX），把标记当代码对待：不改标签名、不改锚点、不改引用键，只改给人读的文字。

**项目专属内容不要写进本 skill**，写进项目自己的 `TRANSLATION_NOTES.md` 或等效文件，例如：

- 固定的基线数字（如某书代码行数恒为 N）；
- 构建命令与工具链坑；
- 某本书特有的作者风格规则（如人称的额外细分）；
- 已定的高危术语冲突表；
- 已定的人名音译表、双关表。

## 最小交付格式

翻译任务交付时，至少说明：

- 译了哪些文件/章节；
- 术语或人名有哪些新决定；
- 结构校验结果（关键数字）；
- 还有哪些拿不准、需要作者确认的点。

不要把“我译完了”当成交付。读者需要知道哪些地方有取舍。
